# 后端流程符合性记录

## STEP 5：正文生成、提案接受与存稿

1. 前端 `WriteChat` 对“写正文”意图走 `/chat/write`，携带 ContextSnapshot 三件套。
2. 后端识别为写作意图后禁用 MCP 工具面，避免将 `<function_calls>` 原样输出给作者。
3. SSE 正确输出 `proposal_start`、`proposal_chunk`、`proposal` 与 `done`；页面渲染“接受 / 弃用”草稿卡。
4. 作者点击“接受”后，`WriteLayout.acceptProposal` 通过 `applyProposal` 写入编辑器并调用 `saveChapter`。
5. UI 回读显示 1,273 字和“已存”；后端 `/chapter?seq=1` 回读：`label=draft`、卷 ID 仍为第一卷、`focalizer=role:沈砚`、正文非空（1,327 字符）。

结论：正文提案不自动污染手稿，只有作者接受才落库；接受后正文、标签、卷和视角均保持一致，符合设计。

## P1-009：停止已完成 Hermes Run 返回 500

- 复现：前端卸载清理可能在 Hermes run 已完成并被网关回收后调用 `/ai/runs/{id}/stop`；上游 404 被直接抛出，Scribe 返回 500。
- 修复：本地审计 trace 已是 `completed/stopped/failed/cancelled/canceled` 时，上游 404 转为幂等成功 `{already_finished:true}`；未知 404 改为明确 502 并留 `stop_failed` trace。
- 回归：`test_stop_completed_run_is_idempotent_when_hermes_has_pruned_it` 通过。

## STEP 6：正文反哺后的角色确认

1. 第一章存稿后，角色目录展示 ingest 产生的待确认引用。
2. 接受“刘时喜”和“季棠”均创建了对应角色，证明确认路径会落实体而不是只改前端。
3. 接受操作现为“立即建角色 + 后台重放本章 ingest”：HTTP 响应不再等待 LLM，前端会在单条上显示“接受中”并禁用重复提交，成功后明确提示“正在后台回填第 N 章关联”。
4. 曾观察到抽取器把“半截鱼骨”“闸底刻字”“潮水与钟声”送入人物确认队列。现已修复：事件参与者仅连接已确认角色，未知事件值被忽略且不会登记为人物候选；`learned/did` 等人物语义字段仍可登记真正的新角色。提示词也明确禁止将器物、地点或自然现象放入 `SUBJ/OBJ/WITNESS`。

结论：角色确认不会再阻塞请求线程；事件图的未知参与者不再污染角色库，符合“先确认实体、再建角色关联”的设计。

## STEP 7：角色档案与弧光锚持久化

1. `CodexView` 的空字段先显式提供“添加”入口，字段编辑在失焦时调用角色更新接口；标签输入使用回车提交。
2. 弧光锚聚合 Ghost、Lie、Truth、Want、Need、arc_type 与 private_agenda，只有产生修改后“保存弧光锚”变为可提交。
3. 真人 UI 验证：季棠外貌、性格标签和全部弧光锚写入后均由页面回读；选择 `positive` 后页面显示“正向成长”，无 HTTP 失败提示。

结论：角色档案的标量、标签集合和弧光聚合数据均能从真实 UI 写入并读回，符合前端受控编辑与后端持久化设计。

## STEP 8：角色扩展档案、能力与关系时间线

1. `DetailView` 以 `Field` 统一承载角色标量字段；已有值可编辑，空值使用“添加”入口，文本与数字字段在失焦或 Enter 时提交完整角色更新。
2. 能力使用独立的增删行表单，写入 `name/level/description/acquired_chapter`；真人 UI 已保存并回读“盐纹辨读 / 高 / 第2章”。
3. `DynamicTimeline` 的关系质变记录与角色档案分离，真人 UI 成功写入并将计数回读为 1；角色关系通过独立关系端点写入。
4. `since_chapter` 没有以当前手稿最大章节为上界，这是支持作者提前规划未来关系的有意语义，而非当前一致性缺陷。

结论：角色扩展档案、能力结构、关系质变和关系记录均能完成 UI→后端→UI 回读；自动保存界面在连续切换时会发生短暂重渲染，单字段提交可稳定完成，不影响持久化正确性。

## STEP 9：能力质变与角色声线折叠

1. `POST /char-states` 接收能力快照与 `affects_voice=true` 后，存储层即时写入角色质变，并自动创建对应的 open voice flag；真人接口读回证实第 4 章能力质变和季棠标记一致。
2. `POST /voice-flags/fold` 真实返回 200；折叠后季棠的 open 标记消失，页面显示由折叠结果生成的“声线指纹 / 风格速写 / 口头禅 / 语气规则”。
3. 前端原本只在角色切换时载入声音数据，角色质变保存不会触发重新读取，造成后端正确、当前页面过期。现由 `DynamicTimeline → DetailView → CodexDetail → CharVoice` 的回调和 `refreshKey` 串联刷新。
4. 组件回归与真人同页复验均证明：第 5 章质变保存后立即出现“1 条待折叠”，无需页面重载。

结论：角色状态、声音待办和折叠后的声线档案已形成可审计闭环；前后端流程现符合“状态变化立即要求声线复核”的设计。

## STEP 10：势力注册表字段与限知桥接

1. `GET /codex-schema/faction` 下发字段注册表；前端据此建立标量、枚举、对象、对象数组与别名输入，而不是另行维护字段清单。
2. `POST /factions` 仅传显式设置字段；`add_faction()` 按注册表白名单 MERGE，保留同名势力未修改字段。真实 UI 创建的《潮名会》由 `GET /factions` 完整读回。
3. 回读的结构化字段使用契约名 `world_rule_affinity` 与 `timeline`，并非展示标签的直译名；前端详情正确将其渲染为“世界规则关联”和“势力大事记”。
4. 五个限知字段的各自 `*_secret` 标志均为 true；列表端按注册表掩码为“🔒 私密”，不把真实值回传给普通详情读取。

结论：势力注册表、API 模型、白名单持久化、展示映射和字段级限知掩码一致；未发现此次创建的数据丢失。

结论：第二章的生成、候选接受、草稿与正文分别落库以及章节 POV 元数据更新符合可控写作设计。

结论：人工素材路径已与自动召回路径同样可审计，同时保持“发布不落稿、采纳才留痕”。
