# scribe3 数据字段「业务合理性」审计 · 最全分析(第二轮)

> **与第一轮的区别**:上一轮(`2026-06-27-数据字段生命周期审计.md`)只追技术链路(谁写→谁读→爆炸半径)。本轮**先确立业务/产品意图,再据此判断每个字段是否合理**——该不该存在、模型对不对、缺什么、是否错模。
>
> **方法**:1 个「业务锚」agent 建立"产品能力→数据需求"标尺 + 5 个表簇 agent 并行,用该标尺逐字段裁决。基线:当前 main(已过 P0/P1/P2/声音/034清债/净新 多批修复)。证据 file:line,只读未改。日期 2026-06-28。
>
> **裁决符号**:✅合理 / ♻️冗余 / ❌错模(建模错对象或错形状) / ✂️应拆分或合并 / ➕缺失(业务需要却没有) / 💀死字段(无写或无读) / 🟠半死(半截链路)。

---

## 一句话定位(裁决总纲)

> 这套系统是一台**"按视角投影知识帧 → 只把帧喂生成 → 事后兜底校验"的限知长篇引擎**。全部数据存在,只为支撑一个核心动作:`project_frame(focalizer, chapter)`——"在第 N 章,以某角色为视角,他到此刻为止知道哪些事"。

**判一个字段是否业务合理,先过三连(B0 §0)**:
1. 它服务于"投影出某 knower 在某 chapter 的知识帧"吗?(限知)
2. 它带"故事时间轴(章号)"吗?系统所有读路径都是 `_at(chapter)`;无章号锚的状态字段几乎都可疑。
3. 私密内容若明文存在某字段、又走任何全读路径,它就是错模。

**六条业务硬约束(违反任一即错模,不论代码能否跑)**:
1. **限知门控唯一来源 = KnowledgeEdge,不是 secret**(secret 只是 verify 元数据)。
2. **私密明文不上全读路径**(secret Fact 的 value、character.backstory、faction.private_operation 绝不原样进非限知出口)。
3. **所有"状态"必须带故事时间轴**(valid_from/since_chapter/until_chapter)。
4. **知识非闭包**(不自动推导后果,推论须独立 `acquired_via=inferred` 边)。
5. **写世界状态唯一入口 = store 单点 `_execute_write` + 创作写经 elicitation 待批**。
6. **每条数据必须写路径∧读路径都在**,否则死/孤儿字段。

## 摘要:本轮最重要的结论

第一轮的结论是"schema 完备但上层路径没接通"。**本轮从业务视角看到更深的一层:系统的几项卖点级能力,在数据模型上是"名义具备、实则空心"**。按业务危害排序的 8 个横切主题(详见下一节):

| # | 横切业务主题 | 危害 | 卖点? |
|---|---|---|---|
| **A** | **限知/私密屏蔽边界不完整**(实体层无 secret 模型 + MCP 召回明文吐 secret) | 🔴限知正确性 | ★核心卖点 |
| **B** | **双时态右端集体死亡**——没有任何东西会"失效" | 🔴创作能力缺失 | ★ |
| **C** | **生产方硬编码/置空,使 schema 能力形同虚设** | 🔴确定性写断路 | |
| **D** | **雄心字段"看得见不落地"**——展示性死表群(craft层/声音9节/声音演变) | 🟠卖点空心化 | ★ |
| **E** | **溯源→生成的断点**——录得进查得出,却不喂生成 | 🟠闭环断裂 | ★ |
| **F** | **命名漂移双写技术债**(一字段两名,真源/退场方读写错配) | 🟠埋雷 | |

## 横切业务主题(核心交付,按危害排序)

### 🔴 主题 A · 限知/私密屏蔽边界不完整(系统命根子有洞)
限知是这套系统的全部理由,但"私密"只在 **proposition 一条路**做对了。三处敞口:

1. **实体层私密无 secret 模型**(C1 #1):`character.backstory`(self-注释"冰山·私密")、`faction.private_operation`(势力暗线)——经 `/entities`(app.py:156)、`/factions`(SELECT *,store.py:883)**明文输出,无 secret 标志、无 focalizer 门控**。命题层有 `proposition.secret`+`_facts` 屏蔽(app.py:97-105),实体层裸奔。**这不是某路由忘屏蔽,是实体表缺字段**——即便将来加 POV 投影视图也没法选择性屏蔽。
2. **MCP 召回全线明文吐 secret value**(C2 #2):`s3_semantic_recall`/`s3_hybrid_recall`/`s3_graph_recall`/`s3_dramatic_irony` 都原样返回 secret 命题的明文 `value`,只附 `is_secret` 标志却不打码(mcp.py:90-120),且 `semantic/hybrid_recall` **连 focalizer 参数都没有**,无法做视角门控。第一轮 P0 只修了 `/graph` 和 REST `_facts()`,**MCP 侧仍是敞口**。docstring 自辩"供主编全知联查",但没有任何机制阻止主编 agent 把召回到的私密原文带进续写 prompt。
3. **is_secret 前后端键名不符**(旧审计 🔴#16,B0 引用):连"锁图标"都点不亮,佐证这条私密轨从未被严肃对待。

> **业务建模决策(B0 §4 决策一)**:是否把 secret 从"提示"升级为"读出口默认 deny 触发器"——私密 Fact 无对应 knowledge 边时,任何读出口默认屏蔽其 value。消除"门控 vs 元数据"双轨漂移。

### 🔴 主题 B · 双时态右端集体死亡——没有任何东西会"失效"
系统宣称双时态,但**所有"终止/失效"字段都没有生产者**:

| 字段 | 表 | 状态 | 业务后果 |
|---|---|---|---|
| `valid_to` | proposition | ❌无生产者、无 supersede 路径(C2 #1) | 事实一旦写入**永不失效**:伤愈/反目/死亡/身份反转无法表达 |
| `until_chapter` | knows | 🟠无调用方写非空(C2) | 角色一旦知道**永不遗忘**:记忆篡改/遗忘无法表达 |
| `until_chapter` | character_relation | ❌写孤儿、无 POST 端点(C3 #2) | 关系**永不失效**:敌变友/师徒决裂/背叛无法表达 |

这三条合起来:**双时态只兑现了 `valid_from` 左端一半,右端全死**。对长篇小说这是**真实创作能力缺失**,不是无害占位(印证 B0 §4 决策三)。`facts_at` 的区间上界 `valid_to>ch` 永远成立 → 限知推演只能叠加、不能撤销。
> **修法骨架**:proposition 需要 supersede 写路径(新事实写入时把同 entity+attribute 旧事实的 valid_to 置为新 valid_from);character_relation 需要 POST 端点 + "建新+旧设 until" 的关系演变流程(SKILL.md 已教 agent 这么做,但没有代码支撑)。

### 🔴 主题 C · 生产方硬编码/置空,使 schema 能力形同虚设
schema/本体宣告了能力,**写入口却悄悄阉割**:

- **faction.status 硬传 "active"**(C1 #2):REST(app.py:356)与 MCP(mcp.py:413)**都**硬传,FactionIn 无 status 字段。枚举 `active/dissolved/dormant/reformed`+idx 全是死约束——**势力覆灭/休眠/重组永远写不进**(乱世题材核心动态)。
- **world_rule.capabilities 硬传 None**(C1 #2):REST(app.py:327)硬传 None,RuleIn 无此字段——Sanderson"能力"维度走 REST 断路,仅 MCP 可写。
- **s3_add_event 不收 participants/effects/causal_in**(C3 #1):经 MCP(主编 agentic 自调)建的事件是**无边孤儿**——involves/causes/causal 三边全空 → events_at 重建无参与者、"看见即知道"发不出知识边、causal_complete 对其永远报"因果缺失"。**事件图的核心价值对主要写入路径完全失效**。
- **knows.certainty**(C2):内存 dataclass 有(ontology.py:50),**DB 无此列**,load_knowledge 恒回填 1.0 → 不确定性建模名存实亡。

### 🟠 主题 D · 雄心字段"看得见不落地"——展示性死表群
schema 都建了,UI 上"看起来已具备",实则不驱动任何生成/检测:

- **craft 引擎层基本死**(C4 #1):`build_craft_block`(craft.py:147,把工艺规则注入渲染 prompt 的唯一入口)**零生产调用,仅测试用**。`craft_rule.artifact_craft/cover_action` 两枚举全链路无消费者(seed 了数据也白种);唯一活路是 `purple_regex` 反向喂升华句 QC。`motif.theme/echoes/unfolding` 不进任何 prompt,母题只靠 `name` 做被动防误删白名单。
- **voice_profile 9 节,3 节纯死**(C5 #2):`sentence_patterns/vocabulary_profile/internal_monologue_style` 零消费——讽刺的是 prompt 锚的是"叙述与内心独白"却用 style_summary,专门的 `internal_monologue_style` 躺着没人读。9 节是 YAGNI 过度设计,真有消费链的只有 4 节。
- **voice_sample 整表死**(C5):0 行是**结构性必然**——无前端录入入口、ingest 不回灌、prompt 锚用的是 profile 不是 sample。精巧的时间门 `latest_voice_samples` 零调用方。与 `profile.reference_lines` 职责重叠。
- **"弧光→声音演变"全链路断裂**(C5 #1):设计意图 `char_state.affects_voice=true → voice_evolution_flag → 更新 voice_profile`,三段全断——`affects_voice` 零消费、`voice_evolution_flag.status` 从不关闭(永远 open 的待办 inbox)、voice_sample 无生产者。三表名义协作,实则各自悬空。

### 🟠 主题 E · 溯源→生成的断点——录得进查得出,却不喂生成
- **char_state_at 不注入写作 prompt**(C5 #3):角色时点快照只被"手动查询框"和 mcp 主动调用消费,**限知帧/续写 prompt 不注入角色当前弧光状态** → 写第N章时生成器不知道角色此刻能力/性格。
- **accept_unverified 只建空壳,丢知识**(C5 #3):accept 只建 `role:{name}` 裸角色 + 标 accepted,**不回填**被该名字阻塞的 fact/knows 边(ingest.py 因角色不存在 `continue` 跳过的知识永久丢失)。seq/role 两字段在 accept 时白存。正确闭环应是 accept→建角色→用 seq 重放该章 ingest。
- **reader_knows 写侧断裂**(C2 #3):读侧闭环完整(dramatic_irony),但写侧只有手动 `s3_record_knowledge` + seed_demo,**没有"叙述揭示→自动 reader_knows"的钩子** → 真机近乎空表 → **戏剧反讽大概率恒空**,停留在 demo 级。

### 🟠 主题 F · 命名漂移双写技术债(埋雷)
一个语义两个列名,且**真源/退场方读写错配**:

| 双写对 | 表 | 真源 | 雷 |
|---|---|---|---|
| `etype` / `event_type` | event | event_type(015) | etype 是退场方仍被读 |
| `valid_from` / `story_chapter` | event | story_chapter | **`max_chapter` 仍只读 valid_from**(C3 #3)→ 只写 story_chapter 的新事件被漏算,体检/渲染章号边界错 |
| `entity` / `entity_id` | proposition | entity_id | 同值双写,harmless 但误导(C2) |
| `seq` / `trigger_chapter` | voice_evolution_flag | seq | 同值双写,033 改 nullable 仅为修旧库(C5) |

> 第一轮把这些列为"working code 不碰"。本轮指出:**event 的 max_chapter 读错源是已埋的活雷**,该优先收口(不是纯技术债)。

### 🟠 主题 G · 本体逃逸——item/term/faction/world_rule 名实不符(B0 §4 决策二)
本体宣称"四类一等公民(角色/物件/地点/阵营)",但**只有 character/place 真走 Entity**,item/term/faction/world_rule 全在 store 层另起独立表+独立 CRUD(store.py:1044+/838+),且**name 无 UNIQUE 约束**,幂等全靠应用层"先删后建"兜(并发/直写仍可造重复)。这层"本体 vs 持久层"断层是设定库脏数据的根。
> **决策**:要么把四类真正纳入 Entity 统一抽象,要么坦诚承认它们是"设定圣经"独立子系统并给对的 CRUD(加 UNIQUE)。现状是最坏的中间态。

### 🟡 主题 H · 章锚字段写而不读 + 前端编辑面缺失
- **章锚孤儿**:`item.first_chapter`/`term.first_mention_chapter`/`world_rule.established_chapter`/`faction.first_mention_chapter` 写侧刚接通(第一轮)但**全无消费方**;`place` 的 027 四扩展(geography/notable_events/first_visit_chapter/political_affiliation)**写读 UI 三缺**纯死。唯一真闭环的章锚是 `character.first_appearance`(CodexView 排序消费)——可作接线范本。
- **前端编辑面缺**:world_rule UI 表单只暴露 name/category/source/cost/note,**limitations/exceptions/capabilities/scope/established_chapter 全填不了**(硬魔法核心维度);`promise.payoff_chapter` 前端不显;`char_state` 的 before_state/trigger_event/affects_voice/confidence 前端表单都不录;faction.known_members、item.special_properties 写得进不展示。
