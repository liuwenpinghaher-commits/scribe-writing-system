## 0. 一句话定位

**scribe3 的写作范式是「主编主笔 + 作者用 chat 引导」**:作者不直接对着空白页码字,而是在右轨用自然语言提思路 / 提要求,由一个"资深主编"(Hermes agentic LLM,挂 scribe3 MCP 自调 `s3_` 工具查 SurrealDB 真相)把书的正文写进 `⟦PROPOSAL⟧` 围栏,前端把围栏内文字渲染成中区的**草稿卡**,作者**接受 / 弃用**;接受即落库,后台 `ingest` 把新写的内容反哺回知识图谱,下一章的限知帧 / 前情自动看得见新知。

这是一个**人在环路(human-in-the-loop)**的闭环:`引导 → 生成 → 审阅 → 接受 → 反哺 → 下一轮看得见`。

## 2. 两种 chat 模式:讨论 vs 写作

主编对话物理上分成**两条独立路由**,本质区别是「**出不出 `⟦PROPOSAL⟧` 围栏 / 调不调工具**」。

| 维度 | ① 讨论模式 | ② 写作模式 |
|---|---|---|
| 路由 | `GET /chat/agentic-stream`(也有非 agentic 的 `/chat/stream`) | `POST /chat/write`(+ `GET /chat/write`,图片走 POST) |
| 后端函数 | `chat_agentic_stream` → `hermes_responses_events` | `chat_write_post` → `_stream_write` |
| 网关 | scribe3 profile 网关 `:8643`(挂 scribe3 MCP) | 同 `:8643`(同样 agentic,可调工具) |
| 系统提示 | `_editor_system(st)` + s3_ 工具引导 | `_editor_write_system(st)`(= `_editor_system` + 写作纪律 + 文风基准) |
| 产出 | 纯文字 delta(进右轨气泡)+ tool 提示 | 围栏外 delta(右轨)+ 围栏内 proposal(中区草稿卡) |
| 工具 | 主编主动调 `s3_project_frame / s3_dramatic_irony / s3_list_promises / s3_qc_chapter / s3_discipline_check / s3_semantic_recall / s3_causal_complete…` 核实真相后回答 | 工具可用,但热路径主要靠 §3 注入块把真相**确定性**喂进 prompt(不依赖模型自觉调工具) |
| 写操作 | 进**待批**(elicitation gate),不立即生效 | 不写库(写库走接受→save) |
| 前端入口 | `api.chatStream(msg,{agentic:true})`(EventSource) | `api.chatWrite(msg,{chapter,focalizer,images,onProposal…})`(fetch 流读) |

**为什么分两条**:讨论要的是**实证**——主编先用只读工具查 SurrealDB 真实数据再答,不臆测(`_editor_system` 末尾明确要求"引用数据时说明来自哪个工具")。写作要的是**交付**——把书的正文用围栏吐出来,让前端能渲染成可接受的草稿卡,且文风 / 限知 / 防复读等约束要**确定性**注入而非外包给模型自觉。

**两者如何协同**(理想工作流):作者先在讨论模式问「这章节奏如何?有什么风险」「焦三此刻知道什么」——主编查库给犀利意见;作者据此在写作模式说「本章这样展开:……」——主编出整章草稿卡;接受后讨论模式又能查到新落库的真相。`WriteChat.jsx` 的 `SUGGESTS` 把两种意图都摆在引导按钮里(前 3 条是写作意图,第 4 条是讨论意图)。

> ⚠ **协同的当前裂缝**:`WriteChat` 永远只调 `api.chatWrite`(写作路由),不调 `api.chatStream`(讨论路由)。也就是说"讨论"和"写作"在 UI 上**没有真正分流**——靠 `_editor_write_system` 的"核心判断:讨论 vs 动稿"段落让模型**自己判断**是否出围栏。审计真机探针实测:模型有时判错(该出围栏没出),正文掉进聊天轨。这正是本会话「围栏兜底」要救的(见 §4)。

## 3. prompt 组装全解(写作模式 instructions 逐块)

`POST /chat/write`(`chat_write_post`,app.py:1187)按**固定顺序**把多个块拼成 `instructions`。顺序本身是设计:基线人设在前、硬约束在中、**强化提醒在最后(recency 效应)**。下表逐块解释。

| # | 块(函数) | 注入什么 | 为何 | 量级 | 过载风险 |
|---|---|---|---|---|---|
| 1 | `_editor_write_system(st)` | = `_editor_system`(北极星 intent + 14 角色名 + `facts_at(99999)[:28]` 全知设定 + 开着的伏笔提醒)**+** 写作纪律(讨论 vs 动稿判断、scope 规则、多候选规则)**+** 文风基准(古白话 / 世界密度两条硬要求 + `_LUANSHI_EXEMPLAR` 范例) | 主编的人设、世界观锚、围栏协议、文风标杆一次性给全 | **最大**(数百字 + 28 条设定 + 范例段) | 高:28 条全知设定在 focalizer 模式下与下方限知帧**语义打架**(见差距 D2) |
| 2 | 章号 + 焦点者声明 | `当前第 N 章` + 焦点者限知声明 / 作者全知声明 | 告诉主编视角模式 | 一句 | 低 |
| 3 | `_avoid_directive(st, ch)` | 前 3 章(本会话已扩到看更多前文)`distinctive_phrases` 提炼的 ≥8 字独特措辞,**最多 40 条**,母题白名单 `motif_terms` 排除 | **确定性防跨章复读**(单遍长程生成的复读病,实测 10 章 106 处逐字搬运,逐章 QC 查不到)。把前文招式喂进系统指令,生成时就避开 | 40 条 × 8+字 ≈ 数百字 | 中:40 条是大块,审计建议降到 ~30 |
| 4 | `_voice_anchor_block(st, foc)` | 焦点者完整 voice_profile(style_summary / catchphrases / tone_rules / 内心独白 / 句式 / 词汇 / 参考语感 + open voice flag 待演变提示)+ 所有登场角色对白声音速记(≤6) | 让生成时**已在声**,而非事后 `check_ooc` | 焦点者一段 + ≤6 条速记 | 中 |
| 5 | `_arc_state_block(st, foc, ch)` | 焦点者在本章的 char_state 快照:能力 / 关系 / 性格 / 当前弧光阶段 | 角色成长要贴合当前状态(不写他还没获得的能力) | 一行 | 低 |
| 6 | `_motif_block(st)` | 贯穿母题 ≤5 条(name:theme(回声)) | 让生成时主动编织母题 | ≤5 行 | 低 |
| 7 | `_frame_block(st, foc, ch)` | **focalizer 模式核心**:`project_frame(st,foc,ch).facts` 经 `_facts` 屏蔽私密后**只保留可见**的事实,≤40 条,格式 `实体|属性|值` | **限知硬边界**——帧外的事物理上进不了 prompt,生成时无从写他不知道的。不依赖模型自调工具 | ≤40 行 | 中(本会话已做) |
| 8 | `_recap_block(st, ch)` | 上一章结尾文字(末 ~300 字)+ 上一章关键事件摘要(≤6) | **前情**——主编"接着往下写"时不失忆,与 avoid(别逐字抄措辞)语义区分 | ~300字 + 一行 | 中(本会话已做) |
| 9 | `_current_tail_block(st, ch)` | 当前章已写部分的末段(~400 字) | **续写衔接**——append 时从此处自然接上,不另起炉灶 | ~400字 | 低(仅当前章有 prose 时) |
| 10 | `_soak_block(req.seed_words)` | 浸泡产出的情绪种子词(前端可选预传) | 让生成贴本场情绪曲线。soak() 需 LLM 调用,不在写作热路径自动触发 | 一行 / 空 | 极低 |
| 11 | `build_craft_block(rules)` | **写作引擎层**(题材无关 8 条:身体先行 / 温度曲线 / 闲笔 / 认知比喻 / 潜台词 / 感官锚定 / 浸泡 / 留白)+ 本书题材规则(per-work craft_rule 表) | 工艺底座 + 本作专属规则 | 8 条引擎 + N 条题材 | **高**:8 条引擎每章全量注入,审计建议按场景裁剪 |
| 12 | `_final_reminder()` | 复述两条最高优先级约束:① 动稿必须用围栏;② 文风贴乱世铜炉 | **recency 效应**——对抗多块拼接后关键规则被稀释的注意力漂移。不含新信息 | 两句 | 低(本会话已做) |

**组装后整体过载判断**:在 focalizer 模式 + 前文充足时,instructions 轻松上 **2000~3500 字**。最大三块是 `_editor_write_system`(全知设定 28 条 + 范例)、`_avoid_directive`(40 条)、`build_craft_block`(8 引擎)。这是审计「五环根因」里**保真 / 记忆做厚了,但 prompt 过载**的来源——块越多,模型对"必须出围栏"这条**交付指令**的注意力越被稀释,正是写作模式经常忘写围栏的诱因之一。

**本会话已做的四类改进**(对照审计批 G1/G2):
- **保真(frame)**:`_frame_block` 把限知帧确定性注入,物理隔断帧外私密。
- **记忆(recap/current_tail)**:`_recap_block` + `_current_tail_block` 让主编不失忆、续写能接上。
- **交付(围栏兜底)**:`_stream_write` 收尾时若 `expect_proposal` 且整轮无围栏且散文 ≥120 字 → 兜底包成 `scope=chapter` proposal(见 §4)。
- **裁剪(avoid + 末尾强化)**:avoid 上限治理 + `_final_reminder` 末尾复述。

## 4. proposal 机制(`⟦PROPOSAL⟧` 围栏)

### 4.1 协议
主编输出里,**围栏外 = 对话**(进右轨),**围栏内 = 书的正文**(进中区草稿卡)。围栏语法:

```
⟦PROPOSAL scope=chapter⟧      ← scope ∈ {chapter | selection | append}
（书的正文，作者笔调，纯散文，不要解说）
⟦/PROPOSAL⟧
```

- `scope=chapter`:整章改写(整章替换)。
- `scope=selection`:改选中段;**多候选**时连续输出 2-3 个独立 selection 围栏(一个收紧 / 一个加潜台词 / 一个换感官切入)。
- `scope=append`:续写,接在当前正文后面。

### 4.2 流式状态机(`proposal.py` · `ProposalParser`)
`feed(chunk)→事件列表`,末尾 `flush()` 吐净。跨 chunk 的标记靠"**留住从最后一个 `⟦` 起的尾巴**"兜住(`_emit_safe`,防止围栏标记被 chunk 边界切断后误判)。事件:`delta` / `proposal_open(scope)` / `proposal_delta(text)` / `proposal_close`。

`_stream_write` 的 `drain()` 把这些事件翻成 SSE:
- `delta` → `{delta}`(右轨)
- `proposal_open` → `{proposal_start:{scope}}`(草稿卡出现,标"书写中…")
- `proposal_delta` → `{proposal_chunk:{text}}`(**流式逐字填进草稿卡**——本会话 S1 已接通真流式)
- `proposal_close` → `{proposal:{scope,prose}}`(整段完成)

> 注:`ProposalParser` 非线程安全(每请求新建一个实例,故无并发问题;勿跨请求复用)。

### 4.3 无围栏兜底(本会话已做)
**根因**:审计真机探针两次明确写作请求都 `proposal=0`、无围栏——主编忽略围栏指令,正文以聊天 delta 流出,前端无法渲染为草稿卡,**交付环系统性破损**。

**兜底逻辑**(`_stream_write`,app.py:864):
1. `_is_write_intent(msg)` 用 `_WRITE_VERB_RE`(写 / 改 / 续写 / 帮我写 / 重写 / 把这段 / 本章 / 展开…)判定本轮是否写作意图,作为 `expect_proposal` 传入。
2. 流收尾后,若 `expect_proposal and not saw_proposal`,把累积的全部 delta 文本拼起来,若 `≥120 字`(`_FALLBACK_MIN_CHARS`,更短视为讨论)→ 末尾补发 `{proposal:{scope:'chapter', prose:累积文本, fallback:True}}`。

效果:"模型忘了写围栏"不再导致正文掉聊天轨——长散文兜底成整章草稿卡。

### 4.4 前端消费(`WriteLayout.jsx` + `DraftCard.jsx`)
- `onProposalStart` → `setProposal({scope,prose:''})` + `setProposalStreaming(true)`。
- `onProposalChunk` → 把 text 追加进 `proposal.prose`(流式书写中)。
- `onProposal`:`selection` 推进 `candidates[]`(多候选);其余 `setProposal(p)`。
- `DraftCard`:`candidates.length >= 1` 走多候选横排卡(每卡【用此版】);否则单卡【接受】/【弃用】。本会话已把分支从 `>1` 修成 `>=1`,消除单 selection 候选时 `proposal===null` 解引用崩溃。
- **接受**:`acceptProposal` → `applyProposal(prose, p, lastSel)` → `persist(next)`。
  - `applyProposal`:`chapter` 整章替换;`append` 接尾;`selection` 用 `to - text.length` 锚点推真实起始,**原文漂移则拒绝**(不静默追加,交 UI 提示"请重新选中")。

## 5. 反哺闭环(ingest)

### 5.1 触发点
- **接受草稿 → `POST /save-chapter`**(`save_chapter`):`st.save_chapter` 落库 → 软校验(`quality_flags` + `find_cross_chapter_repetitions` + `find_leaks`,确定性、快、不打 LLM,结果回前端不阻塞)→ `background.add_task(_bg_ingest)`。
- **正式定稿 → `POST /checkpoint` kind=final**(`checkpoint`):存版本快照,**kind=final 才触发 `_bg_ingest`**(非 final 草稿快照不 ingest)。

### 5.2 ingest 抽取与应用(`ingest.py`)
`_bg_ingest` → `ingest_chapter(st, seq, hermes_complete)`:读本章正文 → Hermes 抽**知识 delta** → `apply_delta`。若 LLM 回复解析失败(坏 JSON / 截断)→ **不 purge、不丢既有知识**,返回 `parse_failed=True`(防静默数据丢失)。

`apply_delta` 把 delta 落库(章级幂等:先 `purge_ingest(seq)` 清本章既有 ingest 产出再重写,重复 ingest 不残留悬挂边):
- **learned**(谁新知道什么)→ 给当事人发 `knows` 边 + `reader_knows`(叙述揭示即读者已知,戏剧反讽闭环)。**S3 去重**:`_find_existing_learned_prop` 近精确匹配(归一化相等 / 长文本互相包含 ≥15 字)到已有"获知"命题则复用,只发新 knows 边,不建重复真相。
- **did**(谁做了什么)→ 当事人 + 在场 `seen_by` 都发 `saw` 边 + `reader_knows`。**看见即知道**。
- **voice_shift** → `add_voice_flag`(只标记角色名,不生成独白)。
- **arc**(G4 弧光自动入账,本会话已做)→ `add_char_state`(ability / relation / personality / composite,经 `ingest_seq` 幂等,confidence=inferred)。让正文里角色成长**自动**变成下一章 `_arc_state_block` 的约束。

### 5.3 反哺如何"下一章看得见"
图谱更新后,下一章 `POST /chat/write` 组装时:
- `_frame_block` 读 `project_frame` → 焦点者**新获知的事实**进了限知帧。
- `_recap_block` 读 `recent_proses` + `events_at(ch-1)` → 上一章尾段 + 事件进了前情。
- `_arc_state_block` 读 `char_state_at` → 角色成长进了弧光约束。

**这就是闭环成立的物理证据**:写 → 存 → ingest → 图谱 → 下一章 prompt 自动含新知,无需作者手工搬运。

## 6. 本会话真机验证

| 验证项 | 结论 |
|---|---|
| **生成质量** | 两次明确写作请求(focalizer=胡不为 / 作者全知=老乌头)均产出**乱世铜炉级散文**(古白话筋骨、世界密度侧笔、冷笔素描)。**生成质量不是瓶颈。** |
| **交付(改进前)** | 两次都 `proposal=0`、无围栏 → 正文掉聊天轨,前端无法渲染草稿卡。**交付环系统性破损。** → 本会话「围栏兜底」修复。 |
| **反哺闭环(写 90 → ingest → 承接 91)** | 写第 90 章 → `_bg_ingest` 抽 delta 落 knows/reader_knows/char_state → 第 91 章 `_frame_block`/`_recap_block`/`_arc_state_block` **确定性反映了第 90 章的新知与尾段**。闭环实测可用。 |
| **流式 proposal(S1)** | `proposal_chunk` 已逐字流进草稿卡,"书写中…"态可见。 |

**根因复述(承接审计)**:ingest 的**写端**(落 knows/reader_knows)自动且扎实;但**反哺读端 / 质量闸 / proposal 交付**三者过去要么外包给模型自觉、要么离线、要么脆弱。生成 prose 够好,但**保真 / 记忆 / 质控 / 交付**四环漏。本会话补上了保真(frame)、记忆(recap/tail)、交付(围栏兜底)、弧光入账;质控接进回路与 prompt 过载治理仍是后续(见 §8)。

## 7. 全网工艺调研(场景构建 / 草稿 / AI 辅助写作)

> 英文 + 中文双语检索。提炼出对本系统**有杠杆**的工艺要点 + 出处。

### 要点 1 · 场景-续景结构(scene & sequel)是基本叙事颗粒
Dwight V. Swain 的经典工艺把叙事拆成交替的**场景(scene)= 目标 goal + 冲突 conflict + 灾难 disaster**,与**续景(sequel)= 反应 reaction + 两难 dilemma + 决定 decision**。每个场景以"新灾难"收尾,推动进入续景;续景是角色做重大决定、消化情绪、设定下一目标的地方。**续景是节奏工具**:节奏太快就拉长续景,要提速就缩短。中文叙事学同构:场景 → 节拍(beat,最小单位 = 主观期待 + 行为 + 客观现实 + 反应)→ 序列(2-5 个递增冲击的场景)→ 幕 → 故事。([dabblewriter](https://www.dabblewriter.com/articles/scene-sequel)、[Helping Writers](https://www.helpingwritersbecomeauthors.com/how-to-structure-scenes/)、[澎湃·小说中的场景](https://www.thepaper.cn/newsDetail_forward_14724013))

### 要点 2 · 节拍单 / 场景卡:写前先有"任务陈述"
专业草稿流程在动笔前先做**beat sheet → scene list**:每个场景压缩成一句"任务陈述"(如"船撞冰山"),一个场景只做一件事;可以把整个故事写成索引卡,**场景 / 续景交替排布**,重排所有节拍。这是"写前规划"——先有目标 / 冲突 / 出口,再填散文。([Jami Gold](https://jamigold.com/2015/10/developing-our-story-from-beat-sheet-to-scene-list/)、[Tame Your Book · 8-Beat](https://tameyourbook.com/scene-and-sequel/))

### 要点 3 · 草稿是迭代的:先松后紧(shitty first draft → revise)
Anne Lamott 的"狗屎初稿"(也叫 messy / vomit / down draft):**第一稿只为把故事讲给自己听**,关掉内心编辑,先全吐到纸上;第二稿才"理出意义"、带意图地塑形。写作是**迭代、循环、非线性**的——没有传统出版小说是不经多轮修改的;初稿最难最慢,之后越来越快(越来越懂自己的故事)。([Kevin T. Johns](https://www.kevintjohns.com/writing-is-iterative/)、[Holly Lisle · One-Pass](https://hollylisle.com/one-pass-manuscript-revision-from-first-draft-to-last-in-one-cycle/)、[Lamott via Saint Leo](https://pressbooks.pub/eng121slu/chapter/first-drafts/))

### 要点 4 · AI 辅助写作:人提供思考,AI 去摩擦;强在初稿 / 头脑风暴,弱在情感深度 / 情节
人在环路最佳模式:**作者出想法 → AI 帮结构化 / 出初稿 → 人做最终审阅,恢复声音、核对事实**。AI 擅长初稿与 brainstorm,**拙于情节(plotting)、差于情感深度**——用在它强的地方,其余自己来。作者普遍痛点是**控制文风、避免套话、保证连贯**。完稿后要做一致性 pass:核对角色细节、世界规则、时间线、**每个角色在每个时刻知道什么**(限知!)——AI 辅助,但靠人精读兜底。一条实用规则:**把终稿读出声**,不像你的句子要么更好留下、要么更平重写。([Medium · Craft-First](https://medium.com/craft-first-writing-with-ai/ai-assisted-writing-best-practices-for-craft-first-authors-f3bfdc9faaf2)、[Laterpress](https://www.laterpress.com/craft-of-writing/ai-writing/)、[Lorka AI](https://www.lorka.ai/knowledge-hub/how-to-use-ai-for-better-writing))

### 要点 5 · 长篇要有大纲 / 卷 / 章纲三级骨架
中文网文工艺:长篇先有**世界观 + 人物卡 + 三幕主线**(第一幕 20-25% 铺垫触发、第二幕 50-60% 发展中点转折、第三幕 20-25% 高潮收束);主线细化为**分卷大纲**,再细化为**逐章章纲**,每章结尾留钩子。编完剧情自然产生长度,**详写则慢、简写则快**就是节奏控制。"一卷一卷地写,写三卷大概能开工,边写边修提纲"。([妙笔生花 · 长篇大纲指南](https://wordflower.cn/blog/how-to-write-novel-outline/)、[知乎 · 网文写作攻略](https://zhuanlan.zhihu.com/p/689906206)、[4T-O 写作框架](https://zhuanlan.zhihu.com/p/1930655069587616474))

## 8. 差距与改进(对照工艺 → 现状 → 改法 → 优先级)

> 总判断:**"主编主笔 + 人引导"是对的范式**(命中要点 4 的人在环路:人提供思考 / 决定接受,AI 去摩擦出初稿)。差距集中在**写前规划缺失、讨论→定稿衔接断、续写到目标字数能力被删、selection 体验弱、大纲/卷结构缺、prompt 过载**。

### G-1 · 场景级规划(写前的目标 / 冲突 / 节拍)—— **P0**
- **工艺**(要点 1/2):动笔前每个场景先定 goal+conflict+disaster / 续景 reaction+decision;一个场景只做一件事。
- **现状**:写作链路**没有场景层**。`scenario.py` 只是测试用的 canonical 泄露场景(焦三/老道),不是给作者用的场景规划工具。作者只能在 chat 里口述"本章这样展开",主编凭一句话直接出整章——**没有结构化的写前节拍**,质量全押在模型一次发挥。
- **改法**:
  1. 新增**场景卡**数据结构(per-chapter scene beats):`{scene_goal, conflict, disaster|turn, exit_hook}`,可由作者填或主编据 intent/promises 提议。
  2. 新增 `_scene_block(st, ch)` 注入块(放在 `_recap_block` 之后、文风之前):把本章场景卡的目标/冲突/出口喂进 prompt,让生成有"这一场要完成什么"的靶子。
  3. chat 里加意图分流:`本章节拍:…` → 主编先回**节拍提议**(不出围栏),作者确认后再"按此写整章"。
- **优先级 P0**:命中"AI 弱在 plotting"——把 plotting 从模型即兴升级为作者/主编显式决定,是质量天花板的最大杠杆。

### G-2 · 多轮讨论 → 定稿的衔接 —— **P0**
- **工艺**(要点 4):人出想法 → AI 结构化 → 出初稿,是**多轮**收敛,不是一句话到整章。
- **现状**:`WriteChat` 只调 `api.chatWrite`(写作路由),**从不调 `api.chatStream`(讨论路由)**——讨论与写作在 UI 上没真正分流,全靠 `_editor_write_system` 让模型自判。审计实测模型常判错,讨论意图也可能误触兜底出草稿卡。讨论模式查到的真相(agentic 工具)与写作模式的注入块是**两套上下文**,讨论结论不会自动带进写作 prompt。
- **改法**:
  1. `WriteChat` 按意图分流:`_is_write_intent` 同款规则在前端判一次,讨论→`chatStream(agentic)`,写作→`chatWrite`;讨论气泡不触发草稿卡。
  2. **会话记忆**:把本章近几轮讨论摘要作为 `_discuss_recap_block` 注入写作 prompt——"作者刚和你讨论定了:……,现在据此写"。否则主编写作时看不见自己几分钟前讨论的结论。
  3. 写作请求支持引用讨论结论(前端把选定的讨论气泡 quote 进 msg)。
- **优先级 P0**:衔接断 = 人在环路的"环"没闭,讨论白费。

### G-3 · 续写到目标字数(render.py 已删)—— **P1**
- **工艺**(要点 5):详写则慢,章节要能写到目标长度;单次 LLM 输出常不足一章。
- **现状**:`render.py` 曾有**分段续写到 target_words**(commit 7ead5e6:`render` 先出大纲再逐段续写拼接,最多 5 段,达标即停),在 commit 03d354f「写作改走主编对话」时**整文件删除**。现在 `_stream_write` 是**单次**生成,主编一轮吐多少算多少;`append` scope 虽能续,但**没有"续到 N 字"的自动循环**,要靠作者反复点"接着往下续写"。
- **改法**:
  1. 在 `_stream_write` 或新 `/render-to-length` 加**目标字数循环**:单轮输出 < target 时,自动用 `_current_tail_block`(已有!)+ "还需约 X 字" 续 append,最多 K 段,达标停。复用已删 render.py 的策略(已在 git 历史 `git show 7ead5e6:scribe3/render.py`)。
  2. 前端 DraftCard 加"续到约 N 字"按钮,触发该循环并流式追加进同一草稿卡。
- **优先级 P1**:有 `append` + `_current_tail_block` 兜底可手动续,但自动达标是顺滑度的明显缺口。

### G-4 · selection 改写体验 —— **P1**
- **工艺**(要点 3):修改是迭代主战场,要能精准定段、给多版本、可回退。
- **现状**:`applyProposal` 的 selection 用 `to - text.length` 锚点替换,**原文漂移则拒绝**(对,但只 toast"请重新选中",不给重试入口)。多候选靠模型连出多个 selection 围栏,无显式"再给一版""把第 2 版再收紧"的迭代回合。改写后无 diff 视图(看不出改了哪几处)。
- **改法**:
  1. 漂移时不只 toast,**高亮原选区**让作者一键重选并重发同一改写请求。
  2. 候选卡加"基于此版再改"——把该候选作为新 selection 起点继续迭代(命中要点 3 的迭代修改)。
  3. 接受 selection 时存一次 `/checkpoint`(非 final),让每次改写可回退(版本已有 `chapter-versions` 基建)。
  4. 草稿卡可选 inline diff(新旧对照),呼应要点 4"完稿读出声"的人审。
- **优先级 P1**。

### G-5 · 章节大纲 / 卷结构缺失 —— **P1**
- **工艺**(要点 5):长篇要大纲→分卷→章纲三级骨架,签约编辑第一看大纲。
- **现状**:有 `intent`(北极星)、`promises`(伏笔)、`motifs`(母题),但**没有卷(volume)/ 章纲(chapter outline)结构**。`/chapters` 只是 seq + title 的扁平列表。主编写每章时只有"前情 + 限知帧",看不见"这章在第几卷、卷的弧线走到哪、本章该推进哪条主线"。(注:旧 scribe 的 TS api 有 `volume_id`,scribe3 未承接。)
- **改法**:
  1. 加 `volume` 表 + 章归属 `volume_id`;`/chapters` 按卷分组。
  2. 加**章纲**字段(每章一句任务陈述 + 该推进的 promise ids),作者填或主编据三幕/promises 提议(命中要点 2 的 scene list)。
  3. 新 `_outline_block(st, ch)` 注入:本章在卷中的位置 + 章纲任务 + 本章应推进/回收的伏笔 → 让生成对齐主线节奏。
- **优先级 P1**:对单章质量是中杠杆,对**长篇一致性 / 节奏**是高杠杆。

### G-6 · prompt 过载的进一步治理 —— **P2**
- **工艺**(要点 4):AI 痛点是控制文风 / 连贯——上下文越杂,控制力越散。
- **现状**(见 §3 量级):focalizer 模式 instructions 常 2000-3500 字。最大三块:`_editor_write_system` 的 28 条全知设定(focalizer 模式下与限知帧打架)、`_avoid_directive` 40 条、`build_craft_block` 8 引擎全量。块越多,"必须出围栏"越被稀释(忘围栏的诱因之一)。
- **改法**:
  1. **focalizer 模式截断全知设定**:focalizer 模式下 `_editor_write_system` 的 `facts_at(99999)[:28]` 应让位给 `_frame_block` 的限知帧(全知设定仅作者视角注入)。消除"全知设定 vs 限知帧"语义打架(审计批 G1#3)。
  2. **craft 按场景裁剪**:8 条引擎按本章场景类型选 3-4 条注入(动作场重身体先行/温度曲线,静场重闲笔/留白),而非每章全量。
  3. **avoid 降到 ~30 条**:本会话已扩窗看更多前文,但条数上限可收。
  4. **文风基准前置加权**:把文风两条硬要求做成更短的高优先级锚,减少范例段长度占用。
- **优先级 P2**:本会话 `_final_reminder` 已部分缓解交付指令稀释;过载治理是持续项。

### G-7 · 质量闸接进生成回路 —— **P2**(承接审计批 G3)
- **工艺**(要点 4):完稿做一致性 pass(角色/世界规则/时间线/限知),AI 辅助人兜底。
- **现状**:`/post-check` 已有全量五类 QC + find_leaks + discipline + validate_setting,但**不在 save/accept 后自动串**,且 `/quality` 仪表盘漏算 `ai_tics`/`oversaturation`(app.py 计数不全)。弱章无"让主编修这章"入口。
- **改法**:save/accept 后自动 `/post-check`,结果回前端;弱章给一键"主编修这章"(触发 dedup/discipline/定向重写,`/dedup-chapter` 已有基建)。`/quality` 纳全五类,InsightView 分类展示。
- **优先级 P2**:质量已有离线工具,接进回路是把"事后体检"变"边写边查"。

## 9. 三个最重要改进点(若只做三件)

1. **G-1 场景级规划(写前节拍)**:把 plotting 从"模型听一句话即兴出整章"升级为"作者/主编先定 goal-conflict-disaster 场景卡 → `_scene_block` 注入"。命中"AI 弱在 plotting"的核心,是单章质量天花板的最大杠杆。
2. **G-2 讨论→定稿衔接**:`WriteChat` 真正按意图分流讨论/写作两路由,并把讨论结论作为 `_discuss_recap_block` 注入写作 prompt。否则人在环路的"环"没闭,多轮讨论白费。
3. **G-3 续写到目标字数**:复活已删 `render.py` 的分段续写策略(已有 `append` + `_current_tail_block` 半套基建),让单章能自动写到目标长度,而非作者反复手点续写。
