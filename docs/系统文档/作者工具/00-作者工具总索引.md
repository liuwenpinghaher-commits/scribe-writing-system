## 一句话:这 5 个工具的共性

> **绝大多数所需数据已经在库里算好了,缺的只是「聚合端点 + 前端视图」——后端改动小、对作者价值大。** 唯一需要新建表的是「进度统计」(因为 chapter 是覆盖式 UPSERT、不留每日码字时间戳)。

## 迁移编号说明(重要)

各文档草案里独立提到的迁移号(如 `043_outline` / `043_daily_progress` / clue 的 `043`)只是**示意"下一个迁移"**。真实实现时按当时仓库实际最大号(现已到 `042`)**顺序分配、避免撞号**——三者若同期落地,应是 `043/044/045`。设计文档里的号不要照抄。

## 跨工具实现顺序建议(按"价值÷成本")

1. **先做 [03 伏笔台账]**:零 schema 改动、纯聚合端点 + 三栏 UI,数据全在,**最快见效**;且 overdue 已单源,直接复用。
2. **再做 [05 护栏定位到句]**:后端"白送类"offset 一行即可,前端已有 `pmPosToProseOffset` 半套基建,MVP 性价比高,直接提升日常写作体验。
3. **再做 [02 时间线视图]**:零 schema、聚合端点 + 纯 CSS 横轴(不引依赖);注意用**不带限知时间门**的全量读画关系全史(Timeline≠Atlas 快照)。
4. **再做 [04 进度统计]**:需建 `daily_progress` 表 + save 单点记账,改动稍大但独立;先替换硬编码 100000 目标即有感。
5. **最后做 [01 大纲/卷章树]**:改动最大(新表 + 4 字段 + 拖拽依赖 `@dnd-kit`),但价值也最高(长篇结构最大空缺);MVP 只读树+卡片墙可先不引拖拽依赖。

> 关键纪律(贯穿 5 篇):**重排/排序一律走 `sort_order` 或叙事位,绝不动 `chapter.seq`**——seq 是故事时间轴,被限知全链路(facts_at/events.story_chapter/promise.setup_chapter)引用,动它=动全书时间轴。这与系统已有的"故事时间 vs 叙事顺序"分离哲学一致([02] 还指出本体尚未真正把两轴分离,是完整版才补的能力)。

## 与生成回路的关系

这 5 个是**作者工具**(看/管),与主题一~四的**生成改进**(写得更好/限知保真/质控/人在环路)互补:
- 作者工具把"系统算好的连续性"可视化 → 作者能发现问题、做决策;
- 生成改进把"决策与约束"喂回主编 → 写得更好。
两者闭环:如 [03 伏笔台账]的超期告警 ↔ 主题一的伏笔回收提醒;[02 时间线]的事件 ↔ 主题二的限知帧;[05 护栏]的句级问题 ↔ 主题三的"让主编改这处"。
