### 1.2 缺什么(逐条)

| 缺口 | 实证 | 后果 |
|---|---|---|
| **payoff_chapter 几乎不显** | 仅 CodexView 表格末列出现;Insight/Write 全无 | 作者看不到"这条收在第几章"——回收时机不可视 |
| **无 setup→payoff 连线** | 全前端无任何"埋→收"的跨章可视化 | 看不出"埋了 20 章才收"这种张力跨度,也看不出哪些已闭合 |
| **无线索(clue)台账** | 表无 `clue` 概念,无字段 | 草蛇灰线"中途几次微提醒"无处登记 → 回收显得"从仓库翻出" |
| **无 clue 概念** | schema 无 clue,store 无相关方法 | 无法做 K.M. Weiland 的"先列 payoff 再倒推 setup+中途线索"工艺 |
| **promise↔chapter 无级联** | `setup_chapter/payoff_chapter` 是裸 `int`,非 `record<chapter>` | 删章不级联;无 `payoff≥setup` DB 级断言(advance_promise store.py:772 也没断言);章号漂移无防护 |
| **无 open/close bracket 审计** | 现仅有"open 超期"单向告警 | 检不出"有 payoff 无 setup"(deus ex machina 的镜像);检不出"埋了一堆从不回收" |
| **无台账专用端点/视图** | 数据散在 `/promises` 与 `/quality.foreshadow` | 作者没有一处"三栏 + 紧迫度排序 + 操作"的仪表盘 |

> 关键判断已核实:promise 表**没有** clue/线索字段;伏笔与章节是**裸 int 关联**,无 record link;`advance_promise` 无 `payoff≥setup` 校验。

## 2. 工艺参考(setup→payoff / open-close bracket / 契诃夫枪 / 草蛇灰线)

> 本台账的设计直接对标下列长篇伏笔工艺。≥5 条带出处。

### 2.1 setup→payoff log(K.M. Weiland:先列 payoff,再倒推 setup 与线索位置)
foreshadow = setup + payoff 两个等重的半。payoff 是"事件真正发生的那一场";setup 是先前埋的线索。Weiland 还区分 **heavy foreshadowing**(早期重埋)与 **light foreshadowing**(payoff 前轻提一笔,把读者"戳醒")——这正是"中途线索(clue)"的工艺依据。修订法:**先列出所有 payoff,再倒推每个 payoff 需要的 setup 线索及其章节位置**,确保 reveal "不是凭空冒出"。
出处:[Helping Writers Become Authors · Setup and Payoff](https://www.helpingwritersbecomeauthors.com/setup-and-payoff-the-two-equally-important-halves-of-story-foreshadowing/)、[同站 · How to Use Foreshadowing](https://www.helpingwritersbecomeauthors.com/how-to-use-foreshadowing/)、[同站 · Unfulfilled Foreshadowing](https://www.helpingwritersbecomeauthors.com/unfulfilled-foreshadowing/)。

### 2.2 open bracket / closed bracket 审计模型(闭必有开 = 禁 deus ex machina)
把每个承诺视为一个**开括号 `[`**,每个回收视为一个**闭括号 `]`**。审计不变量:
- **闭必有开**:出现 payoff(`]`)却找不到对应 setup(`[`)→ 这就是 deus ex machina("交付了一个从未承诺过的 payoff,因为它从没被铺垫,所以显得随机")。**必须告警**。
- **开可故意不闭**:留一个开括号不闭,可以是刻意的(续集钩子 / 留白 / red_herring);但**非刻意的开口超期**要提醒(open 超 N 章)。
deus ex machina 与满意 payoff 的唯一分界是 **breadcrumbing(面包屑/线索铺垫)**:修订期就是"审计你的所有承诺"的时机——逐条核对每个期待是否拿到满意 payoff 或有意义的反转。
出处:[ProWritingAid · How to Avoid Deus Ex Machina](https://prowritingaid.com/art/1404/how-to-avoid-deus-ex-machina.aspx)、[Novelium · Promises and Payoffs](https://novelium.com/academy/glossary/promises-and-payoffs)、[World Builders · Promise → Payoff](https://www.worldbuilders.ai/p/promise-payoff)。

### 2.3 Chekhov's gun(契诃夫之枪:埋了必须响,否则删)
"经济原则":故事里每个元素都应必要,无关元素应删去——挂在墙上的枪后面必须开火,否则就别挂。它与 foreshadowing 互补:foreshadowing **暗示**将来会发生;契诃夫之枪**要求**被暗示的东西**真的到来**。修订法:**列一份"我引入的每个重要细节"清单,payoff 时打钩,从不回收就删**(逆查高潮→回前文埋设)。
出处:[Wikipedia · Chekhov's gun](https://en.wikipedia.org/wiki/Chekhov's_gun)、[Reedsy · Chekhov's Gun](https://reedsy.com/blog/chekhovs-gun/)、[Literature & Latte · What is Chekhov's Gun](https://www.literatureandlatte.com/blog/what-is-chekhovs-gun-a-guide-to-chekhovs-gun-and-the-power-of-foreshadowing)。

### 2.4 草蛇灰线 / 伏笔–照应(中文双向规则)
"草蛇灰线"=同一物/人/语在情节中**多次若隐若现**,如蛇行草中、灰线曳地,断续而连贯。双向规则:**前有交待(伏笔),后必照应**;无照应则前文的交待"成为多余甚至累赘"。两条工艺约束:① **埋设与照应的间距不宜过远**(太远读者忘了 → 回收无感);② 中途宜有"草蛇灰线"式的**微提醒(= clue)**,使照应"如水流就下"自然,而非生硬插入。
出处:[百度百科 · 草蛇灰线法](https://baike.baidu.com/item/%E8%8D%89%E8%9B%87%E7%81%B0%E7%BA%BF%E6%B3%95/22892605)、[知乎 · 草蛇灰线论伏笔](https://zhuanlan.zhihu.com/p/28127039)、[知乎 · 如何给剧情埋好伏笔](https://www.zhihu.com/question/441912401)。

### 2.5 情节线 spreadsheet(线索 / 章节位置 / 指向的 payoff)
专业修订普遍用电子表格按场景/章追踪情节线:列含"章节、时间、地点、**何时丢出线索/秘密/揭示**(谁在何时知道什么,避免 plot hole)";"承诺(誓言/线索/规则/象征)在左列,**payoff 的场景与页码在右列**",确保每个故事承诺都被兑现;修订时用复选框/高亮标记完成。Story Grid 等工具把这做成"逐场景"诊断单元。
出处:[Darcy Pattison · Spreadsheet Plotting](https://www.darcypattison.com/writing/plot/spreadsheet-plotting/)、[Story Grid · Spreadsheet](https://storygrid.com/spreadsheet/)、[Carrow Brown · Outlining With a Spreadsheet](https://carrow.substack.com/p/outlining-your-novel-with-a-spreadsheet)。

> **工艺 → 本台账映射**:
> setup→payoff log → 三栏 + setup→payoff 连线;
> open/close bracket → ledger 的 `audit`(有 payoff 无 setup 告警 + 开口超期);
> 契诃夫枪 → "埋了从不回收"的提醒 + 删除入口;
> 草蛇灰线/clue → `clues[]` 中途线索台账 + 间距(`chapters_open`)可视化。

## 3. 设计

### 3.1 数据模型

#### 3.1.1 基线(MVP 不改 schema)
MVP 完全复用现有 promise 表与单源 overdue 逻辑——**不需要任何迁移**即可交付三栏台账 + setup→payoff 连线。下面的字段/迁移属于"完整期"增量。

#### 3.1.2 增量 A:线索台账 `clues`(完整期)
给 promise 加一个**内嵌数组** `clues`,每条线索记 `{chapter, note}`——对应草蛇灰线的"中途微提醒"与 Weiland 的 light foreshadowing。选内嵌(而非独立表 + relate)因为:线索强属于某条 promise、量小、无需被别处引用、读 promise 时一次取回。

```surql
-- migrations/043_promise_clues.surql(草案)
-- 线索台账:草蛇灰线的中途微提醒。每条 {chapter:int, note:string}。
DEFINE FIELD IF NOT EXISTS clues ON promise TYPE option<array> DEFAULT [];
DEFINE FIELD IF NOT EXISTS clues[*] ON promise TYPE object;
DEFINE FIELD IF NOT EXISTS clues[*].chapter ON promise TYPE int;
DEFINE FIELD IF NOT EXISTS clues[*].note    ON promise TYPE string;
```

> 若日后需要"线索可被事件/命题引用"或全局检索线索,再升级为独立 `clue` 表 + `RELATE promise->has_clue->clue`。当前不必。

#### 3.1.3 增量 B:promise↔chapter record link + payoff≥setup 断言(完整期)
现状 `setup_chapter/payoff_chapter` 是裸 int。chapter 表的记录 id 即 `chapter:<seq>`(见 `save_chapter` UPSERT `type::record('chapter',$seq)`,store.py:783)。升级为 record link 可得:**删章级联检测** + **DB 级 payoff≥setup 断言**。

分阶段迁移(与 `026_record_links.surql` 同款"新字段并存→回填→切换"模式,避免一次性破坏旧数据):

```surql
-- migrations/044_promise_chapter_link.surql(草案)
-- 阶段1:加并存的 record link 字段(不动旧 int 字段)
DEFINE FIELD IF NOT EXISTS setup_ref  ON promise TYPE option<record<chapter>>;
DEFINE FIELD IF NOT EXISTS payoff_ref ON promise TYPE option<record<chapter>>;
-- 阶段2(数据回填,代码侧或一次性脚本):
--   UPDATE promise SET setup_ref  = type::record('chapter', setup_chapter)  WHERE setup_chapter  != NONE;
--   UPDATE promise SET payoff_ref = type::record('chapter', payoff_chapter) WHERE payoff_chapter != NONE;
-- 阶段3:payoff≥setup 断言(回填校验通过后再加)
DEFINE FIELD OVERWRITE payoff_chapter ON promise TYPE option<int>
  ASSERT $value = NONE OR $value >= setup_chapter;
```

**删章级联**:在 `delete_chapter`(若有/新增)里,先查 `SELECT * FROM promise WHERE setup_ref = chapter:$seq OR payoff_ref = chapter:$seq`,命中则**告警**(不静默删 promise)——伏笔比章"重",删章应让作者决定 promise 去留。

> **决策建议**:增量 B 的 record link 收益主要是"删章级联检测"。若当前没有"删章"用户路径,record link 可缓做;但 **payoff≥setup 断言应尽早做**(见 §4 任务,可在 `advance_promise` Python 侧先加,不依赖迁移)。

#### 3.1.4 字段是否要加 —— 结论

| 增量 | 是否必须 | 阶段 |
|---|---|---|
| 三栏台账 + 连线所需字段 | **无须加**(现有字段够) | MVP |
| `payoff≥setup` 校验 | **建议加**(Python 侧先行,DB 断言后补) | 进阶 |
| `clues[]` 线索数组 | 完整期加(草蛇灰线工艺所需) | 完整 |
| `setup_ref/payoff_ref` record link | 可选(有删章路径才必要) | 完整 |

### 3.2 后端 `GET /promises/ledger`(单源)

**单源原则**:overdue 阈值只读 `OVERDUE_SLACK`(app.py:37)+ `intent.overdue_threshold` 覆盖(store.py:861),**与 `/promises`、`/quality` 完全同一份逻辑**。实现时把这段判定抽成一个 helper(如 `_overdue_flag(p, mc, slack)`),三处共用,杜绝漂移(§8.2 缺口表点名"散落两处")。

**返回结构**:三栏(`open / closed / red_herring`)+ 每条携带 `setup_chapter/payoff_chapter/overdue/chapters_open/clues` + 全局 `audit`(open/close bracket 完整性)。

```jsonc
// GET /promises/ledger?work=main
{
  "threshold": 3,                 // 当前生效的超期阈值(单源:intent.overdue_threshold ?? OVERDUE_SLACK)
  "max_chapter": 9,               // 当前最大有事件章号(超期判定的"现在")
  "open": [                       // 已埋未收(status=open 且 kind=promise),按超期紧迫度降序
    {
      "id": "promise:a1b2",
      "text": "铜炉会反噬埋下它的人",
      "kind": "promise",
      "status": "open",
      "setup_chapter": 1,
      "payoff_chapter": null,
      "chapters_open": 8,         // max_chapter - setup_chapter(已开口跨度)
      "overdue": true,            // open 且非 red_herring 且 setup+slack < max_chapter
      "clues": [                  // 草蛇灰线中途提醒(无 clues 字段时为 [])
        { "chapter": 4, "note": "炉壁渗出血色铜锈" }
      ]
    }
  ],
  "closed": [                     // 已回收(status=closed),按 payoff_chapter 升序
    {
      "id": "promise:c3d4",
      "text": "赵芙南知道祭炉秘法",
      "kind": "promise",
      "status": "closed",
      "setup_chapter": 2,
      "payoff_chapter": 7,
      "span": 5,                  // payoff_chapter - setup_chapter(setup→payoff 跨度,连线长度)
      "overdue": false,
      "clues": [{ "chapter": 5, "note": "她对炉火的眼神" }]
    }
  ],
  "red_herring": [                // 障眼法(kind=red_herring),单列,不计超期
    {
      "id": "promise:e5f6",
      "text": "管家形迹可疑(实为障眼)",
      "kind": "red_herring",
      "status": "open",
      "setup_chapter": 3,
      "payoff_chapter": null,
      "chapters_open": 6,
      "overdue": false,           // red_herring 永不超期
      "clues": []
    }
  ],
  "audit": {                      // open/close bracket 完整性审计
    "balanced": false,
    "overdue_count": 1,           // 开口超期数(open 非 herring 超 N 章)
    "payoff_without_setup": [     // 闭无开 = deus ex machina 候选:payoff_chapter < setup_chapter
      { "id": "promise:bad1", "text": "...", "setup_chapter": 9, "payoff_chapter": 3 }
    ],
    "closed_without_setup": [],   // payoff 有值但 setup_chapter 缺失/<=0(数据异常,亦报)
    "never_paid": 1               // = len(open 非 red_herring)。契诃夫枪提醒:埋了还没响
  }
}
```

**audit 判定规则**(纯计算,不改库):
- `payoff_without_setup`:`status=closed && payoff_chapter != null && setup_chapter != null && payoff_chapter < setup_chapter` —— **闭必有开**违例(回收早于埋设,逻辑上是凭空 payoff)。这是 open/close bracket 模型的"闭无开"在裸 int 下的可检形态。
- `closed_without_setup`:`payoff_chapter != null && (setup_chapter == null || setup_chapter <= 0)` —— 数据异常,亦归为"闭无开"。
- `overdue_count`:复用单源 overdue。
- `never_paid`:open 非 red_herring 的计数(契诃夫枪"埋了未响"提醒;数量大时作者该警觉)。
- `balanced`:`overdue_count == 0 && payoff_without_setup == [] && closed_without_setup == []`(red_herring 的"故意不闭"不破坏 balanced)。

> **store 侧**新增纯函数 `promise_ledger(store) -> dict`(放 store.py 或 `health.py`),app.py 端点只做 `work` 解析 + 调用,保证逻辑单源、可单测。

### 3.3 前端 `PromiseDashboard`

#### 3.3.1 落点选择

#### 3.3.3 交互
- **三栏看板**:`open`(紧迫度降序,超期标红)/ `closed`(payoff 升序,带 setup→payoff 连线)/ `red_herring`(单列)。数据全来自 `GET /promises/ledger`,前端**不重算超期**。
- **setup→payoff 连线**:已回收栏每条画一条 `●━━━●`,长度 ∝ `span`(payoff−setup);clue 在线上以 `▲` 标记章位。
- **超期红高亮**:`overdue===true` 的条目整行红边 + 红"超期"标签。
- **点伏笔跳章**:`[跳第N章]` 调用现有"打开某章"路由(WriteLayout 已有按章定位能力,复用其 setChapter/路由);setup 与 payoff 各一个跳转按钮。
- **标记回收**:`[标回收]` 弹一个"回收于第几章"输入 → `POST /promises/{pid}/advance {payoff_chapter}`(见 §4 新端点),成功后刷新 ledger。
- **标 red_herring / 转伏笔**:复用 `PATCH /promises/{pid}`(`promise_kind` 切换),刷新。
- **埋新伏笔**:复用 `POST /promises-new`。
