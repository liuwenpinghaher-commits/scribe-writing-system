## 1. 现状与缺口

### 1.1 已有的"章号轴"数据(逐表列,带 file:line)

本系统所有状态都钉了"故事时间轴(章号)",这是限知引擎的硬约束(`01-本体与数据模型.md` §0 三连第 2 条)。时间线视图要消费的,就是这批轴:

| 表 | 章号字段 | 含义 | store 读方法(file:line) | REST 端点(file:line) |
|---|---|---|---|---|
| `event` | `story_chapter`(int) | 事件发生在故事第几章 | `events_at(chapter)` `store.py:902` / `max_chapter()` `store.py:892` | `GET /events?chapter=` `app.py:193` |
| `char_state` | `chapter`(int) | 角色弧光**质变点**(能力/关系/性格/composite) | `list_char_states(cid)` `store.py:1143` / `char_state_at(cid,ch)` `store.py:1116` | `GET /char-states?character_id=` `app.py:531` / `GET /char-state-at` `app.py:550` |
| `promise` | `setup_chapter` + `payoff_chapter` | 伏笔埋下章 → 回收章(open/closed,promise/red_herring) | `list_promises()` `store.py:765` | `GET /promises`(已带 `overdue` 单源)`app.py:219` |
| `character_relation` | `since_chapter` + `until_chapter` | 关系建立章 → 失效章(双时态右端) | `relations_at(ch)` `store.py:1007` | `GET /character-relations?chapter=` `app.py:500` |
| `proposition` | `valid_from` + `valid_to` | 命题(quality)生效→失效;`supersede_fact` 写右端 | `facts_at(ch)` `store.py:475` / `supersede_fact` `store.py:307` | `GET /facts?chapter=` `app.py:188` |
| `chapter` | `seq` | 章节落库序(=叙事顺序;详见 §1.3) | `list_chapters()` `store.py:818` | `GET /chapters` |

**关键观察**:每一项都自带"何时发生/生效/失效"的整数章号 → 天然可投到一根横轴上。`events_at` 还沿图边带回了 `participants`(SUBJ/OBJ/WITNESS,`store.py:914`)、`effects`、`causal_in`、`motivated_by_goal`、`location` —— 这些正好是事件卡的元数据(§3.3)。

### 1.2 `events_at` 返回什么、够不够喂时间线(代码实证)

`store.py:902` 的 `events_at(chapter)` 对**单章**返回 `list[Event]`,每个 `Event`(`ontology.py` 的 dataclass)含:

```python
Event(
  id="ev:炼钉", type="炼器",
  participants={"SUBJ":"role:焦三","WITNESS":"role:云阳真人"},  # role→entity_id
  location="place:丹房",
  story_time=3,                       # ← 就是 story_chapter
  preconditions=[...],
  effects=["fact:御铜"],               # 看见即知道的种子
  causal_in=[("ev:拜师","enables")],   # 因果入边
  motivated_by_goal="给母治眼凑钱",
)
```

**够喂**:角色(泳道分组键)、类型(卡片着色)、章号(横轴坐标)、因果(连线)、目标(IPOCL 摘要)全有。
**不够的只有一处**:`events_at` 是**按单章查**的(`WHERE story_chapter = $ch`)。时间线要"一次拿到 `[from,to]` 全区间",当前要么前端循环逐章调 `/events`(N 次往返,劣),要么后端加一个区间聚合端点(本设计选后者,§3.2)。

### 1.3 故事时间 vs 叙事顺序:**本体未分离**(核实结论)

这是 Aeon Timeline 的核心范式(§2.1),必须先核实本系统现状:

- `event` 表**只有 `story_chapter` 一根轴**。`018_event_story_chapter.surql` 引入它,`040_naming_collapse.surql` 删掉了旧的 `event.valid_from` 双写列 —— 收口成**单轴单源**(`store.py:894` 注释:"命名漂移收口后唯一真源")。
- `chapter.seq` 是手稿章节的**落库序**,语义上=**叙事顺序**(读者读到的先后)。
- **当前两者事实上同义**:系统假设"第 N 章正文 = 故事第 N 章发生的事",没有为"倒叙/闪回"(故事时间早、叙事位置晚)预留独立坐标。
- **后果**:写一段"第 12 章插叙主角童年(故事时间=第 0 章)"时,本系统无处安放"它在故事编年里属于很早、但在叙事里出现在第 12 章"这个事实。`event.story_chapter` 只能二选一。

→ **这正是"完整版"阶段要补 `narrative_position` 的动机**(§3.1、§6 分期)。MVP / 进阶不触碰它,先把"单轴横铺"做出来。

### 1.4 AtlasView 现状:只画关系,不画时间

`AtlasView.jsx`(173 行,`web/src/views/AtlasView.jsx`)是现有图谱视图:

- 数据源 `api.graph()` → `GET /graph` → `store.graph(chapter)`(`store.py`,见正文):返回 `{nodes:[{id,type,label,secret}], edges:[{src,dst,rel}]}`。节点=角色+命题,边=`knows`(谁知道什么)+ `character_relation`(谁和谁什么关系)。
- 渲染栈:`@xyflow/react`(ReactFlow)+ `elkjs`(ELK `force` 布局,`AtlasView.jsx:63`)。节点用力导向自由布点。
- **它有一个 `chapter` 入参的能力**(`graph(chapter)` 支持按章过滤),但 AtlasView **没接时间滑块**——永远拉全量(`api.graph()` 不传 chapter)。**时间维度在数据层支持、在视图层未消费**。
- `REL_COLOR` / `REL_LABEL`(`AtlasView.jsx:11-50`)已是 26 词中文关系的完整配色表 —— **时间线视图可直接复用这两张表给关系节点/事件着色**。

**结论**:AtlasView 回答"此刻世界长什么样(快照)";它**不**回答"世界沿章号如何演变(过程)"。后者就是 TimelineView 的职责。两者互补,不替代。

### 1.5 缺口一句话

> 数据库已经把"连续性"算成了一批"章号锚状态",但作者**没有任何一个视图能把它们沿章号横铺**,一眼看出"第几章发生了什么事 / 哪些弧光在此质变 / 哪些伏笔在此埋下或回收 / 哪些关系在此建立或破裂"。TimelineView 填这个缺口。

## 2. 工艺参考(全网检索,带出处)

深挖专业时间线工具的可视化范式,提炼**具体可迁移的设计决策**。

### 2.1 Aeon Timeline:故事时间 vs 叙事时间"两套独立排序"〔核心范式〕

Aeon Timeline 3 把事件排序拆成**两套独立、可各自查看与编辑的顺序**:

- **Chronological Order(编年序)**:事件**实际发生**的、基于日期/时刻的顺序。用于 Timeline / Spreadsheet / Subway / Relationship 等多数视图。
- **Narrative Order(叙事序)**:事件在**故事讲述中被引入**的顺序,**独立于其日期**,组织成 Part / Chapter / Scene 的层级结构。

> 官方原话(转述):涉及**闪回或时间旅行的非线性故事**,受益于能同时查看和创建"事件的编年序"与"它们在故事里出现的顺序";世界观构建还能挂在时间线上而**不污染故事叙事**。
> 出处:[Chronological vs Narrative Order — Aeon Timeline 3 KB](https://help.timeline.app/article/149-chronological-vs-narrative-order)、[Storytelling with Narrative View](https://www.aeontimeline.com/features/narrative-storytelling)

**对本系统的意义**:这正是 §1.3 我们**缺**的能力。本系统 `story_chapter` 对应"编年序",但没有独立的"叙事序"坐标。完整版要补的 `narrative_position`(§3.1)就是 Aeon 的 Narrative Order 的最小实现——一个独立排序轴,让"故事第 0 章发生、叙事第 12 章出现"可表达。

### 2.2 Aeon Timeline · Subway View(地铁图):泳道=实体/弧线,站点=事件〔泳道范式〕

Subway View 是一张**地铁线路图式**的可视化:**事件=节点(站/站点)**,**实体/故事弧=轨道(线路)**,事件沿轨道按编年序排布,**轨道在共享事件处汇聚、在分开时岔开**——直观展示"人物/情节线如何随时间交织"。两种布局:

- **Subway(默认)**:每个节点只画一份,多条轨道在共享事件处**合并**再分开(地铁换乘站)。
- **Separated(分离)**:每条轨道**独占一条水平线**,共享事件在每条相关轨道上各画一份副本。

> 出处:[Subway View — Aeon Timeline 3 KB](https://help.timeline.app/article/171-subway-view)、[How To Use Story Arcs](https://help.timeline.app/article/150-how-to-use-story-arcs)

**对本系统的意义**:**"泳道按什么分"有了权威答案——可按实体(角色),也可按 Story Arc(情节线/弧)**。本系统:
- 按**角色**分泳道 → 直接用 `event.participants` 的 SUBJ/OBJ(每个角色一条道,事件落在参与它的所有道上,即 Separated 布局)。
- 按**事件类型**分泳道 → 用 `event.event_type`。
- 按**情节线**分泳道 → 本系统暂无"情节线/弧"实体;最接近的是 `char_state.arc_phase`(角色弧光阶段)或 `promise`(伏笔线)。完整版可考虑引入轻量"arc"标签。
- "共享事件处轨道汇聚"= 一个事件被多角色参与时,在多条泳道上各出现一次(Separated 语义),用**因果连线**串起跨道关系。

### 2.3 Aeon Timeline · 参与者/见证者 + 自动算年龄〔事件卡元数据范式〕

Aeon 的 Roles 配置事件与实体的关系:一个人可以是事件的 **Participant(参与者)** 或 **Witness(见证者)**;若实体有出生日期/出生事件,Aeon 在选中事件时**自动算出该实体此刻的年龄**(精确到年月日),两角色相遇时自动算双方年龄。

> 出处:[The Inspector — Aeon Timeline KB](https://help.aeontimeline.com/article/37-the-inspector)、[Key Concepts: Parts of a Timeline](https://help.aeontimeline.com/article/20-key-concepts)

**对本系统的意义**:**参与者/见证者范式与本系统的 `involves.role ∈ {SUBJ, OBJ, WITNESS}` 字面同构**(`store.py:914`)。事件卡应直接展示 SUBJ/OBJ/WITNESS 三槽。本系统没有"出生日期"故不算年龄,但**等价物是 `char_state_at(char, chapter)`**——"该角色在此章的能力/性格快照",可在事件卡 hover 时显示"此刻焦三:已会御铜、心愿=报仇"。

### 2.4 Plottr:Chapters × Plotlines **网格**〔正交范式,与泳道互补〕

Plottr 的 Visual Timeline 是一张**彩色网格**:**行=章节(Chapters)**,**列=情节线(Plotlines)**,每个**场景卡(scene card)**落在某行某列的格子里,像数字化的索引卡/便利贴墙,支持拖拽、过滤、按情节线着色。系列视图(Series view)能跨多本书追踪未闭合的故事线(open loops / threads)。

> 出处:[Plottr 官网](https://plottr.com/)、[Timeline Creation — Plottr](https://plottr.com/timeline-creation/)、[Plottr Review — NewWriters](https://newwriters.org.uk/best-writing-software/plottr-review/)

**对本系统的意义**:Plottr 是**网格**(章×线),Aeon Subway 是**泳道/地铁**。两者是同一数据的两种投影:
- Plottr 网格 ≈ 本系统"**泳道按情节线/类型分 + 横轴章号**"的转置(行列互换)。
- 本系统的 `promise`(setup→payoff 跨多章的故事线)正对应 Plottr 的"open loops"——网格能让"哪条线在哪章还开着"一目了然。
- 取舍:**泳道(横铺)更适合"沿章号读演变";网格更适合"按线归类清点"**。本视图主打泳道(更贴合"章号横铺"诉求),网格可作为进阶的"切换布局"。

### 2.5 中文 51mazi:时间线 + 事序图(拖拽 + 进度)〔本土轻量范式〕

开源中文写作软件 51mazi(Electron+Vue3)内置**时间线管理**(理清故事时间顺序、避免时间线混乱)与**事序图(Event Sequence Diagram)**——一个**时间轴可视化**工具,支持**拖拽调整事件位置**与**进度(0–100%)追踪**(甘特式)。

> 出处:[51mazi — GitHub](https://github.com/xiaoshengxianjun/51mazi)、[51mazi README_EN](https://github.com/xiaoshengxianjun/51mazi/blob/main/README_EN.md)

**对本系统的意义**:① 验证了"时间线 + 事序图"是中文长篇作者的刚需;② "拖拽调位"提示一个**进阶交互**:作者拖动事件卡 → 改 `story_chapter`(或 `narrative_position`);③ "甘特式进度条"提示**伏笔/弧光可画成跨章的横条(span bar)**——`promise` 的 `[setup, payoff]` 区间、`character_relation` 的 `[since, until]` 区间天然是甘特条。

## 3. 设计

### 3.1 数据层:基本零改;完整版加一个可空字段

**MVP + 进阶:不动 schema**。所有数据已在(§1.1)。聚合在后端读路径完成(§3.2)。

**完整版(故事/叙事双轴分离)**:加**一个可空字段**:

```sql
-- migrations/0XX_event_narrative_position.surql
-- 叙事位:事件在"故事讲述顺序"中的位置,独立于 story_chapter(故事编年)。
-- null = 与 story_chapter 同序(线性叙事,向后兼容);非 null = 倒叙/闪回的独立坐标。
DEFINE FIELD IF NOT EXISTS narrative_position ON event TYPE option<int>;
DEFINE INDEX IF NOT EXISTS idx_event_narrative_pos ON event FIELDS narrative_position;
```

- **语义**:`story_chapter` = Aeon 的编年序(事件实际发生);`narrative_position` = Aeon 的叙事序(读者读到它的位置)。线性叙事下两者相等,故 `narrative_position` 为 null 时**回退** `story_chapter`,**不破坏任何现有读路径**(`events_at`、`max_chapter` 一行不改即继续工作)。
- **为何可空而非必填**:绝大多数事件是线性的;只有闪回/插叙/时间旅行才需要独立叙事位。可空 = 零迁移成本、零默认值争议。
- **读取**:`events_at` 增补一个 `order_axis` 参数(`"story"` | `"narrative"`),仅决定 `ORDER BY` 用哪根轴;`narrative` 时 `ORDER BY narrative_position ?? story_chapter`。

> ⚠ 不要在 MVP 就加这个字段。先把"单轴横铺"跑通、被作者用上,再按真实倒叙需求引入第二轴。过早分两轴会让聚合端点和前端复杂度翻倍而无人消费(YAGNI,对齐 `01-本体` §9-H 的死字段教训)。

### 3.2 后端:`GET /timeline` 聚合端点

新增**一个只读聚合端点**,把四类"章号锚状态"归并成一个**按章分组**的统一结构。读路径,不写库,不碰限知门控(时间线是作者全知视图,展示设定层结构而非某 POV 帧)。

**store 层新增方法**(`store.py`,放在 `events_at` 附近):

```python
def timeline(self, ch_from: int = 1, ch_to: int | None = None) -> list[dict]:
    """聚合 [ch_from, ch_to] 区间内所有"章号锚状态",归并成时间线条目。
    无写、无限知门控(作者全知工艺视图)。每条目带 chapter/kind/lane_keys/label/refs。
    复用既有读方法,不新增 SQL 真源,避免双源漂移。"""
    hi = ch_to if ch_to is not None else self.max_chapter()
    items: list[dict] = []

    # 1) 事件(逐章复用 events_at;区间小,N 次内存查可接受。
    #    若性能敏感可改一条 WHERE story_chapter IN range 的批查,真源仍是 event 表)
    for ch in range(ch_from, hi + 1):
        for ev in self.events_at(ch):
            subj = [v for k, v in ev.participants.items() if k == "SUBJ"]
            obj  = [v for k, v in ev.participants.items() if k == "OBJ"]
            wit  = [v for k, v in ev.participants.items() if k == "WITNESS"]
            items.append({
                "chapter": ev.story_time, "kind": "event", "id": ev.id,
                "label": ev.type, "goal": ev.motivated_by_goal,
                "lane_keys": subj + obj,                 # 角色泳道键(参与者落道)
                "event_type": ev.type,                   # 类型泳道键
                "refs": {"subj": subj, "obj": obj, "witness": wit,
                         "effects": ev.effects, "location": ev.location,
                         "causal_in": [c[0] for c in ev.causal_in]},
            })

    # 2) 伏笔:setup 点 + payoff 点 + 跨章 span(甘特条)
    for p in self.list_promises():
        s = p["setup_chapter"]
        if ch_from <= s <= hi:
            items.append({"chapter": s, "kind": "promise_setup", "id": p["id"],
                          "label": p["text"], "lane_keys": ["__promise__"],
                          "refs": {"status": p["status"], "promise_kind": p["kind"],
                                   "payoff_chapter": p.get("payoff_chapter")}})
        pf = p.get("payoff_chapter")
        if pf and ch_from <= pf <= hi:
            items.append({"chapter": pf, "kind": "promise_payoff", "id": p["id"],
                          "label": p["text"], "lane_keys": ["__promise__"],
                          "refs": {"setup_chapter": s, "promise_kind": p["kind"]}})

    # 3) 角色弧光质变点(每条 char_state 一个点)
    for c in self.characters():
        for cs in self.list_char_states(c.id):
            if ch_from <= cs["chapter"] <= hi:
                items.append({"chapter": cs["chapter"], "kind": "arc",
                              "id": cs["id"], "label": cs.get("summary", ""),
                              "lane_keys": [c.id],
                              "refs": {"character": c.id, "change_type": cs["change_type"],
                                       "arc_phase": cs.get("arc_phase"),
                                       "affects_voice": cs.get("affects_voice")}})

    # 4) 关系建立点 / 失效点(用 since/until;relations 跨章 span 在前端按 src+dst+since 配对画条)
    for r in self._all_relations():   # 见下:不带时间门的全量关系读
        if ch_from <= r["since_chapter"] <= hi:
            items.append({"chapter": r["since_chapter"], "kind": "relation_start",
                          "id": f"{r['src']}->{r['dst']}@{r['since_chapter']}",
                          "label": r["relation"],
                          "lane_keys": [f"role:{r['src']}", f"role:{r['dst']}"],
                          "refs": {"src": f"role:{r['src']}", "dst": f"role:{r['dst']}",
                                   "until_chapter": r.get("until_chapter")}})
        u = r.get("until_chapter")
        if u and ch_from <= u <= hi:
            items.append({"chapter": u, "kind": "relation_end",
                          "id": f"{r['src']}->{r['dst']}@end{u}",
                          "label": r["relation"],
                          "lane_keys": [f"role:{r['src']}", f"role:{r['dst']}"],
                          "refs": {"src": f"role:{r['src']}", "dst": f"role:{r['dst']}",
                                   "since_chapter": r["since_chapter"]}})

    items.sort(key=lambda x: (x["chapter"], x["kind"]))
    return items
```

> 注:`relations_at(ch)`(`store.py:1007`)带"限知时间门"(只返回该章**仍开着**的关系),会**漏掉已失效的历史关系**——时间线恰恰要画"何时建立、何时破裂"的**全史**,故需一个**不带时间门的全量读** `_all_relations()`(裸 `SELECT ... FROM character_relation`,不加 `until` 过滤)。这是与 AtlasView 的关键区别:Atlas 要"此刻快照",Timeline 要"全程演变"。

**FastAPI 端点**(`app.py`,放在 `/events` 附近):

```python
@app.get("/timeline")
def timeline(ch_from: int = Query(default=1, ge=1),
             ch_to: int | None = Query(default=None, ge=1),
             work: str = "main"):
    st = _store_for(work)
    items = st.timeline(ch_from, ch_to)
    return {"from": ch_from, "to": ch_to or st.max_chapter(),
            "max_chapter": st.max_chapter(), "items": items}
```

**泳道切换语义**(顶栏下拉,对应 §2.2 / §2.4):

| 模式 | 分组键 | 数据来源 | 说明 |
|---|---|---|---|
| **按角色**(默认) | `item.lane_keys`(参与者 entity_id) | `participants` SUBJ/OBJ | 一事件参与多角色 → 在多条泳道各画一份(Aeon Separated 语义)。弧光/关系天然落到角色道 |
| **按情节线** | `arc_phase` 或 `__promise__` | `char_state.arc_phase` / `promise` | 接近 Plottr 的 Plotline 列;伏笔线独占一道 |
| **按事件类型** | `item.event_type` | `event.event_type` | 炼器/战斗/对话…各一道,看类型节奏 |

固定泳道:**伏笔道(`__promise__`)** 与 **关系道** 在"按角色"模式下作为顶部/底部的特殊泳道常驻(它们不属于单个角色)。

**跨章连线 / 甘特条画法**:
- **伏笔** `[setup_chapter, payoff_chapter]`:从 setup◇ 到 payoff● 画一条横线;`status=open` 且 `setup+slack < max_chapter` → 标⚠超期(slack 读 `/promises` 已带的 `overdue` 字段,**单源,不在前端重算**)。`red_herring` 用灰色虚线、不标超期。
- **关系** `[since_chapter, until_chapter]`:在 src 与 dst 两条角色泳道间画一条甘特虚线条,`until` 处标✗失效点(用 `REL_COLOR` 着色,复用 `AtlasView.jsx:11`)。
- **因果** `event.causal_in`:在两个事件卡间画一条弧线(地铁式换乘,对应 §2.2 轨道汇聚)。

**交互**:
- 点事件卡 → 跳对应章正文(`chapter.seq = story_chapter`)/ 打开实体详情。
- 点弧光◆ → 打开该角色 `list_char_states` 演进史。
- 点关系条 → 打开"关系演变史"(对接 `01-本体` §9-B 的关系回放,与本视图共享 `_all_relations`)。
- 顶栏章号滑块 → 改 `ch_from/ch_to`,重拉 `/timeline`。

### 3.4 能否复用 AtlasView 的渲染栈?

**部分复用,主体不复用**:

| 复用 | 不复用 |
|---|---|
| ✅ `REL_COLOR` / `REL_LABEL`(26 词中文关系配色,`AtlasView.jsx:11-50`)——抽到共享模块 `web/src/lib/relColors.js`,两视图共用 | ❌ ELK `force` 力导向布局(`AtlasView.jsx:63`)——时间线是**确定性坐标**(x=章号×刻度宽,y=泳道序×行高),**不需要也不能用力导向**(力导向会破坏"章号=x"的硬约束) |
| ✅ 设计 token(`var(--color-brand/secret/irony/line)`)、卡片阴影风格 | ❌ ReactFlow 的自由画布——时间线用**带横向滚动的网格容器**(CSS grid / 绝对定位 + `overflow-x`),更可控;或用轻量 ReactFlow 但禁用自动布局、手动钉 position |
| ✅ `api.js` 的 `j()` 封装与 work 注入(`api.js:17`)——加 `api.timeline()` 一行 | ❌ `api.graph()` 数据形状(节点/边)——时间线用 `{items:[...]}` 扁平数组,不是图 |

**渲染技术选型建议**:MVP 用**纯 CSS(absolute 定位 + grid 刻度 + `overflow-x-auto`)**最简单可控;事件卡是普通 `<div>`,横轴坐标 `left = (chapter - from) * COL_W`。**不引入新依赖**。因果连线/甘特条用 SVG `<line>`/`<path>` 叠一层。若后续要拖拽改章号(§2.5),再评估是否引入 ReactFlow 的手动布局模式。

| **完整** | 故事时间 vs 叙事时间双轴切换;闪回/倒叙独立坐标;(可选)地铁式弧线交叉、Plottr 网格切换 | `narrative_position` migration + `events_at`/`timeline` 双轴 + 双视图 UI | **是(加 1 个可空字段)** |

> **推进策略**:MVP 是"把数据库已算好的连续性变成作者能横铺看的视图"的**最小可用闭环**,优先交付被作者用上;进阶补齐工艺密度(伏笔/弧光/关系全上泳道);完整版仅在出现真实倒叙/闪回写作需求时才引入第二轴——避免过早分轴(YAGNI)。
