### 1.2 缺口(本篇要补)

经核实代码,以下**全部不存在**:

1. **无任何 per-day 写作记录**。`chapter` 表只有 `prose`/`qc_word_count`,**没有 `updated_at`**——一次 `save_chapter`(`store.py:777`)是 `UPSERT`,覆盖式写入,不留时间戳、不留前后字数差。所以**今天 store 里拿不到「今天写了多少字」**。
2. **`chapter_version.created_at` 能否当「码字时间戳」近似日进度?** —— **只能部分近似,不可靠**:
   - 它只在作者**手动打存档点 / 存为正文**(`/checkpoint`,`app.py:1430`)时才产生,**不是每次 save 都有**。日常 `save-chapter` 落库不写 version。
   - 它存的是**该版全文**(`prose` 字段),要算「日 delta 字数」得对相邻 version 做字数差,且同一章多次存档会重复计,跨章累计也要去重——派生逻辑复杂且有盲区(没打存档点的那天会凭空消失)。
   - 结论:**可作为「完整事件日志缺位时的兜底回填源」**(见 §3.1 方案 B),但**不足以**作为主数据源支撑「日字数 / 连胜 / 趋势」。
3. **无可编辑目标**。整稿目标是前端硬编码 `100000`(`Library.jsx:52`、`InsightView.jsx:33`),每日目标根本不存在。`intent` 表(`store.py:854` `get_intent`/`set_intent`)只有 `reader_feeling`/`emotional_arc`/`red_lines`/`overdue_threshold`,**没有字数目标字段**。
4. 无 streak、无日历热力图、无趋势(30/90 天)、无 session 计数。

> **关键判断(据实):本篇是作者工具系列里唯一**可能**需要新表的工具。** 因为「日字数 / 连胜 / 趋势」必须有 per-day 写作记录,而现有 schema 完全没有。推荐新建 `daily_progress` 日聚合表(§3.1 方案 A),目标字段加在 `intent` 表上。

## 2 · 工艺参考(全网素材深挖,带出处)

提炼对照 6 类专业写作 / 网文码字产品的**具体机制与 UX**:

### 2.1 目标怎么设:整稿目标 + 每日目标 + 截止日反推

- **Scrivener Project Targets**:`Project > Show Project Targets` 弹窗设两类目标——**Draft(整稿)目标 + Session(本次会话)目标**;Session 可配「每日定时重置 / 开关项目时重置」;两条进度条:上=整稿进度,下=当日会话进度。([Literature & Latte](https://www.literatureandlatte.com/blog/track-statistics-and-targets-in-your-scrivener-projects))
- **Ulysses Goals**:目标可按**字符/词/行/段/页/朗读时长**计;**每日目标**午夜自动重置;**截止日(Deadline)反推**——设 4000 字总目标 + 4 天截止,自动算出「每天 1000 字」并据此显示当日应完成份额。([Ulysses Help](https://help.ulysses.app/goals))

→ **scribe3 取舍**:作品级**整稿目标**(替换硬编码 10 万)+ **每日字数目标**(默认可空)。截止日反推列为进阶(MVP 不做)。目标存 `intent`(per-work)。

### 2.2 进度怎么可视:进度条变色 + 双轨 + 理想线对照

- **Scrivener / Ulysses 进度条变色**:**蓝色=未达标,达标变绿,超出变红**(Ulysses)——颜色即状态,无需读数字。([Ulysses Help](https://help.ulysses.app/goals))
- **FocusWriter 底部进度条**:屏幕底部一根小进度条 + 鼠标移到底部浮出「已写总字数 / 当日目标完成百分比」。([gottcode.org/focuswriter](https://gottcode.org/focuswriter/))
- **Writing Streak 的「理想线 vs 实际线」**:一条**虚线 = 按时完成应有的字数轨迹**,一条**实线 = 实际累计**,目标是让实线始终压在虚线上方。([writingstreak.io](https://writingstreak.io/))

→ **scribe3 取舍**:① 进度条按真实目标算并**变色**(<100% 黛绿渐变,=100% 绿,>100% 金/「超额」徽标);② 累计推进曲线叠一条**理想线**(若设了整稿目标 + 节奏);③ 每日字数柱状图,达标当日柱顶描金。

### 2.3 streak 怎么算与展示:连续天数,断一天清零

- **定义(共识)**:streak = **连续有写作的天数**;今天写了 +1,**漏一天清零**。([Hearth](https://hearth.sh/features/writing-streaks)、[indieauthormagazine](https://indieauthormagazine.com/seven-apps-to-gamify-your-writing-sessions-and-other-author-approved-methods-for-boosting-your-word-count/))
- **达标判定**:多数 streak 产品要求**当日达到每日目标**才算「保住连胜」(没设每日目标时退化为「当日有净增字数即算」)。
- **展示**:当前连胜 + 历史最长连胜(personal best)并列,是核心荣誉位。

→ **scribe3 取舍**:`current_streak`(到今天为止连续达标天数)+ `longest_streak`(历史最长)。达标 = 设了每日目标则「当日净增 ≥ 每日目标」,否则「当日净增 > 0」。清零按**自然日**(本机时区,与后端 `time.strftime("%Y-%m-%d")` 一致,见 `app.py:64`)。

### 2.4 码字日历 / 热力图:GitHub 风格打卡格

- **橙瓜码字**:多维度统计**每日码字数、码字日历、总字数**,字数/时间/速度矩形图;另有**稿费预测**(按签约字数单价精算,作连载动力)、**拼字比赛**(社交化码字)、随机取名、敏感词检查。([橙瓜网](https://mz.chenggua.com/)、[知乎揭秘](https://zhuanlan.zhihu.com/p/71715822))
- **GitHub 式热力图(habit tracker 通用)**:按日色块,颜色深浅 = 当日产出量;一眼看出连续性与「哪天滑坡」。([HabitBox](https://habitbox.app/blog/daily-habit-tracker-app))

→ **scribe3 取舍**:GitHub 风格**码字热力图**(近 ~12 周 / 一年,色阶按当日字数分 5 档:0 / <0.5× / <1× / 1× / >1× 每日目标)。稿费看板列为**完整期可选**(仅当产品定位含网文连载)。

### 2.5 趋势 / 最高产分析:30/90/全部 + 星期几

- **WordFokus Stats Bar / Trends**:Stats Bar 实时显**字数 / 本次会话时长 / 目标进度**;Trends tab 看 **30 天 / 90 天 / 全部**的字数趋势,并**找出一周中最高产的星期几**(most productive day of week)+ 跨月跨年的写作一致性。([WordFokus 用户指南](https://www.wordfokus.com/user-guide))

→ **scribe3 取舍**:进阶/完整期——`/progress?window=30|90|all` 返回区间趋势;`weekday_histogram`(周一到周日各自平均字数)给「你周X最高产」。

## 3 · 设计

### 3.1 数据层:日进度记录(两方案权衡)

核心问题:「日字数 / 连胜 / 趋势」需要 per-day 写作记录,而现状没有(§1.2)。两条路线:

#### 方案 A(推荐)— 新建 `daily_progress` 日聚合表,save 时增量记账

每次 `save_chapter` 落库时,计算**本次字数 delta** = 新全书字数 − 上次全书字数(用 `chapter.qc_word_count` 缓存,O(1) 聚合),把 delta 累加进**今天**这一行。一书一 DB,故不含 `work` 字段(与 `chapter_version` 同例,见 `032_chapter_version.surql:2`)。

```surql
-- migrations/043_daily_progress.surql · 每日码字账(进度统计/连胜/趋势的真源)
-- 一书一 DB,不含 work 字段;date 为自然日字符串 'YYYY-MM-DD'(本机时区,与 app.py 日预算同口径)。
DEFINE TABLE  IF NOT EXISTS daily_progress SCHEMAFULL;
DEFINE FIELD  IF NOT EXISTS date            ON daily_progress TYPE string;          -- 'YYYY-MM-DD'
DEFINE FIELD  IF NOT EXISTS words_written   ON daily_progress TYPE int DEFAULT 0;   -- 当日净增字数(可负:删多于增)
DEFINE FIELD  IF NOT EXISTS words_total     ON daily_progress TYPE int DEFAULT 0;   -- 当日收盘时全书总字数快照(画累计曲线用)
DEFINE FIELD  IF NOT EXISTS chapters_touched ON daily_progress TYPE array DEFAULT []; -- 当日动过的章 seq 去重集
DEFINE FIELD  IF NOT EXISTS save_count      ON daily_progress TYPE int DEFAULT 0;   -- 当日落库次数(粗活跃度)
DEFINE FIELD  IF NOT EXISTS updated_at      ON daily_progress TYPE datetime DEFAULT time::now();
-- 一天一行:record id = daily_progress:'2026-06-28',天然唯一,UPSERT 即累加。
```

**记账时机与算法**(落在 `save_chapter` 单一落库点,见 §3.2):
1. 读上次记账时缓存的「全书总字数」`prev_total`(存 `meta:words` 单例,或直接 `stats().word_count` 重算——后者更省心,O(章数) 聚合,可接受)。
2. `new_total = stats().word_count`(本次 UPSERT 已落库后)。
3. `delta = new_total - prev_total`。
4. `UPSERT daily_progress:<today>` → `words_written += delta`、`words_total = new_total`、`chapters_touched += [seq]`(去重)、`save_count += 1`、`updated_at = now()`。

> **delta 口径细节**:用「全书总字数差」而非「本章字数差」,天然处理跨章移动文字、删章等;代价是每次 save 多一次 `stats()` 聚合(O(章数),SurrealDB `math::sum` 单查,廉价)。负 delta 合法(当天删字多于写字),streak 达标判定用「净增 > 0 或 ≥ 每日目标」即可正确处理。

**优点**:① 主源单一、读取廉价(画曲线/算 streak 都是直查 `daily_progress`,无需扫全文);② 与 `chapter_version` 解耦(打不打存档点都记账);③ schema 干净,迁移幂等。
**缺点**:① 新增一张表 + 一个记账落点(本篇唯一新表,可接受);② **历史回填**:此前已有章节没有日账——需一次性迁移把存量算成「首日」或按 `chapter_version.created_at` 粗回填(见下「迁移草案」)。

#### 方案 B — 不建表,从 `chapter_version.created_at` + 字数 diff 纯派生

`/progress` 时拉所有 `chapter_version`(`created_at` + `prose`),按日分桶,同章相邻版本算字数差求和得「日 delta」。

**优点**:零新表、零写路径改动。
**缺点(致命)**:① 日常 `save-chapter` **不产生 version**(`store.py:777` vs `:788` 是两条独立路径),只有手动「存档/存为正文」才有——**绝大多数码字日没有数据点,日字数/连胜全是空洞**;② 每次 `/progress` 要把所有 version 全文拉出来算 diff,**昂贵且随稿增长劣化**;③ 同章多版本、跨章去重逻辑复杂易错。→ **不足以支撑核心激励机制**,仅适合做方案 A 缺位时的兜底回填源。

#### 结论与推荐

**采用方案 A**(`daily_progress` 表 + save 增量记账)作为主源;**借方案 B 思路做一次性历史回填**(迁移时把 `chapter_version` 按 `created_at` 日期、字数 diff 粗算进 `daily_progress`,没有 version 的存量章统一记到「书首条已知日期」或当天)。回填是 best-effort,失败不阻断(历史精度不是核心,从今往后精确才是)。

#### 目标存哪:加在 `intent` 表(per-work 单例)

目标是 per-work 配置,`intent:main` 已是单例(`store.py:854`),直接扩字段最省:

```surql

DEFINE FIELD IF NOT EXISTS total_word_goal ON intent TYPE option<int>;  -- 整稿目标;NONE → 前端回退默认 100000
```

### 3.2 后端

#### (a) `save_chapter` 增量记账(`store.py:777`)

在唯一落库点 `save_chapter` 末尾,加一步日账更新——**仍走 `_execute_write`**(开发标准不变量1:改世界状态只经单一落库点):

```python
def save_chapter(self, seq, prose, title="", focalizer=None):
    ...                                   # 既有:embed + qc_word_count UPSERT chapter(已落库)
    self._record_daily_progress(seq)      # 新增:记今日 delta(读 stats 重算总字数)

def _record_daily_progress(self, seq: int) -> None:
    """把本次 save 的净增字数累加进今日 daily_progress 行(经 _execute_write 单点)。
    delta = 本次落库后全书总字数 - 该书最后一次记账的 words_total。"""
    import time
    today = time.strftime("%Y-%m-%d")
    new_total = self.stats().get("word_count", 0)
    rows = self._query(
        "SELECT words_total FROM daily_progress ORDER BY date DESC LIMIT 1")
    prev_total = rows[0]["words_total"] if rows else 0
    delta = new_total - prev_total
    self._execute_write(
        "UPSERT type::record('daily_progress', $d) SET "
        "date=$d, words_written = (words_written OR 0) + $delta, "
        "words_total=$total, save_count=(save_count OR 0)+1, "
        "chapters_touched = array::distinct((chapters_touched OR []) + [$seq]), "
        "updated_at=time::now()",
        {"d": today, "delta": delta, "total": new_total, "seq": seq})
```

> 注意:`_record_daily_progress` 内**不能再开 `transaction()`**——`save_chapter` 可能已在事务上下文里;直接经 `_execute_write` 即正确收集(见 `store.py:197` transaction 收集机制)。记账失败应 **fail-soft**(try/except 包裹,只记日志,不阻断存稿——存稿是命门,统计是锦上添花)。

#### (b) `store.progress()` 读聚合(纯计算,可单测)

```python
def progress(self, today: str | None = None) -> dict:
    """日字数序列 + 累计曲线 + streak + 目标完成度 + 趋势。读 daily_progress + intent,纯聚合。"""
    import time
    today = today or time.strftime("%Y-%m-%d")
    rows = self._query(
        "SELECT date, words_written, words_total FROM daily_progress ORDER BY date")
    intent = self.get_intent()
    total_goal = intent.get("total_word_goal")
    daily_goal = intent.get("daily_word_goal")
    total_words = self.stats().get("word_count", 0)
    cur, longest = _compute_streaks(rows, today, daily_goal)   # 纯函数,见下
    return {
        "today": today,
        "total_words": total_words,
        "total_word_goal": total_goal,           # None → 前端回退 100000
        "daily_word_goal": daily_goal,           # None → 不显每日目标环
        "today_words": next((r["words_written"] for r in rows if r["date"] == today), 0),
        "daily": [{"date": r["date"], "words": r["words_written"],
                   "cumulative": r["words_total"]} for r in rows],
        "current_streak": cur,
        "longest_streak": longest,
        "heatmap": [{"date": r["date"], "words": r["words_written"]} for r in rows],
    }
```

`_compute_streaks(rows, today, daily_goal)` 是**纯函数**(便于 TDD):
- 达标日集合 `met = { r.date | r.words_written ≥ (daily_goal or 1) }`(没设每日目标时阈值=1,即「当日净增>0」)。
- `current_streak`:从 `today`(或 `today`−1,容忍今天还没写)往回数连续达标天数,遇缺口停。
- `longest_streak`:扫 `met` 的最长连续自然日段。
- 自然日相邻判定用 `datetime.date.fromisoformat` + `timedelta(days=1)`。

## 5 · 验收标准

1. **记账正确**:连续两天各存一章(模拟跨日,可注入 `today`),`/progress` 的 `daily` 两条记录字数 = 各日实际净增;`total_words` = `stats().word_count`。
2. **口径一致**:`/progress.total_words` ≡ `/quality.total_words` ≡ `stats().word_count` ≡ 书卡 `word_count`(同一去空白字符数口径,零漂移)。
3. **streak 正确**:连续达标 N 天 → `current_streak=N`;断一天 → 清零重数;`longest_streak` 取历史最长段;设/不设 `daily_word_goal` 两种阈值都对(见 T4 用例)。
4. **目标可编辑**:编辑目标 Modal 改整稿/每日目标 → `PUT /intent` 落库 → 书卡/仪表盘/顶栏进度条**全部按真目标**重算(不再出现硬编码 10 万)。
5. **达标正反馈**:今日跨过每日目标的那次落库触发一次达标 toast + 进度条变绿;`prefers-reduced-motion` 下降级为纯变色无动效。
6. **可视齐全**:InsightView 出现 每日字数柱 + 累计曲线 + 当前/最长连胜 + GitHub 风热力图 + 可编辑目标 + 达标提示(§3.3 草图全部落地)。
7. **fail-soft**:`_record_daily_progress` 抛错时存稿仍成功(统计永不挡写作命门)。
8. **幂等**:`043` 迁移连跑两次不报错;记账同日多次 save 正确累加不重置。
9. 既有测试全绿(`test_store.py`/`test_app.py` 及 store 写不变量守护测试)。
