### U-003 限知章续写时,写作模型手里握着一把能解锁任意秘密的工具(reveal_secret 无机制门)

**来源**:2026-07-14 设定层重构的对抗审查(专攻"secret 能否泄进 prompt")顺藤摸出来的**系统级**问题——不是设定层引入的,是**全系统所有 secret 命题既有的性质**。作者未在使用中撞见,但它正属于作者最在意、且已被咬过的那一类(限知红线 / 知情倒灌;记忆里那次对抗审计 8/8 泄漏)。

**现象(尚未真机复现,是代码事实推出的可达路径)**:限知章续写时,写作模型可以自己调
`s3_hybrid_recall(query="...", reveal_secret=True)`,直接拿到**任意**秘密命题的明文——包括
角色秘密、势力 secret 字段(新的桥接命题)、一切 `proposition.secret=true` 的东西。
`_codex_block` 那套 fail-closed 限知门控(2026-07-14 刚修好)对这条路**完全不设防**。

**根因(已查实)**:
1. `scribe3/mcp.py` 的 `s3_hybrid_recall` 有个 `reveal_secret: bool = False` 参数,**由调用方(即模型自己)决定**。它的 docstring 自己写着:"reveal_secret=True 解锁明文——**仅供主编全知联查**,其输出严禁进入限知章续写 prompt。"
   → 也就是说,这条边界**从设计之初就只靠纪律(提示词)守,没有机制门**。而提示词不是安全边界。
2. `scribe3/app.py` 的 `_work_has_tools()` 恒返回 True → `chat_write` 的 `with_tools=True`
   → **写作路径挂着全套 s3_ 工具**。
3. 本仓的工具面隔离是**按网关 profile** 做的(app.py 里已有 `read_gateway_has_write_tools`
   的审计项)。但实测 `~/.hermes/profiles/scribe3/config.yaml` 与 `.../scribe3_write/config.yaml`
   的 `mcp_servers.scribe3_read.tools.include` **两者都含 `s3_hybrid_recall`**——
   写网关(:8644)同样拿得到这把"能解锁"的工具。
   (同类可疑工具还有 `s3_list_factions` 等一切带 reveal 参数的只读工具,需一并排查。)

**现有的纵深防御(所以这不是敞开的谷仓门,是缺了一道机械锁)**:
- 参数默认 `False`,模型要主动传 `True` 才解锁;
- 系统提示词明写"严禁";
- save-chapter 时有下游泄露检测(`find_leaks` / `_secret_guard_block`)兜底。

**建议修法(顺着本仓既有架构,不新造概念)**:把"能否解锁明文"从**模型的参数**降格为
**网关的能力**——即工具面隔离:
1. `s3_hybrid_recall` 拆成两把工具:恒掩码版(两个网关都给)+ 全知联查版
   (如 `s3_hybrid_recall_reveal`,**只给主编读网关 :8643,写网关不 include**);
   其余带 reveal 参数的只读工具同法处理。
2. profile 配置改 `tools.include` 白名单(可走设置中心的 gateway_files 编辑面)。
3. app.py 的网关审计加一条:**写网关若 include 了任何 reveal-capable 工具 → 报 error**
   (与既有 `read_gateway_has_write_tools` 同一层的门禁,防将来配置漂回去)。

**影响面**:改动 = mcp.py 拆工具 + 两个 profile 的 include 白名单 + 一条网关审计 + 测试。
需要动**真实的 Hermes profile 配置**,故未在设定层重构里擅自执行,留给作者拍板。
不改也能用(有上述三层纵深防御),但限知是本系统的核心价值主张,建议排进下一批。

## 已处理

### U-001 主编上下文红字「Hermes 离线 · 记忆检索不可用」是误报

**现象**:进作品后右栏「主编上下文」检查器常驻红字「Hermes 离线 · 记忆检索不可用」,但主编对话、写作、记忆检索实际全部正常。

**根因(已查实,2026-07-13)**:
- `GET /ai/runtime-status` 对三个网关健康做**与运算**,任一非 `ok` → 顶层 `ok=false`。
- 实测三网关:`scribe3`(:8643)ok、`scribe3_write`(:8644)ok、`default`(:8642)`degraded`——而 default 唯一不合格的检查项是 **disk**(Hermes 自报磁盘 90%),其 `gateway.state=running`、`api_server=connected`、`model=ok`,**功能完全正常**。
- 前端 `scribe3/web/src/context/ContextInspector.jsx:49` 把 `runtime.ok === false` 一律翻译成红字「Hermes 离线」。
- 双重错误:①`degraded`(降级但可用)被等同于 `offline`(不可用);②文案「记忆检索不可用」本身就是错的——记忆检索走 scribe3 后端 + SurrealDB,与 Hermes 磁盘无关。
- 附带疑点:Hermes 报磁盘 90%,但本机 `df -h /` 实测仅 **22%(46G 可用)**——它大概率在测某个容器/沙箱卷或别的挂载点,数字本身不可信。

**建议修法**:
1. 后端 `_hermes_runtime_status`:`ok` 判定从"全 profile 严格 ok"改为"gateway state=running 且 api_server connected 即算在线";把 `degraded` 单列一档(如返回 `degraded: true` + 原因列表)。
2. 前端 ContextInspector:红字「离线」只留给真正连不上的情况;`degraded` 显示黄字(如「Hermes 降级:磁盘紧张」)且不再宣称"记忆检索不可用"。
3. 可选:查清 Hermes 的 disk 检查测的是哪个挂载点,若确属误测,向上游反馈或在配置里关掉该检查项。

**影响面**:纯显示层误导(红字制造"系统坏了"的错觉),不影响任何功能。改动 = 后端 1 处判定 + 前端 1 处映射 + 测试。

**修复**:`hermes_runtime.probe` 的 ok 判据从「health.status=='ok'」改为「gateway 在跑 + api_server 已连即可用」,degraded 单列一档(`degraded` + `degraded_reasons`);前端新增黄字 `hermes_degraded`,并把错误文案「记忆检索不可用」改为「主编对话不可用」。⚠️踩坑:真机 api_server 状态在 `platforms.api_server.state`(既有测试 fixture 是简化的顶层形状),首版修复照抄 fixture 结构导致真机仍误判——靠重启后实测才发现,测试 fixture 已对齐真机结构。**真机验证**:顶层 ok=True,default 标 degraded(reasons=['disk']),红字消失。

### U-002 主编写入的世界规则/势力,设定库里看不到(实时刷新漏表)

**现象**:主编对话里经审批写入了 15 条世界规则 + 6 个势力(每条都点了「已批准」),但设定库里看着还是空的,像是根本没写进去。

**根因(已查实,2026-07-13)**:
- **数据一条没丢**——《印迹》(book_2acba371)库里确实有 15 条 world_rule + 6 条 faction,`/project-tree` 也正确返回它们,浏览器新开页面能完整显示。
- 真凶是 `scribe3/app.py:7246` 的 `_LIVE_TABLES`(SurrealDB LIVE→SSE 的订阅表清单):
  ```
  character, place, proposition, event, knows, reader_knows,
  promise, motif, chapter, material, chapter_scorecard, idea, lesson
  ```
  **漏了 `world_rule`、`faction`、`item`、`term` 四张表**。
- 因果链:主编写库 → 这四张表的变更**不推 live 事件** → 前端项目树(只在「切书」或「收到 live 事件」时重拉,见 `BinderLayout.jsx:74`)保持不动 → 界面还是聊天开始前那份空树 → 看起来像没写进去。
- 用户绕过方式:刷新页面 / 切出去再切回本书,设定就全出来了。

**修法**:`_LIVE_TABLES` 补齐这四张表(前端重拉逻辑对任何 live 事件都重建整棵树,无需改)。

**影响面**:所有经主编/工具写入 world_rule/faction/item/term 的场景都不实时可见,严重误导(让人以为写入失败而反复重写)。

**修复**:`_LIVE_TABLES` 补齐 `faction`/`item`/`term`/`world_rule`;新增门禁测试 `test_live.test_codex_tables_all_in_live_tables`——**设定库树里的每个分类,其表必须在订阅清单里**(防将来再漏)。**真机验证**:界面不刷新,后端写入一条世界规则后计数自动从 16 → 17。
