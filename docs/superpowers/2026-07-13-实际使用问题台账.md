### U-003 限知章续写时,写作模型手里握着一把能解锁任意秘密的工具(reveal_secret 无机制门)

**来源**:2026-07-14 设定层重构的对抗审查(专攻"secret 能否泄进 prompt")顺藤摸出的**系统级**问题——不是设定层引入的,是全系统所有 secret 命题**既有**的性质。作者未在使用中撞见,但它正属于作者最在意、且已被咬过的那一类(限知红线 / 知情倒灌)。

**根因**:`scribe3/mcp.py` 有 6 把只读工具带 `reveal_secret: bool` 参数(semantic/hybrid/graph_recall、list_factions、dramatic_irony、list_entity_relations),`=True` 直接返回秘密命题**明文**。这个参数**由模型自己决定**。每把工具的 docstring 都写着"仅供主编全知联查,其输出严禁进入限知章续写 prompt"——**那是纪律,不是机制**;而 `app._work_has_tools()` 恒 True,写作路径挂着全套工具。

**⚠️ 实测推翻的第一版方案(重要架构事实,别再走回头路)**:原以为能"按网关隔离"——把解锁工具只挂主编读网关。**两条实测证伪**:
1. **主编联查和限知章续写走的是同一个网关 :8643**(`_stream_write` → `hermes_responses_events` → `HERMES_RESPONSES`)。:8644 是 Runs/审批用的,不是写作用的。
2. **Hermes 的 `server_label` 不是选择器。** `hermes_runtime.responses_events` 里 `body["tools"] = [{"type":"mcp","server_label": X}]` —— 真机实测:网关把 `platform_toolsets.api_server` 里**所有** MCP server 的工具**一律**暴露给每个请求,`server_label` 只是个标签,**不做过滤**。加了 `scribe3_chief` server 后,`server_label="scribe3_read"` 的请求照样调到了 `mcp__scribe3_chief__s3_list_factions_reveal`。**配置已回滚。**

**实际修法(fail-safe by construction,不靠"选对 label")**:把"能否解锁"从**模型的参数**降格为**工具的名字**——
1. 6 把工具**去掉 `reveal_secret` 参数**改为恒掩码;明文能力搬进 6 把孪生工具 `s3_*_reveal`。
2. 孪生工具**不写进任何网关 profile 的 `tools.include` 白名单** → 在任何网关的工具面里**物理不存在**。真机实测:模型回 `NO_SUCH_TOOL`,零工具调用事件。
   (要启用它们,须另起一个**绝不服务写作**的专用网关——因为 server_label 不过滤,挂在 :8643 就等于交给写作路径。)
3. 网关自检加门禁 `gateway_exposes_reveal_tools`:任何 profile 的任何 mcp server 的 include 里出现 `*_reveal` → 报 error。防配置漂回去。

**连带修正(三档可见性)**:解锁工具下架后,主编在**作者对话**里也看不见秘密了——而 `secret_agenda` 的定义恰恰是"仅主编可见"。说明此前用 `in_prompt=False` 关掉它是太钝的做法。改为三档:

| 档 | 作者对话(`for_generation=False`)| 限知续写/生成(`for_generation=True`)|
|---|---|---|
| 公开字段 | ✅ 注入 | ✅ 注入 |
| 限知字段(作者勾了 `{key}_secret`)| ✅ 注入(**作者自己的秘密,他当然看得见**)| 仅当能**正证**焦点者知情(fid ∈ known_ids)|
| 主编独知(`chief_only`:secret_agenda / entity_relation.truth)| ✅ 注入 | ❌ **永不**,即便有 knows 边 |

`_editor_write_system` 是唯一的生成入口,恒传 `for_generation=True`;`chat_stream`/`chat_agentic_stream` 吃默认 False。

**过程中撞出的第三处泄露(已修)**:`_editor_system` 里还有一条独立于 `_codex_block` 的 **M6 全知 facts 转储**(focalizer 为空时的正常写法),它对 `for_generation` 一无所知,会把命题桥的镜像以裸格式 `- faction:X · secret_agenda:明文(私密/伏线)` 二次泄露,绕过三档门控。修法:在 **Fact 层**(渲染之前)按结构判据过滤(`entity_id` 以 `faction:` 开头 + `attribute ∈ secret_capable_keys`,与命题桥创建时的谓词同源),而非事后正则渲染出的字符串——因为 lines 有两个来源(fallback 走 `app._line`、门控态走 `brief._fact_inject_line`),赌两个格式永远一致赌不起。两条分支各有测试钉死。

> 仓库教训再次应验:**每新开一个注入点都泄露过一次。** 新增任何 prompt 注入点前,先问它是不是"生成落进读者看到的正文"——是则必须显式传 `for_generation=True`。

### U-004 主编从来就没法通过 MCP 列出势力/世界规则/物件/术语(RecordID 序列化崩溃)

**来源**:2026-07-15 做 U-003 真机工具面探针时**顺带撞出**的既有 bug,不是新引入的。

**现象**:`s3_list_factions` / `s3_list_world_rules` / `s3_list_items` / `s3_list_terms` 四把工具**每次调用都失败**:
```
Error executing tool s3_list_factions: Unable to serialize unknown type:
<class 'surrealdb.data.types.record_id.RecordID'>
```

**根因**:这些 store 方法是 `SELECT * FROM <表>`,每行都带 `id`,类型是 SurrealDB 的 `RecordID`。FastMCP 用 pydantic **严格**序列化 → 直接抛异常,整个工具调用失败。REST 侧同样返回这些行却不崩,只因为 FastAPI 的 `jsonable_encoder` 会兜底(把 RecordID 拆成 dict)——**这层兜底恰好掩盖了洞**,所以一直没被发现。

**为什么一直没人发现**:更大的问题(设定压根不进 prompt,`_codex_block` 只注入 `name+ideology[:18]`)盖住了它——主编本来就"看不见"设定,没人去追究它为什么列不出来。

**修法**:MCP 边界加 `_jsonable()`(递归把 RecordID/datetime 等 SurrealDB 原生类型转字符串),套在 5 个受害返回点上(含 CX-Task 5 新加的 `s3_list_entity_relations`——它同样 `SELECT *`,只是当时表里没数据所以没暴露)。**不改 store/REST**:store 的返回值被 REST、prompt 组装、检测器等一堆地方消费,改那里会波及全系统。

**真机验证**(生产库,只读):6 势力 / 15 世界规则 / 8 物件 / 8 术语全部可序列化,`id` 现在是字符串;掩码仍生效(`artifact_operation` 仍返回 `🔒 私密`)。

### U-001 主编上下文红字「Hermes 离线 · 记忆检索不可用」是误报

**现象**:进作品后右栏「主编上下文」检查器常驻红字「Hermes 离线 · 记忆检索不可用」,但主编对话、写作、记忆检索实际全部正常。

**根因(已查实,2026-07-13)**:
- `GET /ai/runtime-status` 对三个网关健康做**与运算**,任一非 `ok` → 顶层 `ok=false`。
- 实测三网关:`scribe3`(:8643)ok、`scribe3_write`(:8644)ok、`default`(:8642)`degraded`——而 default 唯一不合格的检查项是 **disk**(Hermes 自报磁盘 90%),其 `gateway.state=running`、`api_server=connected`、`model=ok`,**功能完全正常**。
- 前端 `scribe3/web/src/context/ContextInspector.jsx:49` 把 `runtime.ok === false` 一律翻译成红字「Hermes 离线」。
- 双重错误:①`degraded`(降级但可用)被等同于 `offline`(不可用);②文案「记忆检索不可用」本身就是错的——记忆检索走 scribe3 后端 + SurrealDB,与 Hermes 磁盘无关。
- 附带疑点:Hermes 报磁盘 90%,但本机 `df -h /` 实测仅 **22%(46G 可用)**——它大概率在测某个容器/沙箱卷或别的挂载点,数字本身不可信。

**建议修法**:
1. 后端 `_hermes_runtime_status`:`ok` 判定从"全 profile 严格 ok"改为"gateway state=running 且 api_server connected 即算在线";把 `degraded` 单列一档(如返回 `degraded: true` + 原因列表)。
2. 前端 ContextInspector:红字「离线」只留给真正连不上的情况;`degraded` 显示黄字(如「Hermes 降级:磁盘紧张」)且不再宣称"记忆检索不可用"。
3. 可选:查清 Hermes 的 disk 检查测的是哪个挂载点,若确属误测,向上游反馈或在配置里关掉该检查项。

**影响面**:纯显示层误导(红字制造"系统坏了"的错觉),不影响任何功能。改动 = 后端 1 处判定 + 前端 1 处映射 + 测试。

**修复**:`hermes_runtime.probe` 的 ok 判据从「health.status=='ok'」改为「gateway 在跑 + api_server 已连即可用」,degraded 单列一档(`degraded` + `degraded_reasons`);前端新增黄字 `hermes_degraded`,并把错误文案「记忆检索不可用」改为「主编对话不可用」。⚠️踩坑:真机 api_server 状态在 `platforms.api_server.state`(既有测试 fixture 是简化的顶层形状),首版修复照抄 fixture 结构导致真机仍误判——靠重启后实测才发现,测试 fixture 已对齐真机结构。**真机验证**:顶层 ok=True,default 标 degraded(reasons=['disk']),红字消失。

### U-002 主编写入的世界规则/势力,设定库里看不到(实时刷新漏表)

**现象**:主编对话里经审批写入了 15 条世界规则 + 6 个势力(每条都点了「已批准」),但设定库里看着还是空的,像是根本没写进去。

**根因(已查实,2026-07-13)**:
- **数据一条没丢**——《印迹》(book_2acba371)库里确实有 15 条 world_rule + 6 条 faction,`/project-tree` 也正确返回它们,浏览器新开页面能完整显示。
- 真凶是 `scribe3/app.py:7246` 的 `_LIVE_TABLES`(SurrealDB LIVE→SSE 的订阅表清单):
  ```
  character, place, proposition, event, knows, reader_knows,
  promise, motif, chapter, material, chapter_scorecard, idea, lesson
  ```
  **漏了 `world_rule`、`faction`、`item`、`term` 四张表**。
- 因果链:主编写库 → 这四张表的变更**不推 live 事件** → 前端项目树(只在「切书」或「收到 live 事件」时重拉,见 `BinderLayout.jsx:74`)保持不动 → 界面还是聊天开始前那份空树 → 看起来像没写进去。
- 用户绕过方式:刷新页面 / 切出去再切回本书,设定就全出来了。

**修法**:`_LIVE_TABLES` 补齐这四张表(前端重拉逻辑对任何 live 事件都重建整棵树,无需改)。

**影响面**:所有经主编/工具写入 world_rule/faction/item/term 的场景都不实时可见,严重误导(让人以为写入失败而反复重写)。

**修复**:`_LIVE_TABLES` 补齐 `faction`/`item`/`term`/`world_rule`;新增门禁测试 `test_live.test_codex_tables_all_in_live_tables`——**设定库树里的每个分类,其表必须在订阅清单里**(防将来再漏)。**真机验证**:界面不刷新,后端写入一条世界规则后计数自动从 16 → 17。
