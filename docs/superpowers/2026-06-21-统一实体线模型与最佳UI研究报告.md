# 统一实体「线」模型 + 最佳 UI — 研究报告

> 2026-06-21 · 命题:把角色/设定/地点/母题/伏笔等**所有故事元素统一建模为「贯穿章节的线(throughline/thread)」**——引入→发展/复现→使用/兑现,每节点带逐章引导,写每章时注入。
> 结论先行:**这个统一是对的,且有 craft 与业界双重背书。** UI 最佳呈现 = **泳道/地铁图(swimlane)**。

---

## 0. 核心结论
1. **所有故事元素本质都是「throughline(贯穿线)」**——各自有开头/中段/结尾(=引入→发展→兑现)。这是叙事 craft 的公认框架,不是我们的发明。
2. **角色弧光、母题复现、伏笔 setup-payoff、支线,都是这条线的不同实例**,只是"发展型/约束型"权重不同。
3. **最佳 UI 是泳道图**:每条线一条 track,横轴章节,节点标在线上;Aeon Timeline 的「Subway View」是成熟先例。我们现有的**伏笔时间线就是它的雏形**——把它泛化到所有实体即可。

---

## 1. Craft 依据:万物皆「线」

### 1.1 Throughline = 统一框架(关键)
- **"Throughline 是任何拥有自己开头/中段/结尾的故事元素"**;每个角色的成长都有自己的 throughline;主题、支线亦然。([Storymind](https://storymind.com/blog/creative-writing/throughlines-and-how-to-use-them/))
- **故事 = 多条 throughline 像织锦层叠**;**把它们分开,就容易看出哪条断了/有缺口**——单线叙事的危险正是"一条强线掩盖其他线的缺失"。([Storymind](https://www.storymind.com/content/40.htm))
- → 直接支撑:每个实体一条线 + **缺口检测**(悬空/超期/久未复现),正是伏笔引擎已做的,应推广到所有线。

### 1.2 角色弧光 = 被追踪的线(Weiland「Truth Chart」)
- want(基于 lie)→ need(truth);wound/ghost = lie 的起源。**与我们角色字段完全对应。**([HWBA: Want vs Need](https://www.helpingwritersbecomeauthors.com/your-characters-inner-conflict-want-vs-want/) · [Wound](https://www.helpingwritersbecomeauthors.com/brainstorming-wound/))
- **逐章可数的进展节点**:破绽呈现 ×5-7、质疑破绽 ×3-5、尝试改变 ×3-5、倒退 ×2-3、最终蜕变 ×1-2。([HWBA Truth Chart](https://www.helpingwritersbecomeauthors.com/figure-out-your-characters-arc/))
- 弧光节点序:压comfort zone→推出→镜子(自觉)→暴露→直面→把真相付诸行动→赎偿。
- → 角色 = 线 + 节点(beats),**和伏笔的 plant→reinforce→payoff 同构**。

### 1.3 伏笔/承诺 = 线的一个特例
- Promise→Progress→Payoff(Sanderson)、setup+payoff(≥2 铺垫、三次法则,Weiland)、契诃夫之枪、戏剧反讽——都是"引入→强化→兑现 + 想要的效果"。**已在本系统实现,正是统一线的原型。**

**小结**:craft 把角色、主题、支线、伏笔统称 throughline;它们共享「引入→发展→兑现 + 缺口检测」。**用户的洞察成立。**

## 2. 业界数据模型:统一 or 分裂?

| 工具 | 怎么建模"实体随章节演变" | 是否统一 |
|---|---|---|
| **Aeon Timeline** | **Story Arcs**:把事件归入不同 arc(剧情/人物/支线线),独立追踪又相对呈现;**Subway/泳道视图**每条 arc 一条 track;可分别看每个角色的时间线;按 arc/标签/关系筛选 | **统一**:剧情线/人物线/支线同为 arc | [Aeon arcs](https://help.timeline.app/article/150-how-to-use-story-arcs) · [Narrative view](https://www.aeontimeline.com/features/narrative-storytelling) |
| **Novelcrafter** | **Progressions**:把某实体的字段绑到时间线某点,随剧情覆盖更新(角色变老、关系变化、世界政治演变) | 实体统一带 Progressions | [Codex](https://www.novelcrafter.com/features/codex) |
| **Plottr** | plotlines/threads 作为时间线泳道,卡片标在线上 | 线即泳道 | [Plottr](https://plottr.com/plot-devices/) |

**业界共识:把"线/arc"当一等公民,实体挂时间线节点;泳道是主呈现。** 没有谁为每种元素做一套割裂 UI。

## 3. 统一架构建议

### 3.1 一个模型(替掉现在割裂的 beats/char_states/material_echoes)
```
实体 Entity = {
  kind:        角色/设定/地点/阵营/物品/母题/伏笔/支线   ← 类型当字段
  identity:    各类型的专属字段(角色:want/need/lie/wound…;力量:cost/limit;母题:隐喻…)
  appearances: 出场章[]            ← 哪里提到(已有 entity_appearances)
  beats[]:    {章, kind(引入/发展/复现/使用/兑现/误导/转折),
               guidance(本章具体怎么处理), effect(想要的效果), done}  ← 统一节点(并 beats+char_states+echoes)
  preset_logic: 该实体的"逐章必守规则"(角色:wound驱动行为;力量:用必付代价;母题:织入;伏笔:回收效果)
  links[]:     关系(已有,喂关系图谱)
}
```
- **发展型**(角色/母题/伏笔/支线):beats 重——完整 引入→发展→兑现 时间线。
- **约束型**(设定/力量/地点/物品):preset_logic 重(一致性/代价),beats 轻(主要是出场+守规矩)。
- **同一套模型,按 kind 调权重**——这正是用户问的"能否共用一套却按类型调权重",答案:能,业界(Aeon arc)就是这么做。

### 3.2 逐章注入(写作引擎)
写第 N 章时,对每条相关线注入它在本章该做的:
```
【本章·各线指令】
· [角色·渡叔] 本章推进弧光:第3次质疑"三不渡"的执念(beat),wound 该隐隐作痛
· [母题·铜炉] 该复现了(上次第28章),自然织入一处"人如炉中铜"
· [力量·三不渡] 若用到,必付代价(破规→左眼又瞎一分)
· [伏笔·过河钱册] 本章回收,效果=戏剧反讽
```
即把现在的"伏笔节点指令"泛化到所有实体。

### 3.3 健康/缺口检测(throughline 的"看断线")
对每条线:悬空(引入没兑现)、超期(久未发展)、久未复现(母题/角色)、红鲱鱼未澄清、密度过高。统一一套校验。

## 4. 最佳 UI:泳道图(Swimlane / Subway)

**一个界面,类型当字段+筛选,每条线一条 track**(Aeon Subway 是成熟范式;我们伏笔时间线即雏形):

```
设定库   [全部][角色][设定][地点][母题][伏笔][支线]  ←类型筛选   [按类型分组▾]  [+新建]
          1    5    10   15   20   25   30  现在▼
渡叔(角色) ●━━━·━━━━━━●━━━━━━━━━·━━━━━━━━━━━★    弧光:质疑→蜕变
铜炉(母题) ●━━·━━━━━·━━━━━━━━·━━━━━━━·━━━━━     复现密度
三不渡(力量)●┄┄┄┄┄┄┄┄┄┄[规则:用必付代价]┄┄┄┄   约束型(线浅,规则重)
过河钱册   ·━━━━━━━━━━━━━━━━━━━━━━━━━━━★         伏笔已回收
         ●引入 ·发展/复现 ★兑现 ┄约束线  | 点节点看/改 guidance
密度条 ▁▂▃▅▅▃▂  顶部健康:X悬空·Y超期·Z母题久未复现
```
- **横轴章节、每实体一条 track**;节点=beats(点开编 guidance/效果)。
- **类型当字段**:筛选条切类型;约束型(设定/力量)线浅、主要显规则徽标。
- **点实体名 → 全页详情**(现有 EntityEditor,按 kind 显字段)。
- **三视图切换**(Aeon 同款):时间线(默认)/ 列表 / 关系图(已有 AtlasView,线可作边)。
- **写作台右栏「本章·各线指令」面板**:把 §3.2 的注入可视化(像现在的"本章在场",但带"本章该做什么")。

### 4.1 "一个界面用类型字段区分"的可用性 + 陷阱
- **可用**:Aeon/Plottr/Novelcrafter 都这么做;减碎、好筛、缺口一眼。
- **陷阱**:别硬把**约束型**(设定/地点/物品)塞进"发展时间线"——它们 beats 少、规则多,泳道里应**线浅、突出规则徽标**,详情突出 preset_logic,否则空荡荡的线反而误导。

---

## 5. 落地路径(复用已有,别重造)
1. **后端**:把 `beats`(伏笔已有)抽成**通用实体节点**,角色 char_states / 母题 material_echoes 并入;每实体加 preset_logic;注入泛化(§3.2)。
2. **前端**:把**伏笔时间线组件泛化成"实体泳道"**(已是 ReactFlow,加多 lane 多类型);设定库左轨 8 标签 → 1 个泳道界面 + 类型筛选;详情复用 EntityEditor。
3. **健康检测**统一(§3.3)。
4. 渐进:先角色+母题并入(发展型,收益大),设定/力量保持"约束型"轻线。
