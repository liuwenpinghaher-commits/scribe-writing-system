# 统合写作台 — 交互优化方案(替代「三阶段」方案)

> 本文取代 `设计文档/统合写作工作台-三阶段设计方案.md`。
> 结论先行:**作者要的"聊天驱动写作 + 偶尔手动编辑 + 选段讨论/改写"循环,WriteLayout 现在已经实现。** 不重做三阶段,而是保护这条循环并修四个毛刺。

## 一、为什么不走原三阶段方案

原方案提出「推演 → 草稿 → 正文」线性硬模态,经与真实代码核对,有四处与**写作craft**和**代码库现状**双重冲突:

1. **倒退回"整章老虎机"**:原方案阶段2核心是"主编生成整章 → 采用覆盖 → 自动存版本",而 `/chat/write` 现已支持 `scope=chapter|selection|append` 三粒度([app.py:730](../../../scribe3/app.py)),且团队上个 commit(c97cd0a)刚得出教训——"问题定位到具体段落,**定向重写(非全章重生成)**"。原方案正好踩回被抛弃的全章重生成。
2. **双 buffer 灾难**:草稿/正文拆 `draftProse`/`finalProse` 两个编辑器违背"写作即重写",且来回切阶段时无法回答"哪个是真稿"。
3. **限知前提搞反**:原方案设"散文只含 [name] 知道的事",但系统默认**作者全知**,仅显式指定才走某焦点者限知([WriteLayout.jsx:85-88](../../../scribe3/web/src/WriteLayout.jsx),[app.py:734](../../../scribe3/app.py))。
4. **静默砍掉演绎工作流 + 工具按阶段 gating**:演绎是本系统最独特的交互(被原方案忽略);按阶段锁工具是人为摩擦。

**真实写作craft和代码库现状指向同一结论:非模态、作者主导、细粒度协作、护栏环境化。** 本方案据此而立。

## 二、设计原则

- **单一手稿面,无阶段**:一份 prose、一个编辑器、始终可编辑。规划/写/校验是流动地做的事,不是要切换的模态。
- **主编一个角色,全程全工具**:复用 `/chat/write` 已有的"自判讨论 vs 动稿"机制,扩展到自判"规划/写/查"并自然调用对应 `s3_*` 工具。不按阶段 gating。
- **作者主导**:主编帮作者写,不是主编提议、作者审批。
- **护栏环境化**:限知泄露/在场/反讽/AI腔在状态条与侧栏安静亮起,绝不弹窗、绝不打断心流。
- **YAGNI**:不做三阶段、不做双 buffer、不做"每次生成存一版"、不做句长/对话次数伪指标。

## 三、骨架:以现有 WriteLayout 聊天循环为基础

## 四、四项改造

### 改造① 修选段替换的定位 bug(正确性)

**现状**:[WriteLayout.jsx:71](../../../scribe3/web/src/WriteLayout.jsx) 接受 `scope=selection` 时用
`prose.replace(lastQuote, p.prose)` —— 纯文本首次匹配。

**问题**:
- 选中文字在本章重复出现 → 替换到**第一个**匹配,可能不是作者选的那处。
- 主编改写期间作者又动了原文,或 `lastQuote` 含已被规范化的空白 → `includes` 失败 → 退化成**追加到章末**([:71](../../../scribe3/web/src/WriteLayout.jsx) 的 else 分支)。

**目标**:基于**选区偏移(start/end offset)**而非文本匹配做替换。

**实现要点**:
- ProseEditor 在触发 `onDiscuss` 时,同时回传选区的 `{from, to}` 字符偏移(TipTap 提供 selection range),WriteLayout 存入 `lastSel = {from, to, text}`。
- 接受 `scope=selection` 时:`next = prose.slice(0, from) + p.prose + prose.slice(to)`。
- 防漂移:若接受时 `prose.slice(from, to) !== lastSel.text`(原文已变),退回到文本匹配并**提示作者"原文已改动,请确认替换位置"**,不静默追加。

**测试**:重复文本、选区跨段落、改写期间编辑原文三种 case。

### 改造② 修演绎崩溃 + 走 /chat/write(止血 + 保留独特能力)

**现状**:`deduceToChief` 入口在([:77](../../../scribe3/web/src/WriteLayout.jsx)),但 DeducePanel「演绎」按钮调 `api.render` —— 该导出已删 → `TypeError`(死代码崩溃)。

**目标**:演绎 = 一次**特殊的 `/chat/write` 调用**,不重建独立 `/render` 端点。

**实现要点**:
- DeducePanel「演绎第N章」改调 `api.chatWrite`,带 `focalizer=<该角色>` + 固定指令:
  "以 [角色] 截至第N章的**限知体验**,写这一场的演绎草稿(只含该角色所知所感)。"
- 主编在该调用里走限知(系统已支持:显式指定 focalizer 时叙事贴该视角,[app.py:734-735](../../../scribe3/app.py)),返回演绎草稿。
- 草稿经「给主编」→ `deduceToChief` 现有逻辑(以作者视角织进本章正文)不变。
- 删 `api.render` 残留引用;DeducePanel 的 `onToChief` 链路保留。

**测试**:演绎按钮不再崩;演绎草稿→给主编→织入正文全链路通。

### 改造③ 护栏改实时轻提示(环境化)

**现状**:穿帮(leaks)只在保存后由 `saveChapter` 返回更新([:63](../../../scribe3/web/src/WriteLayout.jsx)),写时不可见;QC 同理需手动。

**目标**:护栏=**被动、非阻断、可忽略的一致性警示**(分析信息,不是续写内容),在**底部状态条/侧栏安静呈现**,点开看详情;绝不弹窗、绝不插入正文。

> **证据约束(见第八节 Q3)**:文献关于"打断构思/反应式写作/默认效应"的强警告**全部针对自动内联推送的内容生成**;被动一致性提示是否同样诱发反应式写作**尚无直接证据**(开放风险)。据此规避到最安全一侧:**护栏无动效、无声、不在打字时跳动,只在作者停笔较久才静默刷新,且可一键关闭(opt-in)**。

**护栏分层**:
| 信号 | 数据源 | 触发 |
|---|---|---|
| 🔒 限知泄露 | `find_leaks(prose, focalizer, chapter)` — 仅当视角=某角色时激活 | 停笔静默刷新 |
| 👥 在场 | 比对本章事件 `involves` 的在场角色 vs prose 提及 | 停笔静默刷新 |
| 🎭 反讽机会 | `dramatic_irony(focalizer, chapter)` — 正向提示(可利用) | 切章/切视角时拉取 |
| AI腔/复读 | 复用 `qc_chapter` 的 `repetition`/`purple` | 停笔静默刷新 |
| discipline(双高潮/exposition dump) | `discipline_check` — 慢,**仍手动按需** | 手动 |

**实现要点**:
- 触发用**停笔判定**(空闲 ~3s 无输入才跑,而非 1.5s 边写边亮),避免在心流中跳动;若作者持续打字,检查一直**推迟**。
- 呈现**无动效、无声**:徽章状态变化用静默替换,不闪烁/不滑入;数字只在作者**视线主动落到状态条**时才有意义。
- **可一键关闭**:护栏总开关 opt-in;关闭后完全静默,只保留"存为正文"时的最终审计。
- 作者视角=全知时,🔒/🎭 自动隐藏(无限知约束)。
- 性能:检查在后台,不阻塞输入;若某检查 >2s 未返回,本轮跳过,下次再试。
- 复用现有端点(`/leaks` 经 `find_leaks`、`/qc`),必要时加一个合并轻端点减少往返(可选,先用现有端点验证)。

### 改造④ 存档点替换老虎机版本(去噪)

**现状**:无 `chapter_version` 表;chapter UPSERT 覆盖。原方案要"每次采用主编草稿自动存一版"。

**目标**:版本 = **作者命名的里程碑**,不是生成日志。

**机制**:
- **防崩自动存**:localStorage(ProseEditor 已有)+ 后端轻量自动存(防丢,不进版本表)。
- **存档点(作者主动)**:顶部「存档点」按钮 → 可选填一句摘要("重写结尾前")→ 写入 `chapter_version`。
- **接受 proposal 不自动建版本**(连续编辑,非里程碑)。
- **「存为正文」** = 末次存档 + 触发 `ingest` 回写(显式,作者决定何时入知识库)。
- 版本历史(左面板 💾 tab):作者命名节点 + 时间 +(该刻顺手跑的)QC 快照;**去掉句长/对话次数伪指标**。回看 = 只读 Modal + 「恢复到此版本」。

### 改造⑤ 选段改写升为"多候选 + 可复用按钮"(一等交互)

**依据(见第八节 Q2/Q4)**:Dang et al.(CHI 2023,N=129)证作者**偏好从多个建议中挑**而非单一采用/拒绝;ABScribe(CHI 2024)证**就地变体 + 悬停对比**优于序列粘贴,且"prompt 自动转可复用按钮"获 9/12 作家点赞。这同时命中 Q4 的核心机制——**作者努力/方向(挑选、调指令)提升心理所有权**。

**目标**:把"选段改写"从"主编回一段→采用/拒绝",升为"主编默认回 **2-3 个并排候选**→作者挑/再调",并支持把常用改写指令**存成一键按钮**。

**实现要点**:
- 选段改写时,`/chat/write` 指令追加"给出 2-3 个风格/侧重不同的候选";主编在 `⟦PROPOSAL⟧` 内回多段(或多次 proposal)。
- DraftCard 升级为**多候选并排卡**:每个候选可单独「采用此版」(走改造①的偏移替换)/「以此为基础再改」。仅在 `scope=selection` 默认多候选;`chapter`/`append` 仍单候选(整章多候选成本过高)。
- **可复用按钮**:作者可把一条改写指令(如"压缩、去形容词""加潜台词")存为快捷按钮,选中文字后一键套用。按钮存在前端本地(localStorage,按 work 隔离),不需后端。
- 这是 ④ 之外**唯一新增的"功能"**;其余四项均为修复/重组。**遵循 YAGNI:整章不做多候选,按钮不做云同步。**

**测试**:选段改写默认出多候选;采用任一候选正确落位(复用改造①测试);可复用按钮套用后进入正常改写流。

**后端(迁移 032)**:
```sql
DEFINE TABLE chapter_version SCHEMAFULL;
DEFINE FIELD work       ON chapter_version TYPE string;
DEFINE FIELD seq        ON chapter_version TYPE int;
DEFINE FIELD prose      ON chapter_version TYPE string;
DEFINE FIELD label      ON chapter_version TYPE string;     -- 作者命名摘要(可空)
DEFINE FIELD kind       ON chapter_version TYPE string;     -- 'checkpoint' | 'final'
DEFINE FIELD qc         ON chapter_version TYPE option<object>;  -- 存档那刻的 QC 快照
DEFINE FIELD created_at ON chapter_version TYPE datetime DEFAULT time::now();
DEFINE INDEX cv_work_seq ON chapter_version COLUMNS work, seq;
```

**新端点**:
- `POST /checkpoint?seq=N` — body `{label}` → 写 `chapter_version(kind='checkpoint')`,顺跑 QC 存快照。
- `GET /chapter-versions?seq=N` — 列表。
- `GET /chapter-version/:id` — 单版本全文(回看)。
- `save-chapter` 维持现状(不每次进版本表);「存为正文」额外写 `kind='final'`。

## 七、验证

1. **核心循环回归**:聊天生成整章→接受;手动编辑;选段改写(含重复文本/跨段/改写期间编辑原文三 case);全部正确落位。
2. **演绎链路**:演绎按钮不崩 → 演绎草稿 → 给主编 → 织入正文。
3. **护栏被动性**:限知视角下写出泄露词 → 停笔 ~3s 后状态条静默亮 🔒(打字中不跳动);作者全知视角下 🔒 隐藏;总开关关闭后完全静默。
4. **选段多候选**:选段改写默认出 2-3 候选;采用任一候选正确落位;可复用按钮套用后进入正常改写流。
5. **存档点**:点存档点→进版本表;接受 proposal 不进版本表;回看与恢复可用;「存为正文」触发 ingest。
6. **后端测试全绿**(当前基线 234 tests)。

## 八、证据基础与边界(deep-research 裁决,2026-06-27)

经 104-agent 多源对抗核查(每条 claim 三票、需 2/3 反驳才推翻)。**spec 骨架方向证据支持充分,无需推翻**;以下为逐条裁决与边界。

| 假设 | 裁决 | 关键来源 |
|---|---|---|
| **Q1** 非模态单一手稿面 > 线性阶段模态 | ✅ 成立(设计推论) | Flower & Hayes 1981 认知过程论;创意作家质性研究([arxiv 2411.03137](https://arxiv.org/html/2411.03137v1)) |
| **Q2** 选段定向重写 > 整章重生成 | ✅ 成立 | ABScribe CHI 2024,n=12 职业作家,NASA-TLX d=1.20、修订感 d=2.41([arxiv 2310.00117](https://arxiv.org/abs/2310.00117)) |
| **Q3** 实时轻提示 > 事后审计 | ⚠️ 部分成立(已据此收紧③) | "Reactive Writers" CHI'26;Dang et al. CHI 2023([3580969](https://dl.acm.org/doi/10.1145/3544548.3580969)) |
| **Q4** 作者主导按需协助 > AI提议-采用/拒绝 | ✅✅ 成立(证据最强) | 所有权随AI贡献单调下降([arxiv 2404.03108](https://arxiv.org/abs/2404.03108)、CHI 2024 句级-3.66/段级-5.65 p<0.0001);Analysis Separation 模式 |
| **Q5** 命名里程碑 > 自动版本 | 🟡 部分成立(类比推断) | Scrivener Snapshots 厂商文档;默认效应间接支持;无直接对照实验 |

**关键边界(必须随实现一起记住)**:

1. **Q3 的证据约束**:打断/反应式写作/默认效应的证据**全部针对自动内联内容生成**,不能直接套到"被动一致性提示"。后者是否同样有害**无直接证据**——故改造③ 取最保守设计(停笔刷新、无动效、可关)。
2. **题材外推未证**:几乎所有实验为短篇/段落级、实验室/众包样本;向**长篇小说**(多章一致性/伏笔/弧光)外推**无 RCT**。但核心成本(切换认知代价、努力驱动所有权、被动接受降低能动性)被界定为**人因**,不随模型变强失效。
3. **被对抗核查反驳的 3 条**(不作依据):"AI自动扩写prompt长度增但所有权不升""就地变体 d=1.20 大效应""粒度U型曲线"——均 1-2 被否。
4. **① 与命名里程碑**为设计推论/类比,非直接 UI 实验结论。
