# Scribe3 全系统全维审查 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` for parallel read-only audit rounds, or `superpowers:executing-plans` for inline task-by-task audit. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 按功能域和功能爆炸半径，对 Scribe3 做一轮覆盖业务完善性、逻辑闭环性、架构合理性、UI 交互友好性、数据可信性和工程可维护性的全系统审查，逐个判断“这个功能是否值得存在、是否完整闭环、是否好用、是否正确、是否不会伤害其它功能”。

**Architecture:** 审查按“产品目标 -> 用户旅程 -> 业务对象生命周期 -> 前后端逻辑闭环 -> 架构边界 -> UI 交互体验 -> 工程验证”推进。每个功能域都必须同时审业务角色、使用场景、入口路径、状态流转、数据契约、失败恢复、交互密度、架构归属、测试覆盖、真实浏览器可达性和对其它功能的爆炸半径。第一轮默认只读，不修代码；每轮输出带文件行号的 findings、爆炸半径、评分矩阵、建议修复顺序和验收清单。

**Tech Stack:** React + Vite + Vitest + Playwright/browser sanity check + FastAPI + SurrealDB store + pytest + CodeGraph.

## Global Constraints

- 所有审查先只读收证，不在审查任务中直接修代码。
- 不回退、不整理、不覆盖当前未提交工作区中的无关改动。
- 每条发现必须有证据：文件路径、行号、触发路径、用户可见影响、最小复现方式。
- 本轮不是普通代码审查，也不是“按钮是否存在”的功能验收；审查对象是每个产品能力是否真正服务写作者、是否能闭环、是否能长期维护。
- 每个功能域必须先说明它服务的真实业务目标；没有业务目标的功能按“可删除/合并/降级”审查。
- 每个功能域必须画出闭环：用户触发 -> 系统处理 -> 数据变化 -> 用户反馈 -> 后续动作。闭环断点优先级高于局部 UI 瑕疵。
- 每个功能域必须判断架构归属是否合理：入口放哪里、目录放哪里、详情放哪里、主编/右栏放哪里、后端真相源在哪里。
- 每个功能域必须评价 UI 是否好用：信息密度、控件位置、空态、错误态、视觉层级、响应式、键鼠操作、是否符合用户心智。
- 任何 UI 功能不能只看源码，必须补真实浏览器走查或说明无法走查的原因。
- 任何后端功能不能只看端点存在，必须追到 store/LLM/ingest/测试至少一层消费端。
- “后端已有”不等于“用户可执行”；必须验证入口、状态、按钮、错误反馈和空态。
- 涉及数据修复、删除、迁移、回填的建议必须默认 dry-run，并标出需要用户确认的写操作。
- 每个功能域独立完成后再进入下一个，避免把多域问题混在同一批结论里。
- 审查报告必须区分 P0 数据/安全风险、P1 功能断链、P2 体验/一致性、P3 清债。

## 0.0 全方位审查判定标准

### 什么不算通过

下面情况即使测试通过，也不能算功能通过：

- **只有入口，没有任务闭环。** 例如能点开素材库，但不能完成导入、检索、引用、溯源、写作召回中的关键链路。
- **只有后端能力，没有用户可达路径。** 例如 API、store、prompt 都存在，但真实 UI 没有传参、没有按钮、没有错误反馈。
- **只有组件实现，没有接入真实壳。** 例如 `DirectoryPane`、`EntryRail`、详情组件有测试，但生产 `FourPaneShell` 仍走旧路径。
- **只有成功路径，没有失败恢复。** 例如接口失败被吞、空态和错误态混淆、生成中断后没有重试或状态解释。
- **只有局部 UI 改善，没有信息架构闭环。** 例如把 tab 移到顶栏，但左栏能力丢失、二栏目录缺失、三栏详情和右栏上下文不同步。
- **只有数据写入，没有后续消费。** 例如能新增伏笔或母题，但写作、校验、图谱、仪表盘都不使用它。
- **只有视觉好看，没有真实工作效率。** 例如边框减少了，但常用动作更远、列表更难扫、长章节滚动沉底、宽度不可控。

### 每个功能必须回答的 12 个问题

每个 Wave 报告都必须逐功能回答这些问题，不能只列 bug：

1. **业务目标:** 它服务作者的哪一个真实工作任务？
2. **核心对象:** 它管理的对象是什么，对象生命周期是什么？
3. **入口模型:** 用户从顶栏、左栏、二栏、三栏、右栏哪里进入，入口是否唯一且符合心智？
4. **目录模型:** 二栏展示的是目录、筛选、分类、队列还是结果集？是否会随详情被替换？
5. **详情模型:** 三栏展示的是对象详情、工作台、横切视图还是全画布能力？是否和二栏选中态一致？
6. **右栏协作:** 主编、Pilot、收件箱、选择环等右栏能力何时参与，是否抢占主任务？
7. **数据真相源:** 前端状态、API、store、LLM prompt、ingest 中哪个是权威来源？
8. **状态闭环:** loading、empty、error、degraded、dirty、saved、stale、running 是否都有可理解 UI？
9. **写作回流:** 结果是否能进入正文、设定库、素材召回、校验、图谱、时间线或仪表盘？
10. **失败恢复:** 网络失败、LLM 失败、接口 4xx/5xx、并发切章、空书、长内容时用户如何恢复？
11. **交互效率:** 常用动作是否近、列表是否可扫、信息是否渐进展开、宽度/滚动/响应式是否可用？
12. **爆炸半径:** 修它会影响哪些入口、组件、端点、数据、测试和已有用户习惯？

### 功能成熟度分级

| 等级 | 判定 | 产品含义 |
|---|---|---|
| M0 缺失 | 没有真实入口、真实数据或真实消费 | 不能对用户承诺存在 |
| M1 可见 | 有入口或组件，但闭环缺关键环节 | 容易让用户觉得“功能丢了/点了没用” |
| M2 可用 | 主成功路径成立，但失败态、复用、架构边界有明显缺口 | 可以内测，但需要列入近期修复 |
| M3 闭环 | 成功、失败、沉淀、复用和反馈完整 | 可以作为稳定产品能力 |
| M4 可扩展 | 闭环完整且边界清楚、测试充分、文档一致 | 可以在此基础上继续扩展 |

### 最终总报告结构

最终收尾报告必须按下面结构输出，避免变成零散问题清单：

1. **总判断:** Scribe3 当前是 M0-M4 哪个成熟度，哪些能力已经能承诺，哪些不能。
2. **业务能力地图:** 手稿、设定库、素材库、演绎、伏笔、母题、搜索、校验、图谱、时间线、仪表盘、主编、Pilot、限知等逐项成熟度。
3. **闭环断点地图:** 哪些断点属于入口、目录、详情、右栏、API、store、prompt、ingest、测试。
4. **架构问题地图:** 哪些问题来自组件未接入、职责错位、状态多源、旧壳残留、大文件聚合。
5. **UI/交互问题地图:** 导航、宽度、滚动、空态、错误态、密度、视觉层级、响应式、键盘/鼠标效率。
6. **数据可信性地图:** work 隔离、secret/限知、degraded、静默失败、跨章/跨书污染、删除/归档。
7. **创作质量地图:** 哪些能力真正进入 prompt、召回、校验和写作反馈，哪些只是展示。
8. **P0/P1/P2/P3 Findings:** 每条带证据、影响、建议、验收方式和爆炸半径。
9. **三批修复路线:** 最小止血、产品补全、架构重构，分别说明收益、风险、测试范围。
10. **回归矩阵:** 每个入口类型的浏览器走查、前端测试、后端测试、未覆盖项和原因。

## 0. 审查总方法

### 全维审查不是“功能点打勾”

本计划把每个功能当成一个产品能力，而不是一组文件或按钮。审查者必须从以下问题开始：

1. **这个能力解决什么业务问题？**  
   例如“素材库”不是列表组件，而是作者把外部材料转成可召回、可溯源、可写作注入的参考记忆系统。

2. **这个能力的闭环是什么？**  
   一个功能至少要有“发现/进入 -> 创建/读取 -> 编辑/使用 -> 反馈/校验 -> 沉淀/复用”的闭环。只有入口没有复用，或只有后端没有用户反馈，都算不完整。

3. **这个能力放在当前架构中是否合理？**  
   检查它是不是被塞错栏、重复出现在多个入口、把目录和详情混在一起、把章级能力误放成全书能力、把全局视图伪装成左栏功能。

4. **这个能力是否符合真实写作者的工作流？**  
   不是只看能不能点，而是看是否减少认知负担、是否保留上下文、是否能从失败中恢复、是否能把用户带到下一步。

5. **这个能力是否有可维护的实现边界？**  
   检查前端组件、API、store、LLM prompt、ingest、测试是否各司其职；发现“大文件统管一切”“同一状态多处复制”“后端字段和 UI 文案各说各话”要标架构问题。

### 八个审查维度

每个功能域都按 0-3 分评价。0 是缺失或不可用，1 是部分存在但断链，2 是可用但有明显缺口，3 是完整且可维护。评分不是为了装饰，而是用于排序修复批次。

| 维度 | 审查问题 | 低分信号 | 高分信号 |
|---|---|---|---|
| 业务完善性 | 功能是否覆盖用户真实任务的完整过程 | 有按钮但缺创建/编辑/复用/复盘任一关键环节 | 用户能完成从输入到沉淀的完整任务 |
| 逻辑闭环性 | 状态和动作是否首尾相接 | 请求成功但 UI 不变、数据变了但无反馈、失败被当空态 | 每步都有状态、反馈、下一步 |
| 架构合理性 | 归属、边界、真相源是否清楚 | 入口重复、目录和详情混杂、同一状态多处维护 | 入口/目录/详情/右栏/API/store 边界稳定 |
| 数据可信性 | 数据是否正确、隔离、可追溯 | 错 work、secret 泄露、静默 no-op、脏状态丢失 | 字段语义清楚，错误和降级可见 |
| UI 友好性 | 是否清晰、顺手、符合工作流 | 信息堆叠、窄框、沉底、重复 tab、看不出下一步 | 视觉层级清楚，常用动作近，复杂信息可渐进展开 |
| 创作质量 | 是否真的提升写作质量 | 生成/校验只返回泛泛文本，和当前章/素材/设定无关 | 输出与章、限知、素材、伏笔、母题强相关 |
| 失败恢复 | 出错、空数据、并发、慢请求时是否可恢复 | 无 toast、无 retry、按钮无状态、失败后用户不知道怎么办 | loading/error/empty/degraded 都有明确行为 |
| 工程可维护性 | 测试、模块边界、性能、文档是否支撑长期演进 | 只能手测、文件过大、N+1、文档过时 | 单测/集成/浏览器证据齐全，模块边界清楚 |

### 闭环审查模板

每个功能域报告必须包含这张闭环表。没有完整闭环就不能只写“通过”。

| 环节 | 必须证明的问题 | 证据 |
|---|---|---|
| 目标 | 用户为什么需要它，它在写作流程中解决哪一步 | 用户故事、现有文档、入口文案 |
| 进入 | 用户从哪里找到它，入口是否唯一且符合心智 | 顶栏/左栏/二栏/三栏/右栏/命令面板截图或 DOM |
| 创建/读取 | 它如何获取或产生对象 | API、store、空态、新建态 |
| 使用 | 用户如何把结果用于写作或管理 | 三栏详情、主编、写作注入、跳转 |
| 反馈 | 成功、失败、进行中、降级是否被表达 | toast、按钮状态、degraded 字段、错误边界 |
| 沉淀 | 结果是否进入后续流程，被召回、统计、校验或复用 | ingest、ledger、graph、timeline、material recall |
| 回收 | 删除、归档、撤销、过时数据如何处理 | archive/delete/backfill/dry-run |

### 爆炸半径等级

| 等级 | 定义 | 典型例子 | 审查要求 |
|---|---|---|---|
| R0 全局内核 | 影响所有作品、所有视图或数据真实性 | work 切换、store schema、API base、路由单一真相源 | 先审，必须跑全量测试和浏览器冒烟 |
| R1 主链路 | 影响写作、保存、生成、限知、主编 | `ChapterStudio`、`WriteLayout`、`/chat/write`、`pilot` | 需要源码链路 + 真实浏览器 + pytest/vitest |
| R2 多功能共享面 | 影响多个入口但不直接写稿 | `DetailPane`、`DirectoryPane`、`AppRail`、`MaterialList`、`CodexDetail` | 要列出所有调用方和回归入口 |
| R3 单功能域 | 只影响一个功能岛 | 某个素材导入按钮、某个设定分类表单 | 聚焦测试和局部浏览器复现 |
| R4 展示/体验 | 不改数据但影响可理解性 | 空态、密度、边框、tab 对齐、resize | 浏览器截图或 DOM/console 证据 |

### 每个功能域的固定审查模板

```markdown
## 功能域名称

**用户故事:** 用户从哪里进入，要完成什么动作，完成后应该看到什么。
**爆炸半径:** R0/R1/R2/R3/R4，说明影响范围。
**入口:** 顶栏/左栏/二栏/三栏/右栏/命令面板/后端定时或脚本。
**关键文件:** 前端、API、后端、store、测试、文档。
**数据契约:** 请求字段、响应字段、错误态、degraded/empty/loading 状态。
**业务闭环:** 目标 -> 进入 -> 创建/读取 -> 使用 -> 反馈 -> 沉淀 -> 回收。
**架构归属:** 顶栏/左栏/二栏/三栏/右栏/API/store/LLM/ingest 的职责是否合理。
**交互评价:** 信息密度、视觉层级、常用动作位置、空态/错态/加载态、响应式、键鼠可用性。
**审查步骤:** 业务闭环 -> 架构边界 -> 只读源码 -> 单测 -> 浏览器 -> 日志 -> 评分 -> 结论。
**必须回答:** 是否业务完整、是否逻辑闭环、是否架构合理、是否 UI 友好、是否数据正确、是否有测试、影响谁。
**评分:** 八维评分表，每项 0-3 分，并说明最低分项为什么低。
**发现格式:** `[P级别][爆炸半径][维度] 标题 - 证据 - 影响 - 建议 - 验收方式`。
```

### 基线命令

在每轮审查开始前记录，不要求每个小任务都全量跑。

```bash
cd "<repo-root>"
git status --short

cd "<repo-root>/scribe3/web"
npm test
npm run build

cd "<repo-root>"
pytest -q scribe3/tests
```

如果全量 pytest 太慢，允许先跑功能域相关测试，但最终汇总报告必须写明哪些全量验证没有跑。

### 每个任务的统一深审步骤

每个 Task 除了自身列出的文件和命令，还必须执行下面 9 步。任何 agent 只做源码扫查而不做这些步骤，结论只能算草稿。

- [ ] **Step U1: 写业务定义**

用 3-5 句话说明该能力服务的作者任务、输入是什么、输出是什么、成功状态是什么。

- [ ] **Step U2: 画闭环链路**

按“目标 -> 进入 -> 创建/读取 -> 使用 -> 反馈 -> 沉淀 -> 回收”填表，空白处就是潜在缺口。

- [ ] **Step U3: 标架构归属**

列出顶栏、左栏、二栏、三栏、右栏、API、store、LLM、ingest 中哪些参与该能力，判断是否职责错位或重复。

- [ ] **Step U4: 查用户旅程**

从用户视角走一遍最常用路径和一个失败路径，记录每一步是否知道“我在哪、能做什么、下一步是什么”。

- [ ] **Step U5: 查数据生命周期**

确认对象从创建、读取、编辑、引用、统计、删除/归档的全程是否有真相源和错误处理。

- [ ] **Step U6: 查交互质量**

评价信息密度、控件布局、二级目录、详情宽度、滚动、resize、空态、错误态、加载态、移动/窄屏表现。

- [ ] **Step U7: 查技术契约**

追踪组件 props、API payload、store 字段、LLM prompt、测试断言，找字段语义漂移和前后端断链。

- [ ] **Step U8: 跑验证**

运行该任务列出的测试，并做真实浏览器走查。无法运行时必须写明原因。

- [ ] **Step U9: 打分和排序**

按八个维度打分，最低分项自动进入 findings；多个问题合并到共同根因，不重复报噪音。

## 1. 功能地图与审查顺序

### 产品能力地图

这张表定义“审查完成后必须能回答的业务问题”。如果某个功能通过了技术测试，但这些问题答不上来，仍然不能算审查通过。

| 产品能力 | 业务目标 | 必须闭环的用户流程 | 最容易出问题的维度 |
|---|---|---|---|
| 作品库与 work 隔离 | 让每本书成为独立项目，避免跨书污染 | 选书 -> 进入工作台 -> 切书 -> 回作品库 -> 数据不串 | 数据可信性、架构合理性 |
| 手稿与章工作台 | 支撑作者按卷章推进正文 | 选章 -> 看大纲/节拍 -> 写正文 -> 保存 -> 校验/复盘 -> 进入下一章 | 业务完善性、逻辑闭环性、UI 友好性 |
| 主编与写作对话 | 把 AI 变成当前上下文的创作伙伴 | 选内容/当前章 -> 提问/改写 -> 得到建议 -> 应用/拒绝 -> 记录上下文 | 创作质量、失败恢复、数据可信性 |

## 3. 全维评分和 Findings 分级规则

### 八维总评分

每个功能域总分 24 分。评分不是“平均分好看”，而是用于判断修复策略。

| 总分 | 状态 | 处理方式 |
|---|---|---|
| 21-24 | 成熟能力 | 只保留小修和回归测试 |
| 16-20 | 可用但有缺口 | 按 P1/P2 排队补齐闭环或交互 |
| 10-15 | 半成品能力 | 需要产品级补全，不应只修 bug |
| 0-9 | 架构或业务不成立 | 需要重新设计、合并或下线 |

单项 0 分必须进入 findings；单项 1 分必须说明为什么不立即修。

### P0: 立即阻断

- 数据丢失、错写作品、secret 泄露、破坏性操作无确认、保存状态撒谎。
- 核心业务闭环会造成不可恢复损失，例如写作、保存、限知、作品隔离、删除、回填。
- 用户能通过正常操作触发。
- 需要优先修，修前不应继续依赖该功能。

### P1: 关键功能断链

- 功能存在但用户不可达。
- 按钮点击无请求、请求到后端但 UI 不展示、状态机错误、错误提示吞掉。
- 横切视图锁死导致左栏无法切回。
- 业务闭环关键环节缺失，例如素材能导入但不能召回，校验能发现但不能定位，Pilot 能运行但不能背书。
- 架构归属明显错误并导致用户找不到功能，例如章级能力被放成全局入口，目录和详情互相覆盖。

### P2: 体验和一致性缺陷

- 可用但难理解、信息堆叠、宽度不合理、空态误导、分类命名冲突。
- 有替代路径，但主路径不顺。
- 架构上没有立刻断链，但存在重复入口、重复状态、跨栏职责不清。
- UI 交互增加认知负担，例如常用动作过远、二栏过宽、详情过窄、信息没有渐进层级。

### P3: 清债

- 死代码、过时文档、重复 helper、低风险命名漂移、测试覆盖不足。
- 不应混入 P0/P1 修复批次。
- 业务上可暂不处理，但要记录为什么当前不影响用户主流程。

## 5. 推荐执行策略

### 推荐方案：分 wave 多 agent 只读审查

适用原因：功能域多、相互独立度高，但最终需要统一业务成熟度、爆炸半径和修复批次。每个 agent 只审一个产品能力，必须按同一套“业务闭环 + 架构归属 + 八维评分 + findings”模板输出，主 agent 汇总去重和判级。

执行方式：

1. 先跑 Task A1-A3，建立路由和数据真相源。
2. Wave B、C、D 可并行，但每个 agent 必须使用同一全维审查模板。
3. Wave E 必须在前面功能地图完成后执行。
4. 主 agent 最后做冲突合并：同一根因只保留最高爆炸半径版本，其它作为附属证据。

### 备选方案：单线程逐功能审查

适用原因：如果当前工作区变化太大，或需要边审边修，单线程能减少上下文错位。

代价：耗时更长，但结论一致性更高。

### 不推荐方案：直接全量扫代码列问题

原因：容易得到大量“看起来有问题”的清单，但无法回答用户最关心的“这个能力业务上完整吗、逻辑闭环吗、放得合理吗、好不好用、修它会炸哪里”。

## 6. Self-Review

- **覆盖范围:** 已覆盖全局骨架、写作主链路、设定/素材/知识、工艺能力、横切视图、安全、数据生命周期、性能、测试文档，并补齐状态/降级体验与素材召回内核。
- **全维审查:** 文档明确要求每个能力输出业务闭环、架构归属、用户旅程、八维评分、爆炸半径和三档修复建议。
- **爆炸半径:** 每个任务都有 R0-R4 定义和 exit criteria，可按影响范围排序。
- **可执行性:** 每个任务给出关键文件、接口、命令、浏览器走查点和报告模板；通用 U1-U9 步骤防止只做源码清单。
- **边界:** 本计划是审查计划，不包含修复代码；任何修复应在用户批准具体 finding 后另开任务。
- **无占位:** 文档没有空白占位标记，未覆盖项要求在执行报告中如实记录。
