## 一、系统全景

hermes-novel 是一个基于 Hermes agent + 《乱世铜炉》/《神游》范文浸泡的中文长篇小说写作系统，包含：

- **8 个协同 Skill**：orchestrator / genesis / simulate / outline / write / critic-prose / critic-outline / critic-genesis / edit
- **1 套 Wiki 知识库**（`.agents/wiki/`，v6 架构）：craft 引擎 / toolkit / technique / exemplars / guardrails / voice
- **1 套旧版 Wiki**（`.agents/wiki-backup-v3/`）：principles / anti-patterns / quality-gates
- **1 份系统分析报告**（5 大开源 AI 写作系统对比）

**核心竞品对标**：已对比 Book Genesis / InkOS / MuMuAINovel / NovelForge / Webnovel Writer，结论见第五节。

## 二、范文浸泡写作策略

### 2.1 核心机制

novel-write SKILL 要求 Writer 接收 **5 份文档**（按阅读顺序）：

| 输入 | 内容 | 字数 |
|------|------|------|
| 1 | 风格指纹（乱铜的叙事腔调/节奏/态度） | ~2000 字 |
| 2 | 完整章节范文（场景类型最接近的整章） | 8000-10000 字 |
| 3 | 技法范文片段（本章需要的 2-3 种技法活样本） | 1500-3000 字 |
| 4 | 前一章最后 1500 字 | 1500 字 |
| 5 | 细纲（含嵌入背景，Writer 唯一骨架输入） | 可变 |

**总 context 约 13,000-16,000 字**，这是写作本身之前的注入量。

### 2.2 核心假设

1. **LLM 通过"语感被动习得"而非"规则主动执行"**——如果先读范文再写，输出的句式/节奏/腔调会自然向范文靠近。这对应认知语言学中的 priming 效应。
2. **信息屏障是有意设计的**：Writer 不知道审查标准，批判家不知道写作过程。这防止了"为通过审查而写"的防御性文本。
3. **范文是动态选取的**，不是全量注入：orchestrator 根据细纲中的场景类型选择最匹配的章节范文，根据技法标签选择对应技法片段。这意味着需要一个有索引的范文库。

### 2.3 实际效果与成本

**有效的部分：**
- "脏·活·乱"自检（完稿后扫描：身体描写是否生理性、叙述者是否出声、转折后是否有恢复段）验证了浸泡效果的可检测性
- 硬检规则（E1-E5 Error 级 + W1-W11 Warning 级）能从文本特征层面判断是否 AI 指纹过重

**未解决的问题（来自叙事能力优化方案的诊断）：**
- 在「量子幽灵」35 章产出中发现 6 个系统性弱点：线性时间锁死（无非线性叙事）、全知叙述口吻（无不可靠叙述）、情绪过饱和（无减法约束）、解释性叙述过多、章节结构单一、叙事距离恒定
- **根因**：浸泡改善了散文质量（语感/节奏/感官），但没有改善叙事结构（时间拓扑/叙述者可靠性/留白）

**维护成本估算：**
- 完整范文库（每类场景 1-2 章 × 10 类场景 = 10-20 章范文）：一次性建设，后续按需增补
- 技法库（每种技法 2-5 段范例 × 15 种技法 = 30-75 段）：建设成本较低
- 风格指纹（每个目标风格 1 份 ≈ 2000 字）：最低维护成本的资产

### 2.4 对 scribe3 的启示

**可以保留的**：
- 风格指纹 + 完整章节范文（两份核心输入）
- 技法范文库设计（可以直接迁移当前 wiki 中的 exemplars/emotion.md、opening.md 等）

**需要升级的**：
- 补充叙事结构层（时间线规划、叙事距离配额、留白策略）——这是原系统最大缺口
- 减少 context 注入量：13,000 字的前置注入对 token 成本压力大；scribe3 可以考虑风格指纹（2000字）+ 单份技法范文（500字）= 2500 字精简版

## 三、多 Agent 编排架构

### 3.1 管线结构

```
Phase 0: 创世（一次性）
  genesis → critic-genesis → 人类 → 锁定（每步）

Phase 1: 粗纲锚定（每回一次）
  simulate → critic-outline → 人类 → 锁定

Phase 2: 逐章循环
  outline → critic-outline → write → critic-prose → [edit → critic-prose] → 下一章

回结束: critic-prose 跨章审计
```

### 3.2 信息屏障设计（最重要的架构决策）

| Skill | 传入 | 明确不传入 |
|-------|------|-----------|
| critic-genesis | 被评估素材 + benchmark | 用户原始创意、生成 prompt |
| critic-outline | 大纲 + 角色卡 + 运转规则 + benchmark | 叙事目标、生成过程 |
| critic-prose | 正文 + 角色卡 + benchmark + 技法范文 | 细纲、写作指引 |
| write | 风格指纹 + 完整章节范文 + 技法范文 + 前章尾部 + 细纲 | 审查标准、批判维度、技法解析 |
| edit | 正文 + 批判报告 + 技法范文 | 细纲、风格指纹 |

**设计原因**：Writer 不知道审查标准 → 不会写"符合审查规则"的防御性文本。批判家不知道细纲 → 只评估文学质量，不评估"是否完成任务"。

### 3.3 判定流程与循环上限

- **三档判定**：PASS / REVISE / RESTRUCTURE
- **修订循环上限**：最多 3 轮 edit → 重审。第 4 轮仍不通过 → RESTRUCTURE（回退到细纲/粗纲）
- **RESTRUCTURE 语义**：不是写作失败，是大纲设计问题被正确发现
- **人类交互点**（Phase 0 每步、Phase 1、Phase 2 RESTRUCTURE 时）：所有多版本决策都等待人类选择，不自动选择

### 3.4 角色卡作为核心状态对象

角色卡在所有 Phase 中流转，包含：
- 心理模型（≥3 层同时运行的内在矛盾 + 认知偏差 + 自欺机制 + 盲区）
- 声音胶囊（口头禅/措辞习惯/节奏/示例对话3段）
- 行为逻辑（核心驱动/底线/压力反应）
- **角色的人味**（角色不体面的时候 / 怪癖 / 肉身状态 / 滑稽之处）——这部分明确标注为"给 Writer 的灵感素材，不是执行清单"
- **声音库**（自由独白 ≥500字 + 压力独白 ≥300字 + 关系独白 ≥300字 + 叙述语气 ≥300字）
- **声音进化记录**（每次重大事件后追加新版本独白）

### 3.5 对 scribe3 的架构借鉴

**Hermes delegate_task 的直接映射**：
原系统的 `delegate_task` 调用对应 Hermes v0.17 的 `delegate_task` tool。以 critic-prose 调用为例：

```yaml
# novel-orchestrator 中的 critic-prose 调用
delegate_task:
  skill: novel-critic-prose
  inputs:
    - 正文（当前章）
    - 角色卡
    - benchmark B1/B5/B7/B8/B9
    - 技法范文片段（从 luanshi-wiki/技法库/ 按本章技法匹配）
  explicitly_excluded:
    - 细纲
    - 写作指引
```

**scribe3 中的简化方案**：Hermes 的 script injection 可以把 wiki 知识直接注入 system prompt，不需要通过 delegate_task 传递；信息屏障仍然有效（不向 critic 注入细纲即可）。

## 四、Wiki 知识库：从 v3 到 v6 的演化

### 4.1 wiki-backup-v3 架构（旧版）

```
principles/ — 写作原则（6 页）
  scene-functions / narrative-distance / deep-pov
  exposition-control / character-voice / pacing-rhythm

anti-patterns/ — AI 反模式（3 页）
  hard-checks / sentence-level / description-level

quality-gates/ — 质量标准（3 页）
  review-dimensions / pass-criteria / golden-rules
```

**v3 的设计哲学**：以"规则"为中心——什么是正确的、什么是错误的、怎么判定通过。面向 reviewer 的知识组织。

### 4.2 当前 wiki v6 架构

```
craft/ — 七大引擎（8 页）
  engine-overview + 01-soak 到 07-sensory-anchor

voice/ — 角色之魂（4 页）
  how-to-soak / voice-spec / voice-evolution / contradiction

technique/ — 写作技法（5 页）
  dialogue / exposition / pov / pacing / scene-transition

exemplars/ — 标杆范文（5 页）
  opening / environment / emotion / dialogue / exposition

toolkit/ — 工具箱（3 页）
  emotion-thesaurus / seed-words / sensory-palette

guardrails/ — 硬性红线（2 页）
  hard-checks / format
```

**v6 的演化方向**：从"规则清单"转向"引擎描述"。不是"不要做 X"，而是"用这个引擎，X 自然就消失了"。

### 4.3 关键演化：被删除的原则

v3 中有的、v6 中已内化的：

| v3 原则 | v6 中的处理方式 |
|---------|---------------|
| deep-pov（深层 POV） | 内化进 craft/01-soak（浸泡 = 进入角色大脑）+ craft/03-body（身体先行） |
| scene-functions（8种场景功能） | 部分内化进 craft/04-temperature（温度曲线管理） |
| narrative-distance（叙事距离） | 独立保留为 technique/pov（五级叙事距离） |
| golden-rules（6条黄金规则） | 分散内化进各引擎，不再作为独立规则列出 |

**被强化的**：
- **情感词典**（toolkit/emotion-thesaurus）：v3 没有，v6 新增，覆盖 15 种核心情感的身体信号 + 内部感觉 + 覆盖动作，这是最可直接复用的工具性资产
- **声音进化协议**（voice/voice-evolution）：v3 没有，v6 新增，解决了"角色经历创伤后声音不变"的问题
- **感官签名**（craft/07-sensory-anchor）：v3 没有，v6 新增，每个反复出场场景有稳定的"感官指纹"

### 4.4 当前 wiki 未解决的问题（来自系统诊断）

wiki v6 仍缺少：
1. **非线性叙事引擎**：时间折叠/环形结构/插叙的执行指引
2. **留白策略**：减法约束，如何知道"这里不写"比"写满"更有力
3. **不可靠叙述**：叙述者可靠性挑战、同一事件多视角版本
4. **叙事距离配额**：每卷强制使用 L1/L4 的次数约束

## 五、Craft 知识资产详目

### 5.1 七大引擎（v6 核心）

可直接迁移到 scribe3 的 system prompt 或 skill context：

**引擎 1：浸泡（soak）**
- 写前以 POV 角色身份写 300 字无目的意识流（不进入正文，用后可丢）
- 3-5 句 CoT 推理（情感起点/终点/转折时刻/种子词）
- **关键约束**：不做笔记、不列计划，让范文语感成为写作"本能"

**引擎 2：闲笔（idle）**
- 三类闲笔：世界级（让世界有生命）、角色级（让角色有人味）、关系级（让关系有质感）
- **强制规则**：每章 ≥ 3 个，必须具体到可以画出来，不解释，不服务主线
- **明确豁免契诃夫之枪**——闲笔的价值不在于推动剧情

**引擎 3：身体先行（body）**
- 情感展示顺序永远是：**身体 → 行动 → 沉默 → 语言**
- 三层：L1 无意识微动作（信号最强）→ L2 覆盖动作 → L3 身体失控（全卷 ≤ 3 次）
- 叙述者 95% 闭嘴；5% 例外仅用于"打破读者认知框架"，每章最多 1 句

**引擎 4：温度曲线（temperature）**
- 每 500 字至少 1 次温度变化（微震就够了，不需要大转折）
- 四色：冷（压抑/疏离）/ 暖（柔软/怀念）/ 锐（紧张/对抗）/ 杂（混乱/失控）
- 三种工具：节奏切换（句式长短）/ 叙事距离跳跃（L1↔L4）/ 闲笔插入

**引擎 5：认知比喻（metaphor）**
- 删掉比喻读者少理解什么？答案是"什么也没少" → 删（装饰比喻）
- 比喻来自角色的专业领域（角色不是在"用比喻"，是思维惯性冒出来的）
- 每章 2-4 个认知比喻；比喻后不跟解释句（E3 Error 级硬检）

**引擎 6：潜台词（subtext）**
- 三种模式：屏障对话（两人心知肚明但不说破）/ 转移话题 / 物理替代（用动作替代应说的话）
- 强制规则：每章至少 1 处；叙述者不解释潜台词
- 潜台词的方式本身是角色签名：沈默用物理替代，姜婉用屏障对话，李忱用转移话题

**引擎 7：感官锚定（sensory-anchor）**
- Pixar "2+2" 法则：给拼图碎片（感官线索），让读者自己拼出情感
- 每个关键场景至少 1 个非视觉感官
- 每个反复出场场景应有"感官签名"——读者看到气味就知道在哪里

### 5.2 硬检规则（可程序化执行）

**Error 级（命中即阻断）**：

| ID | 规则 | 检测方式 |
|----|------|---------|
| E1 | 破折号 "——" 全章 > 5 次 | 计数 |
| E2 | "不是A——是B" 句式 | 正则 |
| E3 | 比喻后紧跟解释句 | LLM |
| E4 | 首段出现世界观术语 | 正则+词表 |
| E5 | 角色禁句命中 | 正则+角色卡 |

v3 中额外的 Error 规则（v6 已合并）：

| ID | 规则 |
|----|------|
| E-v3-1 | 作者/读者穿透（"正如前文所述"） |
| E-v3-2 | 结果剧透（"后来证明"/"命运将会"） |
| E-v3-3 | 抽象情绪标签独立句（"他很愤怒"） |
| E-v3-4 | LLM 标记词（impressive/showcase/delve） |
| E-v3-5 | "全场震惊"类集体反应 |

**Warning 级（密度超限则标记，不阻断）**：W1-W11，涵盖句长单调/命名情感词/解说防御机制/闲笔不足/温度恒定/潜台词缺失/感官单一/对话无脏元素。

### 5.3 情感词典（最高价值可复用资产）

覆盖 15 种核心情感，每种提供：**身体信号（4-6 条）+ 内部感觉（2-3 条）+ 覆盖动作（角色特定版本）**

| 情感 | 核心身体信号 |
|------|------------|
| 压抑的悲伤 | 目光短暂移向窗外0.5秒、手指沿杯沿画圈、突然去做不紧急的事 |
| 被压住的恐惧 | 咽口水的动作变慢、脚趾在鞋里蜷起来、后脖颈汗毛竖起 |
| 愤怒（被压制） | 下颌咬紧（太阳穴肌肉跳一下）、说话语速变慢（不是思考，是控制） |
| 震惊 | 所有动作冻结0.5-2秒、然后一个不合时宜的小动作（眨眼/咽口水） |
| 深层疲惫 | 动作之间有微小迟滞、说话时省略不必要的词、目光停留但没在看 |
| 被背叛 | 表情变得非常平（面部肌肉一次性全收紧）、目光从"看人"变成"评估威胁" |
| 嫉妒 | 注意力强迫性回归（移开→数三秒→第四秒又看了）、计时代替情绪标签 |

**完整词典直接可迁移**，是写出"不说情感词但读者能感受到"的核心工具。

### 5.4 标杆范文体系（exemplars）

系统收录了：
- **乱世铜炉引子**（婚宴开篇）—— 零设定导入的标杆
- **神游第1回**（第一人称往事）—— 设定通过事件展开的标杆
- **双雪涛《平原上的摩西》风格提炼**（当代现实主义日常中的不安感）
- **情感范文 18 条**（恐惧/悲伤/愤怒/释然/矛盾情感/麻木/嫉妒等）

每条范文都有：**原文引用 + 结构标注 + 灵魂句分析 + 技法标签 + 对新项目的启示**。

## 六、对 scribe3 的具体借鉴方案

### 6.1 可直接迁移的 Craft 知识（优先级最高）

以下内容可以**不做修改**地注入 scribe3 的 Writer agent system prompt：

**A. 身体先行三层**（来自 craft/03-body.md）

```
情感展示顺序永远是：身体 → 行动 → 沉默 → 语言。
叙述者永远不：命名情感（"他感到悲伤"）、解说防御机制、替读者理解。

三层：
L1：无意识微动作（信号最强——角色自己都不知道在做）
L2：覆盖动作（角色用另一个行为盖住情感——暴露防御机制）
L3：身体失控（身体在控制但失败了——全卷 ≤ 3 次）

叙述者 95% 闭嘴。5% 例外：当一句话能打破读者认知框架时。每章最多 1 句。
```

**B. 温度曲线规则**（来自 craft/04-temperature.md）

```
每 500 字至少 1 次温度变化（微震即可）。
四色：冷/暖/锐/杂。
全章温度差 ≥ 2 级（不能全冷或全锐）。
压抑 ≠ 恒温——压抑型人格表面平静时内部仍有微震（手指频率变了/呼吸变了）。
```

**C. 闲笔规则**（来自 craft/02-idle.md）

```
每章 ≥ 3 个闲笔（至少一个世界级、一个角色级）。
必须具体到可以画出来。不解释——放在那里就好。
明确豁免契诃夫之枪规则。
闲笔是天然的温度变化工具：高压后插一个闲笔 = 给读者呼吸的空间。
```

**D. 认知比喻检验三问**（来自 craft/05-metaphor.md）

```
1. 删了它读者少理解什么？→ 如果"没什么" → 删（装饰比喻）
2. 它来自角色的领域吗？→ 不是 → 重写
3. 它后面有解释句吗？→ 有 → 删解释句（比喻自己能说话）
```

**E. 对话三校验**（来自 technique/dialogue.md）

```
每段对话写完默念：
1. 遮名可辨？（去掉名字能判断是谁说的吗？）
2. 碰了禁句？（角色卡中"绝不说"的话出现了吗？）
3. 有脏元素？（打断/沉默/说半句/跑题 至少 1 个）
三条不过 → 重写。
```

**F. 脏·活·乱 自检**（来自 novel-write SKILL.md）

```
完稿后扫描三项：
脏：至少2处身体描写让读者"皱眉"（涎水/呕吐/冷汗黏腻/血味混唾液）
活：叙述者至少出声1次——跳出来评论/嘲讽/感慨，说一句不属于任何角色的话
乱：转折点前后至少有1段"恢复段"——紧张之后松回来，再断裂
如果三项自然达标，说明浸泡生效了。
```

### 6.2 硬检规则（建议直接实现为 critic 工具）

**5 条 Error 级规则**（命中即 REVISE，无需 LLM 判断）：
1. `"——"` 全章超过 5 次
2. 正则匹配 `不是.{1,15}——是`
3. 比喻句后紧跟解释句（需 LLM）
4. 首段包含世界观术语（需要术语词表）
5. 角色禁句命中（需角色卡的"绝不说"清单）

**情感标签词词表**（W4 Warning 级检查用）：
`悲伤/愤怒/恐惧/开心/痛苦/焦虑/孤独/绝望/紧张/兴奋/欣慰/感激`

**AI 指纹词词表**（参考 v3 anti-patterns）：
`然而/仿佛/竟然/不禁/宛如/忽然/猛地/骤然/陡然/暗暗/默默/悄悄/偷偷/缓缓/微微`

### 6.3 信息屏障设计（建议保留）

scribe3 的 Writer 不应该知道：
- Critic 的评审维度和评分规则
- 粗纲/总纲全文
- 批判家的历史反馈（除非在修订循环中）

scribe3 的 Critic 不应该知道：
- 细纲内容（不评估"是否完成了任务"）
- 写作指引和浸泡过程
- Writer 的意图

**原因**：知道审查标准会导致 Writer 写"符合审查规则"的防御性文本，而不是真正有文学质量的文本。

### 6.4 声音库设计（建议直接迁移）

每个主要角色需要：

| 类型 | 字数 | 内容 |
|------|------|------|
| 自由独白 | ≥500 | 角色无聊时脑中的漫游（思维跳跃/无用想法/领域印记） |
| 压力独白 | ≥300 | 角色命悬一线时的思维碎片 |
| 关系独白 | ≥300 | 角色想某个特定人时的思维纹理 |
| 叙述语气 | ≥300 | 以角色为 POV 时整章叙述的声音示例 |

**好的独白样本的标准**（v3 原则 character-voice.md）：
- 思维跳跃（一个念头没想完就蹦到另一个）
- 有"无用"想法（和当前情境无关的记忆/观察/吐槽）
- 有不完美性（自嘲、矛盾、欲言又止）
- 有领域印记（科学家脑中蹦出参数碎片）

**声音进化**（每次重大事件后追加新版独白，浸泡时使用当前版本而非初始版本）——这解决了"第20章角色和第1章声音完全一样"的问题。

### 6.5 细纲设计（建议保留核心思路）

细纲 ≠ 剧本。细纲包含：
- **情境**（角色处于什么之中，面对什么压力）——不是"发生什么事"
- **转折点**（唯一的硬约束——本章必须到达的那一个点）
- **可以发生的事**（菜单，不是清单——Writer 自行决定用不用）
- **章尾牵引**（让读者想翻下一章的问题/悬念）

**关键原则**：背景信息嵌入细纲，Writer 读完细纲不需要再查任何其他文件。

### 6.6 scribe3 暂不需要的部分

以下在原系统中存在但 scribe3 暂可跳过：
- 粗纲三版本机制（稳健型/高张力型/角色驱动型）——scribe3 已有自己的章节规划方式
- 回级审计（跨章一致性）——初期可以在单章层面解决
- 范文 Wiki 的 usage_log（成功/失败标注）——维护成本较高，初期不值得
- 伏笔种子池的精细管理——可以用 SurrealDB 的知识层替代

## 七、竞品对比中的关键发现

来自 `.worktrees/hermes-f2df0d03/analysis_report.md`，5 大开源系统中对 scribe3 最有参考价值的：

**Book Genesis（MIT 许可）的核心设计**：
- Writer / Evaluator / Editor 完全隔离上下文（与 hermes-novel 的信息屏障设计相同，独立验证了这个思路的正确性）
- V4 → V5 将 21 个技能简化为 8 个，产出质量反而更好——**"少即是多"在 skill 设计上成立**
- Genesis Score = 最弱维度分数（不是平均分）——这强制了所有维度都要合格

**InkOS（墨子 OS）的 7 个"真相文件"**：
- 世界状态 / 资源账本 / 伏笔钩子 / 章节摘要 / 支线进度 / 情感弧线 / 角色矩阵
- 这种结构化状态管理与 scribe3 的 SurrealDB 知识层思路高度一致
- InkOS 使用 Zod Schema JSON，scribe3 使用 SurrealDB——解决相同问题的不同技术路径

**LLM Wiki 模式（来自 llm-wiki.md）**：
- 核心洞见：Wiki 是"持续复利的人工制品"，不是"查询时重新推导"的 RAG 系统
- LLM 维护 wiki，人类负责来源和问题方向
- 这直接对应 scribe3 的知识层设计目标

## 八、总结：优先级排序

**立即可用（直接复制进 scribe3 system prompt 或 skill context）**：

1. 情感词典（15 种情感 × 身体信号 + 内部感觉 + 覆盖动作）
2. 七大引擎规则文本（尤其是身体先行/温度曲线/闲笔/潜台词）
3. 5 条 Error 级硬检规则 + AI 指纹词词表
4. 对话三校验 + 脏·活·乱自检

**需要适配后使用**：

5. 信息屏障设计（Writer 不知道 Critic 的审查标准）
6. 声音库格式（4 类独白 + 声音进化协议）
7. 细纲结构（情境/转折点/菜单/章尾牵引）

**有价值但需要重新设计**：

8. 范文浸泡机制（精简版：风格指纹 2000字 + 单份技法范文 500字，而非原来的 13000字 context）
9. 非线性叙事引擎（原系统缺失，需从头设计）
10. 留白策略（原系统缺失，"情绪过饱和"是已确认的系统性弱点）
