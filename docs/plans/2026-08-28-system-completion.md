2026-08-28。上游：[`2026-08-27-setting-scale.md`](./2026-08-27-setting-scale.md)（千万字规模改造）、
[`2026-08-27-craft-v4.md`](./2026-08-27-craft-v4.md)（文笔线转向）、
[`docs/craft-evidence/storyscope.md`](../craft-evidence/storyscope.md)（人机差异实测）。

## 一、边界（作者已定，不重新讨论）

摘自 `docs/SESSION.md` 现行段落：

1. **产品产出设定资产 + 章级信息调度方案**（谁在第几章知道什么、线索何时埋何时收、
   误导何时证伪、读者与角色认知差）。**正文人写或半自动，文笔不再作考核项。**
2. **目标是草稿不是成品。** 判据第一次可验证：草稿好不好 = 作者改它比从零写快不快。
   可计时、可数。
3. **新 R3 = 重写率**：作者把哪些段整个删掉重写。删重写的段落是负资产，比不给还糟。
4. **理论基础**：风格阈值必被套利（前四轮铁证），但**事实一致性约束不会**——
   某命题第 N 章谁 `knows`、某 `promise` 埋没埋收、正文有没有违反 `world_rule`，
   这些有唯一正确答案，**套利即写错**。

第 4 条是整个设定线成立的唯一理由。任何新增判据都要先过这一关：
**它有没有唯一正确答案？** 没有的，就只能当监控，不能当门。

## 三、已查实的问题（按证据强度与阻塞程度排）

### P0-1 世界饿死：设定全堆在主角身上，世界是空的

| 证据 | 数字 |
|---|---|
| `setting_completeness` 现成结论 | `char_issue_ratio: 0.789`，19 个角色 15 个缺「他要什么」「他让人付出什么」；`completeness_score: 64` |
| 按实体分布 742 条命题 | 8 个实体只有 1 条、11 个 2-4 条 → **35% 的实体只是个名字** |
| 集中度 | 前 5 个角色吃掉 45%（柳岸青 126 / 沈烛 75 / 赫斯 55 / 兰因 53 / 祝眠 25） |
| 核心世界元素 | `org:天龙座`（主要反派）1-2 条；`place:地球`、`place:月球` 各 1-2 条——北极星讲的就是月球 |

**根因**：卷契约只写「这一卷引入几个新实体」，**引入即算数，引入完撂着不管照样满分**。
铺章时 `_ensure_entity` 只建一个名字和类型。这是「契约是地板」定律的第二种形态：
**要什么给什么，没要的一点不给。**

**现成解法没用**：`s3_generate_codex` / `s3_generate_codex_batch` 存在，
作用正是「按合同 LLM 写厚一张设定卡」（`thicken_codex`），整条流水线一次没调过。

### P0-2 验收单查不出内容深度

新写的 `scribe3/tools/verify_scale.py` 报「全部通过」的同时，79% 的角色是空壳。
它检查了规模、引入数、收线数、红线、一致性——**全是数量和结构，没有一项看内容厚度**。
而系统自带的 `setting_completeness` 早就把这个数算出来了，验收单没接。

### P0-3 StoryScope 点出的四个死穴，一条判据都没有

`docs/craft-evidence/storyscope.md`（61575 条人机配对 × 304 特征）给出的**可工程化差距**：

| 死穴 | 人类 | 模型 | 说明 |
|---|---|---|---|
| 设定不当障碍 | 11.1% | 3-4% | 机器的设定是装饰，人的设定是麻烦 |
| 空间铺不开 | 26.1% | 13% | 一个区域要有多个地点 |
| 描写一律拉满 | 68% | 91.8% | 感官密度打满，不知节制 |
| **说教** | 37.4% | 73-77% | 五模型同向，落差仅 **3.7%**，最硬的通病 |

**真命门是 revelation（AUC 0.808，比 setting 还差）**：后置揭示人 66.3% / Claude 42.7%，
颠覆预期人 41.4% / 14.6%，红鲱鱼人 33.1% / 10.1%，不解释的行话人 38.4% / 26%。
**模型默认把话说完、兑现预期、不误导、不留悬置——恰好把设定文的卖点全拆了。**

这几条里，有唯一正确答案、能进门的只有一部分（见第五节判据设计），
其余只能当分布监控。但**现在一条都没有**。

### P1-1 立纲不能滚动

现在是一次 LLM 调用生成 10 卷覆盖 200 章。3000 章要 150 卷，一次调用塞不下。
而且按「契约是地板」，150 卷的地板要逐卷定，这本身是规划问题，不是调用次数问题。

### P1-2 知情帧没有检索

`_hero_knows` 取 `facts[:25]`，不排序、不按相关性检索。第 200 章主角知道 119 条，
给模型看任意 25 条；第 3000 章他会知道几千条，还是 25 条。
`codex_recall` 那套检索机制存在，这条链路没接。

提示词膨胀本身不是问题：实测第 11 章 7197 字、第 195 章 10604 字，基本平的
（欠线台账自限，收掉就不列）。**问题是给的那 25 条对不对，不是给了多少。**

### P1-3 MCP 空壳，产品写路径做不了铺章

确认的空壳：

| 工具 | 行 | 症状 |
|---|---|---|
| `s3_plan_chapter_accounts` | `tools_write.py` L1186-1199 | 审批完只返回章号列表 + 一句 note，不调 LLM、不写 synopsis，**但 `commit_if_approved` 仍报 `status=written`** |
| `s3_expand_arc_window` | L1252-1261 | `_write()` 返回静态 dict，无任何 `st.*` 调用 |

后果：铺章这件事只有我在命令行能做（`tools/expand_wanjie_chapters.py`），
带审批的产品路径永远做不了。这跟 AGENTS.md「Agent 改世界状态走 MCP + 审批」相悖。

**空壳 + 审批成功 = 假绿**，比没有这个工具更糟。

### P1-4 charter 无前端

`GET /outline` 返回里带 charter，前端一次没用过。这轮的核心机制作者看不见。

### P2-1 审批旁路

- `POST /seeds/promote`（`experience.py` L249-279）直写伏笔，响应 `requires_approval: False`
- `/canon/*` 整族不在 REST 403 前缀内，`decide` approve 直接 `apply_change_pack` 写库
- `s3_generate_codex_batch` 的 `persist=true` **不经 `_ask`**（与单卡版 `s3_generate_codex` 不一致）
- `s3_generate_stage`、`s3_save_chapter_draft` 在 `WRITE_GATED` 里却无 `_ask`

### P2-2 工程卫生

14 提交未推、83 文件未提交、腾讯云旧版。CLI 与 MCP 双轨（`plan_charter.py` 已共用
`generate_charters` 内核，但仍无审批；`expand_wanjie_chapters.py` 整条在 MCP 之外）。

## 四、方案（按执行顺序）

### 第 1 步 · 把已有的能力接上（半天，不写新逻辑）

这一步一行新算法都不发明，只是把系统里已经有、且正对症的东西接进流水线。

1. **`verify_scale.py` 接入 `setting_completeness`**，把 `char_issue_ratio`、
   `completeness_score`、`missing_dimensions` 变成验收项。阈值先按现状定：
   `char_issue_ratio ≤ 0.3`、`completeness_score ≥ 80`。
   立刻的效果：现库会从「全部通过」变成不过关，这才是真实情况。

2. **铺章流水线末尾批量调 `s3_generate_codex_batch`**（或其内核 `thicken_codex`），
   把每卷新引入的实体写厚。用系统自己的字段合同，不要另发明一套。

3. **卷契约加一栏 `thickens`**：这一卷要把哪几个**已有**实体写厚。
   按「契约是地板」定律，不写进契约模型就不会做。数量同样从判据反推，
   与 `required_introduces` 同源（这是上一轮的教训：**要求和验收必须同源**）。

### 第 2 步 · 把 StoryScope 的死穴变成判据（一天）

判据设计的分水岭是第一节第 4 条：**有唯一正确答案的才能当门，其余只能当监控。**

**能当门的（客观可算）**：

| 判据 | 算法 | 依据 |
|---|---|---|
| 空间铺开度 | 每个区域（`place` 的上级）下辖地点数；一区一地点的比例 | 人 26.1% vs 模型 13% |
| 设定当障碍 | `world_rule` 有 `cost` 字段且在章内被真正触发（有命题引用）的比例 | 人 11.1% vs 模型 3-4% |
| 实体厚度分布 | 命题数低于阈值的实体占比（P0-1 那个数） | 自测得出 |
| 悬置率 | 埋下后**跨卷未收**的线占比。全收完 = 把话说完 = 无悬念 | revelation：模型默认不留悬置 |

**只能当监控的**：说教（无唯一答案）、感官密度（同）、红鲱鱼比例（需人判是不是误导）。
监控项**绝对不许进提示词**——这是前四轮反复撞的墙，
`verify_scale.py` 头部注释已经写死这条禁令，不要撤。

### 第 3 步 · 补空壳，让产品路径能做（一天）

1. `s3_plan_chapter_accounts` 从空壳补成真实现：把 `expand_wanjie_chapters.py` 里
   已经验证过的逻辑（卷契约注入、限知帧、伏笔台账、编号收线）搬进去。
2. `s3_expand_arc_window` 要么补实现，要么删掉——**空壳 + 审批成功 = 假绿，
   比没有更糟。**
3. `s3_generate_codex_batch` 的 `persist=true` 补 `_ask`，与单卡版对齐。
4. 补一条护栏测试：**`WRITE_GATED` 里的工具，`_write()` 必须真的碰 store 或 LLM。**
   空壳不许再混进来。

### 第 4 步 · 滚动立纲 + 知情帧检索（两天，规模化的前提）

1. **滚动立纲**：`generate_charters` 支持只立后 N 卷，输入是「已完成卷的实际产出」
   而不是只有北极星。150 卷分批立，每批立纲时能看见前面真实发生了什么。
2. **知情帧检索**：`_hero_knows` 改成按当前卷契约的 `key` + 本批章的实体做检索排序，
   不要 `facts[:25]`。`codex_recall` 已有的检索能力直接用。

### 第 5 步 · charter 前端（一天）

分卷面板加 charter 展示与编辑：引入清单、写厚清单、收线数、卷末知情终态（key + what）。
最低限度先做只读展示——**作者看不见的机制等于不存在。**

### 第 6 步 · 工程卫生

提交、推送、更新腾讯云部署。审批旁路按产品决策关闭或审批化。

## 五、验证方法论：什么叫「真的审查了内容」

**这一节比上面所有方案都重要。** 这个项目已经出过两次「指标全绿、东西是废的」：
craft 线 `prose_check` 6/6 全绿、作者判三篇全废；设定线 `verify_scale` 全部通过、
79% 角色是空壳。两次都不是模型不行，是**验收只看了表面**。

下面七条是这一轮实际用出来、并且真的抓到东西的做法。**每一条都必须执行。**

### 1. 数字异常，先怀疑判据，再怀疑数据

十卷全部报「说要收却没收」时，正确反应不是「模型不听话」，而是「十卷全错，
更可能是我判据错了」。查库发现真实收线率 93%——**判据拿立纲时编的措辞
去匹配后来才产生的线，天生对不上。**

**规则：一项检查大面积失败时，先花十分钟验证这项检查本身。**

### 2. 抽样把「要求」和「实物」并排读

`must_know` 报 11 条缺失，逐条把契约要求和库里命题并排看，
发现 8 条是同一件事换了措辞（要求「档案会留下空白，空白本身会被追索」，
库里是「只留下可被追索的档案空白」）。

**规则：任何「缺失/违规」清单，必须抽至少 5 条把原文读出来，不许只看计数。**

### 3. 「没查出问题」必须有阳性对照

`setting_audit.scan` 在真库上从来没查出过任何东西，一度以为库是干净的。
真相是它走 `facts_at`，读取时同键冲突已经被折叠掉了，**这项检查从未生效过**。

**规则：任何返回 0 的检查，必须往库里插一条已知缺陷，确认扫得出来，再删掉。
没有阳性对照的 0 不算数。**

### 4. 阳性对照本身也会写错

第一次跑新验收脚本报「阳性对照失败」，查下来是过滤条件依赖 `detail` 文案，
而矛盾的 detail 里只有两个冲突的值、没有属性名——**探针其实扫出来了，是我的判断条件错了。**

**规则：对照要比条数（前后差值），不要认文案。**

### 5. 看分布，不看总量

960 条命题听起来很多。按实体分布一算，35% 的实体只有 1-2 条。
**总量掩盖结构。**

**规则：任何总量指标，必须同时给出分布（分位数或分桶），并检查长尾。**

### 6. 用系统已有的能力交叉验证

`setting_completeness` 早就算出 79% 角色是空壳。自己新写的验收单没接它，
于是两套结论并存而互不知晓。

**规则：动手写新检查之前，先 grep 系统里有没有现成的。有就接，别另起炉灶。**

### 7. 判断「是不是我引入的」要用 stash 对照

全量回归 451 个失败，抽最大一簇 `test_write_context_outcome.py`，
`git stash` 后照样失败 22 个 → 既有欠账。

**规则：报告失败前，先 stash 跑一次基线。分不清新旧的失败等于没有结论。**

### 还有一条元规则

**每一轮跑完，必须回答这个问题：「如果这套东西其实是废的，
我现在手上哪个数会露馅？」如果答不上来，说明判据不够，先补判据再跑。**

## 六、验收

每一步做完都跑同一条命令，不许换判据：

```bash
scribe3/.venv/bin/python -m scribe3.tools.verify_scale --db <库> --chapters <章数>
```

第 1、2 步做完后，这个脚本应当新增这些项：实体厚度分布、`char_issue_ratio`、
`completeness_score`、空间铺开度、设定当障碍比例、悬置率。

**基线（现库 `wanjie_scale`，200 章）**，改进后要逐项比对：

| 项 | 现值 | 目标 |
|---|---|---|
| 一致性矛盾 | 0（带阳性对照） | 保持 0 |
| 收线率 | 93% | 保持 ≥90%，但悬置率不得为 0 |
| 每卷新鲜度 | 卷 2-9 是 1.0-4.5 | ≥5.0／10 章 |
| `char_issue_ratio` | **0.789** | ≤0.3 |
| `completeness_score` | **64** | ≥80 |
| 实体命题数 ≤2 的占比 | **35%** | ≤15% |
| 设定文字数 | 97887 | 不作目标（字数不是质量） |

最后一项写在这里是提醒：**字数从 17302 涨到 97887 曾经被当成成绩，
但那 97887 字里 35% 的实体只是个名字。量不是质。**

## 七、不要做的事

- 不要重新去追文笔。作者已经定了两次边界。
- 不要把监控指标写进提示词。这是前四轮撞了五次的墙
  （最近一次：`props` 参数以任务形态出现就被机械执行）。
- 不要新增没有唯一正确答案的门。风格阈值必被套利。
- 不要在没有阳性对照的情况下报告「没问题」。
- 不要另起炉灶写系统已有的能力。
- 不要为了让判据通过而调低判据。判据要动，必须先给出为什么原判据是错的。
