## 2. 架构层面问题

### P02 · MCP 写门控被 REST 完全绕过(最该先想清楚的架构裂缝)
- **问题**:MCP 侧 `s3_add_fact` 等 8 个写工具走 elicitation 待批(`mcp.py:30-32` `WRITE_GATED`),但 REST 侧 `POST /facts`(`app.py:174`)、`POST /characters`(`app.py:148`)直接 `add_*` 落库,**无任何审批**,且 `POST /facts` 能写 `secret=True`(`app.py:178`)。同一类"世界状态写"在 MCP 待批、在 REST 裸写。
- **成因**:设计上把 REST 定位为"作者直编"(`app.py:142` 注释),认为作者全权无需审批;待批只防"主编 agent 乱写"。但二者写的是同一张表,门控只覆盖一条路径。
- **风险**:若主编/任何客户端改走 REST,门控形同虚设;`secret` 私密事实可无审批写入。
- **整改**:明确"门控对象是写操作还是写主体"。若是前者→REST 写也应过同一审批层(抽 `commit_if_approved` 为公共服务,REST/MCP 共用);若是后者(信任作者直编)→在文档与代码注释里固化"REST=作者可信通道、MCP=agent 受限通道"的边界契约,并加测试守护"无新写路径绕过"。改动范围:中(抽公共写门控服务)。
- **参考**:策略集中化(Policy as single source),所有写经统一授权层,而非按"入口"分散判定。

### P03 · 限知持久化裂口:add_event 丢字段 → see_event 真库失效
- **问题**:内存 `Event` 有 participants/effects/causal_in/preconditions(`ontology.py:55-68`),但 `store.add_event` 只存 etype/valid_from/goal(`store.py:175-179`),**其余全丢**。导致 `see_event`("看见即知道",依赖 effects+participants,`knowledge.py:53-61`)在真库上**无数据可依、形同空操作**。
- **成因**:持久层最初只为"事件存在性"建表,事件的因果/参与结构后于内存模型设计,迁移未跟进。
- **风险**:限知范式的"事件自动生成知识边"只在内存 World 成立;真库靠 ingest LLM 抽取补,是**结构化保证退化为概率保证**。这是范式持久化的最大短板。
- **整改**:迁移加 `event.participants/effects`(array)字段,`add_event`/`events_at` 补读写,`see_event` 直接吃真库事件。改动范围:中(1 迁移 + store 读写 + 1 测试)。
- **参考**:领域模型与持久模型字段对齐,用"映射完整性测试"守护(往返序列化不丢字段)。

### P06 · 共享单连接 + 无事务 + 并发竞态
- **问题**:`_stores[work]` 每书缓存**一个长生命周期 SurrealStore**(单 WS 连接,`app.py:27-46`),所有并发 REST/MCP 请求 + `_bg_ingest` 后台任务共享;`_execute_write`(`store.py:121-123`)**无 BEGIN/COMMIT**。`grant_public`(`store.py:182`)、migrate 多步写是逐条独立提交。
- **风险**:并发 + 无事务 + 共享连接 = 竞态 + 半套数据。记忆中"第1章 ingest 因 duplicate record 失败"即此路径。
- **整改**:① 关键多步写(grant_public/apply_delta/migrate)包 SurrealDB 事务;② store 改连接池或每请求短连接(代价:连接开销);③ 至少给共享 store 加写锁。改动范围:大(三阶段)。
- **参考**:DB 访问层每请求作用域(request-scoped session)或连接池 + 事务边界显式化。

### P23 · works 注册表绕过单一写点
- **问题**:`create_work/delete_work/rename_work`(`store.py:60-95`)直接 `db.query()` 写 `_reg` 库,绕过 `_execute_write`,破坏系统宣称的"改世界状态唯一经 `_execute_write`"不变量(`store.py:121` 注释);`delete_work` 含 `REMOVE DATABASE`(`store.py:69`)破坏性操作。
- **整改**:注册表写也收敛到一个带审计的写入口,或在文档里把不变量精确限定为"世界状态写"(注册表显式除外)并加注释。改动范围:小。

## 3. 功能与业务逻辑问题

- **P07 · ingest 重复触发覆盖(高)**:`/save-chapter` 已 `background.add_task(_bg_ingest)`(`app.py:587`)自动 ingest,`gen3.py:72` 又显式 POST `/ingest` —— 同一 `seq` 被 ingest 两次。fact id 用 `f"fact:k{seq}-{i}"`(`ingest.py:30`)走 UPSERT(`store.py:151`),第二次若抽取条目数/顺序不同,旧 fact 被覆盖,但**已发的 KnowledgeEdge 仍指向旧 fid** → 角色"知道一条已被改写的事实"或悬挂边。**整改**:ingest 加幂等键(章级"已 ingest"标记,重复跳过或先清后写),去掉 `gen3` 的双触发。
- **P18 · LLM 幻觉角色污染知识图谱(中)**:`apply_delta` 的 `did` 对 `seen_by` 直接 `_ensure_char`(`ingest.py:13/40`),LLM 抽取的幻觉角色名会**凭空建实体 + 发知识边**,污染 `characters()` 并被 `grant_public` 波及。**整改**:`seen_by` 角色必须已存在才发边(或入"待确认"队列),不静默建角色。
- **P33 · 事件块不受限知门控(中)**:渲染的"本章要发生的事件"块(`render.py:60-66`)直接列 `events_at` 全部 participants,**不经 focalizer 帧过滤**。若事件含视角角色不该知道的隐藏参与者,其名进 prompt。当前 scenario 未触发,但缺强制校验。**整改**:事件参与者也按帧过滤,或显式断言"喂入事件 ⊆ 该视角可感知"。
- **P13 · 泄露检测静默失效(中)**:`find_leaks` 异常吞成 `leaks=0`(`app.py:585-586`)= 假绿。**整改**:失败要回 `leaks=null` + 错误,区分"未检测"与"检测通过=0"。
- **P25 · 假成功(中)**:`PATCH/DELETE` 对不存在 id 不报 404,`store._update_by`/`_delete_by` 空结果静默(`store.py:259/265`),前端收 `{ok:true}`。`recall` 的 `k` 无下界(可负)。**整改**:写前查存在性返 404;int 参数加 `Query(ge=1)` 校验。

## 4. 性能问题

> 限知投影是**每次渲染的热路径**,性能问题直接拖慢核心体验。长篇(数百命题×数十角色×数百知识边)放大效应显著。

- **P05 · 零索引,全表扫(高)**:除 `idx_prop_vec` HNSW(`003`)外**无任何 DEFINE INDEX**。受影响热查询:`facts_at`(proposition.valid_from/valid_to,`store.py:213`)、`latest_voice_samples`(`store.py:332`)、`events_at`(`store.py:425`)、`knowledge`(knows 全扫)、`open_promises`(status,`store.py:360` Python 过滤)、`proposition.entity` 等值。**整改**(ROI 最高):加 `DEFINE INDEX ON proposition FIELDS valid_from, valid_to` / `ON knows FIELDS in, since_chapter` / `ON voice_sample FIELDS character` / `ON event FIELDS valid_from` 等。几行 surql,零逻辑风险。
- **P04 · knowledge @property 重复全扫(高)**:`store.knowledge`(`store.py:429-441`)每次访问跑 2 条全表查询;`graph()`(`store.py:411`)先 `facts_at` 再遍历该 property,`dramatic_irony` 两次 project_frame = 知识边全扫 2 遍。@property 语义掩盖了"这是昂贵 DB 调用"。**整改**:改显式 `load_knowledge()` 方法 + 单次投影内缓存;配合 P05 索引。
- **P29 · /quality N 章重活(中)**:逐章 `get_chapter`+`quality_flags`+`causal_complete`(`app.py:280-289`),无缓存/分页。**整改**:QC 结果随存稿缓存(章级),`/quality` 读缓存聚合。
- **P38/前端 · 数据获取无缓存去重**:前端每视图 `useEffect` 手写 `api.x().then(setState)`,无缓存层。**整改**:引入 React Query 类缓存(也顺带解决 loading/error 态,见 P09)。

## 5. 安全问题

> **语境**:本地单用户工具,`127.0.0.1` 是当前主防线。下列问题在"永不暴露"前提下风险可控;**任何反代/端口转发/多用户计划都会让它们变成真实高危**。

- **P01 · 零认证零鉴权(高*)**:无任何 auth middleware,所有读写裸奔(`app.py:24`)。`DELETE /works`、`PUT /intent`、设定库增删改任何人可调。对比被删的 scribe2 曾有 `x_owner_id` + `_own_work` 鉴权——scribe3 **退化掉了 owner 边界**。**整改**(条件化):若仅本地→记录为"刻意取舍 + 绑 127.0.0.1";若计划暴露→加 API key/本地 token 中间件 + 关 CORS。
- **P02 · 写门控 REST 绕过(高)**:见 §2。
- **P08 · root/root 硬编码(高*)**:`store.py:102-105`、`live.py:22` SurrealDB 默认弱口令,不可 env 覆盖。**整改**:凭证移环境变量,默认值仅本地。
- **P22 · CORS *(中*)**:`app.py:25` 配合无认证,任意网页可跨域打本机(DNS rebinding 风险)。**整改**:`allow_origins` 限 `http://127.0.0.1:3311`。
- **P14 · secret 直出(中)**:`/facts`、`/recall` 经 `_facts()` 始终带 `secret` 字段(`app.py:49-51`),不像 `/frame`/`/irony` 走投影屏蔽。**整改**:非投影端点剥离 secret,或仅在"全知调试"模式返回。
- **P26 · 图片附件无校验(中)**:`images:list=[]`(`app.py:467`)裸 list,base64 直拼转发,无大小/数量/MIME 白名单。**整改**:Pydantic `list[ImageModel]` + 大小/数量上限 + MIME 白名单。
- **P24 · f-string 拼表名(中,当前不可达)**:`_update_by`(`store.py:261`)`f"...SET {sets}"` 拼字段名(值仍绑参),当前调用方字段名来自固定映射/Pydantic 字面量,**不可注入**;但是"靠调用方自律"的脆弱边界。**整改**:字段名 allowlist + 表名映射常量化。
- **P28 · 无限流无成本熔断(中)**:`/chat/*`、`/render`、`/ingest` 都打 LLM(600s 超时),无 rate-limit/成本上限。scribe2 曾有 `_COST_BUDGET`。**整改**:加每会话并发上限 + 日成本熔断。

## 9. 技术债务评估

### 总体评分:**6 / 10**(中等偏上债务;核心健康,生产化欠账明显)

**评分依据**:
- **加分项(核心质量 8-9 分)**:限知范式(渲染前知识帧投影)设计干净且**有真库+内存双重测试证明**(`test_store`+`test_ontology`);数据层"内存契约 + 鸭子兼容持久实现 + 对接口编程"是教科书级解耦;`_execute_write` 单一落库点 + MCP `commit_if_approved` 双层写门控机制自洽;后端测试覆盖广(24 测试,核心模块几乎全覆盖)。这是一个**架构骨相很正**的系统。
- **扣分项(系统性欠账)**:安全(无认证/门控 REST 绕过/root 硬编码)、性能(零索引/N+1/全表扫,且正好压在渲染热路径)、一致性(无事务/ingest 覆盖/双实现漂移)、生产化(无 Docker/CI/前端硬编码/前端零测试)四条线**集体缺失**,把整体从 8 拉到 6。

对一个"已验证能写长篇"的原型,6 分合理;但**长篇高强度使用或交付他人前,第一阶段必做**。

### ROI 最高的 3 件事
1. **数据库索引**(P05)— 几行 surql、零风险,直接加速每一次限知投影(核心热路径)。投入小时级,收益持续。
2. **ingest 一致性**(P07+P18)— 幂等键 + 幻觉角色校验。**知识账本是限知的命脉**,账本漂移会让限知"基于错误的已知"而失真,且症状滞后难查。
3. **消除静默吞错 + 结构化日志**(P13+P17)— 可观测性是发现其他一切问题的前提。当前多处失败无声,等于"蒙眼开车";点亮它,前两项的效果才可验证。

### 不建议优先投入(低 ROI / 条件未触发)
- **认证体系**(P01)— 若**永久本地单用户**,绑 `127.0.0.1` 已是足够边界,加完整 auth 是过度工程;**仅当计划暴露/多用户时**才升为最高优先级。按需,不盲目。
- **Docker/CI/前端测试**(P11/P12)— 单人本地开发手测 + 手动启动可接受;**计划交付他人或团队协作时**才必要。
- **死代码"重构"**(P39/P40)— 这不是"投入",直接删除即可,别当重构任务规划。
- **可访问性/魔法值清理**(P47/P42)— 真实收益低,排在所有功能性整改之后。
