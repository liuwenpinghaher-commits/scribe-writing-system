## 1. 枢纽 B(图枢纽)—— 优化空间最大

### 1.1 Graph RAG 缺少 RRF 融合与重排序(与行业最佳实践差距最大)

**现状**:B 枢纽 §3.4 的 `s3_graph_recall` 是**单次 SurrealQL 多跳遍历**——向量召回种子命题后,沿 `knows`/`causes`/`involves` 图边拼知识子图,**一次查询返回**。

**行业最佳实践(2026)**:
- GraphRAG 的生产标准是**三路召回 + RRF 融合**:dense vector(语义)+ sparse BM25(关键词)+ graph traversal(关系),用 Reciprocal Rank Fusion `score = Σ 1/(k + rank_i)` 融合排名
- 纯向量召回对**专名/罕用词**(法器名、人名)弱;纯图遍历缺语义泛化;融合后两者互补
- 融合后加 **cross-encoder 重排序**(`bge-reranker-v2-m3`),增加 ~150ms 但 MRR 提升 18–24%
- 来源:Essa Mamdani《GraphRAG Hybrid Search 2026 完整开发者指南》、AI Learning Guides《RAG in Production 2026》

**优化建议**:
1. B 的 `s3_graph_recall` 与 E 的 Hybrid Search(§3.6)**应合并设计为统一的 `s3_hybrid_recall`**,而非各自独立——两者共享同一向量底座,融合是自然延伸
2. 在 `store` 层实现应用层 RRF(方案 E §3.6 已提到"保守路线:RRF 融合放 store 应用层"),但应**明确将其作为 B 的 Graph RAG 的融合层**,而非 E 的独立项
3. **中期补 cross-encoder 重排序**:召回后对 top-N 做重排,提升主编上下文精度。这对限知投影特别重要——更精准的召回 = 更少噪声进 prompt = 更少幻觉泄露风险

### 1.2 缺少自适应检索深度(Adaptive Retrieval Depth)

**行业实践**:简单查询 → 纯向量(快、便宜);复杂查询(多跳推理)→ 图遍历 + 混合融合(慢、精确)。用查询分类器动态路由:

```python
def route_retrieval(query: str) -> dict:
    classification = classify_query(query)  # 轻量 LLM 或规则
    if classification.complexity == "simple":
        return {"mode": "vector", "k": 5}
    elif classification.requires_graph:
        return {"mode": "graph_hybrid", "depth": 2, "k": 8}
    return {"mode": "hybrid", "k": 10}
```

**优化建议**:B 的 `s3_graph_recall` 当前无查询复杂度路由——所有查询都走完整图遍历。对"焦三现在处境"这类多跳查询是对的,但对"焦三的名字"这类简单查询是浪费。建议在 MCP 工具层加一个轻量路由(可先用规则:含"谁知道/从哪来/为什么"等关系词 → 图遍历;否则 → 纯向量)。

### 1.3 `events_at` 读回的嵌套 SELECT 可能是隐性 N+1

**现状**:B §3.1.4 的 `events_at` 改造用嵌套 `(SELECT ... FROM ->involves) AS parts` 在同一查询取回参与者——这比逐事件查好,但 SurrealDB 对**每行执行一次子查询**的嵌套 SELECT 在事件数多时仍可能退化。

**优化建议**:
- 先用 `EXPLAIN` 验证(E 枢纽 §4 已有此计划,但应**跨枢纽协调**:B 落地 `events_at` 改造时同步跑 E 的 EXPLAIN 验证)
- 若嵌套子查询退化,改为 `SELECT ... FROM event WHERE story_chapter=$ch FETCH ->involves->character, ->causes->proposition`(SurrealDB 的 `FETCH` 子句可批量预加载关联,避免逐行子查询)

### 1.4 缺少知识图谱的 CleanUp 步骤(增量更新去冗余)

**学术证据**:arXiv 2505.24803《Guiding Generative Storytelling with Knowledge Graphs》的 KG pipeline 在**每个场景生成后**执行 `CleanUp(KG, context, scene)` 移除冗余或不再相关的信息,保持 KG 精简。这是长篇叙事中防止 KG 膨胀的关键步骤。

**现状**:scribe3 的 ingest 只做"增量抽取 + 落库",无 CleanUp——命题/知识边单调增长,数百章后知识图谱膨胀,召回噪声增大。

**优化建议**:在 C 枢纽(ingest 管线)或 B 枢纽(Graph RAG)补一个"章级 KG 压缩"步骤:每 N 章(或每卷结束)对知识图谱做一次 LLM 辅助的 CleanUp——合并重复命题、标记过时知识边(设 `until_chapter`)、压缩冗余事件链。这与调研文档 §0.2 的"分层记忆与状态压缩"一致。

### 1.5 RecordLink 迁移可利用 SurrealDB 的 `type::record()` 构造器简化

**现状**:B §3.2.2 的转换脚本用 `string::slice(entity, 5)` 手动切前缀转 record link——对不匹配前缀的行需人工核对。

**优化建议**:SurrealDB 的 `type::record('character', $local)` 可直接从字符串构造 record id。转换脚本可先用 `parse::is::record_id()` 判断是否已是 record,再用 `string::split(entity, ':')` 分离前缀和局部名,通过 `ONT2TBL` 映射表名——比硬编码 `slice(entity, 5)` / `slice(entity, 6)` 更健壮,能处理 `role:` / `place:` / `ev:` / `fact:` 等所有前缀。

## 2. 枢纽 C(知识账本)—— 事务优先级应提前

### 2.1 "先清后写"未包事务是当下最大风险

**现状**:C §3.1 的 `purge_ingest` + `add_fact` + `add_knowledge` 是多条独立 surql,事务化"留 G 枢纽 P06"。但 C 的"先清后写"恰恰是**最需要事务的多步写**——清完但写失败 = 账本空洞(比覆盖更糟)。

**行业实践**:幂等管线的标准模式是"**事务内先清后写**",要么全成要么全不落。Data Pipeline Design Patterns(2026)明确:"idempotency 要求操作原子化,否则部分失败导致状态不一致"。

**优化建议**:把 G 枢纽的 P06(事务)**拆出一个"最小事务"子集**优先到 C 之前落地——只需 `BEGIN TRANSACTION; DELETE...; CREATE...; COMMIT TRANSACTION;` 拼成单条多语句 query(C §3.1 已提到退路)。不必等 G 的完整事务上下文管理器。**这是跨枢纽优先级调整建议**:`D → B → C` 应改为 `D → B → (C+最小事务) → G剩余`。

### 2.2 幻觉校验可利用 KG 做交叉验证(与 B 协同)

**现状**:C §3.2 的 `_resolve_char` 只查 `store.entity(oid)` 是否存在——单一来源。

**优化建议**:B 枢纽落地 `character_relation` 图边后,幻觉校验可升级为**图感知校验**:不仅查角色是否存在,还查 `seen_by` 声称的旁观者与当事人之间是否有 `character_relation` 边(盟友/敌对/亲属)——若无任何关系边,更可能是幻觉。这是"知识图谱增强一致性校验"的标准模式(arXiv 2505.24803)。

### 2.3 缺少 Dead Letter Queue 模式

**行业实践**:生产级数据管线的标准组件之一是 DLQ(Dead Letter Queue)——处理失败的记录不丢弃,入队待人工干预。dataskew.io《Data Pipeline Design Patterns 2026》将其列为 7 大核心模式之一。

**现状**:C 的 `ingest_unverified` 表是 DLQ 的雏形(幻觉角色入待确认),但只覆盖 `seen_by` 幻觉——其他失败类型(解析失败、知识边悬挂)无 DLQ。

**优化建议**:将 `ingest_unverified` 泛化为 `ingest_dlq`(dead letter queue),覆盖所有 ingest 失败类型:幻觉角色、解析失败条目、悬挂边。字段加 `failure_type`(`hallucinated_char` / `parse_error` / `dangling_edge`)和 `raw_payload`(原始 LLM 返回,供调试)。这比 G 的"去吞错加日志"更进一步——不仅日志可见,失败数据本身可追溯、可重放。

## 3. 枢纽 D(本体规范化)—— 最稳健,微调即可

### 3.1 event_type 两层分类法(大类枚举 + 自由子类型)

**现状**:D §3.6 决定 `event_type` 保留自由字符串,不强制枚举——理由是"小说事件类型本质开放,枚举会阻塞创作"。

**行业实践**:arXiv 2505.24803 的 KG pipeline 对叙事元素使用**类型分区**(characters/locations/objects/events),每个类型有受控属性但自由值。这本质是"大类受控 + 子类自由"的两层结构。

**优化建议**:给 `event_type` 引入**两层结构**:`event_category`(受控枚举:`conflict` / `turning_point` / `daily` / `revelation` / `loss`)+ `event_subtype`(自由字符串)。大类枚举支撑"按类型统计/施加结构规则"(诊断 §4.3 的诉求),子类型保创作自由。这比 D 当前的"完全自由"多一层结构化,比"完全枚举"少一分约束。

### 3.2 迁移版本表(P49)应与 D 的命名重构协同

**现状**:D 的三段式迁移(加新名 → 回填 → 删旧名)与 H 的迁移版本表(P49)是独立设计的。

**优化建议**:D 的每条 N(N1–N7)应**各自是一个版本化的迁移**——迁移版本表记录"010_rename_etype 已应用",避免 D 的三段式中间态被重复执行。建议 D 与 H 的 P49 **同批落地**迁移版本表,D 再在其上做命名重构。

## 4. 枢纽 E(性能与索引)—— 可利用 SurrealDB 3.x 新特性

### 4.1 DEFINE EVENT 的 ASYNC / RETRY / MAXDEPTH 未利用

**SurrealDB 3.0+ 新特性**(已从官方文档确认):
- `ASYNC`:事件在触发事务之外异步执行,不阻塞写入
- `RETRY N`:失败自动重试 N 次
- `MAXDEPTH N`:递归事件深度控制(默认 3,最大 16)
- `$input`:v3.0.0 新增,代表触发事件的记录本身

**现状**:E §3.3 的事件示例是同步的,且标注"$before/$after 语义需人工确认"。

**优化建议**:
1. **已确认**:`$event` = "CREATE"/"UPDATE"/"DELETE",`$before`/`$after` 可用——E 的"需人工确认"可降级为"已确认"
2. E §3.3a 的 `ev_chapter_saved`(回写 manuscript 进度)可用 `ASYNC`——它是纯派生计算,不需阻塞存稿事务
3. E §3.3c 的 `ev_promise_closed`(伏笔审计)可用 `ASYNC RETRY 3`——审计写入失败不应阻塞伏笔闭合
4. **红线不变**:ASYNC 事件仍**不可发 `knows` 边**(限知不变量),只做纯 DB 副作用

### 4.2 章节级 RAG 的 embed 分段策略应明确

**现状**:E §3.5 标注"整章超 embed 长度上限的分段策略需人工确认"——bge-small-zh-v1.5 的最大输入是 512 tokens,整章动辄 3000+ 字,超限。

**行业实践**:
- 语义分块(semantic chunking):`window_size=3` 句 + `overlap=1` 句,优于固定大小分块
- 对长文档:取摘要 embed(而非全文),或分段后取均值/首段
- 层级索引:document-level(摘要 embed)+ section-level(主题 embed)+ chunk-level(细节 embed)

**优化建议**:
1. **短期(低成本)**:存稿时用 LLM 生成"章摘要"(200 字内),对摘要 embed 而非全文——一章一向量,维度不超限,召回语义对齐"这章讲了什么"
2. **中期**:补分段 embed——每章按语义分块,每块一向量,召回时返回"章 + 块位置",主编可定位到具体段落
3. 这与 B 的 Graph RAG 共享同一向量底座——章向量服务于"找相关章",命题向量服务于"找相关事实",分工明确

### 4.3 Hybrid Search 的中文分词可走外部分词预处理

**现状**:E §3.6 标注"SurrealDB 内置分词对中文支持需实测"——这是 E 枢纽**最高不确定项**。

**行业实践**:SurrealDB 的内置 tokenizer(`blank`/`class`/`punct`)对中文确实有限——中文无空格,`blank` 分不开。常见解法是 `ngram(1,2)` filter 做子串匹配,但召回质量一般。

**优化建议**:
1. **短期**:不依赖 SurrealDB 原生全文索引,改在应用层用 jieba/pkuseg 预分词,把分词结果存为 `chapter.tokens` 字段(array<string>),在应用层做 BM25 打分——与 RRF 融合在 store 层完成
2. **中期**:若 SurrealDB 后续版本支持中文分词 analyzer,再迁移到原生全文索引
3. 这与"100% SurrealDB 原生"目标有冲突,但**可用性优先于纯粹性**——中文分词是硬需求,不能用"不确定"卡住整个 Hybrid Search

### 4.4 预聚合视图(方案 B)可利用 DEFINE TABLE AS SELECT

**SurrealDB 官方文档确认**:`DEFINE TABLE ... AS SELECT ...` 物化视图在 3.x 可用。

**现状**:E §3.4 方案 B 标注"需人工确认 3.1.5 物化视图语法/触发时机"。

**优化建议**:可从官方文档确认语法后直接落地方案 B——物化视图比每次聚合 SELECT 更优(DB 自动维护,免每次计算)。先在测试库验证 `DEFINE TABLE word_stats AS SELECT count() AS chapter_count, math::sum(qc_word_count) AS word_count FROM chapter GROUP ALL` 的维护时机,确认后落地。

## 5. 枢纽 F(安全加固)—— 认证可深化

### 5.1 Token 认证应采用分层依赖链

**行业实践(2026)**:FastAPI Authentication Best Practices 推荐分层依赖链:
1. 低层:提取并验证 token
2. 中层:从验证后的 claims 加载用户
3. 高层:基于用户做权限检查

**现状**:F §3.1 的 `require_token` 是单层——只验证 token 存在且匹配。

**优化建议**:即便本地单用户,也建议分层:
```python
def get_current_user(token: str = Depends(oauth2_scheme)) -> User:
    # 低层:验证 token
    ...
def require_write(user: User = Depends(get_current_user)) -> User:
    # 高层:检查写权限
    if not user.can_write:
        raise HTTPException(403)
    return user
```
这为未来多用户/多角色预留接口,且让 P02 的"写授权统一"有自然的挂载点。

### 5.2 缺少按端点限流(仅有全局日上限)

**现状**:F §3.8 的成本熔断是"全局日调用上限 + 并发信号量"——粒度粗。

**行业实践**:按端点限流是标准实践——`/render`(贵)和 `/health`(免费)应有不同限额。

**优化建议**:给 LLM 相关端点(`/chat/*`、`/render`、`/ingest`)设独立的"每会话每分钟上限"(如 10 次/分钟),与全局日上限互补。`/health`、`/quality`(读缓存)不限流。

### 5.3 DEFINE ACCESS 的 RECORD 类型已确认可用

**SurrealDB 官方文档确认**:`DEFINE ACCESS ... TYPE RECORD` 支持 SIGNUP/SIGNIN/DURATION,`crypto::argon2::generate`/`compare` 可用,`$auth.id` 在 PERMISSIONS 中可用。

**优化建议**:F §3.10 的"需人工确认 surql 语法"可降级——核心语法已确认。但 `PERMISSIONS FOR select, update, delete WHERE owner = $auth.id` 的行级权限需要各表加 `owner` 字段,工作量确实大,保持"中期、仅暴露场景"的定位不变。

## 6. 枢纽 G(可靠性与代码质量)—— 可补熔断器模式

### 6.1 LLM 调用缺少 Circuit Breaker 模式

**现状**:G §3.1 的流式重试是"重试 3 次"——但若上游持续 5xx(如 doubao 服务降级),每条请求都重试 3 次会放大负载。

**行业实践**:Circuit Breaker(熔断器)模式——连续失败 N 次后"熔断"(快速失败,不再请求上游),等待冷却期后"半开"(试探一次),成功则"闭合"(恢复正常)。与重试互补:重试处理瞬时抖动,熔断器处理持续故障。

**优化建议**:在 `llm.py` 补一个轻量熔断器(可只用计数器 + 时间窗,不引依赖):
```python
class CircuitBreaker:
    def __init__(self, threshold=5, cooldown=60):
        self.failures = 0; self.opened_at = None
        self.threshold = threshold; self.cooldown = cooldown
    def allow(self) -> bool:
        if self.opened_at and time.time() - self.opened_at < self.cooldown:
            return False  # 熔断中
        return True
    def record_failure(self):
        self.failures += 1
        if self.failures >= self.threshold:
            self.opened_at = time.time()
    def record_success(self):
        self.failures = 0; self.opened_at = None
```
熔断时返回友好错误("LLM 服务暂不可用,已熔断")而非反复重试。这对长篇连载的无人值守场景特别重要——作者可能挂着跑一夜,不该让持续失败的重试刷爆账单。

### 6.2 P06 事务的"单条多语句"退路应明确为首选

**现状**:G §3.3 标注"SDK 跨调用事务语义需人工确认",退路是"单条多语句 surql"。

**SurrealDB 官方文档确认**:`BEGIN TRANSACTION; ... COMMIT TRANSACTION;` 可在单次 `db.query()` 内执行——SurrealDB 的事务是 query 级的,不依赖客户端维持会话状态。

**优化建议**:将"单条多语句"从退路升为**首选**——`db.query("BEGIN TRANSACTION; DELETE...; CREATE...; COMMIT TRANSACTION;")` 一次调用完成,无需上下文管理器。G 的 `transaction()` 上下文管理器可改为"拼字符串"模式:在 `__enter__` 开始收集 surql,`__exit__` 一次性提交。这消除了"SDK 跨调用事务"的不确定性。

### 6.3 P34(QC 误报)的修法缺口应补

**现状**:G §7 诚实标注 P34"未展开具体修法"。

**优化建议**:G 已给出方向(排比按词/句法边界、破折号按千字密度),建议补一个独立 T13 任务:
- 排比:`critique.py:39` 的 `s[:3]` 改为取首个标点前的词(用 `re.split(r'[，。！？；]', s)[0][:4]`)

## 7. 枢纽 H(前端与生产化)—— 可提前引入 React Query

### 7.1 useAsync 是过渡方案,React Query 应更早引入

**现状**:H §A2(c) 的 `useAsync` 是自研轻量 hook,标注"React Query 类缓存留作后续"。

**行业实践(2026)**:React Query(TanStack Query)已成为 React 数据获取的事实标准——自动缓存、去重、后台刷新、乐观更新。自研 useAsync 只解决了 loading/error 三态,缺缓存去重(同一数据多次请求会重复 fetch)和后台刷新(数据可能过时)。

**优化建议**:
1. **短期**:useAsync 作为最小可行方案落地(解决"失败可见")
2. **尽早(第一阶段末)**:引入 React Query 替换 useAsync——它体积小(~13KB gzipped),与现有架构兼容,且解决 P04(数据获取无缓存去重)的性能问题
3. 这同时解决了 E 枢纽 P04 的"前端数据获取无缓存"和 H 的"loading/error 三态"——一个库两个枢纽的收益

### 7.2 Docker compose 缺少 health check

**现状**:H §C1 的 compose 用 `depends_on: [surreal]`——但 `depends_on` 只保证启动顺序,不保证服务就绪。

**行业实践**:Docker compose 的 `depends_on` + `condition: service_healthy` + healthcheck 是标准模式:

```yaml
backend:
  depends_on:
    surreal:
      condition: service_healthy
  ...
surreal:
  healthcheck:
    test: ["CMD", "curl", "-f", "http://localhost:8001/health"]
    interval: 5s
    timeout: 3s
    retries: 10
```

**优化建议**:给 surreal 和 backend 都加 healthcheck,backend `depends_on` surreal 的 healthy 条件。否则 backend 可能在 surreal 未就绪时启动,导致首次连接失败。

### 7.3 VITE_API_BASE 构建期注入的局限应明确标注替代方案

**现状**:H §A2 用 `import.meta.env.VITE_API_BASE`——这是**构建期**注入,同一份镜像不能运行期换 base。

**优化建议**:在方案中明确补一个"运行期注入"替代方案——在 `index.html` 注入 `<script>window.__ENV__ = { API_BASE: '...' }</script>`,由 nginx/容器启动脚本动态填充。这样一份镜像可部署到不同环境(开发/ staging/生产),只需改启动脚本不改镜像。这对"交付他人"场景(不同人有不同后端地址)特别重要。

## 8. 跨枢纽优化(全局视角)

### 8.1 集成测试策略缺失

**现状**:每枢纽有单元测试计划,但**无跨枢纽集成测试**——如"B 落地 Event 图边 + C 落地 ingest 幂等"后,端到端"写一章 → ingest → see_event → 限知渲染"链路是否正确?

**优化建议**:补一个跨枢纽集成测试套件(`tests/test_integration_hub.py`):
```python
def test_full_pipeline_after_hub_b_and_c(store):
    """端到端:写章 → ingest → see_event → 限知渲染,验证 B+C 落地后链路正确"""
    # 1. 建角色 + 事件(带 participants/effects,验证 B)
    # 2. save_chapter → ingest(验证 C 幂等)
    # 3. see_event → 在场者获知,不在场者不获知(验证 B+C)
    # 4. build_render_prompt → focalizer 帧不含帧外私密(验证限知不变量)
```
这个测试在 B 和 C 各自落地后都应保持绿——它是"枢纽间不互破"的护栏。

### 8.2 性能基准未建立

**现状**:E 枢纽有 EXPLAIN 验证计划,但无"改动前后的量化性能基准"——如 `facts_at` 在 500 命题时全表扫 vs 索引扫的耗时差。

**优化建议**:在 E 落地前,先建一个性能基准脚本(`tools/bench.py`):造 500 命题 + 100 知识边 + 50 事件的测试数据,测量 `facts_at`/`events_at`/`knowledge`/`semantic_recall` 的 p50/p95 耗时。E 落地后对比,量化收益。这也为后续性能回归提供基线。

### 8.3 "需人工确认"项应集中为决策清单

**现状**:8 份方案散布大量"需人工确认"项——如 D 的 `cover_action`/`done` 语义、F 的部署意图、B 的删角色级联策略、E 的中文分词。

**优化建议**:在总纲(00)补一个"需人工确认决策清单"附录,按"阻塞哪个枢纽"排序:
- **阻塞 B**:删角色级联 vs 软删策略(产品意图)
- **阻塞 C**:`test_ingest.py` 是否依赖 `_ensure_char` 自动建角色(测试迁移)
- **阻塞 D**:`cover_action`/`done` 是未完成还是废弃(产品决策)
- **阻塞 E**:SurrealDB 中文分词可用性(技术验证)
- **阻塞 F**:部署意图是否暴露(决定整套优先级)
- **阻塞 G**:SurrealDB SDK 跨调用事务(技术验证)→ **本报告已确认可用单条多语句,可降级**

每项标"阻塞阶段 + 决策人 + 建议决策",集中管理比散在各方案里更高效。

### 8.4 枢纽间"软重叠"的合并执行

**现状**:多处标注"软重叠需协调":

## 10. 结论

**方案的"骨架"不需要改**——8 枢纽的聚合、依赖图、TDD 计划、验收标准都是扎实的。优化空间集中在:

1. **与 2026 行业实践的差距**:Graph RAG 应加 RRF 融合 + 重排序;LLM 调用应加熔断器;前端应更早引入 React Query
2. **SurrealDB 3.x 新特性的未利用**:ASYNC/RETRY 事件、单条多语句事务、物化视图——这些在官方文档已确认可用,可降级多个"需人工确认"
3. **跨枢纽协同**:事务优先级应提前到 C 之前;Graph RAG 与 Hybrid Search 应合并;软重叠项应同批执行;集成测试与性能基准应补建

这些优化不改变方案的方向,只让它**更精确、更稳健、更贴近 2026 的生产最佳实践**。
