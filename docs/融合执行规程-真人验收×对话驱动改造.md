# 融合执行规程：真人验收 × 对话驱动改造

> **问题**：验证和「禁表单直填」改造能否合在一起做？  
> **答案**：**能，而且应当合在一起。** 分开做会测到假路径（手填凑合），改造也会脱离真作者场景。  
> **一句话**：用**一本隔离新书**当压力场——代理模拟作者（对话 + **自己点批准/接受**）；每撞到表单/写不进就 **STOP→修→回归→从断点续写**。人类不点审批按钮。

关联文档：

- 验收总则：`docs/真人作者全功能验收测试方案-v2.md`（含 P8）  
- 改造决策：`设计文档/2026-07-22-对话驱动写入-禁表单直填-决策与改造方案.md`  
- 边界：`scribe3/AGENTIC_BOUNDARY_DECISION.md`

---

## 1. 融合原则

| # | 原则 |
|---|------|
| M1 | **一条主线**：只跑真人旅程；改造不是并行项目，是旅程里的「修路」 |
| M2 | **不测假路径**：禁止用表单/API 直写「先把书填满再改产品」 |
| M3 | **缺陷即工单**：撞到手填 = 立刻记 F-xx / 新 ID，优先级 P0/P1，进入当轮修复 |
| M4 | **最小可续写修复**：只修到「本意图能对话+批准完成」，不借机大重构无关模块 |
| M5 | **修完必须同路径回归**：同一句作者意图再走一遍，绿了才进入下一旅程步骤 |
| M6 | **证据一体**：同一 `artifacts/e2e-YYYYMMDD-<work_id>/` 里既有章节评分，也有改造记录 |
| M7 | **决策点击也由代理做**：浏览器「批准 / 仍要批准 / 接受 / 用此版」必须 Playwright 真实点击，不得留给人类日常点 |

---

## 2. 双轨角色（可一人分饰）

| 角色 | 职责 | 禁止 |
|------|------|------|
| **作者模拟（代理）** | 对话意图、看板仪式、**点批准/接受**、读稿评分 | 业务表单；把批准/接受甩给人类 |
| **修路工（代理）** | STOP 后改代码、补工具、跑测 | 用 REST 替「作者」灌验收书冒充 UI 完成 |

人类（你）只做：设 `/goal`、看 status、处理真阻塞（密钥/机器宕机）。**不做**日常审批员。

同一 agent 可交替，须标明角色；**批准/接受必须真实 UI 点击**（§3.1），禁止默认用 `api.aiRunApproval` / `saveChapter` 静默代替（后门不计路径通过）。

---

## 3. 主循环（唯一循环）

```
┌─────────────────────────────────────────────────────────┐
│  按 v2 旅程走下一步作者意图                               │
│  （建书→北极星→卷章骨架→设定→章阶段→正文→看板→返工…）      │
└────────────────────────┬────────────────────────────────┘
                         ▼
              能否 对话→提案→批准 完成？
                    │              │
                   是             否（表单墙 / 无工具 / 无审批卡）
                    │              ▼
                    │         STOP · 记 05-gap-research-log
                    │              ▼
                    │         定最小修复（对齐改造方案 PR-A/B/C…）
                    │              ▼
                    │         实现 + 定向单测/组件测
                    │              ▼
                    │         同意图真机回归（必须绿）
                    │              ▼
                    └─────────► 记 journal · 继续下一步
                         ▼
              章末/日末：评分卡 + F 矩阵勾选
```

**没有第二条循环。** 不存在「先改完所有表单再验收」或「先手填验收再回头改」。

### 3.1 浏览器决策点击（强制由代理完成）

产品上作者要「批 / 选」；**执行验收的代理 = 模拟作者**，因此这些按钮**必须由代理点**，不能写在「请用户点击」里收工。

| UI 决策 | 典型选择器 / 文案 | 代理动作 |
|---------|-------------------|----------|
| Hermes 写入审批 | `aria-label="批准"` / 按钮「批准」 | 出现 pending 后点击批准 |
| 过期二次确认 | `data-testid="run-approve-stale"` | 策略：默认点「仍要批准」或按 G 工单策略拒绝 |
| 正文提案 | 按钮「接受」（DraftCard） | 流式结束后点击接受 |
| 多候选 | 按钮「用此版」 | 选第 1 个或按评分策略 |
| 弃用 | 「弃用」「全弃」 | 仅质量不合格时用 |

**实现手段（优先序）**：

1. **Playwright**（本仓已有 `scribe3/web/e2e/lib.mjs`、`pw.mjs`、`full_journey.mjs`）— 验收主路径  
2. 补强 helper（建议落 `scribe3/web/e2e/author_decisions.mjs`）：

```js
// 伪代码契约
export async function approveAllPending(page) {
  // 循环：getByRole('button', { name: '批准' }) → click，直到无 pending
}
export async function acceptDraftProposal(page) {
  // wait 提案卡非「书写中」→ getByRole('button', { name: '接受' }) → click
}
export async function chiefSay(page, text) {
  // 填主编输入框 → Enter → 等待流结束 → approveAllPending / acceptDraftProposal
}
```

3. Goal / 会话内：代理用终端跑 Playwright 脚本，或 patchright/playwright 单步驱动已启动的前端（`E2E_BASE`）

**硬规则**：

- 旅程步骤若停在「等批准/等接受」而代理不点 → **步骤失败**，不是「等人类」  
- 点不到（无 testid / 被盖住）→ STOP → 修 UI 可点性（加 `data-testid`）→ 回归  
- 禁止：只调 `POST .../approval` 或直接 `saveChapter` 算「作者接受」通过（那是后门，不计融合成功）

**与 Goal 文案对齐的一句铁律**（写入 `/goal`）：

> 浏览器内所有「批准写入 / 接受提案 / 用此版」必须由执行代理通过 Playwright 真实点击完成；不得要求人类点击，不得用 API 静默代替。

## 4. 旅程阶段 × 改造触发点（预置雷区）

按 v2 顺序写；每阶段**预期会撞**的表单缺陷（优先修这些）：

| 旅程阶段 | 作者意图（只说话） | 极可能撞到的缺陷 | 最小修复落点 |
|----------|-------------------|------------------|--------------|
| D0 建书+北极星 | 「这本书读者感受…红线…请写入」 | F-01 北极星表单 | `s3_set_intent` + 提案卡 / 暂时 CTA→Run |
| D0 卷章骨架 | 「建三卷十章，每章一句 synopsis」 | F-02/03/04 卷章表单、卡片墙手改 | 结构写工具 + 只读墙 |
| D1 设定 | 「登记主角…关系…规则…」 | F-10～15 设定表单 | 只读 Codex + 已有 s3_add_* 审批体验打通 |
| D1 第1章阶段 | 「大纲/节拍/演绎请写入」 | F-05 阶段 textarea | `s3_patch_chapter_plan` 或阶段提案 |
| D1 正文 | 「写本章」 | 一般已有提案卡 | 修路由/上下文即可 |
| 连写章前仪式 | 看板只读梳理 | 看板点编辑又进表单 | 看板改为只读+对话 CTA |
| 返工 R1 | 「把某设定改成…并列出受影响章」 | 改设定走表单 | 对话 patch 工具 + 影响列表 |

**策略**：不预先改完全部 F-xx，而是 **写到哪修到哪**；但 D0/D1 的 P0 不绿，禁止进入「灌 10 章正文」。

## 5. STOP 工单格式（融合用）

写入 `artifacts/.../05-gap-research-log.md`：

```markdown
## G-00N · <短标题>
- 旅程步骤：STEP x-yy / 第 N 章前
- 作者原话：
- 阻断类型：□ 只有表单 □ 对话无写工具 □ 有工具无审批UI □ 批了不落库 □ 其它
- 对应 F-ID：（或 NEW）
- 期望路径：对话 → 提案 → 批准 → 只读回读
- 最小修复范围：（文件/工具名）
- 非目标：（本轮不做）
- 实现提交：
- 回归：同原话再走 □ 通过
- 续写点：
```

## 6. 每日节奏（融合版）

| 时段 | 作者轨 | 修路轨 |
|------|--------|--------|
| 开场 30min | 环境、打开书、回顾昨日 STOP | 确认 HEAD 服务非陈旧进程 |
| 主时段 | 推进旅程直到撞墙或完成 1 章 | — |
| 撞墙 | 停笔，写 G-xxx | 立刻修最小集 |
| 回归 | 用同一意图验收 | 绿 → 作者续写 |
| 收工 | 评分卡、F 矩阵、手填次数必须为 0 | 列次日可能雷区 |

**手填次数**：journal 里 `form_fill_count` 必须恒为 **0**；一旦 >0 本日记不合格。

---

## 7. 范围控制（防止修路吞掉验收）

每张 G 工单遵守：

1. **只打通当前作者意图**（例如「写入北极星三条」）  
2. 可顺手：只读 CTA、隐藏该字段的 input  
3. 不可顺手：无关模块重构、设计系统大改、十维评估大修  
4. 若最小修复 > ~0.5–1 人日：记 P0，当日可 **暂停连写**，但不得改用手填推进字数  

批量预修仅允许：

- PR-A 只读门面（一次做完，减少反复撞墙）  
- 统一 WriteProposal 卡壳子  

其余仍 **按旅程触发**。

## 8. 建议的启动序列（第一周）

```
Day 0 上午  PR-A 骨架：创作区业务字段默认只读 +「让主编处理」CTA
            （未通的写入会诚实失败，而不是手填成功——暴露真缺口）
Day 0 下午  建隔离书，纯对话设北极星 → 撞则 G-001 修到通
Day 1       对话建卷章 synopsis → 通才进入设定
Day 1–2     对话登记最小圣经 + 第1章黄金闭环（阶段+正文）
Day 2+      连写 + 章前看板；返工剧本插入时继续按 G 修
```

**第一优先合并提交类型**：

1. `fix(ui): read-only creative surfaces + chief CTA`（PR-A）  
2. 随后每个 G-xxx 一个小提交：`fix(dialog-write): …`  
3. 验收证据目录持续追加，不另开「改造项目文档」当主线

## 9. 融合成功标准

| 项 | 标准 |
|----|------|
| 路径 | 从零到至少第 1 章成稿：**0 次业务表单**；**0 次人类点批准/接受** |
| 证据 | journal：`form_fill_count=0`、`human_click_approve_count=0`；G 工单有回归 |
| 改造 | F-01～F-05 与本次旅程撞到的 F-1x 均 closed 或有明确阻塞说明 |
| 质量 | v2 章评分与看板仪式仍执行，不因改造省略 |
| 产品 | 心智：说 / 批 / 选——批与选由**代理 Playwright** 执行 |

---

## 10. 何时允许「暂停故事、只修路」

仅当：

- 连续 2 个 P0 阻断主路径，或  
- 缺少公共设施（无提案卡组件、无审批通道）导致每个意图都重复造轮子  

暂停期间仍 **不得** 用手填灌故事进度；恢复后从原 STEP 续。

---

## 11. 执行口令（给实施者）

```
本轮是「验收×改造」融合，不是两件事。
我是作者模拟时：只对话；批准/接受必须我用 Playwright 点 UI；绝不业务表单；绝不叫人类点按钮。
撞墙时：STOP → G工单 → 最小修 → 同句回归 → 续写。
我是修路工时：禁止 API/表单替作者灌验收书。
证据写在同一 artifacts/e2e-… 目录。
手填次数=0；人类点击审批次数=0。
```

**结论**：可以融，而且应用本规程作为唯一执行方式——**验证提供场景与优先级，改造保证测到的是真产品。**
