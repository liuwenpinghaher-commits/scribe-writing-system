## 一句话结论

本体论改造**只完成了一半**:「世界层(Entity/Fact/Event)+认知层(KnowledgeEdge/project_frame)」这两层真的落地了、也真的在**生成前**物理接管了限知视角的 prompt 组装(不是事后判官),这是一个可验证的真实工程成果;但设计文档承诺的「叙述层 sjuzhet 渲染管线」在 5 天后被整体推翻删除,「戏剧目的层(Goal/Throughline/CausalLink)」从未建过一张表,而且本体自己的核心因果机制——「看见即知道」(`see_event`)——从写下第一行代码起就从未被任何生产路径调用过,知识边的真正来源是另一条完全独立、绕开了本体设计的 LLM 抽取管线。结果是:本体现在是一个**「渲染前的限知安检门」**,而不是设计文档里说的「驱动生成本身的引擎」;真正驱动"写什么"的仍是章前简报(brief.py)+ 大纲/节拍(outline)+ 编辑对话(chat_write)拼出来的一次性长 prompt,本体只负责在这个 prompt 拼出来之后,把不该被这个视角看见的事实物理挖掉。

## 三条最重要发现

1. **限知渲染是本体论改造里唯一被证实真正生效的"引擎级"接入点**:`_frame_block`/`_editor_system` 在写作 prompt 组装时直接调用 `project_frame`(`scribe3/app.py:1204-1216`、`1643-1656`,`scribe3/knowledge.py:24-40`),把 focalizer 帧外的私密事实从物理上排除在 prompt 之外。但同一份设计文档承诺的另外两个"结构性不会犯"的老大难——因果完整(`causal_complete`)和戏剧反讽(`dramatic_irony`)——从未进入生成前的 prompt,只在 `/causal`、`POST /tension-check`、`/post-check`、6 小时体检 cron 这些**生成后**的检测端点里跑(`scribe3/app.py:327`、`2154-2166`、`scribe3/health.py:10,29`)。本体对"该写什么、该不该继续这条因果线"没有发言权,只对"能不能说出已经写好的某句话"有物理否决权。

2. **本体自己的核心因果机制从未被真正跑通**。创始设计文档(`docs/superpowers/plans/2026-06-22-scribe-故事本体v2-全局重构方案.md`)反复把"看见即知道"(Event 落库时给在场 witness 自动发 KnowledgeEdge)当作认知层的范式支柱,代码里也确实实现了 `see_event`/`witnesses_of`(`scribe3/knowledge.py:52-65`)。但全仓搜索显示,`see_event` 只在定义处和一句注释里出现(`scribe3/store.py:541` 的注释"供 see_event 给在场者发知识边"),**没有任何生产代码调用它**;而 `ingest.py` 里真正写 `event` 表的 `apply_delta`(`scribe3/ingest.py:296-301`)从不填 `effects` 字段(恒为空列表),知识边(`knows`)全部来自另一条独立的、LLM 驱动的"who learned what / who did what seen by whom"抽取(`scribe3/ingest.py:120-168`)。也就是说 SurrealDB 里 `event` 表和 `knows` 边是两条平行生长、互不驱动的数据,本体设计里"事件→效果→知识"的因果闭环在真库上从来没有真正成立过一次。

3. **同一天(2026-06-22)出现了一次未被后续文档正面处理的路线反转**:先有 `docs/superpowers/plans/2026-06-22-scribe-角色知识边界与单一真相源-改造文档.md`(commit `e09e8df` 等)明确论证"**不做扣留式知识隔离**,改用标记式(⟨私密·他人不知⟩)以保全知说书人嗓音";几小时后 `55c424f`/`ed4b1a2` 推出"故事本体 v2",核心正是**物理扣留**(`project_frame` 投影,帧外事实物理不出现)。两份文档都在当天进入主线,但没有一份后续文档正面对账"为什么早上否决的方案晚上又做了"。而且物理隔离本身此后被反复"补漏"而非一次性生效——`c1299b3`(06-28)、`51e5a5d`(06-28)、`a370899`(06-28)、`9c7752e`(06-28)、`67df71a`(07-04)五次独立提交都是在修"某个新发现的注入点仍在明文吐私密"——说明限知隔离不是设计文档承诺的"单一渲染只读关卡",而是散布在 `_editor_system`/MCP 召回工具/`_codex_block`/`s3_list_factions` 等至少五个独立注入点上的**手工补丁集合**,任何新开一个注入点都要重新记得挂 `project_frame`,机制本身不自动保证。

## 二、每一步为什么这么改?设计依据站得住吗?

### 2.1 起点:老道泄露事件 → scribe2"标记式"知识边界(2026-06-22 上午)

`docs/superpowers/plans/2026-06-22-scribe-角色知识边界与单一真相源-改造文档.md` 的论证链:
- **现象**(有实证):生成稿里配角"老道"说出了只有主角和读者才知道的私密动机,根因是 `build_writing_context` 把所有角色的私密内核拍进同一个共享 prompt(文档 §0)。
- **方案选型**(有对比表,文档 §2):在"多 agent 各写 prose / 意图 agent + 单叙述者 / 全 live 角色演绎 / 知识标记注入(选中)"四个选项里,选了成本最低的"标记不扣留",理由是"乱世铜炉是全知说书人嗓音,统一声音 > 知识边界的完美"。
- **这个论证站得住**:它是针对"全知说书人"这一具体声音定位做的工艺判断,不是本体论层面的判断,而且写明了非目标(§8:"不做扣留式知识隔离,会损全知说书嗓音")。

**站不住的地方**:这个论证在同一天被推翻,而推翻它的后续文档没有引用它、没有对账"全知说书人声音"这个约束后来是怎么被处理的。查 `设计文档/`及 `docs/superpowers/plans/` 全文,未查到任何后续文档正面回答"为什么放弃标记式改扣留式,全知说书人嗓音怎么办"。间接证据是 `scribe3/app.py:1216`(`set_label = "【焦点者(...)帧内可见设定(限知基座,帧外私密已屏蔽)】"`)和 `_editor_system` 全知分支并存(`app.py:1201` 的 `if focalizer:` 分支 vs `else:` 分支)——现状是"两套并存、按 `focalizer` 参数是否为空切换",相当于把"标记式(全知)"和"扣留式(限知)"都保留、变成两种可选模式,而不是文档争论的"二选一"。这个并存本身是合理的工程解(不同章可以是不同视角),但它不是原文档任何一方论证出来的结论,是事后自然长成的样子。

### 2.2 故事本体 v2(2026-06-22 下午,`55c424f`/`ed4b1a2`)

`docs/superpowers/plans/2026-06-22-scribe-故事本体v2-全局重构方案.md` 的论证依据是"四路并行学术级调研"(计算叙事学/故事引擎/时间认知KR/工具架构),核心论断:把"实体清单+章节流"重构为"事件本体+双时间轴+三知识帧",让 POV 泄露/设定漂移/复发从"事后闸救"变成"结构上不会犯"(文档 §0、§3)。

**对账**:
- "POV 泄露结构性消失"——**部分成立**。`project_frame` 确实让"焦点者帧外事实进不了限知 prompt"成为可验证的代码事实(`ed4b1a2` commit message 里给出的 A/B 复刻实验:全知扁平注入 `含'治眼'=True`,按 focalizer 投影后 `含'治眼'=False`)。但发现 3 已证明,这个"结构性"此后又被打了至少 5 个独立补丁(`c1299b3`/`51e5a5d`/`a370899`/`9c7752e`/`67df71a`),说明"结构性消失"更准确的表述是"**每新增一个 prompt 拼接点都要记得手动接 project_frame,接了才不犯,不接会犯**"——不是编译期/schema 级强制,是约定,且这个约定在实践中确实被违反过多次。这正是设计文档自己在 §3 引用的"Inform 教训"(`"渲染只读"必须代码强制,不能靠约定,大系统里约定必破`,`docs/superpowers/plans/2026-06-22-scribe-故事本体v2-全局重构方案.md:135`)——本体论改造的执行**恰恰重蹈了它自己在设计时明确警告要避免的覆辙**。
- "设定漂移不可能"——**未被验证也未被证伪**:未查到任何测试或事故记录专门验证"Fact 单一真相源"消除了设定漂移;`设计文档/2026-07-03-全系统架构与业务闭环审计.md` 里指出 `entity_link` 字段"从未写入"(文档中 ER 图 `record entity_link "026 option<record<character|place>> 从未写入"`,第131行),说明 Fact 与 Entity 之间设计好的强类型关联实际上有一部分从未被使用,单一真相源在结构上留了缺口。
- "一致性/伏笔变成可跑的查询"——**部分成立**:`causal_complete`(结构查询)、`promise_window_state`(结构查询)确实做成了确定性函数,但只在检测端点跑(问题四详述),不是文档设想的"生成时 schema 校验,不靠事后 critique"(`同文档:101`)。这条承诺**没有兑现**:`motivated_by_goal`/`causal_in` 目前是 ingest 时由 LLM 抽取后**写入**、检测时才**读取校验**,不是生成前的硬约束。

### 2.3 render.py 被整体删除(2026-06-27,`03d354f`)

commit message:"写作改走主编对话, 删除 /render 直渲管线……为统合写作台交互优化做基线"(`03d354f`)。这是本体论叙述层(sjuzhet)承诺("渲染层只读投影 fabula∩知识帧")在 5 天内被推翻的关键节点。**依据是否站得住**:commit message 本身只给了"改走主编对话"这个产品决策理由,未查到配套的设计文档论证"为什么放弃 render.py 这条本体驱动的渲染路径,改用 app.py 里手写的长 prompt 拼接"。这是本次审计中**证据链最薄的一次架构反转**——影响了后续全部生成逻辑走向(`_editor_write_system`/`chat_write` 而非 `render.py:build_render_prompt`),但没有留下等重量级的设计依据文档。

### 2.4 角色知识边界"P2-15 死字段"体检(2026-07-04,`0f1bb71`)

`scribe3/ontology.py:51`(`KnowledgeEdge.certainty`)、`:52-53`、`:66-67`(`Event.preconditions`)的代码注释直接写明"疑似死(P2-15):write→read roundtrip……但无行为消费方;保留待确认"。这是仓库**自己承认**设计文档承诺的字段(certainty 支持 KD45 不强制 0/1、preconditions 支持 STRIPS 前置条件校验)有 write 但无真正消费方——即读得到、但没有任何函数拿它做过判断。这一条不需要审计员推断,是代码里的自我记录,可信度最高。

## 四、本体在写作主链路里到底是引擎还是账本

**证据表**(按"谁在 prompt 组装时消费""谁只在检测端点消费"分类):

| 本体查询/结构 | 生成前(prompt 组装)消费方 | 生成后(检测)消费方 | 判定 |
|---|---|---|---|
| `project_frame` | `_frame_block`(`app.py:1637-1656`,被 `chat_write`/`draft` 等写作端点在 `1724`/`1949` 行调用注入 instructions)、`_editor_system` 限知分支(`app.py:1201-1216`) | `GET /frame`(`app.py:311-312`,只读展示端点) | **引擎**(生成前物理裁剪 prompt 内容) |
| `dramatic_irony` | 未查到任何生成前调用 | `GET /irony`(`app.py:316-317`)、`brief.tension_deterministic`(`brief.py:87-98`)——而后者只被 `POST /tension-check`(`app.py:2154-2166`,函数注释明写"读已存正文,不落库")调用 | **账本**(纯事后信息差盘点,不影响已生成内容) |
| `causal_complete` | 未查到任何生成前调用 | `GET /causal`(`app.py:327`)、`health.py:10,29`(6h 体检 cron)、`store.py:1343-1349`(`_compute_chapter_caches`,存稿后算质量快照) | **账本** |
| `find_leaks` | 未查到任何生成前调用(它天然是"扫已生成散文"的函数,签名要求 `prose` 参数) | `save_chapter` 后置软校验(`app.py:2308-2314`)、`/check`(`2368-2376`)、`/post-check`(`2443-2453`)、`/draft-check`(`2702-2716`) | **账本**(第二道兜底,如设计所承认——`verify.py:1-6` docstring 自陈"这是第二道 POV 修订 pass") |
| `craft_rule`/`purple_patterns` | `_editor_system`/`_editor_write_system` 生成时注入(`app.py:1730`、`1954`,`build_craft_block`) **同时** | `/post-check`/`/check` 检测时也用(`app.py:2381`、`2487`) | **双重身份**——craft_rule 是本次审计里唯一真正"既驱动生成又用于事后检测"的结构 |
| `assemble_chapter_brief`/`assemble_injection`(Fact 全知注入) | `_editor_write_system`(`app.py:1346`)生成时组装简报注入 instructions | `GET /chapter-brief`(`app.py:374-378`)只读展示 | **引擎**(但这条链路里的"Fact"只是全知设定库,不含 Event/因果推理) |
| `char_anchors`(弧光锚)+`arc_directive` | `assemble_chapter_brief`(`brief.py:253-255`)生成前组装进简报 | 同上只读展示 | **引擎** |
| `promise_directives`/`promise_window_state` | `assemble_chapter_brief`(`brief.py:258`)生成前组装"伏笔本章指令" | `/promises`、`/quality`、`/promises/ledger` 检测/展示 | **双重身份**,但生成前只给"提醒文案",不像 project_frame 那样物理裁剪内容 |

**结论**(直接回答问题四):**本体(World/Fact/Event/知识帧)在写作主链路里,严格意义上只有 `project_frame`(限知帧)和 `char_anchors`/`assemble_chapter_brief`(弧光锚+简报)两类结构真正扮演"驱动生成"的引擎角色**——它们在 prompt 拼出来之前就已经决定了"哪些事实能出现""这一章弧光该往哪移"。而 `Event.causal_in`/`motivated_by_goal`(因果本体的核心)、`dramatic_irony`(戏剧反讽本体的核心)、`find_leaks`(POV 泄露判官)全部只在生成**之后**的检测端点/cron 里跑,**从未影响过下一次生成会写出什么**——它们是账本,不是引擎。换句话说:本体在"角色不该说什么"上是引擎(结构性否决权),在"这一章该发生什么因果、该埋下什么反讽"上只是事后记账(没有生成前的建议权或否决权)。

**对这条结论的自我对抗**:是否 `assemble_chapter_brief` 里的伏笔指令/弧光指令已经足够算"驱动生成"?——算,但驱动力很弱:它们是**文案提示**("本章应实质推进或兑现"),模型可以忽略,没有 `causal_complete`/`project_frame` 那种"帧外事实物理进不了 prompt"的结构性强制力。这是引擎强度上的量级差异,不是有无之分,值得在后续 OKR-Loop 设计里明确区分"硬引擎(结构性裁剪)"和"软引擎(文案提示)"两个层级。

## 结语:这个系统到底被改造成了什么?离「用 loop 逻辑朝北极星迭代」还差哪几块拼图?

**系统现在是什么**:一个"限知安检门 + 章前提词器 + 事后质检站"的三段拼接体。安检门(`project_frame`)是本体论改造里唯一真正硬化成结构约束的部分,生成前物理裁剪 prompt;提词器(`assemble_chapter_brief`/`char_anchors`/`craft_rule`)是软性文案提示,生成前注入但不强制;质检站(`find_leaks`/`causal_complete`/`dramatic_irony`/一堆 critique 检测器)全部堆在生成后,靠人或后续 LLM 调用去读检测结果再决定要不要回炉重写。本体论"事件本体驱动叙事生成"的原始野心——让 fabula 里已发生的 Event 决定这一章该讲什么——从未实现;实际驱动"写什么"的是大纲/节拍(outline/beats,人工或 LLM 一次性写就)+ 编辑对话的即兴发挥,Event 表更像是**事后从散文里反向抽取出来存档**的记录,而不是生成前被查询来决定情节的因果图谱。

**生成→检测→回炉环路的通断盘点**(为 OKR-Loop 设计定位缺口):

- **通的环节**:生成(chat_write/doFinal 等写作端点)→检测(`/post-check`/`/tension-check`/`/qc` 汇总 `find_leaks`+`causal_complete`+复读/紫字/AI腔等确定性检测器 + LLM rubric)这一段是接通的,数据结构清楚(`degraded_stages` 字段记录哪些检测器失败,不会假绿——`设计文档/2026-07-04-剩余任务与系统状态交接.md:44` 提到的"P1-5 假绿根治"就是在修这一段的诚实性)。
- **断的环节一:检测结果 → 下一次生成的输入**。`/tension-check`/`/causal`/`/post-check` 产出的违规列表、反讽面、张力评分,目前**没有任何自动回写路径**把它们变成下一章生成 prompt 里的强制指令——它们停留在"返回给前端/调用方看"的层面,靠人(作者或对话中的主编 agent)手动决定要不要因此改写。也就是说"回炉"这一步现在是**人工触发**,不是系统自动闭环。这是 loop 逻辑要补的第一块拼图:需要一个"检测结果→下一章 brief 强制项"的自动转译层,类似 `assemble_chapter_brief` 现在处理伏笔超期的方式(生成硬指令级的"三选一决策"),但要扩展到因果违规、反讽面缺失、craft 检测器命中。
- **断的环节二:本体的因果层(Event/causal_in/motivated_by_goal)不参与"下一步该发生什么"的决策**。因为 `see_event` 死代码、`CausalLink`/`Goal` 未建表,系统里没有一个"给定当前 fabula 状态,查询接下来在因果上合理的候选事件"的函数——这正是 OKR-Loop 如果想做"系统提议下一步情节、而非纯靠人/LLM 临场发挥"所必需的引擎,现在完全不存在,连雏形都没有(design 文档设想的"反应式 beat 选择"从未实现)。
- **断的环节三:北极星(`intent.reader_feeling`/`emotional_arc`/`red_lines`)只作为静态文案块贴进每次 prompt(`_editor_system` 里的"【北极星】"一行,`app.py:1250`附近),没有任何度量函数把"这一章是否让读者更接近这个北极星"量化后反馈进检测或简报——北极星现在是"贴在墙上的标语",不是 loop 里可以被查询、被度量、被用来给生成打分/选择候选稿的目标函数。这是三块拼图里最根本的一块:OKR 的"O"(目标)现在在系统里没有一个可执行的度量算子,更谈不上用它去 close 一个 loop。

一句话收尾:本体论改造把"角色能不能说出某句话"这件事从人工审校变成了代码级物理约束,这是扎实的、可复现的工程成果;但它没有触及"这本书接下来该发生什么、这一章离北极星更近了没有"这两个更难的问题——这两个问题现在仍然完全依赖人和 LLM 的临场判断,本体在这里只是一个记录已发生之事的档案柜,不是决定将发生之事的引擎。这正是 OKR-Loop 设计要补的地方,而不是在现有本体基础上修修补补就能自然长出来的。
