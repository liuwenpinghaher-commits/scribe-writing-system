## 一、在协作回路中的位置与职责

在 Scribe 的协作回路里,**记忆与检索是续航层**——它不是卖点,它是让 AI 在百万字尺度下写得连贯不忘的基础设施。

```
        人(想象 + 意见)
              │
              ▼
    编排层(实现3 Orchestrator)
              │  调用:assembleContext → ContextBundle
              ▼
  ┌─────────────────────────────────────────────┐
  │         记忆与检索(本文,续航层)               │  ← 本文职责范围
  │                                             │
  │  MemoryService ──→ SummaryAgent             │
  │     三层记忆:短期/长期/外部向量库             │
  │     滚动摘要 + 主题锚定 + 分层压缩            │
  │                                             │
  │  RetrievalService ──→ assembleContext        │
  │     E²RAG 双图 + 混合三路召回                │
  │     时间对齐 + token 预算裁剪                │
  └─────────────────────────────────────────────┘
              │  输出:ContextBundle
              ▼
    写作层(实现2 WritingAgent)  → 生成正文
              │  chapter.status → 'done'
              ▼
    记忆更新(updateMemory) ← 回写三层摘要
```

**两个子系统的分工边界:**

| 子系统 | 核心职责 | 不负责 |
|---|---|---|
| **MemoryService** | 章节定稿后将已写内容压缩为三层结构化摘要;维护 `MemoryEntry` 与其向量 | 向量召回、token 裁剪、一致性校验 |
| **RetrievalService** | 写作前从数据库精准召回上下文;拼装 `ContextBundle`;时间对齐过滤;token 裁剪 | 摘要生成、正文写作、伏笔状态推进 |

> **门槛层定位**:连贯性是"写得对"的 table stakes(G7/G8,见设计哲学 §1)。它必须存在、必须在后台隐形运转——**不是系统的卖点,不打扰创作主线**。本文服务的是"不崩"目标,为内核层(品味 / 想象 / 反平庸)腾出空间。

## 二、设计目标与百万字挑战

### 2.1 设计目标

1. **防遗忘**:任何章节生成时,WritingAgent 能获取连贯的历史摘要与相关设定,不因上下文窗口限制而"失忆"。100 万字 ≈ 150–200 万 token,任何现有模型窗口无法容纳全文,必须以"压缩 + 检索"代替"堆上下文"。【已核实 arXiv 2505.12572】
2. **防主题漂移**:长期记忆始终锚定 `AuthorIntent`(北极星),确保百万字后期生成不偏离最初主线。长程生成的主题漂移是已被多篇论文证实的 LLM 结构性问题。【已核实 arXiv 2508.03137 / 2503.23512】
3. **时间正确性**:召回的信息必须"在当前章节 seq 时已存在且尚未失效"——尚未习得的技能不被召回,已死亡角色不以在世状态出现。【已核实 arXiv 2506.05939】
4. **混合精准召回**:叙事文档兼有高频关键词(人名/地名/法术名)和语义近义表述;单靠向量或单靠关键词都会漏检,必须混合。【已核实 arXiv 2503.23512】
5. **token 预算强约束**:`ContextBundle` 必须在预算内装下最高价值内容,超出须按优先级裁剪。
6. **低延迟**:检索 + 拼装 P90 < 800ms,不能成为单次章节生成的瓶颈。
7. **可回流**:人工修订后的新信息能回写进摘要;记忆服务提供 `invalidate_memory` 强制重算。

### 2.2 百万字尺度的具体挑战

| 挑战 | 量化估算(100 万字) | 应对机制 |
|---|---|---|
| 全文 token 不可载入窗口 | ~150–200 万 token | 三层记忆压缩 + 按需检索 |
| 主题漂移 | 长程增量更新漂离主线 | `AuthorIntent` 锚定 + drift_check |
| 摘要体积爆炸 | 全部章摘要 ≈ 230K token | 层级化压缩 + 体积上限 |
| 细节 vs 连贯的取舍 | 增量保细节但连贯性差;分层合并反之 | 混合策略:近期增量 / 远期分层 |
| Segment 数量 | ~2500 段(400 字/段) | pgvector HNSW 索引,不全表扫描 |
| TimelineEvent / EntityRelation | ~1000–20000 条 | 时序区间过滤索引 + GIN 索引 |
| 摘要更新成本 | 500 章 × 多次 SummaryAgent 调用 | 快模型路由 + prefix caching |
| 人工修订回流 | 修改第 N 章影响后续记忆 | `invalidate_memory` + 级联重算 |

> **关键约束**:将已验证的子机制(分层记忆 + 滚动摘要 + 主题锚定 + E²RAG)组合应用于百万字是【设计决策】而非【已核实】实践——几乎没有经验证的百万字端到端最佳实践。本设计须在自建度量下逐步放大字数验证。【已核实 arXiv 2505.12572:>1M 字框架研究极少】

## 三、详细设计

### 3.1 三层记忆架构

```
┌────────────────────────────────────────────────────────────────┐
│                       MemoryService                             │
│                                                                │
│  Layer 1 · 短期记忆 (Short-Term)                               │
│  scope = chapter  |  最近 1–2 章的章末摘要(~200 字)            │
│  来源:每章定稿后 SummaryAgent 生成                             │
│  注入:直接拼入 WritingAgent prompt <recent_context> 区块       │
│  ─────────────────────────────────────────────────────────    │
│  Layer 2 · 长期记忆 (Long-Term)                                │
│  scope = volume / global  |  LLM 滚动摘要 + 北极星锚定         │
│  来源:卷摘要每 5 章更新;全局摘要每 10 章更新                  │
│  防漂移:全局摘要始终嵌入 AuthorIntent.reader_feeling + 主线    │
│  ─────────────────────────────────────────────────────────    │
│  Layer 3 · 外部记忆 (External)                                  │
│  所有 MemoryEntry + Segment 的 embedding → pgvector            │
│  由 RetrievalService 管理语义召回;记忆服务只负责写入           │
└────────────────────────────────────────────────────────────────┘
```

**三层分工:**

| 层 | 粒度 | 目的 | 体积约束 |
|---|---|---|---|
| 短期(chapter) | 最近 1–2 章 | 提供即时上下文:刚发生了什么、章末悬念 | ≤ 500 字/章 |
| 长期(volume/global) | 卷/全书 | 保持连贯主线、锚定北极星、防漂移 | 卷 ≤ 800 字;全局 ≤ 1500 字 |
| 外部(embedding) | 全部 MemoryEntry + Segment | 语义按需召回久远章节细节 | pgvector 管理,无硬上限 |

---

### 3.2 短期记忆设计

短期记忆对应 `MemoryEntry.scope = 'chapter'`,存储**最近 1–2 章**的章末摘要。摘要由 SummaryAgent 生成,约 200 字,聚焦"发生了什么 + 结局状态 + 章末钩子"。

**注入策略:**

```
<recent_context>
  上一章摘要: {chapter_n-1.summary_text}
  上一章大纲末尾 beats: {chapter_n-1.outline["beats"][-3:]}
  本章写作目标(大纲): {chapter_n.outline}
</recent_context>
```

短期记忆直接以文本拼接入 prompt,无需向量检索。

**体积控制:**
- 默认保留最近 **2 章**的 `MemoryEntry(scope=chapter)` 供自动注入。
- 历史章摘要永久保留供外部记忆检索,但不自动注入。
- 若 2 章摘要超过短期 token 预算(400 token),截断较旧的一章。

**RecurrentGPT 借鉴**【已核实 arXiv 2305.13304】:每章定稿后立即更新短期记忆(对应 RecurrentGPT 的"每步更新短期记忆");以当前章 `outline` 核心情节句作为检索 query,而非简单的章标题——与"以当前 plan 作 query"的长期检索机制保持一致。

### 3.3 长期记忆与防漂移机制

#### 3.3.1 卷摘要(scope = volume)

存储当卷所有已完成章节的核心情节、人物状态、卷级钩子,约 500–800 字。始终包含 `Volume.arc_goal` 完成度。更新策略:每 5 章触发一次增量更新,或卷尾时触发。

#### 3.3.2 全局摘要(scope = global)与北极星锚定

全书从第一章至今的主线进展,严格锚定 `AuthorIntent`(北极星)。每 10 章触发一次更新。

**锚定机制** — 全局摘要必须包含三个区块:

```
[主题锚 THEME ANCHOR]
  直接引用 AuthorIntent.reader_feeling + AuthorIntent.central_promise
  不允许改写,只读

[主线进展 MAIN THREAD]
  主角当前目标状态,必须与主题锚逻辑一致
  包含 do_not_betray 红线是否被触碰

[核心变化 KEY CHANGES]
  与初始设定相比,人物/世界发生了哪些实质变化
```

> **为什么用 AuthorIntent 而非旧版的 Work.theme_anchor?** 重构后数据模型以 `AuthorIntent`(北极星实体,含 reader_feeling / core_emotional_arc / why_write / central_promise / do_not_betray)取代单字段 `theme_anchor`。防漂移锚点从一行文字升级为多维意图结构——这是协作回路中人的意图被一等公民对待的体现。`AuthorIntent` 对 MemoryService 只读。

**drift_check 机制:**

```python
def _drift_check(entry: MemoryEntry, intent: AuthorIntent) -> bool:
    """
    用 LLM 判断全局摘要的主线进展是否与 AuthorIntent 保持一致。
    MVP: Prompt 判断;完整版加 embedding cosine 相似度双保险。
    返回 True = 通过,False = 检测到漂移。
    """
    prompt = build_drift_check_prompt(
        summary=entry.summary_text,
        reader_feeling=intent.reader_feeling,
        central_promise=intent.central_promise,
        do_not_betray=intent.do_not_betray,
    )
    result = llm_layer.complete(
        "SummaryAgent", prompt,
        opts={"max_tokens": 60, "temperature": 0}
    )
    # SummaryAgent 返回: {"consistent": true/false, "reason": "一句话"}
    return json.loads(result).get("consistent", True)
```

### 3.4 混合摘要策略:分层合并 vs 增量更新

【已核实 arXiv 2310.00785 BooookScore,ICLR 2024 oral】

| 策略 | 机制 | 优势 | 劣势 |
|---|---|---|---|
| **增量更新** | 将新内容合并进 running summary | 近期细节丰富 | 连贯性较低,可能累积冗余 |
| **分层合并** | 对所有 chunk 分摘要后再聚合 | 连贯性高,结构清晰 | 细节损耗,LLM 调用成本高 |

**混合策略判定树:**

```
卷摘要更新
  └── 始终用【增量更新】 — 卷内细节保留优先

全局摘要更新
  ├── 卷数 ≤ 3(约 60–75 章,约 15–25 万字)
  │   └── 用【增量更新】 — 字数少,细节仍重要
  │
  └── 卷数 > 3(超 25 万字)
      └── 用【分层合并】 — 全局连贯性 > 细节
          Step 1: 取所有 MemoryEntry(scope=volume)
          Step 2: 每 3 卷做一次中间层合并 → 卷组摘要
          Step 3: 对所有卷组摘要做顶层合并 → 新全局摘要
```

**可配置参数:**

```python
MEMORY_CONFIG = {
    "volume_summary_strategy":       "incremental",
    "global_switch_threshold_vols":  3,
    "global_strategy_early":         "incremental",
    "global_strategy_late":          "hierarchical_merge",
    "hierarchical_group_size":        3,       # 每组 3 卷中间合并
    "chapter_summary_max_tokens":     300,
    "volume_summary_max_tokens":      800,
    "global_summary_max_tokens":      1500,
    "volume_update_interval":         5,       # 每 5 章更新一次卷摘要
    "global_update_interval":         10,      # 每 10 章更新一次全局摘要
}
```

### 3.5 摘要更新流程(updateMemory)

触发时机:章节进入 `status = 'done'` → 编排层调用 `updateMemory(chapterId)`。

```
updateMemory(chapterId)
  │
  ├─[Step 1] 生成章摘要
  │   SummaryAgent 输入: Chapter.outline + 本章 Segment 正文
  │   输出: MemoryEntry(scope='chapter', ~200 字)
  │   写入: INSERT MemoryEntry + 计算 embedding
  │
  ├─[Step 2] 卷摘要触发判断
  │   条件: 当卷完成章节数 % 5 == 0 OR 卷尾
  │   ├── YES → SummaryAgent: 增量更新卷摘要
  │   │         UPSERT MemoryEntry(scope='volume') + 重算 embedding
  │   └── NO  → 跳过
  │
  └─[Step 3] 全局摘要触发判断
      条件: chapter.seq % 10 == 0 OR 卷尾
      └── YES → SummaryAgent: 全局摘要更新
                 (卷数≤3: 增量 | 卷数>3: 分层合并)
                 drift_check(新全局摘要, AuthorIntent) → 不通过则重试1次
                 UPDATE MemoryEntry(scope='global') + 重算 embedding
                 覆盖前将旧版本存入 Snapshot 表
```

**核心伪代码:**

```python
def updateMemory(chapter_id: UUID) -> None:
    chapter = db.get_chapter(chapter_id)
    assert chapter.status == 'done'

    # Step 1: 章摘要
    entry = _generate_chapter_summary(chapter)
    db.insert(entry)
    _refresh_embedding(entry)

    # Step 2: 卷摘要
    completed = db.count_completed_chapters(chapter.volume_id)
    is_vol_last = _is_last_chapter_in_volume(chapter)
    if completed % MEMORY_CONFIG["volume_update_interval"] == 0 or is_vol_last:
        vol_entry = _update_volume_summary(chapter.volume_id)
        db.upsert(vol_entry, key=("work_id", "volume_id", "scope"))
        _refresh_embedding(vol_entry)

        # Step 3: 全局摘要
        if chapter.seq % MEMORY_CONFIG["global_update_interval"] == 0 or is_vol_last:
            g_entry = _update_global_summary(chapter.work_id)
            intent  = db.get_author_intent(chapter.work_id)
            if not _drift_check(g_entry, intent):
                g_entry = _update_global_summary(
                    chapter.work_id, retry=True, drift_hint=True
                )
            _archive_global_summary(db.get_global_memory(chapter.work_id))
            db.update_global_summary(g_entry)
            _refresh_embedding(g_entry)
```

### 3.6 衰减策略与体积控制

**短期(章摘要注入):**
- 最近 2 章:全文自动注入
- 第 3–10 章(近期历史):向量检索按需召回
- 第 11 章及以前:仅向量检索,不自动注入
- MemoryEntry 记录本身永久保留,衰减只影响"注入行为"

**卷摘要:**
- 每条卷摘要 ≤ 800 字(~1200 token)
- 全部卷摘要永久保留
- 超过全局合并阈值后启动分层合并,不再直接拼接注入

**全局摘要:**
- 硬上限 1500 字(~2200 token),超限时压缩顺序:
  1. 保留 `AuthorIntent` 锚点(必须保留)
  2. 保留主角当前目标与状态(必须保留)
  3. 各卷一句话进展(各卷 1 句)
  4. 最近 2 卷较详细进展(100 字/卷)

**百万字两层分层合并结构:**

```
全局摘要(≤ 1500 字)
   └── Layer-2 顶层合并
         ├── 卷组摘要 [卷 1-3] (~400 字) ← Layer-1 中间合并
         ├── 卷组摘要 [卷 4-6] (~400 字)
         │   ...
         └── 卷组摘要 [卷 N-2 至 N] (最近一组保留更多细节)

成本估算(20 卷):
  Layer-1: 7 组 × 1 次 SummaryAgent 调用 = 7 次
  Layer-2: 1 次顶层合并
  全书 500 章共约 1000 次 SummaryAgent 调用
  → 使用快模型 + prefix caching 后成本可接受
```

### 3.7 为什么朴素 RAG 与普通 KG-RAG 在叙事文档上失败

在引入 E²RAG 设计之前,必须先清楚两种主流方案的结构性缺陷。

**朴素 RAG 的三个致命缺陷:**【已核实 arXiv 2506.05939,EACL 2026】

**缺陷 A:无时间序感知**

```
第 5 章:王朗与叶秋是至交好友。
第 78 章:王朗被叶秋背叛,二人决裂。
第 120 章(生成中):WritingAgent 要写"王朗拜访叶秋"

朴素 RAG 按余弦相似度召回:
  → 第 5 章"好友"片段 ✓ 时序合法,但
  → 第 78 章"决裂"片段 ✓ 也被召回
  → 两个矛盾信息同时注入,WritingAgent 无法判断当前状态
```

**缺陷 B:chunk 边界切断因果链**

叙事因果常跨多段:"埋设伏笔(第3章) → 触发事件(第45章) → 回收结局(第90章)"。固定大小 chunking 切碎因果链,向量相似度无法恢复三者是同一叙事承诺的三个阶段。

**缺陷 C:无法表达实体当前状态**

召回的是"包含该实体的文本段落",不是"该实体的当前状态",导致"好友"与"仇敌"两类描述在向量空间中都相关,但在叙事时间中互斥。

**普通 KG-RAG 的致命缺陷:演变上下文被抹掉**

```
普通 KG 中:
  王朗 --[朋友]--> 叶秋   (来自第5章)
  王朗 --[仇敌]--> 叶秋   (来自第78章)

问题:两条边并存,无时间信息。
查询"王朗与叶秋的关系"时,两条边都被检索出来——
KG-RAG 给 WritingAgent 的是矛盾关系,不是"当前状态"。
更严重的是:"因何决裂"的因果背景在三元组压缩时丢失。
```

### 3.8 实体-事件双图 E²RAG

#### 3.8.1 概念架构

E²RAG 用**事件节点作为时间维度的中介**——关系的成立时间被编码在事件上,而非直接存在 KG 边上。【已核实 arXiv 2506.05939】

```
┌──────────────────────────────────────────────────────┐
│            E²RAG 双图                                  │
│                                                      │
│  【实体子图 Entity Graph】                              │
│  节点: Character / SettingItem / 地点 / 物品           │
│  边:   EntityRelation(关系类型                        │
│           + valid_from_chapter                       │
│           + valid_to_chapter)                        │
│       → 同一对实体可有多条随时间演变的边               │
│                                                      │
│  ──────── 二部映射 (Bipartite Mapping) ─────────────  │
│       实体节点 ←──── TimelineEvent ────→ 实体节点      │
│                    entity_refs(jsonb)                 │
│                                                      │
│  【事件子图 Event Graph】                               │
│  节点: TimelineEvent(abs_time, rel_order, chapter_id) │
│  边:   事件间因果 cause_event_ids(jsonb)               │
│       → 事件有确定章节,可做时间对齐过滤               │
└──────────────────────────────────────────────────────┘
```

**二部映射的查询语义:**

查询"第 N 章时王朗的当前关系" → 在 `EntityRelation` 表中找 `valid_from_chapter ≤ N AND (valid_to_chapter IS NULL OR valid_to_chapter ≥ N)` 的边——返回正确的当前关系,不再是矛盾的历史快照叠加。

#### 3.8.2 双图的 PostgreSQL 落地(不上 Neo4j)

### 3.9 混合三路召回策略

叙事文档兼有两类检索需求:精确实体匹配(人名/地名/法术名)适合关键词,语义近义表述适合向量,时序因果关系适合图查询。【已核实 arXiv 2503.23512 SCORE】

**三路召回架构:**

**路C:E²RAG 图查询**

```sql
-- C1: 提及实体的当前有效关系

       er.valid_from_chapter, er.source_event_id
FROM entity_relations er
WHERE er.work_id = :work_id
  AND (er.src_entity_id = ANY(:mentioned_ids)
       OR er.dst_entity_id = ANY(:mentioned_ids))
  AND er.valid_from_chapter <= :current_seq
  AND (er.valid_to_chapter IS NULL OR er.valid_to_chapter >= :current_seq)
  AND er.deleted_at IS NULL;

-- C2: 提及实体的最近时间线事件
SELECT te.id, te.chapter_seq, te.rel_order, te.description,
       te.event_type, te.entity_refs
FROM timeline_events te
WHERE te.work_id = :work_id
  AND te.chapter_seq <= :current_seq
  AND te.entity_refs @> ANY(
      SELECT JSONB_BUILD_ARRAY(JSONB_BUILD_OBJECT('type','character','id',eid::text))
      FROM UNNEST(:mentioned_char_ids) AS eid
  )
  AND te.deleted_at IS NULL
ORDER BY te.rel_order DESC
LIMIT 20;

-- C3: planted/triggered 伏笔
SELECT f.id, f.summary, f.state, f.foreshadow_chapter_id, f.payload
FROM foreshadows f
WHERE f.work_id = :work_id
  AND f.state IN ('planted', 'triggered')
  AND f.foreshadow_chapter_id IN (
      SELECT c.id FROM chapters c WHERE c.seq <= :current_seq
  )
  AND f.deleted_at IS NULL;

-- C4: 角色当前状态 Point-in-Time 快照
SELECT DISTINCT ON (cs.character_id)
    cs.character_id, cs.state_desc, cs.change_type, c.seq AS state_chapter_seq
FROM char_states cs
JOIN chapters c ON c.id = cs.chapter_id
WHERE c.work_id = :work_id
  AND c.seq <= :current_seq
  AND cs.character_id = ANY(:mentioned_char_ids)
  AND cs.deleted_at IS NULL
ORDER BY cs.character_id, c.seq DESC;
```

**RRF 融合(路A/B 文本候选):**

```python
def reciprocal_rank_fusion(rankings: list[list[str]], k: int = 60) -> dict[str, float]:
    """RRF 公式: score(d) = Σ 1 / (k + rank(d, list_i))。k=60 为经验值。"""
    rrf_scores: dict[str, float] = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            rrf_scores[doc_id] = rrf_scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return rrf_scores
```

> 路C(图查询)结果**不参与 RRF 融合**,而是作为"结构化强制注入"类别,直接进入 `ContextBundle.entity_relations / char_states / active_foreshadows`,不与文本段落竞争排名。

### 3.11 token 预算裁剪算法

**候选优先级评分:**

```python
def compute_priority(candidate, current_chapter_seq, mentioned_entity_ids) -> float:
    # 权重(均为【设计决策】,需实验调优)
    W_RELEVANCE  = 0.35  # 检索相关性(RRF 分数 / 图查询命中)
    W_RECENCY    = 0.25  # 时效性:越近期越重要
    W_ENTITY_HIT = 0.20  # 是否涉及草稿大纲已提及实体
    W_TYPE       = 0.10  # 内容类型优先级
    W_SCOPE      = 0.10  # 记忆摘要范围(global > volume > chapter)

    # 时效性:指数衰减,HALF_LIFE = 30 章
    d = max(0, current_chapter_seq - getattr(candidate, 'chapter_seq', 0))
    recency_score = math.exp(-d / 30.0)

    # 实体命中
    candidate_entities = set(getattr(candidate, 'entity_ids', []))
    entity_hit = len(candidate_entities & mentioned_entity_ids) / max(len(mentioned_entity_ids), 1)

    # 类型优先级
    TYPE_PRIORITY = {
        'rule': 0.9, 'character': 0.85, 'faction': 0.7, 'place': 0.6,
        'item': 0.65, 'term': 0.5,
        'global': 0.9, 'volume': 0.75, 'chapter': 0.5,
        'relation_change': 0.85, 'ability_change': 0.8,
        'item_transfer': 0.7, 'plot': 0.6,
    }
    type_key   = getattr(candidate, 'type', getattr(candidate, 'scope',
                          getattr(candidate, 'event_type', 'term')))
    type_score = TYPE_PRIORITY.get(type_key, 0.5)

    return (W_RELEVANCE  * candidate.retrieval_score
          + W_RECENCY    * recency_score
          + W_ENTITY_HIT * entity_hit
          + W_TYPE       * type_score)
```

**三阶段裁剪算法:**

```
阶段1:结构化强制注入
  → 实体关系(EntityRelationItem) 序列化后计 token,超 entity_budget 截止
  → 角色状态(CharStateItem) 追加进 entity_budget
  → 伏笔(ForeshadowSnippet) 按优先级降序,超 foreshadow_budget 截止
  → 计算已用 used_so_far,剩余 remaining = token_budget - used_so_far
  → 若 remaining < 0 → 抛 BudgetTooSmall

阶段2:文本候选池贪心填充
  → 合并 setting_snippets + memory_snippets + event_snippets
  → 按 priority 降序排列
  → 贪心:能放入 remaining_budget 则选中,否则截断

阶段3:超出检查
  → 最终验证(防 token 估算偏差)
  → 若仍超出,从最低 priority 开始移除,直至满足预算
```

**裁剪原则:**

| 原则 | 说明 |
|---|---|
| 结构化优先 | 实体关系/角色状态/伏笔有独立预算,不与文本竞争 |
| 时效衰减 | 距当前章节越远,priority 越低 |
| 全局摘要保护 | MemoryEntry(scope=global) 有最高类型优先级 |
| 世界规则保护 | SettingItem(type=rule) 有最高类型优先级 |
| 不截断实体文本 | 单条 EntityRelationItem 超出预算则整条跳过,不截半 |

### 3.13 ChronoQA 式时序/因果自评

借鉴 E²RAG 论文的 ChronoQA 基准三类问题,设计检索服务内建**轻量自评探针**,在 `assembleContext` 后验证是否有明显时序错误。【已核实 arXiv 2506.05939】

**三类探针:**

```python
# 探针 A:时间顺序类 — 检查因果边是否倒置
def check_temporal_consistency(event_snippets: list[EventSnippet]) -> list[str]:
    warnings = []
    events_by_id = {e.event_id: e for e in event_snippets}
    for ev in event_snippets:
        for cause_id in ev.cause_event_ids:
            cause = events_by_id.get(cause_id)
            if cause and cause.chapter_seq > ev.chapter_seq:
                warnings.append(
                    f"因果倒置: 事件[{ev.event_id}](ch{ev.chapter_seq})"
                    f" 的前因[{cause_id}](ch{cause.chapter_seq}) 发生在其之后"
                )
    return warnings

# 探针 B:因果一致性类 — 检查关系终止时间与源事件是否吻合
# 探针 C:人物状态类 — 检查 DISTINCT ON 结果无重复
```

```python
@dataclass
class SelfCheckResult:
    warnings:       list[str]
    is_critical:    bool        # 严重时序冲突:阻断生成
    recommendation: str

def self_check(bundle: ContextBundle) -> SelfCheckResult:
    warnings = (check_temporal_consistency(bundle.event_snippets)
              + check_relation_validity(bundle.entity_relations)
              + check_char_state_uniqueness(bundle.char_states))
    is_critical = any("因果倒置" in w for w in warnings)
    return SelfCheckResult(
        warnings=warnings, is_critical=is_critical,
        recommendation="建议重新运行 ExtractAgent 修复事件顺序" if is_critical else "正常"
    )
```

`is_critical=True` 时,Orchestrator 记入 `ConsistencyFlag`(error_class = 00 §5 第1大类"时间线与情节逻辑"),不静默继续生成。

```python
    work_id     = chapter.work_id
    current_seq = chapter.seq

    # 1. 实体识别与归一化(MVP: 正则+设定圣经名称列表;完整版: ExtractAgent NER)
    mentioned_entities = await extract_entities_from_outline(draft_outline, work_id, current_seq)
    mentioned_entity_ids = [e.id for e in mentioned_entities]
    mentioned_char_ids   = [e.id for e in mentioned_entities if e.type == 'character']
    query_embedding      = await llm_service.embed(draft_outline)

    # 2. 三路并发召回
    kw_results, vec_results, graph_results = await asyncio.gather(
        run_keyword_search(draft_outline, work_id, current_seq),
        run_vector_search(query_embedding, work_id, current_seq),
        run_graph_query(mentioned_entity_ids, mentioned_char_ids, work_id, current_seq),
    )

    # 3. 路A/B RRF 融合(文本候选)
    fused_settings = reciprocal_rank_fusion([
        [r.id for r in kw_results.settings],
        [r.id for r in vec_results.settings],
    ])
    fused_memories = reciprocal_rank_fusion([[r.id for r in vec_results.memories]])
    fused_events   = reciprocal_rank_fusion([
        [r.id for r in kw_results.events],
        [r.id for r in vec_results.events],
    ])

    # 4. 综合优先级评分 + 按 top_k 截取候选
    top_settings = sorted(score_candidates(kw_results.settings + vec_results.settings,
                          fused_settings, current_seq, set(mentioned_entity_ids)),
                          key=lambda x: -x.priority)[:15]
    top_memories = sorted(score_candidates(vec_results.memories, fused_memories,
                          current_seq, set(mentioned_entity_ids)),
                          key=lambda x: -x.priority)[:10]
    top_events   = sorted(score_candidates(kw_results.events + vec_results.events,
                          fused_events, current_seq, set(mentioned_entity_ids)),
                          key=lambda x: -x.priority)[:15]

    # 5. 构造初始 ContextBundle(路C 图查询结果直接注入)
    bundle = ContextBundle(
        chapter_id          = chapter_id,
        draft_outline       = draft_outline,
        entity_relations    = graph_results.entity_relations,
        char_states         = graph_results.char_states,
        active_foreshadows  = graph_results.foreshadows,
        setting_snippets    = top_settings,
        memory_snippets     = top_memories,
        event_snippets      = top_events,
        token_budget        = token_budget,
        token_used          = 0,
        truncated_count     = 0,
        citations           = build_citations(graph_results, top_settings,
                                              top_memories, top_events),
        assembled_at        = datetime.utcnow().isoformat(),
    )

    # 6. token 预算裁剪(三阶段算法,见 §3.11)
    bundle = trim_to_budget(bundle, token_budget, entity_budget=1000, foreshadow_budget=800)

    # 7. 自评探针(见 §3.13)
    check_result = self_check(bundle)
    if check_result.is_critical:
        logger.warning(f"assembleContext 自评严重问题: {check_result.warnings}")

    return bundle
```

## 七、失败模式与缓解

### 7.1 记忆层失败模式

| 失败模式 | 触发条件 | 缓解方案 |
|---|---|---|
| **全局摘要漂移** | 长期增量更新偏离 AuthorIntent | drift_check + 重试;卷数 > 3 强制切分层合并 |
| **摘要体积爆炸** | 增量更新无限累积 | 严格体积上限 + 分层合并压缩 |
| **细节丢失** | 分层合并过早或压缩率过高 | 近期细节走检索(外部记忆)而非靠摘要 |
| **修订内容不一致** | 人工修改章节后未重触 update_memory | `invalidate_memory` 强制重算 + 级联更新 |
| **SummaryAgent 调用失败** | LLM 超时/限速 | 异步任务队列;失败记录至错误日志;生成前检查 updated_at |
| **embedding 过时** | summary_text 更新但 embedding 未重算 | 每次 summary_text 写入后同步触发 `_refresh_embedding` |

### 7.2 检索层失败模式

| 失败模式 | 缓解措施 |
|---|---|
| **时序穿帮** | 严格时间对齐 SQL 过滤 + 自评探针 |
| **实体演变丢失** | ExtractAgent 在每章定稿后强制运行;工程4 记录缺失 |
| **向量空间偏移** | 记录 embedding_model_version;模型变更时触发重建任务 |
| **关键词假阳性** | 实体消歧:同名实体有不同 UUID,结合 work_id 过滤 |
| **token 预算耗尽** | 分别设置 entity_budget / foreshadow_budget;仍超则抛 BudgetTooSmall 由 Orchestrator 处理 |
| **pgvector HNSW 精度下降** | 监控 recall@k;必要时增大 ef_search 或切换 IVFFlat |
| **rel_order 竞争条件** | DB UNIQUE 约束 + advisory lock |
| **召回延迟超标 P90 > 800ms** | 三路查询异步并发(asyncio.gather);embedding 预热;关键索引覆盖率监控 |

### 7.3 长程崩坏的系统性防御

```
第1层(预防):每章定稿后即触发章摘要更新 — 不积累
第2层(锚定):全局摘要始终包含 AuthorIntent + drift_check
第3层(压缩):分层合并控制体积,避免摘要本身变成噪音
第4层(补救):外部记忆(向量检索)作为细节后备,摘要丢失的细节可按需召回
第5层(回流):人工修订后 invalidate_memory 强制重算,不允许旧记忆持续污染
第6层(检测):assembleContext 后 selfCheck 自评探针
第7层(监控):BooookScore 式长程连贯性指标追踪崩坏率趋势
```

## 八、MVP vs 完整版

### 8.1 MVP(数万字闭环)

**目标**:跑通 assembleContext → WritingAgent 生成的端到端闭环。

| 功能 | 状态 |
|---|---|
| 章摘要生成 | ✅ 基础 Prompt |
| 卷摘要增量更新 | ✅ |
| 全局摘要增量更新(无漂移检测) | ✅ |
| MemoryEntry embedding 写入 | ✅ 写入但暂不用于向量检索 |
| 路A(关键词)+ 路B(向量)召回 | ✅ Segment + SettingItem + MemoryEntry |
| 时间对齐:简单 `seq < current_seq` | ✅ |
| EntityRelation:读当前版本,不做 valid_from/to 区间 | ✅ |
| CharState:用 Character.traits 静态字段代替 | ✅ |
| E²RAG 图查询(路C) | ❌ |
| token 裁剪:简化贪心 | ✅ |
| selfCheck 探针 | ❌ |
| invalidate_memory | ❌ 手动重运行 |
| 漂移检测 | ❌ 仅 AuthorIntent 注入 |

**MVP ContextBundle(精简版):**

```python
@dataclass
```

### 8.2 增强版(十万字级)

新增:
- `EntityRelation.valid_from_chapter / valid_to_chapter` 区间查询
- `CharState` Point-in-Time Snapshot 查询
- `TimelineEvent` 时序过滤向量检索
- `entity_budget / foreshadow_budget` 分配机制
- selfCheck 探针 A 类(时间顺序检查)
- `invalidate_memory` 自动触发
- 全局摘要版本快照存 Snapshot
- drift_check Prompt 上线

**验收标准**:人物关系变化(好友→仇敌)被正确反映在 ContextBundle 中;伏笔状态无时序穿帮。

### 8.3 完整版(百万字级)

新增:
- 路C(E²RAG 图查询)全量上线
- RRF 融合路A + 路B,路C 独立注入
- selfCheck 全三类探针
- 两层分层合并(卷数 > 3 自动切换)
- pg_jieba / jieba 中文分词(路A 精度提升)
- 异步并发三路查询(asyncio.gather)
- 向量空间版本管理(embedding_model_version + 重建任务)
- drift_check 加 embedding cosine 相似度双保险
- 向量索引监控(recall@k 追踪)

**Neo4j 升级门槛**:若在 50 万字以上,E²RAG 图查询 P90 > 400ms 且无法通过 PostgreSQL 索引优化解决,才评估迁移 Neo4j。在此之前 PostgreSQL 关系表足以支撑。【设计决策,对应 00 §3 原则9】

| 里程碑 | 检索能力 |
|---|---|
| MVP | 关键词 + 向量 + 简单时间过滤 |
| 增强版 | + EntityRelation 区间 + CharState 快照 + selfCheck |
| 完整版 | + E²RAG 双图 + 三路 RRF + 分层摘要 + 向量监控 |
