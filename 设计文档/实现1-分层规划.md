## 1. 在回路中的位置与职责

### 1.1 回路定位

分层规划模块是协作回路(00 §1)中"AI 实现"通道的**起点**:它把来自内核1(`Imagination` / `AuthorIntent`)的想象与意图,逐层展开为结构化、可执行的大纲树——从全书弧线,到卷级结构,到章级事件序列。

```
内核1 (Imagination / AuthorIntent)
  │  想象碎片 + 北极星意图
  │
  ▼
【实现1: 分层规划】
  │  阶段0: 人定锚(Work 层)
  │  阶段1: OutlineAgent → 全书弧线 + 卷级 VolumePlan
  │  阶段2: PlanningAgent → 章级 Chapter.outline + beat_targets
  │  关键决定点 → OptionSet(对接内核1,人来选)
  │  方法论约束注入(StructureTemplate + WebnovelRhythmRules)
  │  内核2 TasteModel 约束规划风格
  │
  ▼
Chapter.outline / Chapter.beat_targets / Volume.structure_beats
  │
  ├──→ 实现2(写作生成):读 outline 写正文
  ├──→ 实现3(编排引擎):调度规划→写作流水线
  ├──→ 门槛1(连贯性保障):读 cast / foreshadow_ops / setting_refs 做预检
  └──→ 工程6(质量度量):读 beat_targets 计算覆盖率 / 偏差
```

### 1.2 铁律边界

| 属于本模块 | 不属于本模块 |
|---|---|
| 全书 / 卷 / 章大纲生成 | 正文内容生成(→ 实现2) |
| 关键规划决定点产出 OptionSet | Prompt 编排调度(→ 实现3) |
| StructureTemplate 加载与 beat 分配 | 角色声音 / 设定校验(→ 门槛1/2) |
| WebnovelRhythmRules 节奏约束 | 记忆摘要与向量检索(→ 实现4) |
| TropeLibrary 检索与激活 | 伏笔状态机运行(→ 门槛1) |
| DHO 动态大纲回填 | Agent 模型路由(→ 工程3) |
| 局部重规划触发与执行 | 版本分支管理(→ 工程4) |

### 1.3 与内核的关系

**被内核1 驱动**:规划的每一层级都以 `AuthorIntent`(北极星)和 `Imagination`(已排期的想象碎片)为输入,而非由 AI 自主决定故事走向。

**被内核2 约束**:`TasteModel` 的正例库和反例库注入 OutlineAgent / PlanningAgent 的系统提示,影响风格取向、套路偏好、爽点密度偏好。

**关键决定点产出 OptionSet**:在以下规划节点,模块**不由 AI 自己拍板**,而是产出 `OptionSet`(多方案供选):
- 卷级弧线的核心走向(2–3 个候选弧线方向)
- 重大情节转折点的处理方式(2–4 个差异显著的方案 + 各自代价)
- 关键卷尾钩子的设计(2–3 个强度相当但风格各异的选项)
- 在 `deviation_score > 0.6` 的重规划场景中,修复路径的多候选

## 2. 设计目标与百万字挑战

### 2.1 设计目标

1. **想象 → 大纲的有损最小转化**:Imagination / AuthorIntent 的核心创意必须在层层展开中保真传递,不被"LLM 均值化"稀释。
2. **两 / 三阶段框架落地**:全书/卷级 → 章级 → 正文,每阶段产物严格结构化入库,可版本化、可回溯。【已核实 2505.12572 / 2412.13575 / 2506.16445 / 2508.03137】
3. **DHO 动态分层大纲**:大纲不是静态文档,随生成过程实时回填"实际事件",下游规划始终锚定真实故事状态。【已核实 2412.13575】
4. **压缩-扩展比可调**:大纲长度作为可配置参数,在信息保真与 token 成本之间取最优点。【已核实 2505.12572,R≈0.01 仅其配置】
5. **方法论形式化**:西式结构(三幕/STC/英雄之旅/七点/雪花/Story Grid)和网文节奏(黄金三章/爽点/钩子/套路库)形式化为机器可操作的约束,注入规划 Agent。
6. **百万字可维护**:大纲树按卷分段维护,按需加载,跨卷 DHO 同步,避免"全量大纲溢出 LLM 窗口"。
7. **局部重规划**:人工修改某卷/章后,只重规划受影响范围,不触发全量重算。

### 2.2 百万字挑战的具体回答

**挑战 1:百万字大纲一次性放不下 LLM 窗口**

百万字小说 ≈ 200–500 章;若每章大纲 400 token,全量大纲约 8–20 万 token,加上设定圣经远超旗舰模型单次窗口。

**应对**:分层维护——全书摘要(< 2000 token)+ 每卷弧线(单卷 < 3000 token)+ 章级大纲(按需按卷批次加载)。OutlineAgent 每次只处理一个卷或若干章的规划,而非全书。

**挑战 2:跨卷一致性——第 50 卷能否"记住"第 1 卷埋下的设定与伏笔**

**应对**:规划新卷时,通过实现4(`assembleContext`)检索全局级 `MemoryEntry`(滚动摘要)+ 相关设定项 + 开放伏笔列表,而不是重读全文。形成"规划上下文包"注入 Agent。

**挑战 3:边写边改,大纲与正文脱节**

**应对**:DOME 的 DHO(Dynamic Hierarchical Outline)——章写完后将实际产出的关键事件回写进 `Chapter.outline.actual_events`,下一章规划以此为基础,而非只靠初始 `planned_events` 推演。【已核实 2412.13575】

**挑战 4:主题在百万字后半段漂移**

**应对**:每次规划新卷时强制注入 `AuthorIntent.core_emotional_arc`(北极星)+ 全书弧线摘要;PlanningAgent 每章大纲需标注与 `theme_anchor` 的关联——若连续 K 章语义相似度低于阈值,触发主题漂移告警。【已核实 2508.03137】

**挑战 5:规模估算**

| 维度 | 保守估计 | 充裕估计 |
|---|---|---|
| 百万字总章数 | 250 章(每章 4000 字) | 500 章(每章 2000 字) |
| 卷数 | 10–15 卷 | 20–25 卷 |
| 每章大纲 token | 300–500 | 600–800 |
| 全量大纲 token | ~10–15 万 | ~30 万 |
| 每次规划上下文 | 单卷 < 8000 token | 单卷 < 12000 token |

> 结论:以"单卷批次"为规划单元,每次规划上下文完全可控。【设计决策】

## 3. 详细设计

### 3.1 两 / 三阶段框架总览

【已核实:arXiv 2505.12572 / 2412.13575 / 2506.16445 / 2508.03137——主流范式收敛为分层规划框架】

```
阶段 0 ─── 人定锚(Human Anchor)
│   输入来源: 内核1 AuthorIntent + 初始 Imagination
│   人输入:前提(premise)、"要让读者感受什么"、题材/受众、结构类型偏好
│   AI 动作: 结构化并写入 Work 层;产出 OptionSet(结构类型候选)供人确认
│   产物:Work.premise / AuthorIntent / Work.structure_type / Work.planning_config
│   可选:初始 Character 表 / 初始 SettingItem
│
阶段 1 ─── 全书/卷级大纲(Global & Volume Outline)
│   执行者:OutlineAgent(旗舰档模型)
│   输入:Work 字段 + AuthorIntent + 已排期 Imagination + TasteModel
│   产出:
│     ├─ 全书弧线摘要(< 1500 token,存入 Work.global_outline JSONB)
│     └─ 每卷:Volume.arc_goal + Volume.structure_beats(StructureBeat 数组)
│   关键决定点:产出 OptionSet(2–3 个候选弧线方向)→ 人选 → chosen_option_id 写回
│
阶段 2 ─── 章级分段大纲(Chapter Outline)
│   执行者:PlanningAgent(快/中档模型,频繁调用)
│   输入:目标卷 Volume 数据 + 前卷尾章 actual_events + 开放伏笔列表 + CharState
│         + StructureTemplate beats 分配 + WebnovelRhythmConfig + TasteModel
│   产出:每章 Chapter.outline(JSONB,详见 §3.5)
│        + Chapter.beat_targets(beat 绑定 + PayoffBeat + HookRecord)
│        + Chapter.hook_text / hook_strength 草案
│   关键决定点:重大情节转折 → OptionSet(2–4 方案 + 代价)→ 人选
│
阶段 3 ─── 正文生成衔接(规划模块仅提供大纲)
│   实现2(写作生成)读取 Chapter.outline.planned_events 生成正文
│   规划模块在此阶段的职责:
│   ├─ 提供 assembleContext 所需的 outline.setting_refs 字段
│   └─ 接收正文生成完成后的"DHO 回填"信号
│
回流 ─── 动态大纲更新(DHO 落地)
    正文生成完成 → ExtractAgent 抽取实际事件 → actual_events 回填
    deviation_score 计算 → dho_locked = true
    下一章规划读取本章 actual_events 作为起始状态
```

### 3.2 DOME DHO 落地:动态分层大纲

【已核实:arXiv 2412.13575 DOME,NAACL 2025——DHO 在长文生成中优于静态大纲】

**核心洞察**:静态大纲在长程生成中与实际产出脱节——LLM 写作过程中会引入原大纲未预期的情节细节。DOME 的 DHO 方案:每生成一个片段后,立即将实际关键信息反写进大纲的对应层级,使大纲始终反映"已发生的真实状态"。

**Chapter.outline 双轨字段**:

```jsonc
{
  "planned_events"  : [ /* 规划阶段生成的预期事件序列 */ ],
  "actual_events"   : null,    // 正文生成前为 null;完成后由 ExtractAgent 填入
  "plan_deviation"  : null,    // 偏差摘要(<100字)
  "dho_locked"      : false    // true = 本章实际化完成,下游规划以 actual_events 为准
}
```

**章级 DHO 状态机**:

```
[初始状态]
    │
    ▼
OUTLINE_DRAFT
    │  OutlineAgent / PlanningAgent 生成 planned_events
    ▼
OUTLINE_APPROVED
    │  人工确认(低风险章节可自动通过)
    │  触发条件:OptionSet 已选定 或 自动批准规则满足
    ▼
WRITING_IN_PROGRESS
    │  WritingAgent(实现2)生成正文,Segment 入库
    ▼
WRITTEN_PENDING_BACKFILL
    │  ExtractAgent 抽取实际事件 → actual_events 回填
    │  计算 deviation_score
    ▼
DHO_LOCKED  ←──────────────────────────────────────────────┐
    │  dho_locked = true                                      │
    │  下一章规划可读取本章 actual_events                        │
    │  可选:人工修订 → dho_locked = false → 回到 WRITTEN_PENDING_BACKFILL ┘
    ▼
CHAPTER_DONE (Chapter.status = 'done')
```

**关键约束**:PlanningAgent 为第 N+1 章生成 `planned_events` 时,**必须优先读取第 N 章的 `actual_events`**(若 `dho_locked=true`),而非 `planned_events`。实际写出的偏差不被掩盖,下一章规划锚定在真实故事状态上。

### 3.3 大纲压缩-扩展比与信息保真

【已核实(中等置信):arXiv 2505.12572——R≈0.01 仅其配置,定性结论"大纲长度显著影响信息保真、存在可调最优比"可采纳;具体数值泛化性待验】

**定义**:

```
压缩比 R_c = len(chapter_outline_tokens) / len(chapter_target_tokens)
扩展比 R_e = 1 / R_c
```

`len` 以 token 计。R_c 越小表示大纲越"稠密压缩"。

**问题边界**:
- 大纲过短(R_c ≪ 0.01)→ 信息丢失,正文 LLM 自由发挥过多,偏离预期情节
- 大纲过长(R_c ≈ 0.10)→ 几乎是复述正文,失去规划指导意义且浪费 token

**`Work.planning_config` JSONB**:

```jsonc
{
  "outline_compression_target"  : 0.04,       // 目标压缩比,初始默认值【设计决策】
  "volume_outline_max_tokens"   : 2000,        // 每卷大纲上限
  "chapter_outline_max_tokens"  : 400,         // 每章大纲上限
  "outline_verbosity_level"     : "standard",  // compact / standard / detailed
  "auto_adjust_on_deviation"    : true         // 偏差连续高时自动上调压缩目标
}
```

**token 预算计算**:

```python
MIN_OUTLINE_TOKENS = 150  # 低于此值无法表达完整事件链

def compute_outline_budget(chapter_target_words: int,
                           config: PlanningConfig) -> int:
    """
    根据目标章节字数和压缩比计算本章大纲的 token 预算。
    汉字:token ≈ 1:1.2(大模型分词估算)
    """
    target_tokens = chapter_target_words * 1.2
    raw_budget = int(target_tokens * config.outline_compression_target)
    return max(MIN_OUTLINE_TOKENS, min(raw_budget, config.chapter_outline_max_tokens))
```

**偏差度量与自调节**:每章生成完成后,计算实际偏差率:

```python
deviation_score = jaccard_distance(
    set(extract_key_event_summaries(planned_events)),
    set(extract_key_event_summaries(actual_events))
)
```

若连续 3 章 `deviation_score > 0.5`,系统建议(或自动)上调 `chapter_outline_max_tokens`。

> 【设计决策】:初始默认值取 `outline_compression_target=0.04`,参考 arXiv 2505.12572 的定性结论;**必须在具体语料上通过自建度量调优**。不同题材(网文速节奏 vs 文学慢节奏)最优比可能差异 2–4 倍。

### 3.4 规划驱动源:想象 → 大纲的转化机制

**想象碎片的排期与注入**:内核1 中处于 `scheduled` 状态的 `Imagination` 碎片,在 PlanningAgent 生成对应章节的 `planned_events` 时被精准注入 Prompt。

```python
def get_scheduled_imaginations(
    chapter_id: UUID,
    work_id: UUID
) -> list[Imagination]:
    """
    拉取计划落在本章(或尚未排期但意图标记为'尽快'的)Imagination 碎片。
    注入 PlanningAgent 的 Prompt 中作为"必须体现的创意要求"。
    """
    return db.query(
        Imagination,
        work_id=work_id,
        status__in=('structured', 'scheduled'),
        scheduled_for__chapter_id=chapter_id
    ).order_by('created_at')
```

**AuthorIntent 注入格式(Prompt 片段)**:

```
# 北极星(必须在规划中体现)
- 读者应感受到:{{author_intent.reader_feeling}}
- 核心情感弧光:{{author_intent.core_emotional_arc}}
- 绝不背叛的红线:{{author_intent.do_not_betray | json}}

# 本章待落地的想象碎片
{% for img in scheduled_imaginations %}
- [{{img.type}}] {{img.raw_text}}
{% endfor %}
```

**关键规划决定点的 OptionSet 产出**:

```python
class PlanningDecisionPoint(str, Enum):
    VOLUME_ARC_DIRECTION    = "volume_arc_direction"    # 卷弧走向
    MAJOR_PLOT_TURN         = "major_plot_turn"         # 重大情节转折
    VOLUME_END_HOOK         = "volume_end_hook"         # 卷尾钩子设计
    REPLAN_REPAIR_PATH      = "replan_repair_path"      # 重规划修复路径

async def produce_option_set(
    work_id: UUID,
    decision_point: PlanningDecisionPoint,
    context: PlanningContext,
    num_options: int = 3
) -> OptionSet:
    """
    在关键规划决定点产出 OptionSet。
    每个选项包含:文本描述 + 与 AuthorIntent 的契合度说明 + 叙事代价。
    写入 OptionSet 表,等待内核1 回路的人工选择。
    """
    options = await outline_agent.generate_options(
        context=context,
        n=num_options,
        must_differ_on=DIFFERENTIATORS[decision_point],
        taste_model=await get_taste_model(work_id)
    )
    return await db.create(OptionSet(
        work_id=work_id,
        decision_point={"type": decision_point, "context_summary": context.summary},
        options=options,
        chosen_option_id=None
    ))
```

### 3.6 章级大纲的结构化设计:Chapter.outline JSONB 完整规范

`Chapter.outline` 是规划模块最核心的数据产物。它必须结构化而非自由文本,以确保:
1. WritingAgent(实现2)能精确提取"本章要写什么"
2. 门槛1(连贯性保障)能预先校验出场角色和涉及设定
3. DHO 回填有明确的字段锚点
4. 工程6(质量度量)能读取 beat 覆盖率等可量化指标
5. 已排期的 `Imagination` 碎片有明确的插入点

**Chapter.outline JSONB 完整规范**:

```jsonc
{
  // ── 元信息 ──────────────────────────────────────────────────────
  "chapter_seq"        : 42,
  "volume_seq"         : 3,
  "planned_word_count" : 3000,
  "outline_version"    : "1.2",
  "generated_by"       : "PlanningAgent",
  "generated_at"       : "2026-06-19T10:00:00Z",

  // ── 北极星对齐声明(规划必须与 AuthorIntent 关联) ──────────────
  "intent_alignment": {
    "core_feeling_served" : "孤绝感与绝处逢生的震撼",      // 对应 AuthorIntent.reader_feeling
    "red_line_check"      : "未触碰 do_not_betray 红线",
    "imagination_refs"    : ["img_uuid_001", "img_uuid_002"]  // 本章落地的 Imagination.id
  },

  // ── 场景与背景 ────────────────────────────────────────────────
```

【稳定知识】系统内置六种结构模板核心参数:

| 模板 ID | 名称 | scope | totalBeats | fusionWeight | 适用类型 |
|---|---|---|---|---|---|

| `story-grid` | Story Grid 价值追踪 | chapter | 1 | 0.60 | 章节质量诊断 |

**三幕结构**关键位置:建置(0–25%)→ 情节转折 1(25%)→ 对抗(25–75%)→ 情节转折 2(75%)→ 解决(75–100%)。【稳定知识】

**STC15** 关键位置:催化剂(10%)→ 进入第二幕(20%)→ 中点(50%)→ 一切皆失(75%)→ 灵魂黑夜(78%)→ 进入第三幕(80%)→ 结尾画面(99%)。mandatoryBeats 8 个,minCompletionRatio=0.85。【稳定知识】

**英雄之旅 12** 关键位置:平凡世界(0–8%)→ 冒险召唤(10%)→ 跨越门槛(20%)→ 磨难(60%)→ 复活(88%)→ 携宝归来(97%)。适合玄幻/修仙类型,refusal_of_call 节点为 optional。【稳定知识】

**七点结构**适合单卷或中短弧线:钩子(0%)→ 情节转折 1(25%)→ 夹击 1(37.5%)→ 中点(50%)→ 夹击 2(62.5%)→ 情节转折 2(75%)→ 解决(90%)。scope=volume。【稳定知识】

**雪花法**与分层规划范式天然契合:一句话摘要 → 一段话摘要 → 角色概要 → 分页梗概 → 场景清单 → 正文,对应系统的 Work / Volume / Chapter / Segment 层级。雪花法在本系统中不是 beat 清单而是**生成过程协议**,直接对应 OutlineAgent/PlanningAgent/WritingAgent 的三层分工。【已核实 2506.16445】

**Story Grid** 不定义固定 beat 序列,而是要求每个场景/章节记录价值变化(valueType / shiftFrom / shiftTo / shiftMagnitude),确保每章不是"哑场景"(价值无变化的纯过渡)。存入 `Chapter.outline.value_shift`。【稳定知识】

#### 3.8.3 beat 分配算法

```python
def assign_beats_to_chapters(
    template: StructureTemplate,
    chapter_ids: list[UUID],
    total_chapters: int
) -> dict[UUID, list[BeatAssignment]]:
    """
    将结构模板的 beat 按相对位置映射到具体章节。
    算法:beat.positionIdeal × 总章节数 做最近邻分配;
         若章节数不足则合并 optional beat,mandatory beat 不合并。
    """
    result: dict[UUID, list[BeatAssignment]] = {cid: [] for cid in chapter_ids}
    for beat in template.beats:
        if beat.optional and total_chapters < len(template.beats) * 0.6:
            continue  # 章节数不足时跳过 optional beat
        ideal_idx = clamp(int(beat.positionIdeal * total_chapters), 0, total_chapters - 1)
        chapter_id = chapter_ids[ideal_idx]
        result[chapter_id].append(BeatAssignment(
            beat_id=beat.beatId,
            beat_type=beat.beatId,
            mandatory=not beat.optional
        ))
    return result
```

### 3.10 套路库(TropeLibrary)

#### 3.10.1 `TropeTemplate` schema

套路是可版本化、可扩展的叙事模板。系统内置条目 `source=builtin`,用户自定义条目 `source=user`。

核心字段:
- `structure.setupPhase`:铺垫阶段描述 + 必要元素 + 建议章节数
- `structure.coreLoop`:核心循环 + 升级机制 + 建议循环章数
- `structure.payoffPhase`:大爽点/终局描述 + 建议触发时机
- `usageConstraints`:同作品最大激活数、冷却章数、冲突套路列表

**示例 — 系统流金手指**(`trope-system-001`):设定→触发激活→系统任务循环(每 5 章一循环,阶梯升级)→系统真相揭露。payoffTypes: system_reward/power_up/rank_up/revelation。maxActiveInstancesPerWork=1。

**示例 — 扮猪吃虎**(`trope-disguise-001`):建立信息差(主角真实实力仅读者知道)→蔑视-忍耐-升级-爆发循环(每 8 章)→真实身份/实力完全公开。payoffTypes: face_slap/reversal/recognition。cooldownAfterPayoffChapters=25。

#### 3.10.2 `TropeInstance` 状态机

```
[planning] → [setup] → [active] → [climaxed] → [completed]
                                              ↘ [abandoned]
```

`TropeInstance` 记录:激活章节、预计爽点章节、当前阶段(`setup/loop/payoff`)、循环次数(`loop_count`)、与 Foreshadow 的关联。

#### 3.10.3 `LongArcTropeSchedule`(跨卷长线套路)

【设计决策】百万字下存在跨越多卷的长线套路,需要专门里程碑计划表:

- `milestones[]`:每个里程碑含目标卷序号、卷内相对位置、类型(setup/loop_climax/escalation/major_payoff/final_payoff)、状态
- `escalationCurve`:linear / exponential / sigmoid / step
- `freshnessMechanism`:避免审美疲劳的机制(如每卷引入新的系统玩法)

### 3.11 融合约束集(FusionConstraintSet)

同一作品同时有西式结构约束、网文节奏约束、套路实例约束,三者可能冲突。`FusionConstraintSet` 定义仲裁规则,存入 `Work.fusion_constraint_set` JSONB。

**冲突优先级(可配置)**:`structure` > `webnovel_rhythm` > `trope`

**内置融合规则**:

| 规则 ID | 名称 | 条件 | 仲裁结果 |
|---|---|---|---|
| `fr-001` | 低谷章节网文爽点降级 | 本章绑定 stc-all-is-lost / stc-dark-night-of-soul | 爽点要求降至 0;允许悬念型钩子;仍需钩子强度≥2 |
| `fr-002` | Midpoint 可叠加大爽点 | 绑定 stc-midpoint / sp-midpoint | 允许叠加 intensity≥4 的 PayoffBeat;重置 payoff 间隔计数 |
| `fr-003` | 套路爽点避让西式低谷 | 套路 payoff 位置落在 [0.70,0.80] 且主模板为 stc15 | 建议前移至 0.65 或后移至 0.82;人工确认可保留 |
| `fr-004` | 卷尾高潮强制爽点 | 本章为卷尾(≥ climaxPositionInVolume) | 强制至少 1 个 intensity≥4 PayoffBeat;钩子强度≥4 |
| `fr-005` | 黄金三章特殊保护 | Chapter.seq ≤ goldenChapterCount | 网文节奏优先级高于西式铺垫约束;允许提前 intensity≥3 爽点 |
| `fr-006` | 套路多样性约束 | 连续 N 章同类型 PayoffBeat 超过 maxSameTypeRatio | 警告;建议检索不同类型套路 |

`ManualOverride` 机制允许人工为特定章节覆盖任意约束,类型枚举:suppress_structure_check / force_payoff / force_hook_strength / custom。

### 3.14 章级规划的事件排布算法

```python
def plan_volume_chapters(
    volume: Volume,
    total_chapters_in_volume: int,
    open_foreshadows: list[Foreshadow],
    character_states: list[CharState],
    prev_tail_summary: str,
    scheduled_imaginations: list[Imagination],
    author_intent: AuthorIntent,
    taste_model: TasteModel,
    config: PlanningConfig
) -> list[ChapterOutlineDraft]:
    """
    为一个卷生成所有章的大纲草稿。
    策略:"锚点先行 + 想象落地 + 填充连接事件"
    1. 将 structure_beats 按 relative_pos 映射到章节槽
    2. 将已排期的 Imagination 碎片插入对应章节槽
    3. LLM 填充章间连接事件,满足 AuthorIntent 和 TasteModel
    4. 为每章分配伏笔操作
    5. 生成章尾钩子
    """
    # Step 1: 结构锚点映射
    beat_slots: dict[int, list] = {}
    for beat in volume.structure_beats['beats']:
        ch_idx = clamp(
            int(beat['position_hint']['relative_pos'] * total_chapters_in_volume),
            0, total_chapters_in_volume - 1
        )
        beat_slots.setdefault(ch_idx, []).append(beat)

    # Step 2: 想象碎片插入
    imagination_slots: dict[int, list[Imagination]] = {}
    for img in scheduled_imaginations:
        if img.scheduled_for and img.scheduled_for.get('chapter_seq'):
            ch_idx = img.scheduled_for['chapter_seq'] - volume.chapters[0].seq
            imagination_slots.setdefault(ch_idx, []).append(img)

    # Step 3: 构造规划上下文,调用 PlanningAgent LLM
    planning_context = PlanningContext(
        volume_arc_goal      = volume.arc_goal,
        author_intent        = author_intent,
        taste_model          = taste_model,
        beat_assignment_map  = beat_slots,
        imagination_map      = imagination_slots,
        open_foreshadows     = [f for f in open_foreshadows
                                if f.state in ('planted', 'triggered')],
        character_states     = character_states,
        prev_summary         = prev_tail_summary,
        total_chapters       = total_chapters_in_volume,
        outline_token_budget = config.chapter_outline_max_tokens,
    )
    raw_outlines = call_planning_agent(
        context    = planning_context,
        prompt     = build_chapter_planning_prompt(planning_context),
        max_tokens = total_chapters_in_volume * config.chapter_outline_max_tokens * 1.2
    )

    # Step 4: 解析、校验、伏笔后处理
    drafts = []
    for idx, raw in enumerate(raw_outlines):
        draft = parse_chapter_outline(raw)
        validate_chapter_outline(draft, beat_slots.get(idx, []))
        drafts.append(draft)

    drafts = assign_foreshadow_ops(drafts, open_foreshadows, volume)
    return drafts


def assign_foreshadow_ops(
    drafts: list[ChapterOutlineDraft],
    open_foreshadows: list[Foreshadow],
    volume: Volume
) -> list[ChapterOutlineDraft]:
    """
    后处理:将即将到期的开放伏笔 payoff 分配到最合适章节。
    策略:接近 payoff_window 上限的伏笔优先;每章 payoff 不超过 2 个。
    """
    urgent = [f for f in open_foreshadows if is_approaching_payoff_deadline(f, volume)]
    for f in urgent:
        best_idx = find_best_payoff_chapter_idx(drafts, f)
        if best_idx is not None:
            drafts[best_idx].foreshadow_ops.append({
                'op': 'payoff',
                'foreshadow_ref': str(f.id),
                'description': f'回收伏笔: {f.summary}'
            })
    return drafts
```

### 3.15 百万字下的层级维护策略

**层级树内存模型**:

```
Work (1 条)
  ├─ global_outline          # 全书弧线摘要, < 2000 token,常驻内存
  ├─ AuthorIntent            # 北极星, < 200 token,常驻内存
  └─ Volumes (N 条)
       ├─ arc_goal           # 每卷弧线目标, < 200 token/条
       ├─ structure_beats    # 每卷 beats, < 300 token/条
       └─ Chapters (K 条/卷)
            ├─ outline       # 每章详细大纲, 300-600 token/条
            └─ beat_targets  # 每章 beat 分配, < 100 token/条
```

**规划时的按需加载策略**:

```
生成第 N 章时,规划模块注入的上下文:
  ├─ Work.global_outline + AuthorIntent               (全局锚点,始终注入)
  ├─ TasteModel(positive_exemplars + negative_list)   (内核2,始终注入)
  ├─ 当前卷 Volume.*                                  (本卷弧线,始终注入)
  ├─ 前 2 章 Chapter.actual_events(或 outline)        (近期进度,始终注入)
  ├─ 前 1 卷尾章 Chapter.actual_events                (跨卷衔接,始终注入)
  ├─ 开放伏笔摘要(top-K 按紧迫度排序, K≤5)
  ├─ 本章出场角色 CharState
  └─ 已排期的本章 Imagination 碎片

  ⚠ 不注入:所有历史章 outline(改用实现4 的 MemoryEntry 覆盖)
  ⚠ 不注入:全量设定圣经(改用 assembleContext 按需检索)
```

**大纲版本分段存储**:
- 建立 `(volume_id, seq)` 联合索引,按卷批量读取
- 不在内存中维护全量大纲树;编排器(实现3)按卷批次加载
- `Volume.status` 字段驱动加载优先级:`active` > `planned` > `done`

```
                  ├──→ 实现2(写作生成): 读 planned_events 写正文
                  ├──→ 实现3(编排引擎): 读 outline 调度写作队列
                  ├──→ 实现4(assembleContext): 读 setting_refs 召回设定
                  ├──→ 门槛1(连贯性保障): 读 cast / foreshadow_ops 做预检
                  └──→ 工程6(质量度量): 读 beat_targets 计算覆盖率

                OptionSet → 内核1 回路等待人工选择
```

## 6. 失败模式与缓解

### 6.1 规划层核心失败模式

| 失败模式 | 触发条件 | 危害 | 缓解措施 |
|---|---|---|---|
| **想象漂移** | AI 规划时忽视 Imagination / AuthorIntent,滑向均值故事 | 书写的不是作者想要的书 | `intent_alignment` 字段强制填写;AuthorIntent 列为系统提示第一约束;工程6 度量主题契合度 |
| **主题漂移** | 卷数增多后 arc_goal 背离 theme_anchor | 百万字后故事跑偏 | 每次规划新卷强制注入全书弧线摘要 + AuthorIntent;主题相似度告警【已核实 2508.03137】 |
| **DHO 脱节** | actual_events 长期未回填 | 雪球效应:越写越偏 | `dho_locked=false` 时阻断写作队列入队;连续 3 章 `dho_locked=false` 触发告警 |
| **OptionSet 积压** | 人工长期不选择,规划流程卡死 | 写作队列停滞 | 超时(默认 48 小时)后编排器使用 AI 推荐项自动选择并标注(可回滚) |
| **结构 Beat 堆积** | 多个 mandatory beat 集中在同一章 | 该章过于密集 | `validate_outline` 检查每章 mandatory beat ≤ 2;超出时 PlanningAgent 重分配 |
| **伏笔爆炸** | 开放伏笔数超过上限 | 追踪困难 | `open_foreshadow_cap=20`;规划时强制优先安排 payoff |
| **大纲 token 超限** | `chapter_outline_max_tokens` 过高 + 卷章数多 | 单次调用放不下 | 硬性上限:单次 PlanningAgent 最多处理 20 章大纲;超过则分批 |
| **重规划雪崩** | 一次卷设定修改触发数百章重规划 | 时间和成本不可接受 | 工程4 影响分析提供精确的 `affected_chapter_seqs`;默认 scope=VOLUME_TAIL |
| **压缩比失衡** | `outline_compression_target` 过低 | 正文偏离预期 | 监控 deviation_score;连续高偏差时自动上调压缩目标 |
| **空洞大纲** | planned_events 模糊 | 正文生成也模糊 | event.summary 字数 ≥ 20 字 + key_entities 非空;否则拒绝 |
| **爽点同质化** | 连续 N 章同类型 PayoffBeat 超过阈值 | 读者审美疲劳 | fr-006 融合规则触发;检索不同类型套路 |
| **弧光曲线偏离** | 实际张力长期与曲线目标偏差 > 0.3 | 节奏失控 | 工程6 每卷末弧光曲线回顾报告;建议下卷补偿性调整 |

### 6.2 长程崩坏的三道防线

```
第一道防线:规划层 ── 生成大纲时强制锚定
  AuthorIntent (北极星) + TasteModel (品味) + 全书弧线摘要 + 开放伏笔列表
  → 在输入层面确保规划不失忆、不失味

第二道防线:DHO 回填 ── 实际产出及时回写
  每章写完即回填 actual_events + deviation_score
  → 在大纲树上维持"真实状态"而非"计划状态"

第三道防线:监控告警 ── 偏差积累预警
  连续 N 章 deviation_score > 阈值 → 告警 + 建议人工审查大纲
  AuthorIntent 在最近 K 章 actual_events 中语义相似度持续下降 → 意图漂移告警
  beat 覆盖率低于阈值 → 结构完成度告警
```

## 7. MVP vs 完整版

### 7.1 MVP — 阶段一:验证规划闭环

**目标**:从 AuthorIntent + 前提生成多卷大纲树,支持按章顺序生成正文,维持基本一致性,OptionSet 选择流程跑通。

**实现范围**:
- `Work` / `Volume` / `Chapter` 表建立,含 `outline` JSONB 简化版
- OutlineAgent:生成全书弧线 + 卷级 arc_goal
- PlanningAgent:章级 `planned_events` + `hook_design` + `intent_alignment.core_feeling_served`
- OptionSet:重大卷弧决定点产出 2 个候选
- DHO 回填:手动触发,关键词匹配简化抽取
- 重规划:仅支持单章重规划

**不做**:StructureBeat 枚举 / TropeLibrary / FusionConstraintSet / ArcCurveModel / LongArcTropeSchedule / 压缩比自调节 / 自动伏笔分配 / 深度预检

**验收**:5–10 万字连贯生成,大纲树前端可视化,人工可编辑章级大纲,OptionSet 选择流程跑通。

### 7.2 增强版 — 阶段二:结构化与方法论对齐

**新增**:
- 完整 `Chapter.outline` JSONB(含 cast / foreshadow_ops / setting_refs / intent_alignment)
- StructureBeat 绑定 + BeatType 枚举(STC + THREE_ACT + WEBNOVEL)
- DHO 回填:LLM 抽取(ExtractAgent)+ deviation_score
- `validate_outline` 完整预检
- `assign_foreshadow_ops` 自动伏笔分配
- TropeLibrary 内置 10 条套路 + TropeInstance 激活
- `WebnovelRhythmConfig` 完整实现
- `FusionConstraintSet` 基础规则集(fr-001 至 fr-006)
- 卷级弧光曲线预设

**验收**:十万字级,beat 覆盖率可度量,伏笔分配可追踪,主题漂移告警可触发。

### 7.3 完整版 — 阶段三:百万字生产级

**新增**:
- 局部重规划全功能(与工程4 影响分析深度集成)
- 跨卷 DHO 同步
- `LongArcTropeSchedule` + 多卷里程碑追踪
- 作品级弧光曲线实时偏差监控
- Story Grid 价值变化追踪(`value_shift`)
- TropeLibrary 向量语义检索
- FusionConstraintSet 用户自定义规则
- 卷大纲 3 候选 OptionSet
- `planning_config` 前端可视化调节
- 规划 token 消耗追踪与预警

**验收**:百万字连载,局部修改重规划 < 30 秒,deviation_score 可控,跨卷主题不漂移,OptionSet 选择率 > 80%。

## 9. 开放问题

### 9.1 需实验验证的核心问题

**Q1:OptionSet 在规划层的最佳介入粒度是什么?**

当前设计在卷弧走向和重大情节转折处产出 OptionSet。但若每章关键事件都产出 OptionSet,作者选择负担会显著增加。如何量化"关键程度"阈值——低于阈值 AI 自主决定,高于阈值产出 OptionSet——需要用户研究数据。初步假设:每卷 1–3 次人工选择是合理密度。

**Q2:最优 `outline_compression_target` 是多少?**

arXiv 2505.12572 的 R≈0.01 基于中文公版古典小说语料的单一模型。网文(快节奏、事件密集)与文学小说的最优比可能相差 2–4 倍。需建立实验:固定内容,变化压缩比,以 deviation_score + 读者满意度双指标评估。

**Q3:DHO 回填的最优时机**

当前设计"每章写完后立即回填"。若章节失败率高,频繁回填的成本是否合理?是否需要"批量回填"(写完整卷再统一回填)?批量回填可能导致多章规划基于过时状态。

**Q4:跨卷 DHO 同步的边界**

当某章 `deviation_score > 0.7` 时,影响可能需要回溯修改前几卷的 arc_goal。如何界定"可接受偏差"与"需要跨卷重规划"的阈值?

**Q5:Imagination 碎片的排期冲突处理**

多个 Imagination 碎片争抢同一章节时,当前设计未定义优先级。候选方案:时间戳优先 / TasteModel 相关性排序 / OptionSet 让作者选择排期顺序。

**Q6:结构锚点 vs 自由规划的平衡**

强制 structure_beats 约束了 LLM 的创意空间。对于纯网文题材,是否应允许 `structure_type = WEBNOVEL_FREE`,只保留 `WEBNOVEL_PAYOFF_BEAT` 和 `WEBNOVEL_VOLUME_CLIMAX` 这两个强制 beat?

**Q7:beat 完成度判定的 LLM 可靠性**

ReviewAgent 通过 LLM 判断章节是否满足 `completionCheck`。这个判定的准确率如何?是否需要引入结构化抽取步骤(而非端到端 yes/no)来提高一致性?

**Q8:多 POV 下的结构分析扩展**

当前 `scene_context.pov_character` 只支持单个 POV。百万字作品常见多主角轮换视角。`cast` 字段和 `beat_targets` 是否需要扩展为"多 POV 段落级"beat 分配?

**Q9:PlanningAgent 批次大小的最优值**

当前以"单卷"为批次。对于 50+ 章的卷,单次输出可能超过模型可靠输出长度上限。是否需要进一步细分为"半卷批次"?阈值如何确定?

**Q10:弧光曲线的自适应重计算**

当作品实际进度偏离预设弧光曲线时,系统应如何重新计算剩余部分的目标?重新拟合还是局部修正?修正后如何影响已规划但未生成的章节 beat_targets?

### 9.2 已知局限性

- **百万字端到端未验证**:本文档的所有跨卷规划策略均为工程设计决策,未经真实百万字连载验证。必须通过工程7(路线图)的分阶段验收建立真实数据。
- **Agent 模型能力依赖**:`PlanningAgent` 的事件排布质量高度依赖所用模型的叙事推理能力;不同模型版本的输出结构稳定性差异未知。
- **JSONB schema 演化**:`Chapter.outline` 的 JSONB 规范在项目迭代中必然变化;需建立 `outline_version` 字段 + migration 策略避免历史数据失效。
- **OptionSet 机制的有效性**:"关键决定点产出 OptionSet"是本文档相对于旧 02/03 的核心重构——把"AI 自己拍板"改为"AI 给方案、人来判断"。但 OptionSet 的选项设计质量(是否真的有差异、是否真的对齐 AuthorIntent)高度依赖 Agent 的生成能力,需要用户研究验证有效性。
- **网文节奏阈值均为经验估算**:`minSmallPayoffsPerChapter` / `majorPayoffIntervalChapters` 等所有数字阈值均为行业经验估算【设计决策】,必须在系统实际运行后通过工程6 数据校准。
