## 一、在回路中的位置与职责

### 1.1 编排引擎是什么

系统的第一性定义(00 §1)是一个把作者稀缺输入无损放大的**协作回路**:人提供想象与意见,AI 全程主笔,系统保障这个循环快速、准确、"好"地运转。

编排引擎(Orchestrator)是这个回路的**驱动器**——它不是全自动流水线,也不是简单的任务队列调度器。它的本质职责是:

```
把"人在环的协作回路"翻译成可执行的状态序列:
  ① 驱动 AI 各 Agent 实现人的想象
  ② 在关键决策点暂停,产出多方案,等人判断
  ③ 收到人的意见/选择后,驱动 AI 按意见重做
  ④ 定稿后触发记忆/品味更新,为下一轮回路供料
```

旧设计把编排理解为"全自动写章流水线",缺少①②③④的回路感知。本文的重构不是推翻其技术内核(Agent 角色、反思循环、幂等断点均保留),而是把那套机制重新接入回路——**编排的是"人在环的回路",而非无人值守的批量生产**。

## 二、设计目标与百万字挑战

### 2.1 设计目标

| # | 目标 | 评判标准 |
|---|---|---|
| G1 | **回路可感知** | 关键决策点(见 §3.2)必须产出 OptionSet 暂停,人的每次 FeedbackNote 必须驱动重做 |
| G2 | **人在环不阻塞产能** | 自动推进段(后台隐形)与人工判断段(前台显形)分离;人不在时不浪费算力傻等 |
| G3 | **AI 输出可解释** | 每次生成附带依据(用了哪些记忆/设定/伏笔);人判断时有据可依 |
| G4 | **幂等与断点续跑** | 任意状态宕机重启,从检查点恢复,不重复计费、不重复落库 |
| G5 | **百万字稳定** | 第800章行为与第1章语义等价;Orchestrator 自身无状态(持久态全在DB) |
| G6 | **成本可控** | 每章 token 消耗可追踪;超预算时分级降级不阻断主流程 |

### 2.2 回路视角下的百万字挑战

旧设计只从技术连贯性角度列挑战(上下文窗口、主题漂移、伏笔遗忘)。新增**回路视角的挑战**:

| 挑战 | 回路影响 | 应对设计 |
|---|---|---|
| **人的判断密度随字数增加会下降** | 作者写到第500章审疲劳,开始跳过选项 | 判断密度自适应:高戏剧密度章节强化人工暂停点,体力活章节允许自动推进(见 §3.3 自动推进规则) |
| **品味模型冷启动:前50章没有足够偏好信号** | OptionSet 方案差异不够个性化 | 前50章强制至少1个显性 OptionSet,从每次选择快速学习 PreferenceSignal |
| **FeedbackNote 语义多样性随写作推进增大** | "更狠""这段假"在第800章指向不同的问题域 | FeedbackNote 解析时注入品味模型上下文(内核2),使解析器随品味演进 |
| **上下文窗口无法容纳全文** | WritingAgent 拿不到全部前情 | ContextBundle(实现4)按 token 预算裁剪;第800章组装时间与第1章等价 |
| **主题漂移【已核实 2508.03137】** | 越写越偏离初始 AuthorIntent | 每次 OptionSet 生成和 WritingAgent 执行都注入 AuthorIntent.reader_feeling 作锚 |
| **回炉成本失控** | MAX_REWRITE 次内未解决,强制通过降质量 | 硬上限 MAX_REWRITE=3;与工程3联动实时追踪成本,超预算时提前降级反思轮次 |

> **证据分级**:百万字回路组合为【设计决策】,无经验证的端到端最佳实践(00 §3 原则10)。

### 3.2 人在环暂停点详解

系统有三类显式暂停点,职责各不相同:

#### 暂停点A:规划分叉(AWAITING_PLAN_CHOICE)

**触发条件**:
- 当前章的情节存在多条不可互相兼容的走向(如角色命运分叉、主线转折选择)
- Orchestrator 在 PLANNING 阶段调用 `DecisionPointDetector.detect(chapter_outline)`,返回 `is_branch_point=True`

**产出**:OptionSet,包含 2-4 个规划方案,每个方案包含:
```python
@dataclass
class PlanOption:
    option_id: str            # "A" / "B" / "C"
    title: str                # 一句话概括这个方案
    outline_delta: dict       # 与基准大纲的差异(jsonb)
    narrative_cost: str       # 这个选择要"付出"什么(伏笔、人物代价)
    author_intent_alignment: float  # 与 AuthorIntent.reader_feeling 的对齐度(0-1)
    taste_match_score: float  # 与 TasteModel 的匹配度(0-1)
```

**人工动作**:在工程2(编辑器)中选择方案或提自然语言意见。选择结果写入 OptionSet.chosen_option_id,同时触发 PreferenceSignal(source=option_choice)落库。

**自动推进条件**:
- 非分叉点(线性情节):PLANNING 直接进 CONTEXT_ASSEMBLY
- 人工大纲模式(Chapter.outline 已存在且 status=human_set):跳过整个 PLANNING

#### 暂停点B:草稿方案选择(AWAITING_DRAFT_CHOICE)

**触发条件**:
- 本章 ReviewAgent 判定 hook_strength < 0.7 且为高戏剧密度章节
- 或 beat_targets 中含 "climax" / "reversal" / "revelation" 等高情感密度标签
- 或 Chapter.seq 为全书关键节点(由 AuthorIntent.core_emotional_arc 标注)

**产出**:OptionSet,包含 2-4 个**关键场景的不同写法变体**(WritingAgent 用不同的叙事视角/情感基调/节奏生成):
```python
@dataclass  
class DraftVariant:
    option_id: str
    variant_label: str          # 如"克制内敛版" / "高爆发版" / "留白悬念版"
    excerpt: str                # 关键段落节选(500字以内),让人快速感受差异
    full_text_ref: str          # 完整版本的 Snapshot.id 引用(点击可展开)
    style_tags: list[str]       # 使用的风格标签
    taste_alignment_notes: str  # 与当前 TasteModel 的匹配说明
```

**自动推进条件**:
- 普通过场章、铺垫章:直接跳过方案选择,进 AWAITING_HUMAN

#### 暂停点C:人审与意见(AWAITING_HUMAN)

**所有章节必经**,无法跳过(但可配置超时后自动推进)。

**展示内容**:
1. 定稿正文
2. **生成依据摘要**(见 §3.5):本章用了哪些记忆、哪些设定、如何呼应 AuthorIntent
3. ReviewAgent 的 overall_score 与问题列表(仅 medium 及以上)
4. 若为 force_pass 章节:显著标注"AI 未达标准,建议人工复审"

**人工动作**:
- **通过**:Chapter.status → "done",推进 SNAPSHOT
- **提意见**:自然语言批评写入 FeedbackNote.nl_critique → 触发 REVISION
- **直接编辑**:人工修改正文(工程2编辑器),改动记录为 Snapshot(created_by="human") → 跳过 REVISION,直接进 SNAPSHOT

### 3.3 自动推进规则

**判断密度自适应**(对应设计哲学 §4 原则4:判断密度决定节奏):

```python
@dataclass
class ChapterDensityProfile:
    """Orchestrator 在 PLANNING 状态开始时计算"""
    chapter_id: UUID
    is_branch_point: bool          # 情节分叉
    drama_density: float           # 0-1,高情感密度
    is_arc_climax: bool            # 卷/全书高潮
    is_filler: bool                # 体力活:过场/铺垫/交代

def compute_pause_points(profile: ChapterDensityProfile) -> PausePointConfig:
    """
    决定本章需要哪些人工暂停点
    """
    return PausePointConfig(
        require_plan_choice   = profile.is_branch_point,
        require_draft_choice  = profile.drama_density > 0.7 or profile.is_arc_climax,
        require_human_review  = True,              # 永远需要
        auto_proceed_writing  = profile.is_filler  # 体力活章节:写作段全自动
    )
```

**体力活章节的全自动写作段**:当 `is_filler=True` 时,WRITING 状态完成后不产出 OptionSet,直接进 AWAITING_HUMAN(只做最终人审)。这是"放手自动化"的具体落地。

### 3.4 FeedbackNote 驱动的 REVISION 流程

**这是系统最核心的人机交互**——人提自然语言意见,AI 驱动重做,人不动 prose。

```
伪代码:REVISION 状态执行逻辑
──────────────────────────────────────────────────────────
function execute_revision(chapter_id, feedback_note: FeedbackNote):

    # 1. 解析自然语言批评为结构化指令
    directive = FeedbackNoteParser.parse(
        nl_critique    = feedback_note.nl_critique,
        taste_model    = TasteModelAdapter.get_current_taste(owner_id),
        chapter_context = chapter_summary,
        author_intent  = AuthorIntentAdapter.get(work_id)
    )
    # directive 示例:
    # { "scope": "scene_3", "action": "rewrite",
    #   "directive": "主角反应太平静,加情绪张力,用动作代替内心独白",
    #   "preserve": ["伏笔A", "设定B"] }

    feedback_note.parsed_directive = directive
    db.save(feedback_note)

    # 2. 确定重做范围
    rewrite_scope = infer_rewrite_scope(directive)
    # "targeted"  → 只改指定段落
    # "partial"   → 改多个相关场景
    # "full"      → 全章重写(罕见,提示人确认)

    if rewrite_scope == "full":
        # 全章重写需人确认(避免误操作)
        emit_confirm_required_event(chapter_id, "全章重写请确认")
        return   # 等人确认后重新触发

    # 3. WritingAgent 按指令重做
    writing_input = WritingAgentInput(
        chapter_id         = chapter_id,
        scene_plan         = original_scene_plan,
        writing_directives = enrich_with_directive(original_directives, directive),
        context_bundle     = context_bundle,   # 复用已有 ContextBundle
        previous_draft     = current_draft,
        feedback_note      = feedback_note,    # 新增:直接传入 FeedbackNote
        revision_round     = current_revision_round
    )
    new_draft = WritingAgent.revise(writing_input)

    # 4. 写 PreferenceSignal(反馈意见本身即品味信号)
    TasteModelAdapter.ingest_signal(PreferenceSignal(
        source   = "feedback",
        signal   = { "directive": directive, "nl_critique": feedback_note.nl_critique },
        polarity = "+",   # 对意见方向打正向权重
        work_id  = work_id
    ))

    # 5. 更新 FeedbackNote 的 resulted_snapshot_id
    snapshot = VersionAdapter.create_snapshot(chapter_id, new_draft, "ai_revision")
    feedback_note.resulted_snapshot_id = snapshot.id
    db.save(feedback_note)

    # 6. 状态回到 AWAITING_HUMAN(展示新草稿供再次审阅)
    task.status = AWAITING_HUMAN
    task.revision_round += 1

──────────────────────────────────────────────────────────
MAX_REVISION = 5   # 超过5轮提示作者考虑直接编辑
```

### 3.6 WritingAgent 自反思循环(WRITING 状态内部)

自反思在 WRITING 状态内部执行,提交给 ReviewAgent 之前。基于 StoryWriter(2506.16445)【已核实】和 arXiv 2508.03137【已核实】:

```
伪代码:WritingAgent 内部自反思循环
──────────────────────────────────────────────────────────
function WritingAgent.generate(input: WritingAgentInput) -> WritingAgentOutput:

    # 1. 首次生成
    draft = llm.complete(
        role   = "writing",
        prompt = build_writing_prompt(input),   # 含 TasteBundle 注入
        opts   = { model: "flagship", max_tokens: 6000 }
    )

    # 2. 自反思循环(最多 MAX_REFLECTION=2 轮)
    for reflection_round in range(MAX_REFLECTION):
        reflection = llm.complete(
            role   = "writing_reflection",
            prompt = build_reflection_prompt(draft, input, REFLECTION_CHECKLIST),
            opts   = { model: "flagship", max_tokens: 1500 }
        )

        if not reflection.needs_revision:
            break

        if reflection.revision_scope == "local":
            draft = apply_local_revision(draft, reflection.revision_instructions)
        else:  # structural
            draft = llm.complete(
                role   = "writing",
                prompt = build_writing_prompt(input, reflection_hint=reflection),
                opts   = { model: "flagship", max_tokens: 6000 }
            )

    return WritingAgentOutput(full_text=draft, ...)

──────────────────────────────────────────────────────────

    "是否严格遵循 ScenePlan 中的所有场景目标?",
    "是否有角色 OOC(对照 VoiceProfile)?",

    "是否出现了 TasteModel.negative_list 中的 AI 腔表达?",  # 新增:品味约束
    "是否体现了 AuthorIntent.reader_feeling 的北极星方向?",  # 新增:意图约束

### 3.7 写作-审校回炉循环(WRITING 状态外层)

```
伪代码:Orchestrator 的写作-审校回炉循环
──────────────────────────────────────────────────────────
function orchestrate_write_review(chapter_id, plan, context, taste_bundle):

    rewrite_round   = 0
    review_feedback = None

    while rewrite_round <= MAX_REWRITE:

        writing_output = WritingAgent.generate(WritingAgentInput(
            ...
            context_bundle  = context,
            taste_bundle    = taste_bundle,   # 新增:品味束
            review_feedback = review_feedback,
            rewrite_round   = rewrite_round

        # 并行后台校验
        consistency_flags = ConsistencyAdapter.check(chapter_id, writing_output.full_text)
        foreshadow_issues = ForeshadowAdapter.validate_actions(writing_output)
        bible_issues      = StoryBibleAdapter.validate(chapter_id, writing_output.full_text)

        review_output = ReviewAgent.review(ReviewAgentInput(

        if rewrite_round == MAX_REWRITE:
            review_output.decision = "force_pass"
            log_quality_warning(chapter_id, review_output)
            return writing_output, review_output

        review_feedback = build_rewrite_guidance(review_output)
        rewrite_round  += 1

## 六、失败模式与缓解

### 6.1 失败类型分类

```
A. Agent 执行失败(LLM 调用超时 / Provider 错误 / 输出格式不合法)
B. 服务调用失败(检索超时 / 一致性引擎错误 / 伏笔模块异常)
C. 产出质量不合格(ReviewAgent 持续 rewrite,达到 MAX_REWRITE)
D. 人工意见无法解析(FeedbackNote 语义模糊,无法生成 parsed_directive)
E. 人审超时(AWAITING_HUMAN / AWAITING_*_CHOICE 等待超时)
F. 宕机/任务中断(进程崩溃、容器重启)
G. 并发冲突(多章同时写同一设定项引发状态竞争)
```

### 6.2 各类失败的处理策略

#### A 类:Agent 执行失败

```python
AGENT_RETRY_POLICY = {
    "OutlineAgent":   RetryPolicy(max_attempts=3, backoff_seconds=[5, 15, 30]),
    "PlanningAgent":  RetryPolicy(max_attempts=3, backoff_seconds=[5, 15, 30]),
    "WritingAgent":   RetryPolicy(max_attempts=2, backoff_seconds=[10, 30]),
    "ReviewAgent":    RetryPolicy(max_attempts=3, backoff_seconds=[5, 15, 30]),
    "SummaryAgent":   RetryPolicy(max_attempts=3, backoff_seconds=[5, 15, 30]),
    "ExtractAgent":   RetryPolicy(max_attempts=3, backoff_seconds=[5, 15, 30]),
    "FeedbackNoteParser": RetryPolicy(max_attempts=2, backoff_seconds=[5, 10]),
}
```

**降级策略**:

| Agent | 降级处理 |
|---|---|
| `OutlineAgent` | 使用人工大纲(若存在);否则 FAILED,告警人工介入 |
| `PlanningAgent` | 跳过 Planning,WritingAgent 直接使用 ChapterOutlinePayload |
| `WritingAgent` | FAILED,不可降级(核心 Agent);告警人工介入 |
| `ReviewAgent` | 视为 `force_pass`;记录 quality_warning="review_skipped" |
| `SummaryAgent` | 跳过摘要更新,标记 memory_stale=True;后台异步补跑 |
| `ExtractAgent` | 跳过回流,标记 extract_pending=True;后台异步补跑 |
| `FeedbackNoteParser` | 向作者返回"意见解析失败,请换个说法或拆成更具体的描述"提示;不进入 REVISION |

**LLM 输出格式不合法**:
```python
def parse_with_retry(raw_output: str, schema: type, max_attempts: int = 2):
    """尝试解析 LLM 输出;失败时让 LLM 自我修复(fix_json prompt);超限抛 AgentOutputParseError"""
```

#### C 类:达到 MAX_REWRITE 上限

```
rewrite_round = MAX_REWRITE(=3)时:
  1. ReviewAgent 输出 decision="force_pass"
  2. ChapterTask.quality_warnings 追加:
     { type: "max_rewrite_reached", round: 3,
       top_issues: [最后一轮 issues[:3]], chapter_id }
  3. 流程继续推进到 DRAFT_READY
  4. 工程2(编辑器)在章节旁显示"⚠️ AI未达标准,建议人工复审"
  5. EvaluationAdapter 自动对此类章节降低默认质量分
```

#### D 类:FeedbackNote 无法解析

当 FeedbackNoteParser 连续 2 次返回 `parse_confidence < 0.5` 时:

```
1. 向作者返回解析失败提示,附上最佳猜测解读(供参考)
2. 提供模板选项:
   "是否是以下意图之一?
    □ 某段情绪反应不够真实
    □ 节奏太快/太慢
    □ 人物说话不像 ta
    □ 这段信息量太少
    □ 其他(请具体说)"
3. 若作者从模板选择:补全 parsed_directive 继续 REVISION
4. ChapterTask 保持 AWAITING_HUMAN 状态不推进(不丢失意见)
```

#### E 类:人审超时

## 七、MVP vs 完整版

### MVP 阶段(目标:跑通单 Agent 写章 + 最小回路)

**包含**:
- `ChapterOrchestrator` 核心状态机(去掉方案选择分叉:无 AWAITING_PLAN_CHOICE / AWAITING_DRAFT_CHOICE;简化为 PLANNING→WRITING→AWAITING_HUMAN→SNAPSHOT→MEMORY_TASTE_UPDATE→DONE)
- `OutlineAgent`(章大纲生成,无分叉方案)
- `WritingAgent`(无自反思,单轮生成;注入空 TasteBundle)
- `SummaryAgent`(章级摘要)
- 最小 REVISION 流程:AWAITING_HUMAN 接收 FeedbackNote → WritingAgent 重做 → 回 AWAITING_HUMAN
- 无 `PlanningAgent`(WritingAgent 直接使用 OutlinePayload)
- 无 `ReviewAgent`(跳过审校)
- 无 OptionSet 产出(无方案暂停点)
- 无 TasteModel 注入
- 无并发(严格串行)

**验收**:能按大纲连续生成 5-10 万字;作者能用自然语言提意见驱动重做;人审-意见-重做这条回路闭合。

### 增强版阶段(目标:回路质量提升 + 方案选择)

**新增**:
- `PlanningAgent`(场景细化)

- TasteModel 注入 WritingAgent(TasteBundle)
- PreferenceSignal 落库(option_choice + feedback 两类来源)
- FeedbackNoteParser 基础版(结构化解析意见)
- `SummaryAgent` 卷级滚动更新
- 完整 `ExtractAgent`
- DraftRationale 生成(成稿依据展示)
- 并发:多章流水线(同卷最多2章)
- 断点续跑:完整版(所有状态幂等重入)

**验收**:十万字级;作者看到方案选项和生成依据;品味模型开始学习;回炉机制有效改善质量。

- 批量 ExtractAgent(降低成本)
- OrchestrationLog 分析仪表盘(成本/质量趋势,对接工程6)
- MAX_REWRITE=3 + MAX_REFLECTION=2 + MAX_REVISION=5 全参数生效

**验收**:在自建度量上,百万字崩坏率可控;品味模型带来可感知的个性化质量提升;作者审疲劳下的自动推进机制稳定。

## 八、并发:多章流水线与多 POV 隔离

### 8.1 并发模型总览

| 场景 | 并发模式 | 隔离级别 |
|---|---|---|
| **单作品顺序生成**(默认) | 同一 work_id 按 seq 串行 | 无并发 |
| **多章流水线**(同卷内) | 前一章进入 AWAITING_HUMAN 时,后一章进入 WRITING | 同卷内最多2章并发,不同阶段 |
| **多 POV 并行**(跨 POV 线) | 不同 POV 线可同时生成 | POV 线级隔离 |
| **批量卷大纲生成** | 多卷 OutlineAgent 并发(只读) | 安全 |

**回路约束下的并发限制**:方案选择(AWAITING_PLAN_CHOICE / AWAITING_DRAFT_CHOICE)和人审(AWAITING_HUMAN)状态下,前一章暂停不会阻塞后一章的自动推进段。但后一章的 PLANNING 分叉检测依赖前一章的 MemoryEntry 最终态——**前一章必须完成 MEMORY_TASTE_UPDATE 后,后一章才能进入 PLANNING**。

### 8.2 幂等与断点续跑(百万字核心保障)

**设计原则**:Orchestrator 是**重试安全(retry-safe)**的——任何状态重跑,结果语义等价。

    先查是否存在未完成的 ChapterTask(status not in DONE/FAILED)。
    存在:从 ChapterTask.status 对应状态重入。

    使用 PostgreSQL SELECT ... FOR UPDATE SKIP LOCKED 防双写。

## 2. 各状态的幂等实现

# IMAGINATION_READY:
#   重入时重新检索 Imagination(实时性优先,无副作用)

# PLANNING:
#   scene_plan 序列化存 ChapterTask.scene_plan_cache
#   重入时直接读取,不重新调用 PlanningAgent

# AWAITING_PLAN_CHOICE / AWAITING_DRAFT_CHOICE:
#   OptionSet 已存在:直接展示,不重新生成
#   人的选择已落库:直接读取 chosen_option_id 推进

# CONTEXT_ASSEMBLY:
#   ContextBundle 不持久化(每次重新 assemble,保证实时性)
#   TasteBundle 按 TasteModel.version 缓存(版本未变则复用)

# WRITING:
#   草稿保存为临时 Snapshot(branch_label="draft_rN")
#   重入时读取最新草稿 Snapshot,重新审校(不重新写作)

# REVISION:
#   FeedbackNote.resulted_snapshot_id 非空:该轮已完成,跳过
#   为空:重新执行该轮 revision

# SNAPSHOT:
#   create_snapshot 前先查 branch_label="ai_final" 是否存在,存在则跳过

# BACKFLOW:
#   TimelineEvent/CharState 写入时带 (chapter_id, seq) 唯一索引

# MEMORY_TASTE_UPDATE:
#   MemoryEntry 写入前查 chapter_id 对应 entry 是否已存在
#   TasteModel ingest_signals:PreferenceSignal 带 (chapter_id, source) 唯一索引

**成本控制分级降级策略**:

```python
def compute_degradation_level(chapter_id, cost_budget_remaining_ratio) -> DegradationLevel:
    """
    根据剩余成本预算决定降级级别
    """
    if cost_budget_remaining_ratio > 0.5:
        return DegradationLevel.NONE         # 正常运行
    elif cost_budget_remaining_ratio > 0.2:
        return DegradationLevel.LITE         # WritingAgent 自反思降为 MAX_REFLECTION=1
    elif cost_budget_remaining_ratio > 0.0:
        return DegradationLevel.MINIMAL      # 自反思=0;ReviewAgent 快速版(跳过 reader simulator)
    else:
        return DegradationLevel.EMERGENCY    # 通知作者;暂停生成直到充值/调预算
```

**批量与人审节奏**:当作者快速审校放行多章时,ExtractAgent 积压的抽取任务可合并:一次 LLM 调用处理2-3章的抽取,降低 per-chapter overhead(工程3联动)。

## 开放问题

1. **分叉点检测的准确率**:DecisionPointDetector 用规则还是 LLM 分类判断 `is_branch_point`?规则快但覆盖不全;LLM 准但增加成本。需在 MVP 后评估误判率。

2. **OptionSet 方案差异度**:2-4 个规划方案若差异太小(LLM 倾向生成相似变体),人工选择无意义。需要在 PlanningAgent prompt 中强制约束方案间的差异维度。

3. **品味模型冷启动速度**:前50章 PreferenceSignal 积累不足时,TasteBundle 注入效果有限。是否需要在新建作品时引导作者填写初始品味偏好(正例/负例)?

4. **自反思改善率与成本比**:MAX_REFLECTION=2 的实际收益需实测。若每轮改善不显著而成本高,应降为1甚至0。

5. **REVISION 多轮意见的顺序依赖**:作者对同一章提了多条意见,应串行处理(按序逐条 REVISION)还是合并成一次重做?串行保证每条意见可追溯,但成本高;合并成本低但解析复杂。建议 MVP 采用合并,完整版提供串行选项。

6. **ReviewAgent 中 AuthorIntent 对齐评分的可靠性**:ReviewAgent 用 LLM 判断"这章是否体现了 reader_feeling",主观性强、难量化。需要设计工程6(质量度量)的人工校准曲线来验证此评分的有效性。

7. **人审超时自动推进的风险**:`auto_proceed_on_human_timeout=True` 可能导致低质量章节自动定稿。建议默认 False,并在工程2 提供显眼的催审提示。

8. **并发章节的 TasteModel 更新竞争**:若同时有2章在 MEMORY_TASTE_UPDATE 状态,TasteModel 版本号乐观锁会有冲突。需要决定是串行化 TasteModel 更新还是允许乐观并发(后者可能导致信号丢失)。

9. **断点续跑中的 WRITING 草稿完整性判断**:当前设计默认从已有草稿继续审校。但若宕机前草稿不完整(WritingAgent 中途崩溃),应重新写作而非重新审校。需区分"草稿完整"和"草稿不完整"两种恢复路径(以草稿字数/结构完整性判断)。

10. **OrchestrationLog 存储增长与查询性能**:百万字≈333章,每章约25-35条日志,总量约1万条。需要 `(chapter_id, event_type, created_at)` 复合索引;超过1年的历史日志可归档到冷存储。
