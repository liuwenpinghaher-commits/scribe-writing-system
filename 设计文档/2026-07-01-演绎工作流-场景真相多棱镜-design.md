# 演绎工作流升级设计:「场景真相 · 多棱镜投影」

> 把「演绎」从旁挂的临时草稿工具,升级为限知多 POV 写作的**承重核心**:先立客观**场景真相**,再从真相派生每个涉及角色的**限知投影(含误读/盲区)**,草稿据此生成、正文据此校验。写作流扩为五阶段:大纲 → 节拍 → **演绎** → 草稿 → 正文。

**日期**:2026-07-01 · **范围**:scribe3 后端(章表字段 + 生成/消费)+ 前端(演绎阶段 + 左栏演绎面板)

---

## 一、背景与问题

**现状**(据代码):演绎是左栏一个旁挂面板 `DeducePanel` —— 选一个角色 → 调 `chat_write(chapter, focalizer=该角色)` 生成"该角色这一场限知草稿" → 可复制 / 点「给主编」设成 seedQuote 让主编成文。**不落库、临时、可选、脱节**:草稿并未真正基于演绎生成。

**问题根因**:让每个角色**各演各的**,既拼不出一致场景,又丢了限知多 POV 最出彩的东西——**戏剧反讽**(读者透过焦点者的误读看见真相)。

**限知多 POV 的craft本质**:同一场景,**客观真相只有一个**,但每个角色**只看到、只误读**其中一部分。写好它必须:①先立"上帝视角的真相";②从真相派生每个角色的"限知切片(含盲区/误读)";③焦点者切片当 POV 骨架、他人切片约束其行为并埋反讽。

---

## 二、核心设计:场景真相 · 多棱镜

演绎阶段 = **一份场景真相 + N 个角色限知投影**(不是 N 份互不相干的草稿)。

### 2.1 场景真相(objective,全知)
本章这一场**客观上真正发生了什么**——含角色们察觉不到的隐藏机制(如"借命正在发生""纸人已被附魂""崔判在等某个魂")。

- **依赖**:本章 大纲 + 节拍 + 设定圣经(含 `backstory_secret`/私密事实,全知)。
- **产出**:一段全知冷叙的场景真相(prose)。
- **作用**:**所有角色投影都从这一份真相派生 → 天然一致,不会各演各的打架。**

### 2.2 角色限知投影(subjective,五层)
对每个**涉及角色**,主编从「场景真相 + 该角色截至本章的限知帧」派生五层(一段结构化 prose,五个小标题):

| 层 | 含义 | craft 价值 |
|---|---|---|
| **看到/听到** | 感知层:他这一场感官能接收到的 | POV 感知边界 |
| **知道** | 限知帧内他已确知的事实(来自 ingest 的 proposition/knows) | 不写他不知道的私密 |
| **以为/误读** | 他对所见的解释——**与真相的差** | **戏剧反讽的原料** |
| **做了/说了** | 他这一场的行动/台词 | 约束他人行为一致 |
| **没察觉的** | 真相里他完全的盲区 | 悬念/反讽的暗面 |

- **依赖**:场景真相 + 该角色限知帧(`chat_write(chapter, focalizer=该角色)` 已有的限知投影链路)。
- **产出**:该角色五层投影(prose),落库。

## 三、五阶段写作流

```
大纲 → 节拍 → 【演绎:真相 + 多棱镜】 → 草稿 → 正文
```

| 阶段 | 中区 | 左栏(数据) | 右栏(主编) |
|---|---|---|---|
| 大纲 | synopsis 框 | 帧/伏笔等 | 讨论(规划) |
| 节拍 | beats 列表 | 同上 | 讨论 |
| **演绎(新)** | **场景真相 / 某角色投影 详情(可编辑存)** | **演绎树(真相根+涉及角色)** | 讨论(演绎:帮想这角色漏了什么) |
| 草稿 | 编辑器 | 参考 | 写作:**据真相+投影**成文 |
| 正文 | ProseEditor | 校验(帧/泄露有精确边界) | 写作/校验 |

**消费**:
- **草稿**:主编自动拿到 `chapter.scene_truth` + `chapter.deductions`(本章全部已落库投影)。以**焦点者投影为 POV 骨架**、**他人投影约束其行为并埋反讽**、**场景真相为事实骨架**,以作者视角写限知初稿——不再凭空全知。(主编 prompt 已具备"把演绎草稿织进叙事"的指令,扩成注入结构化真相+多投影。)
- **正文**:焦点者投影的"看到/知道/盲区"给 `find_leaks` 精确的限知边界,穿帮校验更准。

---

## 四、涉及角色 + 软门

- **涉及角色**:默认 = 名字出现在本章 **大纲/节拍** 文本里的角色(智能预填),作者可在演绎树上 **+添加 / 移除**。存 `chapter.involved_characters=[character_id]`。
- **软门**:进「草稿」时若仍有涉及角色未演绎 → **提示**"还有 X 个角色未演绎",提供"去补"入口,但**不硬卡**(不阻断写作;作者可坚持继续)。演绎树上未演角色标灰、已演打勾。

---

## 五、数据模型(方案 A:章表字段)

复用现有 beats/draft 落库套路,章表新增:

```
chapter.scene_truth        : str            # 场景真相(全知 prose)
chapter.involved_characters: list[str]      # 涉及角色 id
chapter.deductions         : list[dict]     # [{character_id, character_name, prose, updated_at}]
```

- `patch_chapter` 支持写这三个字段(现已支持 synopsis/beats,加入即可)。
- 不新建表、不新建生成引擎:演绎生成走现有 `chat_write(focalizer)` 限知链路;场景真相走 `chat_write`(无 focalizer=全知,注入含 secret 的设定块)。

## 七、验收标准

1. 五阶段 tab:大纲/节拍/**演绎**/草稿/正文;演绎阶段三栏一致(左演绎树 | 中详情 | 右主编)。
2. 演绎树:根「场景真相」+ 本章涉及角色;点真相→中区可生成/编辑/存全知真相;点角色→中区五层投影可生成/编辑/存;已演打勾。
3. 场景真相与角色投影都落库(刷新不丢);同一章多角色投影从同一真相派生、彼此一致。
4. 进草稿:主编据真相+全部投影成文(可从初稿看出焦点者 POV + 反讽痕迹);仍有未演涉及角色时软提示不硬卡。
5. build 绿、四阶段→五阶段真机零报错、演绎生成/编辑/落库真机通。

## 八、实施顺序

1. 后端:章表三字段 + patch 白名单 + 草稿注入。

5. 真机验收:五阶段截图 + 演绎生成/编辑/存 + 草稿据演绎成文 + 零报错。
