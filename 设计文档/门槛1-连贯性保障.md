## 铁律:门槛层的存在方式

> *"门槛层要隐形,内核层要显形。"* ——设计哲学 §4 第 7 条,00 §3 第 8 条

连贯性保障做的事情只有一件:**在后台安静地确保小说不崩**。它不是 Scribe 的脸,不是卖点,不在界面中心。作者天天打交道的是「内核」——想象输入、方案选择、意见驱动重做。连贯性保障的最优状态是**作者感知不到它**:错误安静地被发现,用低打扰方式浮出,作者一裁决它就消化回流,然后继续写作。

**本文档的两大职责**:

1. **连贯性校验**:19 类错误检测(符号状态、时间线、人物、世界观、叙事风格),产出 `ConsistencyFlag[]`,后台运行,结果以低打扰方式呈现(角标/侧栏)。
2. **伏笔状态机**:F-T-P 三元组 + planted/triggered/paid/abandoned 状态机,在后台追踪所有叙事承诺,以预警方式(非阻断方式)通知作者未回收风险。

**不做的事**:不修改任何正文、不占据主界面、不阻塞写作流程、不向作者推送非 critical 的低置信度噪音。

## 2. 设计目标与百万字挑战

### 2.1 三条核心目标

**目标一:高精确率,防标红疲劳**【设计决策】

百万字连载中,误报比漏报破坏更大。作者一旦产生"标红疲劳",便会开始忽略所有标记,整个门槛层失效。引擎宁可漏报低置信度的疑似冲突,也要保证每一个 `ConsistencyFlag(severity=critical|major)` 都高度可信。**精确率目标 > 0.85**,不以召回率为优化目标。

**目标二:增量校验,百万字可行**

新章节不触发全书重扫。通过受影响范围分析,仅校验本章 + 与本章存在依赖关系的历史范围。符号状态、时间线事件、伏笔池均采用快照/索引机制,绝大多数检测不需要读取历史章节全文。

**目标三:可裁决、可解释、可回流**

每个 `ConsistencyFlag` 携带 `evidence_refs`,指向冲突的具体来源(段落/设定项/时间线事件),作者可一键跳转核实。作者的 confirmed/dismissed 裁决实时驱动阈值自适应,引擎随人类反馈持续校准,越用越准。

### 2.2 百万字的四大挑战

**挑战一:检索范围爆炸**

100 万字 ≈ 200–400 章。`TimelineEvent` 表可达数千行,`ConsistencyFlag` 历史累积过大。

应对:维护 `SymbolStateSnapshot` 快照表(每章写一条状态变更,O(1) 查询);时间线检测使用滑动窗口(近 N 章 + 实体首次出现章);伏笔池按状态+向量相似度分层检索(paid/abandoned 不参与检索)。

**挑战二:LLM 误报风险**

LLM 判定的 Stage 3 若无阈值控制,会在高频率误报中磨光作者信任。

应对:三阶段流水线,Stage 1(规则引擎)+ Stage 2(向量语义)先过滤,Stage 3(LLM)只处理候选项;per-work 阈值配置根据裁决回流自动调整;dismissed_rate > 60% 时自动将该类型降级为 fast 模式暂停 LLM 检测。

**挑战三:"一改全乱"——设定修改导致历史标记失效**

作者修改某章设定后,可能导致后续数百章的历史标记全部失效或全部需要重校。

应对:`ConsistencyFlag` 携带 `source_version`(章节快照 ID)。设定或章节修订后,触发"受影响范围重校验"而非全量重扫。历史标记依据的 `SettingItem` 被修订后,自动置为 `status=stale`。重校验走异步队列,不阻塞写作。

**挑战四:伏笔规模膨胀**

百万字小说可能含数百个显性/隐性伏笔。全量注入 prompt token 成本不可控;跨百章状态追踪不能依赖模型记性。

应对:数据库级状态机保证持久化;向量+关键字双通道检索按相关性取 top_k=30 注入;critical 预警伏笔强制进入检测不受截断;paid/abandoned 冷存不参与检索。

## 3. 详细设计

### 3.1 符号状态跟踪子系统

#### 3.1.1 SymbolicState 枚举【已核实 SCORE arXiv 2503.23512】

物品、角色、势力等实体的离散状态集合。实体类型涵盖物品(`SettingItem.type='item'`)、角色(`Character`)、关系(`EntityRelation`)。

```
SymbolicState := {
  active,       -- 实体存在且可正常引用
  lost,         -- 已丢失/失踪,当前持有者不明
  destroyed,    -- 已被摧毁/死亡/消灭,不可逆
  hidden,       -- 存在但对主角/叙事不可见
  transferred,  -- 已转移至明确的新持有者
  dormant,      -- 暂时休眠/封印/沉寂
  unknown       -- 状态未在章节中明确描述
}
```

#### 3.1.2 SymbolStateSnapshot 表(引擎内部辅助表,不在 00 §4 规范模型中)

```sql
CREATE TABLE symbol_state_snapshot (
    id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    work_id        UUID NOT NULL REFERENCES works(id),
    entity_type    TEXT NOT NULL,            -- 'item' | 'character' | 'relation'
    entity_id      UUID NOT NULL,            -- 指向 SettingItem 或 Character
    state          TEXT NOT NULL,            -- SymbolicState 枚举值
    chapter_id     UUID NOT NULL REFERENCES chapters(id),
    segment_id     UUID REFERENCES segments(id),
    confidence     FLOAT NOT NULL DEFAULT 1.0,
    change_reason  TEXT,
    created_at     TIMESTAMPTZ DEFAULT NOW()
);

CREATE INDEX idx_sss_entity ON symbol_state_snapshot(entity_id, chapter_id);
CREATE INDEX idx_sss_work_state ON symbol_state_snapshot(work_id, state);
```

只写状态变化行,状态未变不写入,防膨胀。超过 `N_MAX_SNAPSHOTS` 时合并旧快照为历史摘要行。

#### 3.1.3 状态机转移规则

```
  active ──→ lost       (主角丢失/遗忘/被盗)
  active ──→ destroyed  (明确摧毁/角色死亡)
  active ──→ transferred(转让/被夺)
  active ──→ hidden     (隐匿/封印)
  active ──→ dormant    (角色沉寂/封印)

  lost   ──→ active     (找回)         [需叙事理由,否则 major 标记]
  lost   ──→ destroyed  (确认销毁)
  lost   ──→ transferred(找到新主人)

  hidden ──→ active     (重新出现,需叙事说明)
  dormant──→ active     (觉醒/解封,需叙事说明)
  transferred──→active  (归还,需叙事理由)

  destroyed ──→ active  [无叙事理由 → item_state_contradiction / critical]
  destroyed ──→ 任何状态 [有叙事理由如"神器重铸" → 合法转换]
```

核心规则:
- `destroyed → active` 无叙事说明 → `error_class=item_state_contradiction`, `severity=critical`【已核实 SCORE 2503.23512】
- `lost → active` 无找回情节 → `severity=major`
- `dormant → active` 无觉醒描述 → `severity=minor`

#### 3.1.4 状态更新伪代码

```python
def update_symbol_states_for_chapter(chapter_id: UUID) -> list[SymbolStateSnapshot]:
    """
    由 ExtractAgent 在章节正文落库后调用。
    解析本章涉及的实体状态变更,写入 symbol_state_snapshot。
    """
    segments = db.query(Segment).filter_by(chapter_id=chapter_id).all()
    full_text = " ".join(s.text for s in segments)

    # 步骤1: 从设定圣经获取本章涉及实体
    involved_entities = setting_bible_service.resolve_entities(full_text)

    # 步骤2: 查询各实体最近状态快照(O(1) 查询,不扫全书)
    current_states: dict[UUID, SymbolStateSnapshot] = {}
    for entity in involved_entities:
        snap = db.query(SymbolStateSnapshot)\
                 .filter_by(entity_id=entity.id)\
                 .order_by(SymbolStateSnapshot.chapter_id.desc())\
                 .first()
        current_states[entity.id] = snap

    # 步骤3: LLM 抽取本章实体状态变更事件
    state_changes = extract_agent.extract_state_changes(
        text=full_text,
        entities=involved_entities,
        current_states=current_states
    )
    # state_changes: list[{entity_id, new_state, confidence, change_reason, segment_id}]

    # 步骤4: 写入快照(只写变化)
    new_snapshots = []
    for change in state_changes:
        if change["new_state"] != current_states.get(change["entity_id"], {}).state:
            snap = SymbolStateSnapshot(
                work_id=chapter.work_id,
                entity_type=change["entity_type"],
                entity_id=change["entity_id"],
                state=change["new_state"],
                chapter_id=chapter_id,
                segment_id=change.get("segment_id"),
                confidence=change["confidence"],
                change_reason=change["change_reason"]
            )
            db.add(snap)
            new_snapshots.append(snap)
    db.commit()
    return new_snapshots
```

### 3.2 时间线冲突检测子系统【已核实 DOME arXiv 2412.13575】

#### 3.2.1 设计思路

DOME 使用时序知识图谱(Temporal KG)存取已生成内容并配 Temporal Conflict Analyzer 自动评估一致性。本系统 MVP 阶段用 PostgreSQL 关系表模拟 KG 核心功能,预留 Neo4j 迁移接口。

时间线冲突的本质:两个或多个 `TimelineEvent` 之间的 `abs_time`(故事内绝对时间)或 `rel_order`(相对顺序)存在矛盾,或与叙事内的明确时间表述不符。

#### 3.2.2 TimelineEvent 有效区间模型

```
TimelineEvent.abs_time  → 故事内时间("第三年春"/"昭元三年"/"大战后第五天")
TimelineEvent.rel_order → 全书事件相对排序整数(由 ExtractAgent 维护)

EntityRelation.valid_from_chapter → 关系从哪章生效
EntityRelation.valid_to_chapter   → 关系截止章节(null = 当前仍有效)
```

#### 3.2.3 时序冲突检测接口

```python
class TemporalConflictAnalyzer:
    """
    对应 DOME 的 Temporal Conflict Analyzer。
    MVP 以 PostgreSQL 关系表实现,接口预留图查询语义。
    """

    def get_entity_timeline(
        self,
        entity_id: UUID,
        work_id: UUID,
        chapter_range: tuple[int, int] | None = None
    ) -> list[TimelineEvent]:
        """
        返回实体在指定章节范围内的所有时间线事件,按 rel_order 排序。
        chapter_range=(from_seq, to_seq),None 表示滑动窗口范围。
        """
        q = db.query(TimelineEvent).filter(
            TimelineEvent.work_id == work_id,
            TimelineEvent.entity_refs.contains([str(entity_id)])
        )
        if chapter_range:
            q = q.join(Chapter).filter(
                Chapter.seq >= chapter_range[0],
                Chapter.seq <= chapter_range[1]
            )
        return q.order_by(TimelineEvent.rel_order).all()

    def detect_order_conflicts(
        self,
        new_events: list[TimelineEvent],
        work_id: UUID
    ) -> list[dict]:
        """
        检测新事件与历史事件的时序矛盾。
        返回: list of {new_event_id, conflict_event_id, conflict_type}
        """
        conflicts = []
        for ne in new_events:
            historical = self.get_entity_timeline(
                entity_id=ne.entity_refs[0],
                work_id=work_id
            )
            for he in historical:
                if self._is_order_conflict(ne, he):
                    conflicts.append({
                        "new_event_id": ne.id,
                        "conflict_event_id": he.id,
                        "conflict_type": "timeline_order_contradiction"
                    })
        return conflicts

    def _is_order_conflict(self, e1: TimelineEvent, e2: TimelineEvent) -> bool:
        if e1.abs_time and e2.abs_time:
            t1 = parse_story_time(e1.abs_time)
            t2 = parse_story_time(e2.abs_time)
            if t1 is not None and t2 is not None:
                if t1 < t2 and e1.rel_order > e2.rel_order:
                    return True
                if t1 > t2 and e1.rel_order < e2.rel_order:
                    return True
        return False
```

### 3.3 19 类错误的检测策略【已核实 ConStory arXiv 2603.05890】

对应 00 §5 五大类 19 子类枚举。每类标注检测方法(R=规则引擎/L=LLM 判定/V=向量相似度/G=图查询)、默认 severity、触发条件。

#### 大类一:时间线与情节逻辑(6 子类)

| 子类 | error_class | 方法 | 默认 severity | 核心触发条件 |
|---|---|---|---|---|
| T1 时序矛盾 | `timeline_order_contradiction` | R+G | critical | `TimelineEvent.rel_order` 与 `abs_time` 声明顺序不一致 |
| T2 因果断裂 | `causal_break` | L | major | 关键状态变更无前因;LLM 置信度 < 0.65 |
| T3 事件重复 | `event_duplication` | V+L | minor | 语义相似度 > 0.92 且同实体,LLM 确认为重复叙述 |
| T4 不可能并发 | `impossible_concurrence` | R+G | major | 同实体同时出现在地理不可达的两地 |
| T5 关系有效区间违反 | `relation_validity_violation` | R+G | major | `EntityRelation` valid 区间外引用该关系 |
| T6 时间描述内部矛盾 | `intra_chapter_time_conflict` | L | major | 章内两处时间表述 LLM 判定矛盾 |

**T1/T5 规则引擎伪代码**:

```python
# T1 时序矛盾
for event in chapter_new_events:
    conflicts = db.query(TimelineEvent).filter(
        TimelineEvent.work_id == work_id,
        TimelineEvent.entity_refs.contains(event.entity_refs),
        TimelineEvent.rel_order > event.claimed_before_order
    ).all()
    if conflicts:
        emit_flag("timeline_order_contradiction",
                  evidence=[event.id] + [c.id for c in conflicts],
                  severity="critical")

# T5 关系有效区间
for (src, dst, relation) in chapter_relations:
    er = db.query(EntityRelation).filter_by(

       (er.valid_to_chapter and er.valid_to_chapter.seq < chapter.seq) or \
       (er.valid_from_chapter.seq > chapter.seq):
```

### 3.4 检测执行管线(Detection Pipeline)

#### 3.4.1 check() 主流程——三阶段流水线

```
                   check(chapter_id) 入口
                          │
         ┌────────────────▼────────────────┐
         │  Stage 0: 前置准备               │
         │  · 获取本章所有 Segment          │
         │  · 查询本章涉及实体              │
         │  · 加载最新符号状态快照          │
         │  · 确定检索窗口(§3.4.3)          │
         └────────────────┬────────────────┘
```

#### 3.6.2 OOC 双通道检测

```python
def detect_ooc(
    character_id: UUID,
    dialogue_segments: list[Segment],
    voice_profile: dict
) -> list[OOCCandidate]:
    """
    通道一(规则引擎):关键词特征检测
    通道二(向量引擎):语义相似度检测
    双通道结果合并后超阈值才交 ReviewAgent(LLM)精判。
    """
    candidates = []
    for seg in dialogue_segments:
        score_rule = _rule_ooc_score(seg.text, voice_profile)
        score_semantic = _semantic_ooc_score(
            seg.embedding, voice_profile["embedding_centroid"]
        )
        combined_score = 0.4 * score_rule + 0.6 * score_semantic

        if combined_score > OOC_INITIAL_THRESHOLD:  # 默认 0.65,随裁决回流调整
            candidates.append(OOCCandidate(
                segment_id=seg.id,
                character_id=character_id,
                ooc_score=combined_score,
            ))
    return candidates


def _rule_ooc_score(text: str, vp: dict) -> float:
    """forbidden 关键词出现 → 拉高偏离度;high_frequency 缺失 → 小幅拉高。"""
    score = 0.0
    for kw in vp["keyword_patterns"]["forbidden"]:
        if kw in text:
            score += 0.3
    hf_miss = sum(1 for kw in vp["keyword_patterns"]["high_frequency"]
                  if kw not in text)
    score += 0.1 * (hf_miss / max(1, len(vp["keyword_patterns"]["high_frequency"])))
    return min(1.0, score)


def _semantic_ooc_score(seg_embedding: list[float], centroid: list[float]) -> float:
    """余弦距离:越大越偏离 voice profile。"""
    return 1.0 - cosine_similarity(seg_embedding, centroid)
```

与门槛2(设定圣经)协同边界:一致性模块不修改 `voice_profile`,只读取并产出 `ConsistencyFlag`。门槛2 负责在新章节 ExtractAgent 运行后更新 `voice_profile`。

### 3.8 阈值回流机制(高精确率自适应)

```
作者裁决 confirmed/dismissed
         │
         ▼
┌──────────────────────────────────────────────────┐
│  Feedback Processor(异步,低优先级)                │
│  confirmed → 正样本;dismissed → 负样本           │
│  累积 N_FEEDBACK=50 条触发阈值重算                │
└──────────────────────────────────────────────────┘
         │
         ▼
┌──────────────────────────────────────────────────┐
│  per-(error_class, detection_method) 阈值更新     │
│                                                  │
│  precision = confirmed / (confirmed + dismissed)  │
│                                                  │
│  if precision < 0.85:                            │
│      threshold[error_class] += 0.05             │
│      (提高阈值,降召回,提升精确率)                │
│                                                  │
│  if precision > 0.95 and recall_proxy < 0.5:    │
│      threshold[error_class] -= 0.03             │
│      (降低阈值,增加召回)                          │
└──────────────────────────────────────────────────┘
         │
         ▼
┌──────────────────────────────────────────────────┐
│  新阈值持久化到 work.engine_config jsonb           │
│  每个 work_id 维护独立阈值配置                    │
└──────────────────────────────────────────────────┘
```

### 3.9 伏笔 F-T-P 状态机【已核实 CFPG arXiv 2601.07033】

#### 3.9.1 F-T-P 三元组概念

Foreshadow-Trigger-Payoff 是叙事学"悬念承诺"的最小形式化表示。

| 角色 | 叙事含义 | 示例 |
|---|---|---|
| **Foreshadow** | 埋设:向读者发出暗示/承诺 | "主角第3章随手捡起一块玉佩" |
| **Trigger** | 触发:伏笔被激活/提及(可选) | "第47章仇人认出了玉佩" |
| **Payoff** | 回收:承诺被兑现,悬念解答 | "第89章玉佩被证明是家族信物" |

Trigger 是可选中间态。简单伏笔可直接 `planted → paid`,复杂伏笔经历多次 `triggered`。

#### 3.9.2 Foreshadow 实体(严格引用 00 §4)

```
Foreshadow: id, work_id→Work, summary,
            foreshadow_chapter_id→Chapter,   -- F: 埋设章节(非空)
            trigger_chapter_id→Chapter,      -- T: 首次触发章节(可空)
            payoff_chapter_id→Chapter,       -- P: 回收章节(可空)
            state(planted/triggered/paid/abandoned),
            payload(jsonb)                    -- 扩展字段,见下
```

payload JSONB 扩展(关键字段):

```jsonc
{
  "foreshadow_type": "物品|人物|预言|悬念|情节|主题|隐喻|其他",
  "importance": "critical|major|minor",
  "foreshadow_text": "原文片段摘录",
  "foreshadow_segment_ids": ["seg_uuid"],
  "trigger_history": [
    {
      "chapter_id": "uuid",
      "segment_ids": ["uuid"],
      "trigger_type": "mention|deepened|redirected",
      "triggered_at": "ISO-8601"
    }

  "warning_level": "none|watch|alert|critical",
```

#### 3.9.4 状态转移表

| 当前状态 | 事件 | 触发条件 | 目标状态 | 副作用 |
|---|---|---|---|---|
| `planted` | `trigger_detected` | ExtractAgent 扫描到伏笔被呼应但未回收 | `triggered` | 追加 trigger_history;更新 trigger_chapter_id(首次) |
| `planted` | `payoff_detected` | ExtractAgent 扫描到完整回收(跳过 triggered) | `paid` | 填写 payoff_chapter_id/payoff_text;清除预警 |
| `planted` | `human_abandon` | 作者主动在 UI 标记弃置 | `abandoned` | 记录操作人与原因;从预警队列移除 |
| `planted` | `system_timeout` | 距 planted 超过预警阈值,作者确认 | `abandoned` | 同上 |
| `triggered` | `trigger_detected` | 再次被提及 | `triggered` | 仅追加 trigger_history,不改变主状态 |
| `triggered` | `payoff_detected` | 完整 payoff | `paid` | 填写 payoff 字段;清除预警 |
| `triggered` | `trigger_reverted` | 修订回流:前文触发证据被删除 | `planted` | 清空 trigger_chapter_id;清除对应 trigger_history |
| `triggered` | `human_abandon` | 作者主动弃置 | `abandoned` | — |
| `paid` | 任意 | — | `paid`(不变) | 终态,仅记录审计日志 |
| `abandoned` | 任意 | — | `abandoned`(不变) | 终态,仅记录审计日志 |

#### 3.9.5 FSM 核心控制器

```python
class ForeshadowFSM:
    """状态机控制器。所有状态转移均通过此类,保证逻辑集中、可审计。"""

    VALID_TRANSITIONS = {
        ("planted",   "trigger_detected"):  "triggered",
        ("planted",   "payoff_detected"):   "paid",
        ("planted",   "human_abandon"):     "abandoned",
        ("planted",   "system_timeout"):    "abandoned",
        ("triggered", "trigger_detected"):  "triggered",   # 自循环,追加 history
        ("triggered", "payoff_detected"):   "paid",
        ("triggered", "trigger_reverted"):  "planted",
        ("triggered", "human_abandon"):     "abandoned",
        ("triggered", "system_timeout"):    "abandoned",
    }

    def apply(
        self,
        foreshadow_id: UUID,
        event_type: str,
        chapter_id: UUID,
        evidence_segments: list[UUID],
        payoff_quality: str = None,
    ) -> FSMTransitionResult:
        with db.transaction():
            # 行级锁,防并发冲突
            foreshadow = db.get_foreshadow_for_update(foreshadow_id)
            key = (foreshadow.state, event_type)

            if key not in self.VALID_TRANSITIONS:
                return FSMTransitionResult(success=False,
                    reason=f"Invalid: {foreshadow.state} + {event_type}")

            new_state = self.VALID_TRANSITIONS[key]
            updated = self._apply_side_effects(
                foreshadow, event_type, new_state,
                chapter_id, evidence_segments, payoff_quality
            )
            return FSMTransitionResult(
                success=True,
                old_state=foreshadow.state,
                new_state=new_state,
                updated_foreshadow=updated,
            )

    def _apply_side_effects(self, foreshadow, event_type, new_state,
                             chapter_id, evidence_segments, payoff_quality):
        foreshadow.state = new_state
        if event_type == "trigger_detected":
            if foreshadow.trigger_chapter_id is None:
                foreshadow.trigger_chapter_id = chapter_id
            foreshadow.payload.setdefault("trigger_history", []).append({
                "chapter_id": str(chapter_id),
                "segment_ids": [str(s) for s in evidence_segments],
                "trigger_type": "mention",
                "triggered_at": now_iso(),
            })
        elif event_type == "payoff_detected":
            foreshadow.payoff_chapter_id = chapter_id
            foreshadow.payload["payoff_quality"] = payoff_quality or "full"
            foreshadow.payload["payoff_segment_ids"] = [str(s) for s in evidence_segments]
            foreshadow.payload["warning_level"] = "none"
        elif event_type == "trigger_reverted":
            foreshadow.trigger_chapter_id = None
            foreshadow.payload["trigger_history"] = [
                h for h in foreshadow.payload.get("trigger_history", [])
                if h["chapter_id"] != str(chapter_id)
            ]
        elif event_type in ("human_abandon", "system_timeout"):
            foreshadow.payload["warning_level"] = "none"
            foreshadow.payload["abandon_reason"] = event_type
        foreshadow.payload["updated_at"] = now_iso()
        return foreshadow
```

### 3.10 伏笔预警机制

#### 3.10.1 预警分级

| 预警等级 | 触发条件 | 界面表现(工程2) | 推荐行动 |
|---|---|---|---|
| `none` | planted 距当前章 < W₁ | 无 | 无 |
| `watch` | 距当前章 ≥ W₁ | 侧栏标黄 | 无紧迫行动 |
| `alert` | 距当前章 ≥ W₂ | 侧栏标橙 | 建议规划近期回收 |
| `critical` | 距当前章 ≥ W₃ | 侧栏标红 + 角标 | 作者需决策:回收或 abandon |

**默认阈值**【设计决策,可 per-work 配置】:

| 参数 | 默认 | 百万字含义(200–400 章) |
|---|---|---|
| W₁(watch) | 20 章 | planted 超 20 章未推进 |
| W₂(alert) | 50 章 | 约 10–20 万字内未回收 |
| W₃(critical) | 100 章 | 约 20–40 万字内未回收 |
| W₄(timeout,建议 abandon) | 150 章 | 需作者显式决策 |

importance 修正系数:

```
critical 伏笔 × 0.5  (重要伏笔更早预警:W₁=10章,W₂=25章,W₃=50章)
major    伏笔 × 1.0  (使用默认阈值)
minor    伏笔 × 2.0  (次要伏笔可以更晚:W₁=40章,W₂=100章,W₃=200章)
```

极长期主线伏笔(如第1章埋下的最终 boss 身份)需在 `payload.planned_payoff_chapter_range` 中显式声明预期范围,系统据此动态调整阈值。

#### 3.10.2 预警更新逻辑

```python
def compute_warning_level(
    chapters_elapsed: int,
    importance: str,
    planned_range: list[int] | None
) -> str:
    multiplier = {"critical": 0.5, "major": 1.0, "minor": 2.0}.get(importance, 1.0)
    effective_W1 = int(W1 * multiplier)
    effective_W2 = int(W2 * multiplier)
    effective_W3 = int(W3 * multiplier)

    # 若有规划范围,范围截止前不升级预警
    if planned_range and chapters_elapsed < planned_range[1]:
        return "none" if chapters_elapsed < effective_W1 else "watch"

    if chapters_elapsed >= effective_W3:
        return "critical"
    if chapters_elapsed >= effective_W2:
        return "alert"
    if chapters_elapsed >= effective_W1:
        return "watch"
    return "none"
```

### 3.12 后台化与低打扰设计

**这是门槛层最重要的设计约束,任何违背都是错误。**

#### 3.12.1 低打扰原则对应的工程约束

| 场景 | 低打扰实现 |
|---|---|
| 一致性校验结果展示 | 主界面不弹框;侧栏折叠展示;仅 critical/major 才触发角标计数(工程2) |
| 伏笔预警展示 | 侧栏颜色标记(watch=黄/alert=橙/critical=红);不主动弹出;不打断写作流 |
| 校验运行时机 | 章节写入完成后异步调用,不在生成流程关键路径上 |
| 引擎降级 | full→fast→rule_only→[] 降级链,降级时不阻塞写作 |
| 高 dismissed_rate | 自动暂停该类 LLM 检测,减少噪音 |
| 重校验调度 | 全走异步队列(background 优先级),不阻塞当前章节写作 |

#### 3.12.2 作者裁决回流(从界面到引擎)

```
工程2(侧栏) → 作者裁决(confirmed/dismissed/fixed)
                    │
                    ▼
          update_flag_status(flag_id, new_status)
                    │
                    ├─ 写入 ConsistencyFlag.status
                    └─ 触发 Feedback Processor(异步)
                              │
                              ▼
                        阈值回流(§3.8)
                        precision 重算
                        work.engine_config 更新
```

裁决不仅影响单条标记,还持续校准整个引擎的置信度阈值,使引擎越用越精准。

```python
def compute_affected_chapters(
    setting_item_id: UUID,
    modification_type: Literal["content_change", "name_change", "state_change"]
) -> list[UUID]:
    """找出受某设定项修改影响的章节,用于增量重校验。"""
    item = db.get(SettingItem, setting_item_id)

    # 方法1: 从 ConsistencyFlag.evidence_refs 找引用该 setting_item 的历史标记
    flags_with_ref = db.query(ConsistencyFlag).filter(
        ConsistencyFlag.evidence_refs["historical"].contains(
            [{"type": "setting_item", "id": str(setting_item_id)}]
        )
    ).all()
    affected = {f.chapter_id for f in flags_with_ref}

    # 方法2: 从 Segment 向量检索找高度相关章节
    related_segments = vector_search(
        query_embedding=item.embedding,
        work_id=item.work_id, threshold=0.75, limit=50
    )
    affected.update(s.chapter_id for s in related_segments)

    # 只检索 first_chapter_id 之后的章节
    first_chapter = db.get(Chapter, item.first_chapter_id)
    return [cid for cid in affected
            if db.get(Chapter, cid).seq >= first_chapter.seq]


async def schedule_recalibration(
    affected_chapter_ids: list[UUID],
    priority: Literal["high", "normal", "background"] = "background"
):
    """大范围重校验走异步队列,不阻塞写作。"""
    for chapter_id in affected_chapter_ids:
        task_queue.enqueue(
            "consistency_engine.check",
            chapter_id=chapter_id, mode="full", priority=priority
        )
```

```
章大纲确认(实现1)
  │
  ├─ declareForeshadowOps(chapterId, ops)   ← 规划阶段提前声明伏笔操作
  ▼
assembleContext(实现4)
  │
  ├─ getForeshadowContext(chapterId, "writing") ← 伏笔上下文注入写作 prompt
  ▼
WritingAgent 生成(实现2)
  ▼
[章节写入完成] → 异步触发 ─────────────────────────────────────────────┐
                                                                       │
                             check(chapterId)      scanForeshadow()    │
                             ← 连贯性校验          ← 伏笔扫描          │
                             (并行,后台异步)                            │
  ▼
结果 → 工程2(侧栏/角标) → 作者选择裁决/忽略 → 裁决回流(阈值自适应)
  │
人审/回流(工程4)
  │
  ├─ [若有修订] handleRevisionBackflow(chapterId, ...)
  ▼
updateMemory(实现4) + 设定圣经回写(门槛2) + evaluate(工程6)
                                               │
                                     getForeshadowStats / get_engine_stats
```

## 6. 失败模式与缓解

### 6.1 连贯性校验失败模式

| 失败模式 | 描述 | 缓解策略 |
|---|---|---|
| **符号状态链断裂** | `SymbolStateSnapshot` 某章未正确写入,后续检测基于错误状态 | 快照写入加事务保障;检测前校验快照完整性;缺失时回填最近 5 章 |
| **设定漂移未检测** | 设定项修改后未触发受影响章节重校验 | `notify_setting_modified` 在门槛2 设定修改事务中同步调用;已依赖该设定的 open 标记自动置 stale |
| **LLM 误报爆炸** | 某类检测持续高误报,作者产生标红疲劳 | 回流机制自动提升阈值;dismissed_rate > 60% 时告警 + 自动 fast 模式暂停该类 LLM 检测 |
| **时间线事件缺失** | ExtractAgent 未抽取到关键时间线事件,时序检测漏报 | 漏报优于误报(见 §2.1);`manual` 模式可补充抽取;漏报率通过人工抽样度量 |
| **向量索引陈旧** | Segment embedding 未同步,向量检测基于过期数据 | embedding 写入与文本写入同一事务;失败时标记该章向量检测为 stale,降级为规则引擎 |
| **SymbolStateSnapshot 膨胀** | 百万字下快照表占用较大 | 只写状态变化行;超 N_MAX_SNAPSHOTS 时合并旧快照为历史摘要行 |

**降级链**:

```
full 模式失败 → fast 模式(跳过 Stage3 LLM)
fast 模式失败 → rule_only 模式(仅 Stage1 规则引擎)
rule_only 失败 → 返回 [] + 写入 severity=info 的 engine_degraded 提示标记
               不阻塞写作流程
```

**原则**:连贯性引擎失败不应阻塞章节写作。

### 6.2 伏笔状态机失败模式

| 失败模式 | 描述 | 缓解策略 |
|---|---|---|
| **抽取漏报** | ExtractAgent 未检测到已回收的伏笔,paid 伏笔仍在 planted | 每 10 章对 critical 伏笔执行专项重扫描;WritingAgent 的 `payoff_log` 作为辅助信号 |
| **抽取误报** | 普通叙事细节被误标为伏笔,伏笔池充斥虚假承诺 | 置信度阈值(0.65)过滤;低置信候选入 pending 表;频繁被拒的类型自动提升阈值 |
| **伏笔池膨胀** | 数百条伏笔导致检索效率下降,上下文 token 成本上升 | paid/abandoned 冷存不参与检索;IVFFlat 索引(lists=100);每 100 章生成清理建议报告 |
| **状态机脏数据** | 并发写入导致状态不一致 | 所有转移通过 ForeshadowFSM.apply() 串行执行,内部 `SELECT FOR UPDATE` 行锁 |
| **修订回流状态错误** | 章节被修订删除触发证据,Foreshadow 仍为 triggered | 工程4 在修订时调用 `handleRevisionBackflow`;检查 segment 是否存在于 evidence_refs |
| **LLM 幻觉(虚假 payoff)** | WritingAgent 声称了 payoff 但正文无对应内容 | `payoff_log` 仅作辅助信号;最终状态推进由 ExtractAgent 独立扫描正文确认;不一致时记录 conflict_flag |
| **长期"挖坑不填"** | 早期伏笔经 300 章仍未回收 | 多级预警(watch/alert/critical)提供早期窗口;卷结束时生成"伏笔回收报告";payoff_rate 指标追踪 |

### 6.3 百万字下的性能防范

| 性能风险 | 量化估计 | 缓解 |
|---|---|---|
| `TimelineEvent` 表扫描 | 400 章 × 10 事件/章 = 4K 行 | 滑动窗口 + entity_refs GIN 索引 |
| `ConsistencyFlag` 历史 | 累积可能 5K+ 行 | chapter_id + status 复合索引;只查 open/confirmed |
| LLM 并发调用 | Stage 3 最多 N 个并发 | max_concurrent_llm=4(可配置);走实现3 成本路由 |
| OOC embedding 计算 | 每章对话段落全部比较 | voice_profile 缓存于内存;非对话段落跳过 OOC 检测 |
| 伏笔向量检索 | 数百条伏笔 embedding | IVFFlat(lists=100) + state 过滤减少候选集 |

## 7. MVP vs 完整版

### 7.1 MVP 阶段(验证核心闭环)

**目标**:能检测最高频硬逻辑错误,不误报爆炸,接口可用,伏笔可追踪。

连贯性校验 MVP:
- [ ] `check()` 接口 + Stage 1 规则引擎(符号状态 + 命名矛盾 + 关系有效区间)
- [ ] `SymbolStateSnapshot` 表 + 基础状态机(active/lost/destroyed)
- [ ] `ConsistencyFlag` 写入 + 基础 evidence_refs
- [ ] `update_flag_status()` 接口(confirmed/dismissed 回流)
- [ ] 工程2 侧栏展示 open flags(跳转冲突段落)

MVP 暂不实现:Stage 3 LLM 判定全类、向量 OOC、完整时间线冲突(T2/T3/T4/T6)、阈值自适应回流。

伏笔 MVP:
- [ ] `Foreshadow` 表 + payload JSONB(无 summary_embedding)
- [ ] 4 状态机:planted/triggered/paid/abandoned
- [ ] **仅人工标注** + 规划声明(`extraction_source="human_annotate"`)
- [ ] 简单章节计数预警(W₁=20/W₂=50/W₃=100,无 importance 修正)
- [ ] 侧栏全量列表按 warning_level 排序
- [ ] `scanForeshadow` 仅做预警等级更新,不调用 LLM 抽取
- [ ] 基础 CRUD + PATCH state API

MVP 不包含:ExtractAgent LLM 抽取、向量检索、修订回流联动、低置信度候选流程。

### 7.2 增强版(对抗中长程崩坏)

- [ ] Stage 2 向量语义(OOC 双通道 + 事件重复)
- [ ] Stage 3 LLM 判定(T2/C1/C4/N1/N3)

## 9. 开放问题

以下为待定或需实验验证项,当前设计中不视为已确定:

1. **故事内时间解析器的实现复杂度**:中文网文时间表述多样("翌日清晨"/"三年后的深秋"/"大战后第七天"),需健壮的 `parse_story_time()`。T1 时序矛盾检测依赖此解析器,若解析失败则降级为 LLM 判定。是否值得专项投入,需评估实际频率。

2. **OOC 阈值初始值确定**:θ_ooc 默认 0.65,最优值高度依赖作品风格和模型选择。需 MVP 运行 50+ 章后通过回流统计确定每部作品的实际最优值。

3. **LLM 判定成本实际占比**:Stage 3 理论上只处理 Stage 1+2 过滤后的候选。但写作早期(设定不完整、快照不充分)时,规则引擎召回率低,LLM 负担可能更重。需在增强版阶段度量实际成本分布。

4. **CFPG 检测率在中文网文语料的可复现性**:69.8% 是英文实测结果;中文伏笔表达方式是否需要专用 Prompt,待验证。

5. **top_k=30 的伏笔检索上限**:实际写作中是否足够?是否会漏掉关键伏笔?需在增强版阶段度量。

6. **notify_setting_modified 的调用时机**:设定修改触发受影响章节重校验是高代价操作(潜在数百章)。是否同步触发还是全部走后台异步队列,需结合用户体验(立即看到更新 vs 容忍延迟)决策。

7. **多 POV 作品的 OOC 处理**:本设计假设每章有明确的 POV 角色。多 POV 章节或全知视角作品,OOC 检测和 N1/N3 检测的策略需专门设计,当前版本为 MVP 级占位处理。

8. **伏笔依赖图是否需要支持**:一个伏笔的 payoff 依赖另一个伏笔先 paid 的情形(如多线交汇),当前不支持。依赖关系由作者用 tags 手动关联,是否需要正式建模待完整版阶段决策。

9. **百万字崩坏率真实曲线**:调研文档已明确"崩坏率随长度的真实曲线仍是未知数"【已核实为未知】。本模块的有效性最终需要通过自建度量(至少 20 万字以上的端到端测试)来验证,在此之前所有设计参数均为估算值。

10. **连贯性引擎与伏笔状态机的合并边界**:本文档将两者合并为一个后台门槛文档。在实现时,连贯性引擎和 ForeshadowFSM 建议作为同一后台服务的两个子模块,共用同一 ExtractAgent 调用(避免对同一章节正文发起重复 LLM 调用),具体合并策略需在增强版实现时细化。
