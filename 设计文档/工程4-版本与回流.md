## 1. 在回路中的位置与职责

### 1.1 一句话定位

本文是**协作回路的持久化与传播层**:内核1 产生的每个 Snapshot(AI 草稿、重做版、定稿)都在这里被安全写入、版本化管理、可差异比对;当作者在回路中"接受重做"或"修改设定"时,本文负责把这个人工确认的语义**向外扩散**——回写门槛2(设定圣经)、更新实现4(记忆)、触发门槛1(连贯性增量校验)、喂回内核2(品味信号)。

### 1.2 回路位置图

```
        人(作者)
         │ ④ 提意见 / 接受重做 / 修改设定
         ▼
  ┌─────────────────────────────┐
  │  内核1 · 作者协作回路        │
  │  FeedbackNote → parsed_directive → 重做任务
  │  → RewriteAgent 执行重写     │
  └──────────────┬──────────────┘
                 │ Snapshot(ai-draft)  ← 本文接管
                 ▼
  ┌─────────────────────────────────────────────────────────┐
  │  工程4 · 版本与回流                                       │
  │                                                         │
  │  ① 写入新 Snapshot(ai-draft/human-final/merged)          │
  │  ② 维护版本树(parent_id DAG + ChapterHead 指针)           │
  │  ③ 提供 diff 数据(供工程2 UI 展示)                        │
  │  ④ 人工"接受重做/确认定稿"时触发回流:                      │
  │     → 回写门槛2(SettingItem/CharState/EntityRelation)    │
  │     → 更新实现4(MemoryEntry)                             │
  │     → 发 PreferenceSignal → 内核2(品味)                  │
  │     → 影响分析 → 触发门槛1 增量校验                        │
  │  ⑤ AI 覆盖保护(is_human_locked 检查)                     │
  │  ⑥ 增量存储 + 归档(百万字存储策略)                         │
  └─────────────────────────────────────────────────────────┘
```

## 2. 设计目标与百万字挑战

### 2.1 设计目标

| # | 目标 | 可度量指标 |
|---|---|---|
| G-1 | Snapshot 不可丢失 | 任意 `snapshot_id` 在 100ms 内恢复全文 |
| G-2 | diff 快速可用 | 相邻版本 char-level diff ≤ 50ms(章均 3000 字) |
| G-3 | 回流端到端延迟 | 人工"接受重做" → 回流完成(回写门槛2 + 触发校验入队) ≤ 2s |
| G-4 | 影响分析精确率 ≥ 90% | 受控测试集上"应被波及章节"召回率 ≥ 90%,误报率 ≤ 15% |
| G-5 | 百万字存储可控 | 500 章 × 10 版本,增量存储后总体积 ≤ 全量的 25% |
| G-6 | 人工修改不被 AI 覆盖 | `human-final` 分支任意段落不被 AI 重生成静默覆盖 |
| G-7 | 品味信号不遗漏 | 每次"接受重做/拒绝重做"均产生 PreferenceSignal,回流率 = 100% |

### 2.2 百万字下的具体挑战

**挑战 I:版本体积爆炸**
500 章 × 10 版本 × 6KB/章 ≈ 30MB 纯文本;加上 embedding、JSONB 元数据、delta 开销,实际可达数百 MB。
→ 解法:增量 delta 存储 + 检查点 + 冷归档(§3.8)。

**挑战 II:影响分析的图搜索复杂度**
改一个核心设定(如主角能力体系)可能波及 400 章。全量 Segment 扫描不可接受。
→ 解法:预计算 EntityChapterIndex 倒排索引 + 有效区间剪枝(§3.6)。

**挑战 III:回流的语义抽取质量**
人工改写正文时,系统需理解"改了什么语义"才能决定回写哪个设定条目。纯规则覆盖不全,纯 LLM 有幻觉。
→ 解法:规则优先提取 + LLM 辅助 + 人确认低置信度变更(§3.4)。

**挑战 IV:链式重做产生的版本爆炸**
一段文字被重做 5 次(链式 FeedbackNote),每次产生一个 ai-draft 分支,版本树横向膨胀。
→ 解法:同一 `target_id` 的新重做取消旧重做任务;分支按时间归档(§3.8)。

**挑战 V:回流级联效应**
改第 5 章设定 → 重校验 100 章 → 10 章需修改 → 再次回流 → 无限循环。
→ 解法:epoch 去重 + 最大深度限制 + 级联必须经人确认(§3.4.6)。

## 3. 详细设计

### 3.1 Snapshot 版本树:AI 草稿分支 vs 定稿分支

#### 3.1.1 版本树拓扑

版本树以 `Snapshot` 表为节点,`parent_id` 为有向边,形成章节粒度的有向无环图(DAG)。

```
Chapter C14 的版本树示例:

S1 ── ai-draft ── epoch=1
│   "AI 首次生成草稿"
│
├── S2 ── ai-draft ── epoch=2          ← FeedbackNote-1 触发重做
│   "RewriteAgent 重做:压缩心理独白"
│   │
│   └── S3 ── ai-draft ── epoch=3      ← FeedbackNote-2 链式重做
│       "RewriteAgent 重做:加快节奏"
│
└── S4 ── human-final ── epoch=4       ← 作者接受 S2 并定稿
    "作者接受重做版 S2,微调一处细节"
    │
    └── S5 ── human-final ── epoch=5   ← 作者二次精修
        "二次精修后的终稿"
        [is_human_locked = TRUE]        ← 作者显式锁定

HEAD → S5
```

**核心规则**:
- 每个 `Chapter` 同时可以有多条活跃 branch,但只有一个 `HEAD`(当前展示给作者的版本)
- `HEAD` 始终指向最新的"已确认"版本
- AI 重做只产生 `ai-draft` 分支 Snapshot,不自动移动 HEAD;HEAD 的移动必须由人工确认

#### 3.1.2 branch_label 枚举与创建时机

| branch_label | 含义 | 创建时机 | 谁创建 |
|---|---|---|---|
| `ai-draft` | AI 编排器自动生成的草稿 | `WritingAgent` / `RewriteAgent` 每次生成后 | 本文 VersionService |
| `ai-draft-v{n}` | 多候选草稿(OptionSet 多方案) | `WritingAgent` 配置输出多候选时 | 本文 VersionService |
| `human-final` | 作者定稿或部分定稿 | 人工首次编辑或接受 AI 草稿时 | 本文 VersionService |
| `merged` | 从多分支合并产生 | 执行 cherry-pick 或三路合并后 | 本文 VersionService |
| `archived` | 已归档 | 超出保留窗口后软迁移 | 归档定时任务 |

#### 3.1.3 HEAD 管理表

`Snapshot` 表之外,维护一张 `ChapterHead` 轻量指针表:

```sql
CREATE TABLE ChapterHead (
  chapter_id   UUID PRIMARY KEY REFERENCES Chapter(id),
  snapshot_id  UUID NOT NULL REFERENCES Snapshot(id),
  updated_at   TIMESTAMPTZ DEFAULT now()
);

-- 读取章节内容时:先查 ChapterHead → 再取 Snapshot.content
-- 不直接在 Snapshot 表上做 "WHERE is_head=TRUE" 全扫描
```

`Snapshot` 表保留冗余字段 `is_head BOOLEAN` 仅用于加速单次快照查询,双写 `ChapterHead` 保证一致性。

#### 3.1.4 Snapshot 完整建表 DDL

```sql
CREATE TABLE Snapshot (
  -- 00 §4.4 规范字段
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  chapter_id      UUID NOT NULL REFERENCES Chapter(id),
  content         TEXT,              -- 全量文本;增量版本时为 NULL
  created_by      TEXT NOT NULL CHECK (created_by IN ('ai', 'human')),
  parent_id       UUID REFERENCES Snapshot(id),
  branch_label    TEXT NOT NULL DEFAULT 'ai-draft',
  created_at      TIMESTAMPTZ DEFAULT now(),

  -- 本模块扩展字段
  delta           JSONB,             -- 增量存储:unified-diff-v1 格式
  word_count      INTEGER,           -- 快照字数,避免每次重计
  is_full         BOOLEAN DEFAULT TRUE,  -- TRUE=全量,FALSE=增量(用 delta 恢复)
  epoch           INTEGER DEFAULT 1,     -- 单调递增,每次人工确认提交递增
  is_head         BOOLEAN DEFAULT FALSE, -- 冗余标记,加速 HEAD 查询
  is_human_locked BOOLEAN DEFAULT FALSE, -- 人工锁定:锁定后 AI 不可覆盖
  lock_at         TIMESTAMPTZ,
  lock_by         TEXT,              -- 锁定者 user_id 或 'system'

  -- 元数据(代表 Agent 标识/模型版本/生成成本/FeedbackNote 关联)
  meta            JSONB DEFAULT '{}',

  -- 软删除
  deleted_at      TIMESTAMPTZ
);

-- 索引
CREATE INDEX idx_snapshot_chapter  ON Snapshot(chapter_id, created_at DESC);
CREATE INDEX idx_snapshot_parent   ON Snapshot(parent_id) WHERE parent_id IS NOT NULL;
CREATE INDEX idx_snapshot_branch   ON Snapshot(chapter_id, branch_label, created_at DESC);
CREATE INDEX idx_snapshot_head     ON Snapshot(chapter_id) WHERE is_head = TRUE;
CREATE INDEX idx_snapshot_epoch    ON Snapshot(chapter_id, epoch DESC);
```

### 3.2 多方案与链式重做产生的版本拓扑

#### 3.2.1 OptionSet 多候选方案 → 版本拓扑

内核1 的 OptionSet 为一个决策点生成 2–4 个差异化方案,每个方案产生独立的 `ai-draft-vN` 分支 Snapshot:

```
Chapter C14 的 OptionSet 版本拓扑:

                S_base (ai-draft, 草稿主干)
               /        |          \
    S_opt_A            S_opt_B      S_opt_C
  (ai-draft-v1)      (ai-draft-v2)  (ai-draft-v3)
  方案A正文节选      方案B正文节选   方案C正文节选

  [作者选择 C]
        │
        ▼
  S_chosen (ai-draft, 基于 S_opt_C 继续生成完整章节)
        │
        ▼
  S_final (human-final)    ← 作者确认定稿

HEAD → S_final
未选的 S_opt_A / S_opt_B 保留在版本树中,不删除(供历史对比)
```

**关键设计**:`meta` 字段记录 `optionset_id` 和 `option_id`,使每个候选 Snapshot 可溯源到具体的 OptionSet 方案。

#### 3.2.2 链式 FeedbackNote → 链式 Snapshot

内核1 支持链式反馈(对重做版再次提意见),每轮反馈产生新的 `ai-draft` Snapshot:

```python
# FeedbackNote 链 → Snapshot 链的对应关系:

FeedbackNote_1 (target=S1, resulted_snapshot_id=S2)
  └── FeedbackNote_2 (target=S2, resulted_snapshot_id=S3)
        └── FeedbackNote_3 (target=S3, resulted_snapshot_id=S4)
              [作者接受 S4]

S1 ──(parent)──▶ S2 ──(parent)──▶ S3 ──(parent)──▶ S4 ──(parent)──▶ S_final(human)
                                                      ↑
                                              HEAD 移动到这里(接受后)
```

**FeedbackNote.parent_feedback_id** 记录链式关系,与 `Snapshot.parent_id` 链一一对应,形成可完整追溯的改写历程。

#### 3.2.3 创建 Snapshot 的统一入口

所有 Snapshot 的创建都走同一个函数,保证元数据的一致性:

```python
def create_snapshot(
    chapter_id: str,
    content: str | None,          # 全量时有值;增量时为 None
    created_by: Literal["ai", "human"],
    parent_id: str | None,
    branch_label: str,
    meta: dict | None = None,     # agent_id / model_id / feedback_id / optionset_id 等
    delta: dict | None = None,    # 增量时有值
    is_full: bool = True
) -> Snapshot:
    """
    创建新 Snapshot。
    - AI 调用:created_by='ai',branch_label='ai-draft'
    - 人工定稿:created_by='human',branch_label='human-final'
    - 若是 FeedbackNote 重做,meta 中带 feedback_id
    - 若是 OptionSet 候选,meta 中带 optionset_id + option_id
    """
    snap = Snapshot(
        chapter_id=chapter_id,
        content=content,
        created_by=created_by,
        parent_id=parent_id,
        branch_label=branch_label,
        delta=delta,
        is_full=is_full,
        word_count=len(content) if content else estimate_from_delta(delta),
        epoch=get_next_epoch(chapter_id),
        meta=meta or {},
        is_head=False  # HEAD 由 set_head() 单独管理
    )
    db.insert(snap)
    maybe_create_checkpoint(snap.id)  # 检查是否需要物化全量检查点
    return snap


def set_head(chapter_id: str, snapshot_id: str) -> None:
    """
    移动 HEAD 指针。同步更新 ChapterHead 表和 Snapshot.is_head 冗余字段。
    移动 HEAD 是人工确认行为的终态:
      - 接受重做 → set_head(chapter_id, new_snapshot.id)
      - 定稿 → set_head + 可选 lock_chapter
      - 回退 → set_head(chapter_id, previous_human_final.id)
    """
    # 清除旧 HEAD 标记
    db.execute(
        "UPDATE Snapshot SET is_head=FALSE WHERE chapter_id=:cid AND is_head=TRUE",
        {"cid": chapter_id}
    )
    # 设置新 HEAD
    db.execute(
        "UPDATE Snapshot SET is_head=TRUE WHERE id=:sid",
        {"sid": snapshot_id}
    )
    db.upsert(ChapterHead(chapter_id=chapter_id, snapshot_id=snapshot_id))
```

### 3.3 diff 呈现(供工程2)

#### 3.3.1 三层 diff 粒度

| 粒度 | 用途 | 算法 |
|---|---|---|
| 字符级 `char` | 前端高亮精确变更位置 | Myers diff O((N+M)D) |
| 词语级 `word` | 更可读的"意思变了哪里" | tokenize → Myers diff |
| 段落级 `segment` | 影响分析判断哪些段落变化;cherry-pick 操作的最小粒度 | 按换行符分段 → LCS diff |

#### 3.3.2 diff 计算核心伪代码

```python
@dataclass
class DiffHunk:
    hunk_type: Literal["added", "deleted", "unchanged"]
    a_start: int        # 在 A 版本中的偏移(字符/词/段 由粒度决定)
    a_end: int
    b_start: int        # 在 B 版本中的偏移
    b_end: int
    a_text: str
    b_text: str
    segment_id: str | None  # 粒度=segment 时,对应已存库的 Segment.id

@dataclass
class DiffStats:
    added: int
    deleted: int
    unchanged: int
    change_ratio: float   # (added+deleted)/(added+deleted+unchanged)

@dataclass
class DiffResult:
    snapshot_a_id: str
    snapshot_b_id: str
    granularity: str
    hunks: list[DiffHunk]
    stats: DiffStats


def compute_diff(
    snapshot_a: Snapshot,
    snapshot_b: Snapshot,
    granularity: Literal["char", "word", "segment"] = "char"
) -> DiffResult:
    text_a = resolve_full_text(snapshot_a)  # 若增量则先恢复全文
    text_b = resolve_full_text(snapshot_b)

    match granularity:
        case "char":
            units_a, units_b = list(text_a), list(text_b)
        case "word":
            units_a = tokenize_words(text_a)
            units_b = tokenize_words(text_b)
        case "segment":
            units_a = split_paragraphs(text_a)
            units_b = split_paragraphs(text_b)

    edit_script = myers_diff(units_a, units_b)
    hunks = build_hunks(edit_script, context_lines=3)
    stats = DiffStats(
        added   = sum(len(h.b_text) for h in hunks if h.hunk_type == "added"),
        deleted = sum(len(h.a_text) for h in hunks if h.hunk_type == "deleted"),
        unchanged = sum(len(h.a_text) for h in hunks if h.hunk_type == "unchanged"),
        change_ratio = 0.0  # 后计算
    )
    stats.change_ratio = (stats.added + stats.deleted) / max(
        stats.added + stats.deleted + stats.unchanged, 1
    )
    return DiffResult(snapshot_a.id, snapshot_b.id, granularity, hunks, stats)


def resolve_full_text(snap: Snapshot) -> str:
    """
    若 snap.is_full=True,直接返回 snap.content。
    否则沿 parent_id 链向上找到最近的全量快照,顺序应用 delta 恢复全文。
    链长度上限 = MAX_DELTA_CHAIN(默认 20),超过则存在检查点必被命中。
    """
    if snap.is_full:
        return snap.content
    chain: list[Snapshot] = []
    cur = snap
    while not cur.is_full:
        chain.append(cur)
        cur = fetch_snapshot(cur.parent_id)
    # cur 现在是最近的全量快照
    text = cur.content
    for s in reversed(chain):     # 从旧到新应用 delta
        text = apply_unified_diff(text, s.delta)
    return text
```

#### 3.3.3 供工程2 的 diff 视图约定

工程2 从工程5 API 获取 `DiffResult`,按以下约定渲染:

```
视图约定(工程2 实现,本文定义语义):

  绿色底色高亮   → added hunk (新版本新增)
  红色删除线     → deleted hunk (被删除的旧内容)
  蓝色段落标记   → segment 粒度 diff 中发生变化的段落
  灰色折叠       → unchanged hunk 超过 5 行时折叠

两种视图模式:
  [并排对比]   → A/B 两列,对齐 hunk
  [内联差异]   → 单列,交替显示 deleted(红)/added(绿)

快捷操作(供 cherry-pick):
  每个 hunk 右侧有 [接受这段] / [保留原版] 按钮
  → 触发 cherry_pick_segments(selected_hunk_indices=[...])
```

### 3.4 修订回流:意见/设定修改→回写门槛层→触发校验

#### 3.4.1 设计核心:回流是"意见→重做"主交互的语义扩散

旧设计把修订回流定位为"人工改正文 → 反哺设定圣经"。在新协作回路中,**这个定位需要重构**:

- **主要触发路径**:内核1 的 `FeedbackNote → RewriteAgent → 新 Snapshot` → **作者接受重做** → 回流
- **次要触发路径**:作者直接在门槛2(设定圣经)修改 SettingItem → 回流
- **第三触发路径**:作者在正文中手工编辑(不走 FeedbackNote)→ 回流

三条路径共享同一套回流流水线,但触发语义不同:

| 触发路径 | `created_by` | 回流触发条件 | PreferenceSignal |
|---|---|---|---|
| 接受 FeedbackNote 重做 | `ai` → 人确认后升为 `human-final` | 立即触发 | 必须产生(§3.5) |
| 门槛2 设定圣经修改 | `human`(setting_edit) | 立即触发 | 不产生 |
| 正文手工编辑 | `human` | 人提交时触发 | 不产生 |

#### 3.4.3 变更分类器(Step 1)

```python
@dataclass
class ChangeClassification:
    source_type: Literal["feedback_accept", "setting_edit", "text_edit", "flag_resolution"]
    change_domain: Literal["character", "world_rule", "item", "place",
                           "faction", "foreshadow", "timeline", "style", "other"]
    affected_entities: list[str]   # 涉及的实体 id
    confidence: float
    needs_confirmation: bool       # 低置信度时需人工确认


def classify_change(request: RevisionBackflowRequest) -> ChangeClassification:
    # --- 路径 A:接受 FeedbackNote 重做 ---
    if request.source_type == "feedback_accept":
        feedback = fetch_feedback_note(request.feedback_id)
        directive = feedback.parsed_directive
        # ParsedDirective.critique_type → change_domain 直接映射
        domain_map = {
            "characterization": "character",
            "prose_quality":    "style",
            "pacing":           "style",
            "tone":             "style",
            "plot_logic":       "world_rule",
            "emotion":          "character",
        }
        return ChangeClassification(
            source_type="feedback_accept",
            change_domain=domain_map.get(directive["critique_type"], "other"),
            affected_entities=directive.get("scope_refs", []),
            confidence=directive.get("parse_confidence", 0.8),
            needs_confirmation=False  # 接受重做时作者已经确认过意图
        )

    # --- 路径 B:门槛2 设定圣经直接修改 ---
    if request.source_type == "setting_edit":
        item = fetch_setting_item(request.setting_item_id)
        return ChangeClassification(
            source_type="setting_edit",
            change_domain=item.type,   # SettingItem.type 直接对应 change_domain
            affected_entities=[item.id],
            confidence=1.0,
            needs_confirmation=False
        )

    # --- 路径 C:正文手工编辑 ---
    if request.source_type == "text_edit":
        diff = compute_diff(
            fetch_snapshot(request.before_snapshot_id),
            fetch_snapshot(request.after_snapshot_id),
            granularity="segment"
        )
        changed = [h for h in diff.hunks if h.hunk_type != "unchanged"]
        known_entities = fetch_all_entities(request.work_id)
        mentioned = find_entity_mentions(changed, known_entities)

        if mentioned and all(e.is_structured for e in mentioned):
            return ChangeClassification(
                source_type="text_edit",
                change_domain=infer_domain_from_entities(mentioned),
                affected_entities=[e.id for e in mentioned],
                confidence=0.85,
                needs_confirmation=False
            )
        # 含未知实体 → LLM 辅助分类
        llm_result = llm_classify_change(changed, request.work_id, known_entities)
        return ChangeClassification(
            **llm_result,
            needs_confirmation=(llm_result["confidence"] < 0.7)
        )
```

#### 3.4.4 变更提取(Step 2)

```python
@dataclass
class ChangeItem:
    """一条结构化变更:描述"什么变成了什么"。"""
    change_type: Literal["add", "modify", "deprecate"]
    target_type: Literal["SettingItem", "CharState", "Character",
                         "EntityRelation", "Foreshadow", "MemoryEntry"]
    target_id: str | None          # 修改/废弃时有值;新增时为 None
    old_value: dict | None         # 旧值(审计用)
    new_value: dict                # 要写入的新值
    evidence_text: str             # 触发此变更判断的原文摘录
    evidence_snapshot_id: str      # 来源 Snapshot.id
    confidence: float


def extract_change_items(
    diff: DiffResult,
    classification: ChangeClassification,
    work_id: str
) -> list[ChangeItem]:
    """
    策略:规则层先跑(快速,确定性强) → LLM 辅助层补充复杂变更 → 人确认低置信度项。
    """
    items: list[ChangeItem] = []

    # ── 规则层:CharState 提取(快速模式识别) ──────────────────────────────────
    # 模式:"[角色名] + [能力/状态动词]"  →  CharState 变更
    # 例:"韩立突破至化神境" → CharState(char=韩立, ability=化神境, chapter=当前章)
    for hunk in [h for h in diff.hunks if h.hunk_type != "unchanged"]:
        for cs_change in extract_char_state_pattern(hunk.b_text, work_id):
            items.append(cs_change)

    # ── 规则层:SettingItem 直接修改 ─────────────────────────────────────────
    if classification.source_type == "setting_edit":
        items.append(ChangeItem(
            change_type="modify",
            target_type="SettingItem",
            target_id=classification.affected_entities[0],
            old_value=fetch_setting_item(classification.affected_entities[0]).content,
            new_value=extract_setting_new_value(diff),
            evidence_text=diff_to_evidence_text(diff),
            evidence_snapshot_id=diff.snapshot_b_id,
            confidence=1.0
        ))

    # ── LLM 辅助层:复杂/非结构化变更 ─────────────────────────────────────────
    if needs_llm_extraction(classification, items):
        llm_items = llm_extract_changes(
            changed_text=get_changed_text(diff),
            existing_items=items,
            work_context=fetch_work_context(work_id),
            classification=classification
        )
        for item in llm_items:
            item.confidence = min(item.confidence, 0.75)  # LLM 提取上限 0.75
        items.extend(llm_items)

    return deduplicate_change_items(items)
```

#### 3.4.5 回写门槛层与更新记忆(Step 3a/3b)

```python
BACKFLOW_AUTO_THRESHOLD = 0.80  # 高于此阈值自动回写;低于则进入待确认队列


def execute_backflow(
    change_items: list[ChangeItem],
    chapter_id: str,
    work_id: str,
    requires_confirmation: bool
) -> BackflowResult:
    confirmed, pending = [], []

    for item in change_items:
        if item.confidence >= BACKFLOW_AUTO_THRESHOLD and not requires_confirmation:
            confirmed.append(item)
        else:
            pending.append(item)

    # ── 高置信度:直接回写 ────────────────────────────────────────────────────
    for item in confirmed:
        match item.target_type:

            case "SettingItem":
                # → 门槛2(设定圣经)接口
                story_bible_service.update_setting_item(
                    item_id=item.target_id,
                    new_content=item.new_value,
                    change_type=item.change_type,
                    source_chapter_id=chapter_id,
                    evidence_text=item.evidence_text
                )

            case "CharState":
                # → 门槛2 接口
                story_bible_service.upsert_char_state(
                    character_id=item.new_value["character_id"],
                    chapter_id=chapter_id,
                    state_desc=item.new_value["state_desc"],
                    change_type=item.new_value["change_type"]
                )

            case "Character":
                story_bible_service.update_character(
                    character_id=item.target_id,
                    fields=item.new_value
                )

            case "EntityRelation":
                story_bible_service.update_entity_relation(
                    relation_id=item.target_id,
                    new_relation=item.new_value
                )

            case "Foreshadow":
                foreshadow_service.update_foreshadow(
                    foreshadow_id=item.target_id,
                    new_state=item.new_value
                )

            case "MemoryEntry":
                # → 实现4(记忆与检索)接口
                memory_service.update_memory(
                    chapter_id=chapter_id,
                    delta=item.new_value,
                    scope=item.new_value.get("scope", "global")
                )

    # ── 触发记忆摘要重建 ─────────────────────────────────────────────────────
    # 只要有实体级变更,就通知实现4 更新相关记忆段
    if any(i.target_type in ("CharState", "SettingItem", "Character")
           for i in confirmed):
        memory_service.update_memory_for_chapter(chapter_id)

    # ── 写入审计记录 ─────────────────────────────────────────────────────────
    db.insert(BackflowRecord(
        work_id=work_id,
        trigger_chapter_id=chapter_id,
        trigger_snapshot_id=get_head_snapshot(chapter_id).id,
        change_items=[i.__dict__ for i in confirmed],
        impact_set=None,   # 将在 Step 4 填充
        confirmed_by="auto" if not requires_confirmation else "pending"
    ))

    return BackflowResult(confirmed=confirmed, pending=pending, work_id=work_id)
```

#### 3.4.6 防循环机制(epoch + depth 限制)

```python
BACKFLOW_MAX_DEPTH = 3
# work_id → last_epoch_processed;存在 Redis 或内存(进程级)
_BACKFLOW_EPOCH_CACHE: dict[str, int] = {}


def should_trigger_backflow(work_id: str, current_epoch: int, depth: int) -> bool:
    """
    双重防循环:
    1. epoch 去重:同一 work 在同一 epoch 内不重复触发
    2. depth 限制:级联深度超过 3 时截断
    """
    if depth >= BACKFLOW_MAX_DEPTH:
        logger.warning(f"[Backflow] 级联深度 {depth} 超限,work={work_id},停止")
        return False
    last = _BACKFLOW_EPOCH_CACHE.get(work_id, 0)
    if current_epoch <= last:
        logger.warning(f"[Backflow] epoch 重复 {current_epoch},work={work_id},跳过")
        return False
    _BACKFLOW_EPOCH_CACHE[work_id] = current_epoch
    return True
```

**级联必须经人确认**:Step 4 触发门槛1 校验后,若校验产生新的 `ConsistencyFlag`,这些 Flag 需要人工"裁决已修复"才能再次触发回流,不会自动级联。

### 3.5 回流的 PreferenceSignal 回路

#### 3.5.1 设计原则

"接受重做"这个动作是作者**对 AI 生成方向的明确认可**,是品味信号质量最高的来源之一。本模块在 Step 3c 负责产生 PreferenceSignal,交由内核2 汇总学习。

**信号的双面性**:
- 接受重做 → 重做方向是**正向**信号
- 拒绝重做(保持原版)→ 重做方向是**负向**信号,且原版方向是正向信号

#### 3.5.2 接受重做时的信号产生

```python
def emit_feedback_preference_signals(
    feedback: FeedbackNote,
    old_snapshot: Snapshot,
    new_snapshot: Snapshot,
    accepted: bool,
    user_id: str
) -> None:
    """
    在作者点击 [接受重做版] 或 [拒绝,保持原版] 后调用。
    产生 PreferenceSignal,发往内核2。
    """
    directive = feedback.parsed_directive

    if accepted:
        # ── 正向信号:接受此次重做方向 ──────────────────────────────────────
        create_preference_signal(
            owner_id=user_id,
            work_id=feedback.work_id,
            source="feedback",
            signal={
                "critique_type":       directive["critique_type"],
                "primary_instruction": directive["primary_instruction"],
                "style_direction":     directive["style_direction"],
                "feedback_id":         feedback.id,
                "snapshot_before_id":  old_snapshot.id,
                "snapshot_after_id":   new_snapshot.id
            },
            polarity="+",
            weight=1.5   # 双重确认:先提意见再接受,权重最高
        )

        # ── 对 diff 的语义特征产生额外信号 ──────────────────────────────────
        diff = compute_diff(old_snapshot, new_snapshot, granularity="segment")
        if diff.stats.change_ratio > 0.3:
            # 改动较大且被接受 → 对"大幅改写风格"的正向信号
            create_preference_signal(
                owner_id=user_id,
                work_id=feedback.work_id,
                source="revision_diff",
                signal={
                    "change_ratio": diff.stats.change_ratio,
                    "direction": directive["style_direction"]
                },
                polarity="+",
                weight=0.8
            )

    else:
        # ── 负向信号:拒绝此次重做方向 ──────────────────────────────────────
        create_preference_signal(
            owner_id=user_id,
            work_id=feedback.work_id,
            source="feedback",
            signal={
                "critique_type":       directive["critique_type"],
                "primary_instruction": directive["primary_instruction"],
                "style_direction":     directive["style_direction"],
                "feedback_id":         feedback.id,
                "rejected": True
            },
            polarity="-",
            weight=0.8
        )
```

#### 3.5.3 PreferenceSignal 权重表(本模块产生的信号)

| 触发事件 | source | polarity | weight | 说明 |
|---|---|---|---|---|
| 接受 FeedbackNote 重做 | `feedback` | `+` | 1.5 | 双重确认,权重最高 |
| 拒绝 FeedbackNote 重做 | `feedback` | `-` | 0.8 | 重做方向被否定 |
| 重做 diff change_ratio > 0.3 且被接受 | `revision_diff` | `+` | 0.8 | 大幅改写风格被认可 |
| 接受 OptionSet 候选方案 | `option_choice` | `+` | 1.0 | 由内核1 产生,本模块不重复 |
| 人工定稿(`human-final` 首次创建) | `revision_diff` | `+` | 1.2 | 定稿 = 对当前版本的整体认可 |

**注意**:OptionSet 的 PreferenceSignal 由内核1 `record_option_choice` 产生,本模块不重复产生,避免重复计权。

### 3.6 影响分析算法

#### 3.6.1 总设计目标

影响分析回答:**"改了这一处设定/角色/伏笔,究竟哪些章节需要重新检查?"**

其精确性决定门槛1 增量校验的召回率与资源消耗:召回率低则遗漏不一致;误报率高则浪费校验计算。

```
输入:
  change_items: list[ChangeItem]   — 来自 Step 2 的变更列表
  work_id: str

输出:
  ImpactSet {
    affected_chapters:   list[AffectedChapter]
    impact_reason_map:   dict[chapter_id, list[ImpactReason]]
    estimated_severity:  dict[chapter_id, float]   # 0.0–1.0
    analysis_duration_ms: int
  }

算法步骤:
  1. 对每个 ChangeItem 独立计算影响章节集合
  2. 所有集合取并集,合并同一章节的多个影响原因
  3. 计算每章严重度评分
  4. 返回 ImpactSet
```

#### 3.6.2 EntityChapterIndex:预计算倒排索引

百万字规模下,实时全量扫描 Segment 表(500 章 × 多段落)代价过高。引入预计算倒排索引:

```sql
CREATE TABLE EntityChapterIndex (
  entity_id    UUID NOT NULL,            -- SettingItem/Character/Foreshadow 的 id
  entity_type  TEXT NOT NULL,            -- 'SettingItem'|'Character'|'Foreshadow' 等
  chapter_id   UUID NOT NULL REFERENCES Chapter(id),
  chapter_seq  INTEGER NOT NULL,         -- 冗余,方便范围查询
  work_id      UUID NOT NULL REFERENCES Work(id),
  ref_count    INTEGER DEFAULT 1,        -- 该章节提及次数(影响严重度权重)
  last_updated TIMESTAMPTZ DEFAULT now(),
  PRIMARY KEY (entity_id, chapter_id)
);

CREATE INDEX idx_eci_entity   ON EntityChapterIndex(entity_id, work_id);
CREATE INDEX idx_eci_chapter  ON EntityChapterIndex(chapter_id);
CREATE INDEX idx_eci_seq      ON EntityChapterIndex(work_id, entity_type, chapter_seq);
```

**索引维护时机**:
1. `ExtractAgent` 处理完每章段落后,批量 `UPSERT` 该章所有实体引用
2. `SettingItem` / `Character` 创建或改名时,重建该实体的索引行(重命名需更新关键词)
3. 全量重建接口 `rebuild_entity_chapter_index(work_id)` 供老作品迁移使用

#### 3.6.3 各变更类型的影响范围计算(完整伪代码)

```python
def compute_impact_for_change_item(
    item: ChangeItem,
    work_id: str,
    all_chapters: list[Chapter]
) -> list[AffectedChapter]:
    """
    根据变更类型分别计算受影响章节。
    四类实体各有不同的影响区间规则。
    """
    affected: list[AffectedChapter] = []

    # ══════════════════════════════════════════════════════════════════
    # 类型 1:SettingItem 变更
    # 规则 SI-1:影响范围 = [first_chapter_id.seq, +∞)
    # 理由:设定项在首次引入后的所有章节都可能依赖此设定
    # 过滤 SI-F1:仅保留 EntityChapterIndex 中命中该 item 的章节(索引优先)
    # ══════════════════════════════════════════════════════════════════
    if item.target_type == "SettingItem":
        setting = fetch_setting_item(item.target_id)
        first_seq = get_chapter_seq(setting.first_chapter_id)

        # 从索引直接获取(O(k),k = 该设定被引用的章节数)
        index_rows = db.query("""
            SELECT chapter_id, chapter_seq, ref_count
            FROM EntityChapterIndex
            WHERE entity_id = :eid AND work_id = :wid
              AND chapter_seq >= :first_seq
            ORDER BY chapter_seq
        """, {"eid": item.target_id, "wid": work_id, "first_seq": first_seq})

        for row in index_rows:
            affected.append(AffectedChapter(
                chapter_id=row.chapter_id,
                chapter_seq=row.chapter_seq,
                reason=ImpactReason(
                    type="setting_changed",
                    source_item_id=item.target_id,
                    detail=f"设定项「{setting.name}」发生变更"
                ),
                severity=compute_severity_setting(item, row.ref_count)
            ))

    # ══════════════════════════════════════════════════════════════════
    # 类型 2:Character / CharState 变更
    # 规则 CS-1:
    #   Character 基础属性变更 → 全书所有出现该角色的章节
    #   CharState 变更 → [state发生章节.seq, +∞) 内出现该角色的章节
    # 过滤 CS-F1:仅保留出现过该角色的章节(通过 EntityChapterIndex)
    # ══════════════════════════════════════════════════════════════════
    elif item.target_type in ("Character", "CharState"):
        char_id = (item.new_value.get("character_id")
                   if item.target_type == "CharState"
                   else item.target_id)
        character = fetch_character(char_id)

        if item.target_type == "CharState":
            change_seq = get_chapter_seq(item.new_value["chapter_id"])
        else:
            change_seq = 1  # 基础属性 → 全书

        index_rows = db.query("""
            SELECT chapter_id, chapter_seq, ref_count
            FROM EntityChapterIndex
            WHERE entity_id = :eid AND work_id = :wid
              AND chapter_seq >= :from_seq
            ORDER BY chapter_seq
        """, {"eid": char_id, "wid": work_id, "from_seq": change_seq})

        for row in index_rows:
            affected.append(AffectedChapter(
                chapter_id=row.chapter_id,
                chapter_seq=row.chapter_seq,
                reason=ImpactReason(
                    type="character_changed",
                    source_item_id=char_id,
                    detail=f"角色「{character.name}」状态/属性发生变更"
                ),
                severity=compute_severity_char(item, row.ref_count)
            ))

    # ══════════════════════════════════════════════════════════════════
    # 类型 3:EntityRelation 有效区间变更
    # 规则 ER-1:影响区间 = [valid_from_chapter.seq, valid_to_chapter.seq]
    #           (valid_to 为空时取书末)
    # 过滤 ER-F1:区间内提及了 src_entity 或 dst_entity 的章节
    # ══════════════════════════════════════════════════════════════════
    elif item.target_type == "EntityRelation":
        relation = fetch_entity_relation(item.target_id)
        from_seq = get_chapter_seq(relation.valid_from_chapter)
        to_seq   = (get_chapter_seq(relation.valid_to_chapter)
                    if relation.valid_to_chapter else MAX_CHAPTER_SEQ)

        # 查两个实体的索引取并集
        for entity_id in [get_entity_id(relation.src_entity, work_id),
                          get_entity_id(relation.dst_entity, work_id)]:
            if not entity_id:
                continue
            rows = db.query("""
                SELECT chapter_id, chapter_seq, ref_count
                FROM EntityChapterIndex
                WHERE entity_id = :eid AND work_id = :wid
                  AND chapter_seq BETWEEN :from_seq AND :to_seq
                ORDER BY chapter_seq
            """, {"eid": entity_id, "wid": work_id,
                  "from_seq": from_seq, "to_seq": to_seq})
            for row in rows:
                affected.append(AffectedChapter(
                    chapter_id=row.chapter_id,
                    chapter_seq=row.chapter_seq,
                    reason=ImpactReason(
                        type="relation_changed",
                        source_item_id=item.target_id,
                        detail=f"「{relation.src_entity}」与"
                               f"「{relation.dst_entity}」的关系变更"
                    ),
                    severity=0.65
                ))

    # ══════════════════════════════════════════════════════════════════
    # 类型 4:Foreshadow 状态/内容变更
    # 规则 FW-1:影响区间 = [foreshadow_chapter.seq, payoff_chapter.seq]
    #           整个伏笔跨度内的章节都可能依赖该伏笔的语义
    # 无额外过滤:伏笔区间内任何章节都可能提及相关线索
    # ══════════════════════════════════════════════════════════════════
    elif item.target_type == "Foreshadow":
        fsw = fetch_foreshadow(item.target_id)
        f_seq = get_chapter_seq(fsw.foreshadow_chapter_id)
        p_seq = (get_chapter_seq(fsw.payoff_chapter_id)
                 if fsw.payoff_chapter_id else MAX_CHAPTER_SEQ)

        # 伏笔区间内全部章节(不再用 EntityChapterIndex 过滤,因为伏笔可能隐式影响)
        for ch in [c for c in all_chapters if f_seq <= c.seq <= p_seq]:
            affected.append(AffectedChapter(
                chapter_id=ch.id,
                chapter_seq=ch.seq,
                reason=ImpactReason(
                    type="foreshadow_changed",
                    source_item_id=item.target_id,
                    detail=f"伏笔「{fsw.summary[:30]}…」发生变更"
                ),
                severity=0.80   # 伏笔变更影响通常最大
            ))

    return affected


def compute_impact(
    change_items: list[ChangeItem],
    work_id: str,
    all_chapters: list[Chapter]
) -> ImpactSet:
    """
    并行计算所有 ChangeItem 的影响,取并集,合并同章节的多原因。
    """
    t0 = time.monotonic_ns()

    # 并行计算(asyncio.gather 或 ThreadPoolExecutor)
    per_item_results = parallel_map(
        compute_impact_for_change_item,
        [(item, work_id, all_chapters) for item in change_items]
    )

    # 合并:同一 chapter_id 的多条 AffectedChapter 合并 reason 列表
    chapter_map: dict[str, AffectedChapter] = {}
    for results in per_item_results:
        for ac in results:
            if ac.chapter_id in chapter_map:
                chapter_map[ac.chapter_id].reasons.append(ac.reason)
                chapter_map[ac.chapter_id].severity = max(
                    chapter_map[ac.chapter_id].severity, ac.severity
                )
            else:
                ac.reasons = [ac.reason]
                chapter_map[ac.chapter_id] = ac

    # 按严重度排序,设置 recheck_priority
    affected = sorted(chapter_map.values(), key=lambda x: x.severity, reverse=True)
    for ac in affected:
        ac.recheck_priority = (
            "high"   if ac.severity >= 0.70 else
            "medium" if ac.severity >= 0.40 else
            "low"
        )
        ac.status = "pending"

    duration_ms = (time.monotonic_ns() - t0) // 1_000_000
    return ImpactSet(
        work_id=work_id,
        trigger_change_ids=[item.target_id for item in change_items],
        affected_chapters=affected,
        total_affected_count=len(affected),
        high_priority_count=sum(1 for ac in affected if ac.recheck_priority == "high"),
        analysis_timestamp=datetime.utcnow(),
        analysis_duration_ms=duration_ms
    )
```

#### 3.6.4 严重度评分算法

```python
def compute_severity_setting(item: ChangeItem, ref_count: int) -> float:
    """
    SettingItem 变更的严重度:
    基础分 + 变更类型加成 + 引用密度加成
    """
    base = 0.60
    # 废弃比修改更严重(可能引起更多一致性断裂)
    if item.change_type == "deprecate":
        base = 0.80
    elif item.change_type == "add":
        base = 0.30  # 新增通常影响较小
    # 引用密度:每多10次引用,严重度 +0.02(上限 0.20)
    density_bonus = min(0.20, ref_count * 0.02)
    return min(1.0, base + density_bonus)


def compute_severity_char(item: ChangeItem, ref_count: int) -> float:
    base = 0.70  # 角色变更通常影响面广
    if item.target_type == "CharState":
        # CharState 局部性更强
        base = 0.55
    density_bonus = min(0.20, ref_count * 0.02)
    return min(1.0, base + density_bonus)
```

```python
def trigger_incremental_recheck(impact_set: ImpactSet) -> None:
    """

            focused_error_classes=focused_classes,

def infer_relevant_error_classes(reasons: list[ImpactReason]) -> list[str]:
    """
    根据影响原因类型推断需重点检查的 ConsistencyFlag.error_class(00 §5 枚举)。
    """
    error_class_map = {
        "character_changed":  ["OOC", "ability_inconsistency",
                               "relation_inconsistency", "motivation_break"],
        "setting_changed":    ["rule_violation", "geography_contradiction",
                               "system_contradiction"],
        "foreshadow_changed": ["causality_break", "event_contradiction"],
        "relation_changed":   ["relation_inconsistency", "timeline_contradiction"]
    }
    classes: set[str] = set()
    for r in reasons:
        classes.update(error_class_map.get(r.type, []))
    return list(classes)
```

### 3.7 AI 覆盖与人工保护

#### 3.7.1 三级保护机制

| 级别 | 条件 | AI 行为 |
|---|---|---|
| 完全保护 | HEAD 是 `human-final` 且 `is_human_locked=TRUE` | 拒绝写入,抛 `AIOverwriteProtectedError` |
| 旁路保护 | HEAD 是 `human-final` 且未显式锁定 | AI 可在新 `ai-draft` 分支生成,但不移动 HEAD |
| 自由写入 | HEAD 是 `ai-draft` 或无 HEAD | AI 可写入并移动 HEAD |

```python
@dataclass
class OverwriteCheckResult:
    can_overwrite: bool
    reason: str
    must_create_new_branch: bool = False
    new_branch_label: str = "ai-draft"
    message: str = ""


def ai_can_overwrite_chapter(chapter_id: str) -> OverwriteCheckResult:
    head = get_head_snapshot(chapter_id)

    if head is None:
        return OverwriteCheckResult(can_overwrite=True, reason="no_existing_version")

    if head.branch_label == "human-final" and head.is_human_locked:
        return OverwriteCheckResult(
            can_overwrite=False,
            reason="human_locked",
            message=f"章节已被作者锁定(快照 {head.id}),AI 不可覆盖。"
                    f"如需 AI 重写,请先解锁或切换到新的 ai-draft 分支。"
        )

    if head.branch_label == "human-final" and not head.is_human_locked:
        return OverwriteCheckResult(
            can_overwrite=True,
            reason="human_final_unlocked",
            must_create_new_branch=True
        )

    return OverwriteCheckResult(can_overwrite=True, reason="ai_draft_head")


def write_agent_create_snapshot(
    chapter_id: str,
    generated_content: str,
    agent_meta: dict
) -> Snapshot:
    """WritingAgent / RewriteAgent 生成完成后调用此函数写入 Snapshot。"""
    check = ai_can_overwrite_chapter(chapter_id)
    if not check.can_overwrite:
        raise AIOverwriteProtectedError(check.message)

    move_head = not check.must_create_new_branch
    parent = get_head_snapshot(chapter_id)

    snap = create_snapshot(
        chapter_id=chapter_id,
        content=generated_content,
        created_by="ai",
        parent_id=parent.id if parent else None,
        branch_label="ai-draft",
        meta=agent_meta
    )

    if move_head:
        set_head(chapter_id, snap.id)

    return snap
```

```python
def save_human_edit(
    chapter_id: str,
    content: str,
    base_snapshot_id: str,  # 客户端提交:基于哪个 snapshot 编辑的
    user_id: str
) -> SaveResult:
    """
    保存人工编辑。
    若提交时 HEAD 已更新(并发),触发三路合并或返回冲突给前端。
    """
    current_head = get_head_snapshot(chapter_id)

    if current_head.id == base_snapshot_id:
        # 无冲突
        snap = create_snapshot(
            chapter_id=chapter_id,
            content=content,
            created_by="human",
            parent_id=base_snapshot_id,
            branch_label="human-final"
        )
        set_head(chapter_id, snap.id)
        trigger_backflow_async(chapter_id, snap.id, user_id)
        return SaveResult(success=True, snapshot_id=snap.id)

    # HEAD 已更新 → 三路合并
    merge_result = merge_with_conflict_detection(
        base_id=base_snapshot_id,
        ours_id=create_temp_snapshot(content),   # 当前用户的版本
        theirs_id=current_head.id
    )

    if not merge_result.conflicts:
        merged_snap = create_snapshot(
            chapter_id=chapter_id,
            content=apply_merge(merge_result),
            created_by="human",
            parent_id=current_head.id,
            branch_label="merged"
        )
        set_head(chapter_id, merged_snap.id)
        trigger_backflow_async(chapter_id, merged_snap.id, user_id)
        return SaveResult(success=True, snapshot_id=merged_snap.id, auto_merged=True)

    # 有冲突 → 返回给前端人工解决(人优先原则:冲突段默认保留人的版本)
    return SaveResult(
        success=False,
        conflicts=merge_result.conflicts,
        base_snapshot_id=base_snapshot_id,
        current_head_id=current_head.id
    )
```

### 3.8 百万字版本存储策略

#### 3.8.1 存储规模估算

| 指标 | 数值 | 说明 |
|---|---|---|
| 总章节数 | 500 章 | 百万字 ÷ 2000 字/章 |
| 每章版本数 | 8–12 个 | AI 草稿 2–3 + 重做 2–3 + 人工定稿 2–3 + OptionSet 候选 1–2 |
| 每章平均字数 | 2000 字 ≈ 6000 字节(UTF-8) | 中文字符约 3 字节/字 |
| 全量快照总量 | 500 × 10 × 6KB ≈ 30MB | 全量存储上限 |
| 增量存储节省 | 约 70–80% | 同章相邻版本 diff 通常仅改变 10–30% 文本 |
| 增量存储实际体积 | ≈ 6–9MB | 含 delta JSONB 开销 |

**结论**:即使全量存储也只有 30MB,PostgreSQL 完全可承受。增量存储的主要价值是减少 IO 读放大(恢复时只读 delta 链而非全文),以及为将来字数规模扩大预留空间。

```sql
-- 自动检查点触发函数(应用层 or 数据库触发器)
CREATE OR REPLACE FUNCTION maybe_create_checkpoint(p_snapshot_id UUID)
RETURNS UUID AS $$
DECLARE
  chain_len INTEGER;
  full_text  TEXT;
  new_id     UUID;
BEGIN
  -- 计算增量链长度(CTE 递归向上追溯)
  WITH RECURSIVE chain AS (
    SELECT id, parent_id, is_full
    FROM Snapshot WHERE id = p_snapshot_id
    UNION ALL
    SELECT s.id, s.parent_id, s.is_full
    FROM Snapshot s JOIN chain c ON s.id = c.parent_id
    WHERE NOT c.is_full
  )
  SELECT count(*) INTO chain_len FROM chain WHERE NOT is_full;

  IF chain_len < 20 THEN
    RETURN p_snapshot_id;  -- 无需检查点
  END IF;

  -- 物化全文并创建全量检查点
  full_text := resolve_full_text_plpgsql(p_snapshot_id);
  INSERT INTO Snapshot(chapter_id, content, created_by, parent_id,
                       branch_label, is_full, epoch)
  SELECT chapter_id, full_text, created_by, id,
         branch_label, TRUE, epoch + 1
  FROM Snapshot WHERE id = p_snapshot_id
  RETURNING id INTO new_id;

  RETURN new_id;
END;
$$ LANGUAGE plpgsql;
```

```python
def get_version_history(
    chapter_id: str,
    max_depth: int = 50,
    include_archived: bool = False
) -> list[VersionTreeNode]:
    """
    从 HEAD 向上追溯版本树,限制深度(防止前端一次加载过多)。
    返回扁平列表,前端自行按 parent_id 组装树形结构。
    """
    sql = """
        WITH RECURSIVE tree AS (
          SELECT s.*, 0 AS depth
          FROM Snapshot s
          JOIN ChapterHead ch ON ch.snapshot_id = s.id
          WHERE ch.chapter_id = :chapter_id

          UNION ALL

          SELECT s.*, t.depth + 1
          FROM Snapshot s
          JOIN tree t ON s.id = t.parent_id
          WHERE t.depth < :max_depth
            AND (:include_archived OR s.deleted_at IS NULL)
        )
        SELECT id, parent_id, branch_label, created_by, created_at,
               word_count, epoch, is_head, is_human_locked, meta, depth
        FROM tree
        ORDER BY depth ASC, created_at DESC
    """
    rows = db.execute(sql, {
        "chapter_id": chapter_id,
        "max_depth": max_depth,
        "include_archived": include_archived
    })
    return [VersionTreeNode.from_row(r) for r in rows]
```

## 6. 失败模式与缓解

### 6.1 回流误提取(LLM 幻觉写入错误设定)

| 现象 | LLM 从正文修改中抽取出不存在的设定变更,污染设定圣经 |
|---|---|
| 缓解 1 | LLM 提取的变更项置信度上限 0.75;低于 `BACKFLOW_AUTO_THRESHOLD`(0.80)的需人工确认 |
| 缓解 2 | 规则层先跑,LLM 只处理规则无法覆盖的部分(降低 LLM 调用频率) |
| 缓解 3 | 门槛2 `update_setting_item` 内置历史版本,错误写入可回滚 |
| 缓解 4 | `BackflowRecord` 提供完整审计链,支持手动撤销某次回流 |

### 6.2 影响分析漏报(假阴性,章节未被识别为受影响)

| 现象 | 章节确实引用了被修改的设定,但影响分析未识别到,遗留潜在不一致 |
|---|---|
| 缓解 1 | 双重过滤:EntityChapterIndex(关键词)+ 向量相似度并用 |
| 缓解 2 | `ExtractAgent` 处理完每章后必须更新索引,保证索引完整性 |
| 缓解 3 | 核心实体(主角、核心规则)的变更降低相似度阈值(0.72 → 0.55),提高召回 |
| 缓解 4 | 提供"全量重校验"API 作为最后保障 |

### 6.3 影响分析误报(假阳性,浪费校验资源)

| 现象 | 章节被标记为受影响但实际无依赖,浪费门槛1 计算资源 |
|---|---|
| 缓解 1 | 相似度阈值可按 work_id 配置(作者可调高减少误报) |
| 缓解 2 | 重校验是异步的,误报只浪费计算资源,不影响正确性 |
| 缓解 3 | `ConsistencyFlag.status=dismissed` 历史记录用于持续调优阈值 |

### 6.4 版本树膨胀(AI 频繁重做 + 多候选草稿)

| 现象 | ai-draft 分支快速增多,版本树查询变慢 |
|---|---|
| 缓解 1 | 增量存储减少单 Snapshot 体积 |
| 缓解 2 | 定期归档 ai-draft(30天压缩,90天软删除) |
| 缓解 3 | `get_version_history` 限制返回深度(默认 50 层) |
| 缓解 4 | 同一 `target_id` 的新重做任务可取消旧任务(防止过期草稿堆积) |

### 6.5 回流级联循环

| 现象 | 回流触发校验 → 校验发现问题 → 修改 → 再次触发回流 → 无限循环 |
|---|---|
| 缓解 1 | `BACKFLOW_MAX_DEPTH=3` 硬性截断 |
| 缓解 2 | epoch 去重:同一 work 同一 epoch 内不重复触发 |
| 缓解 3 | 级联回流必须经人工确认才能继续,不自动级联 |

### 6.6 AI 覆盖人工修改

| 现象 | `WritingAgent` 重生成时静默覆盖了作者已定稿的内容 |
|---|---|
| 缓解 1 | `ai_can_overwrite_chapter()` 前置检查,`human-final+is_human_locked` 时直接拒绝 |
| 缓解 2 | 即使未锁定,HEAD 是 `human-final` 时 AI 只能在新 branch 生成,不移动 HEAD |
| 缓解 3 | 工程2 醒目展示"当前章节已有人工定稿"警告 |

### 6.7 PreferenceSignal 遗漏

| 现象 | 作者接受/拒绝重做但信号未产生,品味模型失去学习机会 |
|---|---|
| 缓解 1 | `adopt_ai_draft` 和 `save_human_edit` 内部封装信号产生,不依赖调用方记得调用 |
| 缓解 2 | 信号产生失败时记录 dead-letter 队列,由补偿任务重试 |
| 缓解 3 | 工程6 度量"接受重做事件 vs PreferenceSignal 数量"差异,监控遗漏率 |

### 6.8 delta 链损坏(增量恢复失败)

| 现象 | 某个 delta hunk 损坏,导致从该点开始的全文无法恢复 |
|---|---|
| 缓解 1 | delta 字段含 `checksum` 字段,恢复时校验完整性 |
| 缓解 2 | 检查点每 20 个 delta 自动创建全量快照,限制损坏影响范围 |
| 缓解 3 | `human-final` 分支永远全量存储(不做 delta),保证最重要内容的直接可读 |

## 7. MVP vs 完整版

### 7.1 MVP 阶段(支持 5–10 万字闭环)

| 功能模块 | MVP 实现 |
|---|---|
| **Snapshot 创建** | 全量存储(不做增量),AI 生成和人工提交各创建快照 |
| **版本切换** | HEAD 切换(采纳/丢弃 AI 草稿);无 cherry-pick |
| **基础 diff** | 字符级 diff,供工程2 高亮展示 |
| **AI 覆盖保护** | 检查 `is_human_locked`;`human-final` HEAD 时 AI 在新分支生成 |
| **修订回流(最小版)** | 仅支持门槛2 设定圣经页面直接修改的回流(setting_edit 路径);无 LLM 辅助变更提取 |

**MVP 不做**:
- 增量存储与检查点
- LLM 辅助变更提取(feedback_accept / text_edit 路径的语义回流)
- 乐观锁并发冲突处理

- 多候选 OptionSet 分支版本管理
- 段落级 cherry-pick
- 归档策略

## 8. 证据与引用

**【已核实 arXiv 2505.12572】百万字以上 AI 写作框架**
当前研究以检索+压缩为主流,版本分支与修订回流是工程层的设计空白。本模块的 delta 增量存储和 EntityChapterIndex 预计算索引是填补此空白的工程设计决策。

**【已核实 arXiv 2506.16445 / 2508.03137 / 2305.13304】分层记忆与历史压缩**
分层记忆(章级/卷级/全局)是对抗长程遗忘与主题漂移的关键机制。本模块的修订回流在回写设定圣经同时触发实现4 记忆更新,保证记忆层与版本层的语义同步。

**【已核实 arXiv 2506.05939】E²RAG 实体-事件双图检索**
实体-事件双图检索比朴素 RAG 更能保留实体演变上下文。本模块的 EntityChapterIndex 是同类思路的工程化实现:把"哪些章节引用了哪些实体"预计算为倒排索引,影响分析时直接查索引而非重新 RAG。

**【已核实 arXiv 2603.05890】ConStory 五大类 19 子类错误分类**
`infer_relevant_error_classes` 函数将影响原因映射到 ConStory 错误类型子集,使门槛1 的增量校验可以聚焦于最相关的错误类型,避免全量 19 类重跑。

**【稳定知识】Myers diff 算法**
Myers(1986)"An O(ND) Difference Algorithm and Its Variations"是字符/词语级 diff 的工业标准,git 内部亦采用此算法。本模块的 `compute_diff` 基于此算法,无需引用外部包。

**【设计决策】双重防循环:epoch 去重 + 最大深度 3**
纯深度限制在网络稳定延迟下可能被绕过(同一 epoch 的并发触发);纯 epoch 去重在分布式多进程下有竞争问题。两者结合是保守但可靠的工程选择。epoch 阈值 3 是经验值,超过 3 层的级联几乎都是误触发。【设计决策】

**【设计决策】LLM 辅助变更提取置信度上限 0.75 / 自动回写阈值 0.80**
防止 LLM 幻觉直接污染门槛2 设定圣经。两个阈值的间隙(0.75–0.80)故意留空,保证 LLM 提取的项目必须经人确认——这与"人只提意见不亲手写 prose"的协作原则一致:人确认语义,AI 执行写入。阈值需在 Phase 2 通过"需人确认的回流比例"度量持续调优。【设计决策】

**【设计决策】影响分析精确率目标 ≥ 90% / 误报率 ≤ 15%**
基于"宁可多校验一点,不可遗漏关键不一致"的设计偏好。误报代价是浪费门槛1 计算资源;漏报代价是遗留不一致章节被读者读到。在百万字连载场景下,漏报代价更高,故召回率优先。【设计决策】

## 9. 开放问题

**O-1:EntityChapterIndex 中"实体改名"的处理**
当 `SettingItem.name` 或 `Character.name` 发生修改时,EntityChapterIndex 的关键词匹配会失效(旧名字仍在段落文本中)。是否需要维护"别名历史"(`name_aliases`)字段,影响分析时同时匹配旧名和新名?MVP 阶段暂不处理,Phase 2 评估。

**O-2:FeedbackNote 接受后的回流粒度**
接受一条针对"段落语气"的 FeedbackNote,理论上不需要回写设定圣经(只是 prose 风格变化)。但当前分类器的 `style` 类型会跳过回写。问题是:有没有"看起来是风格变化,但实际上修改了人物行为模式"的 edge case?需要定义更精细的"必须回写 vs 可以跳过"的判断规则。

**O-3:影响分析与门槛1 的职责边界**
当前设计:本模块负责"影响了哪些章节";门槛1 负责"具体校验这些章节的哪些错误"。但两者都需要访问 EntityChapterIndex 和 Segment 表。是否应该把 EntityChapterIndex 的维护责任完全转移给门槛1,本模块只消费查询?需要与门槛1 文档对齐后决定。

**O-4:BackflowRecord 的 `impact_set` 字段大小**
500 章的 ImpactSet 序列化后可能超过 1MB(每章一条 AffectedChapter 对象)。JSONB 字段在 PostgreSQL 中存储超过 8KB 的值会触发 TOAST 压缩,虽然功能正常但查询性能有影响。是否在 Phase 2 引入独立的 `BackflowImpactChapter` 表?

**O-5:多人协作场景下 PreferenceSignal 的归属**
当前设计假设 `PreferenceSignal.owner_id` = 作者 user_id。如果是"作者 + 编辑"协作,编辑接受/拒绝重做产生的信号归谁?错误地把编辑的品味偏好混入作者的品味模型会产生噪音。MVP 阶段推迟,Phase 4 定义协作权限模型时一并处理。

**O-6:delta 链恢复的并发安全**
`resolve_full_text` 沿 `parent_id` 链顺序读取快照并应用 delta。在高并发写入场景下,若某个中间节点快照的 delta 正在写入(事务未提交),恢复可能读到不完整状态。是否需要给 delta 链的读取加显式事务隔离级别?当前数据库默认读已提交(READ COMMITTED),理论上不会读到未提交数据,但需要在压测中验证。

**O-7:影响分析结果的持久化**
当前 ImpactSet 只存 JSONB 摘要在 `BackflowRecord.impact_set`。若前端需要展示"每次回流触发了哪些章节的重校验及其状态",需要实时查询门槛1 的 `ConsistencyFlag` 状态——但 `ConsistencyFlag` 会持续变化(open→dismissed→fixed)。是否引入独立的 `BackflowImpactChapter` 关联表,维护"本次回流影响的章节 + 当前最新校验状态"的实时视图?
