### 2.2 百万字工程挑战

**核心声明**【已核实 arXiv 2505.12572】:截至 2026 年 6 月,仅极少数研究真正验证 >100 万字框架。已验证子机制均在万字到十万字量级。将其组合外推到百万字是工程假设——**不存在可直接套用的百万字端到端最佳实践,必须自建度量边做边验证**。【设计决策】

工程响应:
1. **小步放大字数**:每批次固定字数档位验收(5万 → 20万 → 50万 → 100万)
2. **崩坏率曲线自建**:§3.4 定义专项观测挂点,积累质量指标随章数的实测曲线
3. **质量门禁**:工程6 指标 + 工程10 Agent 轨迹 eval 共同作为 CI 门禁——改 prompt/机制后自动回归
4. **A/B 对比实验**:量化每个机制对崩坏率的实际贡献,指导调优优先级

### 3.1 部署架构

#### 3.1.1 单机底座:docker compose(Hermes 复用路线)

依据工程8 核实更新:**存储 = SQLite + sqlite-vec(复用 Hermes qmd 技能)、Chat UI = 复用现成**。自建仅限领域 MCP Server + 小说编辑器面板。

```
docker-compose.yml
├── hermes          # Hermes Agent 主进程,承载主编 :8642 (OpenAI 兼容 API)
├── scribe-mcp      # 自建领域 MCP Server(Python stdio → SQLite) :无端口(stdio)
├── frontend        # 小说编辑器面板(React + Vite + Nginx) :3000
│                   # Chat 对话核心复用 Open WebUI / Hermes Desktop(不自建)
└── phoenix         # Arize Phoenix 本地可观测 :6006
```

服务依赖关系:
```
frontend ──REST/SSE──▶ hermes(:8642/v1/chat/completions)
hermes   ──stdio MCP──▶ scribe-mcp
hermes   ──OTel Span──▶ phoenix(:6006)
scribe-mcp ──SQL──────▶ scribe.db   (SQLite 单文件,挂载 ./data/scribe.db)
```

SQLite 单文件设计:
- `scribe.db`:承载稿件/版本/设定/伏笔/记忆/素材等所有关系数据 + sqlite-vec 向量索引
- Hermes `state.db`:主编 Agent 内部状态(由 Hermes 自管)
- 两者均挂载本地 volume,防重建丢失

#### 3.1.3 演进到规模化:触发阈值与迁移路径

| 触发信号 | 阈值 | 演进动作 |
|----------|------|----------|
| sqlite-vec 向量数 | >~50 万 | 切 PostgreSQL + pgvector(接口契约不变,见实现4) |
| 多租户并发写 | 出现锁竞争 / 并发 >5 用户 | 切 PostgreSQL;或 per-user SQLite(隔离彻底) |
| pgvector 相似查询 P99 | >500 ms | 引入 HNSW 索引;或独立 Qdrant |
| Worker CPU 持续 | >80% | `docker compose --scale hermes-worker=N` |
| 章生成 P95 时延 | >120 s | 拆 Hermes 子 Agent 并行批量章节 |
| 数据量 | >~50 万字(单 SQLite 性能参考) | 评估切 PostgreSQL 时机 |

**规模化迁移时**:embedding 生成逻辑不变,只换存储后端;实现4 检索接口契约保持不变。届时自建 `scribe_mcp/server_pg.py` 对接 PostgreSQL + pgvector,切换 `config.yaml mcp_servers` 指向即可。

#### 3.1.4 环境分离

| 环境 | 用途 | 配置方式 |
|------|------|---------|
| local | 本地开发,热重载 | `docker-compose.override.yml`(挂载源码 volume) |
| ci | GitHub Actions 自动化测试 | `docker-compose.ci.yml`(无 phoenix,SQLite 临时文件) |

#### 3.2.5 生成质量回归门禁(对接工程6 + 工程10)

质量回归是防"改 prompt 后质量退化"的核心 CI 门禁。工具:**promptfoo**(对齐工程10)。

| 指标 | 来源 | 门禁类型 | 阈值说明 |
|------|------|---------|---------|
| `booook_score` | 工程6 | 硬门禁 | 下降 > 5% 阻断 |

### 3.3 CI/CD 流水线

| Stage | 触发 | 时长 | 关键动作 |
|-------|------|------|---------|
| 1 Fast Checks | 每次 push/PR | ≤ 2 min | ruff+mypy / eslint+tsc / pip-audit+bandit |

#### 3.4.1 技术选型原则

- **OpenTelemetry GenAI 语义约定**(SIG v1.41)【已核实 [OTel AI Blog](https://opentelemetry.io/blog/2025/ai-agent-observability/)】:唯一结构化标准,防厂商锁定
- **Arize Phoenix(本地)**:LLM/Agent trace 可视化 + eval;本地部署,无数据外发;免费开源【已核实】
- **promptfoo**:CI 评测门禁;Prompt 回归;声明式 YAML,Git 友好【已核实】
- **不使用 Langfuse**:功能重叠且偏重(工程10 §1.1 结论);Phoenix + promptfoo 已满足需求【设计决策】

埋点通过 **Hermes Hook**(pre/post_llm_call / on_session_end 等)注入 OTel Span,不侵入业务逻辑。

#### 3.4.2 Span 树与必记字段

```
invoke_agent  [INTERNAL]           ← 主编执行一轮
  └─ chat [CLIENT]                 ← 单次 LLM 调用
        └─ execute_tool [INTERNAL] ← 工具调用(search_book/web_search/…)

invoke_workflow [INTERNAL]         ← 写作流程(规划→写作→评议)
  └─ invoke_agent [INTERNAL]       ← 子 Agent(并行评审/批量章节)
        └─ chat [CLIENT]
              └─ execute_tool [INTERNAL]
```

LLM 调用层必记字段:

| 字段 | 示例值 |
|------|--------|
| `gen_ai.system` | `"anthropic"` |
| `gen_ai.request.model` | `"claude-opus-4-5"` |
| `gen_ai.usage.input_tokens` | `4200` |
| `gen_ai.usage.output_tokens` | `830` |
| `estimated_cost_usd` | `0.0142` |
| `scribe.work_id` | `uuid` |
| `scribe.chapter_id` | `uuid` |
| `scribe.agent_role` | `"WritingAgent"` |
| `scribe.skill_name` | `"写章流程"` |

Hermes Hook 注入点:
```python
# hermes-config/plugins/scribe-memory/__init__.py
def register(agent):
    agent.hooks.pre_llm_call(inject_otel_span)      # 开始 Span
    agent.hooks.post_llm_call(close_otel_span)       # 记录 token/cost
    agent.hooks.post_tool_call(record_tool_span)     # 工具调用结果
    agent.hooks.on_session_end(flush_to_phoenix)     # 推送 Phoenix
```

### 3.5 安全清单(对齐工程9)

工程9 定义了完整的爆炸半径风险图谱与护栏分层。本节提炼**工程化侧的落地检查点**。

#### 3.5.1 LLM API Key 管理

| 项目 | 要求 | 实现 |
|------|------|------|
| Key 存储 | 禁止硬编码 | `.env`(开发);Vault/Secrets Manager(生产) |
| Key 轮换 | 不重启服务 | Hermes 热加载;LLM 客户端持有引用而非值 |
| Key 泄露防范 | 禁止日志/追踪打印 | OTel Collector 过滤器 scrub `api_key`/`authorization` |
| Hermes key | 注入 `hermes-config/config.yaml` 环境变量 | 不写进 Git |

#### 3.5.2 手稿数据保护(最高价值资产)

| 项目 | 要求 | 实现 |
|------|------|------|
| AI 写前检查 | `is_human_locked=TRUE` 段落零次 AI 写入 | scribe-mcp `commit_segment` 写前校验(工程9 G-2) |
| 数据隔离 | 不同 owner/work 完全隔离 | 所有查询 `WHERE work_id IN (owner 可见集)` |
| 备份 | 按 work_id 粒度可恢复 | 每日 SQLite 快照加密上传对象存储 |
| 软删除 | 删除后保留 30 天 | `deleted_at` 字段 |
| 传输加密 | HTTPS | 生产 Nginx/反代配置 TLS |

#### 3.5.3 Hermes 安全层复用

Hermes Agent 内置 7 层安全(工程9 §1 已核实):容器 drop caps / no-new-privileges / PID 上限 / 只读根 / 危险命令审批 / SSRF 防护 / Session 隔离 / 供应链扫描。

Scribe 在 Hermes 之上**额外自加**:
- 工具 result 进系统提示前 JSON 编码 + 标注 `[TOOL_DATA_UNSAFE]`(工程9 §3.2 间接注入防护)
- 成本熔断:每会话 token budget 上限 + error rate 触发(工程9 G-4)
- `AgentSkill.approved_by_human=TRUE` 才可激活(内核0 §3.6,工程9 §3.1)
- 手稿 DLP:LLM 调用 body 中手稿内容做 PII 扫描再发送(工程9 §3.1)

## §8 · 成本估算方法与风险

### 8.1 成本估算方法

**原则:只给方法,不编单价**——具体单价须按当时 Provider 官网实时核算。

LLM 成本结构:
```
总成本 = Σ(每章成本)
= Σ( OutlineAgent token × 规划模型价格      [快模型]
   + WritingAgent token × 旗舰/Hermes4价格  [按路由]
   + OptionSet 生成 token × 旗舰模型价格
   + 多视角评审子 Agent × 快模型价格
   + SummaryAgent/ExtractAgent × 快模型价格 )

百万字 token 估算(参考):
  正文输出: 100万字 ÷ 1.5字/token ≈ 67万输出 token
  context 输入(含设定+摘要+大纲): 2000–5000 × 400章 ≈ 80万–200万 input token
  多 Agent 开销: 输出的 2–4 倍
  估算范围: input 200万–600万;output 200万–400万 token(实测校准)

成本降低杠杆:
  - 规划/摘要用快模型(价格差 10x–30x)
  - Hermes 4 本地跑(Batch 9 后零边际成本)
  - Prompt prefix cache:设定圣经等稳定内容可降 input token
  - 增量校验:只对有变化章节重校验
  - 多方案:关键节点才触发,非每段都跑
```

基础设施成本(SQLite 优先路线更低):
```
Batch 0–9: 云主机(8核16GB)+ 本地 Hermes;无独立数据库服务费用
Batch 10 切 pgvector: 托管 PostgreSQL(RDS/Cloud SQL)按需
百万字 embedding 存储: <10MB(SQLite 单文件几乎可忽略)
```

### 8.2 风险汇总

**核心风险:百万字无银弹**【设计决策,依据 arXiv 2505.12572】

> 已验证子机制均在万字到十万字量级有支撑。组合外推到百万字是工程假设。**必须靠自建度量验证,不存在可直接套用的百万字最佳实践。**
> 缓解:小步放大字数 + A/B 对比实验 + 自建崩坏率曲线 + promptfoo 质量门禁安全网。

主要风险表:

| 风险 | 来源 | 严重度 | 缓解 |
|------|------|-------|------|
| **Hermes 版本锁定** | 工程8 §9 | 高 | `uv.lock` 固定版本;升级前跑 Scribe 集成测试套件;每次升级走 Spike S-04 沙盒验证 |
| **单 memory provider** | 工程8 §6 | 高 | Batch 1 阶段用 state.db 延迟绑定;设计好迁移接口;Scribe MCP 作独立检索不依赖 provider |
| **sqlite-vec alpha 稳定性** | 工程8 核实更新 A | 中 | sqlite-vec 目前暴力扫描,<10万向量适用;Batch 0 S-01 验证;到阈值按 §3.1.3 迁 pgvector |
| **协作回路形同虚设** | 内核1 UI 摩擦 | 极高 | Batch 3b 重点打磨多方案/意见 UI;A/B 测试使用率;摩擦高则调整交互设计 |
| **百万字无银弹** | 所有模块 | 极高 | 自建度量(工程6+工程10) + 小步放大 + A/B 实验 |
| **品味模型冷启动** | 内核2 | 高 | Batch 4 引导流程 + 手动初始化;积累后验证效果 |
| **主动引擎误报刷屏** | 内核0 §3.5 | 中 | 低误报优先;安静札记不打断;分级触发 |
| **成本雪崩** | 工程3/工程9 | 中 | 成本熔断阈值(工程9 G-4);超预算降档快模型;Hermes 4 本地零边际 |
| **MCP stdio 稳定性** | 工程8 §9 Q-1 | 中 | Batch 0 S-02 验证;发现问题改 HTTP+SSE 传输 |
| **手稿 AI 覆写** | 工程9 G-2 | 极高 | `is_human_locked` 写前检查;Batch 1 即上线,不延后 |
| **标红疲劳(误报)** | 门槛1 | 中 | 高精确率优先;人裁决数据回流调阈值 |
| **迁移数据损坏** | 数据层 | 高 | 迁移前 SQLite 备份;Alembic downgrade 必须实现;staging 先跑 |
