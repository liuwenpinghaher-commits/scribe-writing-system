# LLM 长篇生成"生成→确定性检测→分流回炉"编排层调研报告

> 北极星方案任务4 动工前定向调研(goal 调研义务,≤1h);调研日期 2026-07-05;方式 WebSearch + 论文原文核对;裁决见决策台账 D-009。

## 题 1:回炉轮数上限 —— 查到

- **LangGraph `recursion_limit` 默认 25**(指图的 super-step 总步数,不是"修订轮数"),官方 docs 明示可按需调高,但社区共识是"撞上限多半是卡死循环,不是任务太复杂,别盲目调大"。**OpenAI Agents SDK `max_turns` 默认 10**,超限抛 `MaxTurnsExceeded`,定位是"抓死循环的保险丝"。
- **Self-Refine(NeurIPS 2023)上限 4 轮**,论文原文"up to a maximum of 4 iterations";Fig.4 实测收益递减:Code Opt. 各轮增量 Δ=5.0→0.9→0.9,即**第 1 轮拿走绝大部分收益**。
- **Reflexion(NeurIPS 2023)**:HotPotQA 以"连续 3 次失败"为停止条件;AlfWorld 跑 12 个 trial,学习曲线是"头两个 trial 跳升、其后缓慢爬升"——注意它多轮持续有效的前提是**每轮有环境/单测这种外部确定性信号**。
- **反面实证(强)**:Huang et al.《LLMs Cannot Self-Correct Reasoning Yet》(ICLR 2024) 测了 2 轮 intrinsic self-correction:GSM8K 75.9%→75.1%→74.7%,无外部反馈时**多轮不涨反跌**。工程侧佐证:Instructor 文档称校验失败后**首次重试即可修复 95%+**。
- 结论:业界没有统一"2 轮"标准值,但"外部信号驱动 + 1~2 轮修复 + 硬上限防死循环"是论文与框架共同收敛的形态;"2 轮后收益骤降"有 Self-Refine Δ 曲线 + Instructor 95% + Huang 下跌三路证据支撑。
- 来源:https://docs.langchain.com/oss/python/langgraph/errors/GRAPH_RECURSION_LIMIT ;https://arxiv.org/abs/2303.17651 ;https://arxiv.org/abs/2303.11366 ;https://arxiv.org/abs/2310.01798 ;https://openai.github.io/openai-agents-python/running_agents/ ;https://python.useinstructor.com/concepts/retrying/

## 题 2:外部信号 vs 自评 —— 查到(且有直接可抄的先例)

- **CRITIC(ICLR 2024)**是"外部工具信号驱动修正"的标杆:初稿→调外部工具(搜索/解释器)生成 critique→**critique 与初稿拼接**作为反馈驱动修正,循环"Verify⇒Correct⇒Verify"。其 ablation 关键结论:去掉外部工具后仅边际提升甚至**劣于初稿**——直接支持"收敛判据只挂确定性信号、LLM rubric 不参与"。
- **"findings→constraint 措辞"的公开工程实践**:① **Guardrails AI 的 REASK**:validator 失败时把 `FailResult.error_message` 自动注入 reask prompt 重问,且其 OnFail 策略本身就是分级分流(reask/fix/filter/refrain/noop/exception)——与 blocking/advisory/pass 三分流同构;② **Instructor**:Pydantic 校验错误原文回灌重试("You returned X but I expected Y, please fix it"),并有实践提醒**剪掉错误信息里的冗余 token**。
- 长文本侧:《Can AI writing be salvaged?》(arXiv 2409.14509) 的流程是"检测问题 span→打类别→**按类别用专用改写 prompt** 逐段修"——即 findings 先归类、再映射到固定约束模板,而非把原始检测输出直接倾倒进 prompt。
- 来源:https://arxiv.org/abs/2305.11738 ;https://www.guardrailsai.com/docs/concepts/validator_on_fail_actions ;https://python.useinstructor.com/concepts/reask_validation/ ;https://arxiv.org/pdf/2409.14509

## 题 3:journal/resume 模式 —— 部分查到

- **LangGraph checkpointer**:每个 super-step 后存全量状态快照,故障后从最后 checkpoint 续;durability 有 sync/async 两档(async 有崩溃丢 checkpoint 风险)。Diagrid 的批评文指出其局限:checkpoint 只是存档点,**检测失败、触发 resume、防止双进程同抢一个 thread_id 都要自己做**。
- **Temporal**:不存快照而是 **append-only event history + 重放**(已成功的 activity 直接跳过),且事件史由 Temporal 服务的独立存储持久化,**与应用业务 DB 分离**——这是"执行账本独立于主 DB"的最强先例。
- **JSONL 文件账本在 LLM 批处理管线里是成熟惯例**:BatchLLM 用 crash-safe JSONL checkpoint 且**校验输入/模型设置指纹、不匹配拒绝续跑**;LumiOpen dispatcher 重启后"从最后写出的一行继续,不重算";append-only JSONL 的卖点是"无 DB 复杂度、无迁移负担、逐行可 grep",且 **idempotency(幂等键)是安全 resume 的前提**。
- "独立文件 vs 主 DB"的专文论证:**未查到**直接对比文章;Temporal 分离设计 + JSONL 惯例是最接近的旁证(另一个隐含理由:主 DB 写入本身是被编排的副作用之一,账本若在主 DB 里,DB 故障时账本与状态一起损坏)。
- 来源:https://docs.langchain.com/oss/python/langgraph/persistence ;https://www.diagrid.io/blog/checkpoints-are-not-durable-execution-why-langgraph-crewai-google-adk-and-others-fall-short-for-production-agent-workflows ;https://docs.temporal.io/encyclopedia/event-history ;https://github.com/he-yufeng/BatchLLM ;https://github.com/LumiOpen/dispatcher ;https://www.grizzlypeaksoftware.com/library/batch-processing-with-llm-apis-oe2dad34 ;https://zylos.ai/research/2026-03-04-ai-agent-workflow-checkpointing-resumability/

## 题 4:同步 vs 异步编排端点 —— 查到(单用户本地场景为推断)

- 通用共识清晰:**FastAPI `BackgroundTasks` 只适合秒级 fire-and-forget**(同进程、无持久化、无重试、重启即丢);**分钟级、需可靠性的任务→独立 worker(Celery/RQ/Dramatiq)+ 任务 ID**;标准 API 形态是 **202 Accepted + Location/Retry-After + 轮询 status**,SSE 可替代轮询做低延迟进度推送。
- **"单用户本地工具用同步长请求"的权威专文:未查到**。基于以上证据的工程推断:单用户、本地、无代理链路时,同步长请求的两大风险(worker 占用、中间层超时)基本不成立,async 端点 + 客户端长超时可行,且 journal 已兜底"断连≠丢进度";但**一旦要前端进度条或多章排队,就应切 202+job 模式**。

## 题 5:regenerate 防同质化 —— 查到

- **长篇故事生成里的 targeted repair 直接先例:Re3(EMNLP 2022)**:Rewrite 模块用打分器 rerank 候选,**Edit 模块只对事实不一致处做定向编辑**而非整段重生成。代码侧同构:Agentless、PAFT(minimal-edit 修复)、TokenRepair;span 级文本修复见 2409.14509。
- **"越改越平"有实证**:《Pride and Prejudice: LLM Amplifies Self-Bias in Self-Refinement》(arXiv 2402.11436) 证明自我精修会**放大模型自偏置**;多项研究记录迭代精修导致**输出多样性下降、趋向"平庸中心倾向"**;Self-Refine 的提升也被指偏表层流畅度。这批证据同时支撑"rubric 分不参与收敛"。
- **重试变化策略**:不要同 prompt 复跑;适度升温 + 加入具体风格约束再 regenerate;"重写时保留原稿版本"未见专文,但 LangGraph time-travel 多版本状态与创作工具版本化是普遍惯例。

## 对 POST /loop/chapter 的设计建议(采纳裁决见台账 D-009)

1. 硬上限 2 轮定案(题1)。【采纳】
2. 收敛只挂确定性信号(题1/2/5)。【已是宪法】
3. findings→prompt 用「检测器名+违例引文+祈使式约束」三元组模板(题2)。【采纳,loop.build_regen_constraints】
4. severity 分流加"targeted repair"档(题5)。【缓议 P2+:须在"复用完整组装链"宪法下实现,P0 不做】
5. 第 2 轮 regenerate 附上轮失败摘要,禁同 prompt 复跑(题5)。【采纳】
6. journal 按 Temporal 语义:attempt 幂等键;指纹校验;孤儿扫描/并发锁列为后续(题3)。【部分采纳:幂等键+每次新 journal 文件;指纹/并发锁记遗留风险】
7. 端点先同步、响应带 journal 路径留 202 演进位(题4)。【采纳】
8. 每轮稿留版本引用进 journal/响应(题3/5)。【采纳,rounds[].version_id】
