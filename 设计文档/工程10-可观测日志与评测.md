## §1 · 在回路中的位置与职责

### 1.1 系统回路定位

工程10 是**基础设施可观测层**。它不生产内容,但让系统的每一条 LLM 调用、每一次工具调用、每一个子 Agent 步骤都变得**可追溯、可测量、可门禁**。

```
        人(想象 + 意见)
             │
             ▼
  ┌─────────────────────────────────┐
  │      主编智能体 (内核0)            │  ← 协作回路指挥
  │  chat / proactive / subagent    │
  └──────┬──────────────────────────┘
         │ 每次 LLM 调用 / 工具调用
         │ 均产生 Span
         ▼
  ┌─────────────────────────────────┐
  │   OTel Collector (本地边车)       │  ← 接收 Span,可脱敏过滤
  └──────┬──────────────────────────┘
         │
    ┌────┴─────┐
    ▼          ▼
 Langfuse    Metrics
 (trace/     (Prometheus/
  eval/       histogram)
  Prompt版本)
         │
         ▼
  CI 评测门禁 (promptfoo / pytest)
         │
         ▼
  工程3 成本熔断 ← 成本归因
  工程9 故障隔离 ← 延迟/错误率
```

**一句话职责**:采集 Scribe 协作回路中所有 Agent/LLM/工具调用的结构化 Span,聚合为成本与延迟指标,支撑 LLM-as-judge 和 Agent 轨迹评测,并以 CI 门禁的形式阻止质量/策略/成本回退进入生产。

### 1.2 与工程6 的分工边界(重要)

| 维度 | **工程10(本文)** | **工程6** |
|---|---|---|
| 度量对象 | 系统/Agent/LLM 运行行为 | 作品内容质量 |

## §2 · 设计目标与百万字挑战

| 目标 | 可测量描述 | 证据级别 |
|---|---|---|
| **零盲区可追溯** | 主编→LLM 每次调用均有 trace_id 贯穿,工具调用嵌套可见 | 【设计决策】 |
| **隐私安全** | prompt/completion 默认不落全量索引;仅元数据默认可观测 | 【已核实 OTel GenAI SIG】 |
| **eval 不是摆设** | 每条 eval 都绑定 CI 门禁阈值或人工审查触发;没有"能跑但不阻断"的 eval | 【设计决策】 |
| **成本可下钻** | 按 model/user/feature/session 归因,支持 p95 延迟与 estimated_cost_usd | 【已核实 OTel GenAI 字段】 |
| **百万字不爆表** | 500 章、数千次 LLM 调用场景下 trace 存储与查询不成瓶颈 | 【设计决策】 |

**百万字特殊挑战**:单部作品数千次 LLM 调用,跨越数周写作;trace 需支持跨会话关联(同一 work_id);Agent 轨迹可能有几十步工具链;eval 要区分"章节内容生成"与"一致性校验"等不同任务类型。

## §3 · 详细设计

### 3.1 日志/追踪规范:OTel GenAI 语义约定

采用 **OpenTelemetry GenAI 语义约定**(SIG v1.41 Development)【已核实 [OTel AI Blog](https://opentelemetry.io/blog/2025/ai-agent-observability/)】作为唯一结构化标准。不使用任何平台私有 SDK(防厂商锁定)。

#### 3.1.1 Span 类型与层级

```
invoke_agent  [INTERNAL]          ← 主编执行一轮(chat/proactive/subagent 派发)
  └── chat / text_completion [CLIENT]   ← 单次 LLM 调用
        └── execute_tool [INTERNAL]     ← 工具调用(search_book / web_search / …)

invoke_workflow [INTERNAL]        ← 跨任务的写作流程(规划→写作→评议)
  └── invoke_agent [INTERNAL]     ← 子 Agent(并行评审、批量章节)
        └── chat [CLIENT]
              └── execute_tool [INTERNAL]
```

**层级规则**:
- `invoke_agent` → `chat` → `execute_tool`:父子关系用 `parent_span_id` 串联
- 并行子 Agent 各有独立 `span_id`,共享同一 `trace_id` + `session_id`
- `create_agent`(子 Agent 初始化)作为 `invoke_agent` 的前置 Span

#### 3.1.3 内容隐私:prompt/completion 放 Events 不放 Attributes

```
【已核实 OTel GenAI SIG】:
- prompt/completion 文本放 Span Events(event name: gen_ai.content.prompt / gen_ai.content.completion)
- 不放 Span Attributes(attributes 会全量进索引,触发 PII 风险)
- Collector 层可按策略过滤 Events(调试环境保留,生产默认删除)
- 默认模式:仅元数据可观测;按需开启内容(debug flag per work_id)
```

```python
# 埋点示例(OTel Python SDK)
from opentelemetry import trace
from opentelemetry.semconv_ai import SpanAttributes, GenAiOperationNameValues

tracer = trace.get_tracer("scribe.agent")

with tracer.start_as_current_span("chat") as span:
    span.set_attribute(SpanAttributes.GEN_AI_SYSTEM, "anthropic")
    span.set_attribute(SpanAttributes.GEN_AI_REQUEST_MODEL, model)
    span.set_attribute("work_id", str(work_id))
    span.set_attribute("task_type", task_type)

    # 内容放 event,不放 attribute
    span.add_event("gen_ai.content.prompt",   {"content": prompt_text})
    response = await llm_call(...)
    span.add_event("gen_ai.content.completion", {"content": response.text})

    span.set_attribute(SpanAttributes.GEN_AI_USAGE_INPUT_TOKENS,  response.usage.input)
    span.set_attribute(SpanAttributes.GEN_AI_USAGE_OUTPUT_TOKENS, response.usage.output)
    span.set_attribute("estimated_cost_usd", compute_cost(model, response.usage))
```

#### 3.1.4 Correlation ID 贯穿协作回路

协作回路六阶段(想象→规划→多方案→写作→评议→重做)必须共享 `trace_id`:

```
用户发起 chat("第5章需要一个反转")
  → trace_id = T1, span: invoke_agent(operation=handle_imagination)
      → span: chat(生成 OptionSet)
          → span: execute_tool(propose_options)
  → 用户选 Option B
  → trace_id = T1(续), span: invoke_agent(operation=write_chapter)
      → span: chat(写章节文本)
          → span: execute_tool(search_book)
          → span: execute_tool(check_consistency)
  → 用户反馈"节奏太慢"→ FeedbackNote
  → trace_id = T1(续), span: invoke_agent(operation=act_on_feedback)
      → span: chat(重做章节)

所有 Span 共享 trace_id=T1 + work_id + chapter_id + session_id
```

**实现方式**:`session_id` 注入 OTel Context Propagation 的 baggage;跨子 Agent 调用通过 W3C TraceContext 透传 `trace_id`。

### 3.2 Hermes Agent Hook 对接埋点

Hermes Agent 提供 `pre_tool_call` / `post_tool_call` / `pre_llm_call` / `post_llm_call` 四类 Hook,是最低侵入的埋点入口:

```python
# Hermes Hook 埋点(伪代码,映射到 OTel Span)
class ScribeObservabilityPlugin:
    def pre_llm_call(self, model, messages, params):
        span = tracer.start_span("chat")
        span.set_attribute("gen_ai.system", model.provider)
        span.set_attribute("gen_ai.request.model", model.name)
        span.add_event("gen_ai.content.prompt", {"content": format_messages(messages)})
        context_stack.push(span)

    def post_llm_call(self, response, usage):
        span = context_stack.pop()
        span.set_attribute("gen_ai.usage.input_tokens",  usage.input)
        span.set_attribute("gen_ai.usage.output_tokens", usage.output)
        span.set_attribute("estimated_cost_usd", compute_cost(response.model, usage))
        span.add_event("gen_ai.content.completion", {"content": response.text})
        span.end()

    def pre_tool_call(self, tool_name, tool_args):
        span = tracer.start_span("execute_tool", child_of=context_stack.peek())
        span.set_attribute("gen_ai.tool.name", tool_name)
        span.add_event("tool.input", {"args": sanitize(tool_args)})
        context_stack.push(span)

    def post_tool_call(self, tool_name, result, error=None):
        span = context_stack.pop()
        span.set_attribute("tool.success", error is None)
        if error:
            span.set_attribute("error.type",    type(error).__name__)
            span.set_attribute("error.message", str(error))
        span.end()
```

**零遥测问题**:Hermes 默认无遥测;上述 Plugin 实现 `IHermesPlugin` 接口后注册即可,不需修改 Hermes 核心代码。

| 平台 | 类型 | 推荐场景 | 说明 |
|---|---|---|---|

**选型决策**【设计决策,2026-06 修订】:**OpenTelemetry GenAI 约定(厂商无关、不锁定)做埋点 + Arize Phoenix(本地、轻量、按需)看 trace/eval + promptfoo 做 CI 门禁**。trace 落本地(同 SQLite/文件),**不上 Langfuse 的多服务栈**(过重,与 SQLite 优先底座不匹配)。埋点经 Hermes 的 `pre/post_tool_call`、`pre/post_llm_call` Hook 注入,零侵入。规模化(多租户/海量 trace)再评估 Langfuse 自托管。**仪器化对准 OTel 标准,任何平台都可后续替换,零迁移成本。**

## §4 · 评测体系

### 4.1 离线 vs 在线评测

| 维度 | **离线 eval** | **在线 eval** |
|---|---|---|
| 时机 | CI/发布前;Prompt 变更时 | 生产实时采样 |
| 数据 | 标注数据集 + 生产采样集 | 实时 trace 流 |
| 目的 | 质量回退检测、门禁 | 漂移发现、边界案例积累 |
| 成本 | 可控(批量跑) | 需采样率控制 |
| 输出 | Pass/Fail + 指标对比 | 告警 + 新 Dataset 入库 |

**在线采样策略**:每 work_id 按 `min(10%, 20章/卷)` 采样;重点采样工具调用失败、Agent 步数异常多、成本异常高的 trace。

### 4.2 LLM-as-judge(偏差与缓解)

**LLM judge 与人类评分一致性约 85%**【已核实,见 eval 研究综述】。但存在系统性偏差,必须缓解:

| 偏差类型 | 表现 | 缓解策略 |
|---|---|---|
| **位置偏好** | 倾向评高列表首位选项 | 随机化选项顺序;多次评分取均值 |
| **冗长偏好** | 倾向认为更长的回答更好 | rubric 中显式惩罚不必要冗长 |
| **自我偏好** | 同模型评自己生成的内容偏高 | 用**不同模型**做 judge(生成≠评分) |
| **标准模糊** | 评分标准含糊时分数方差大 | rubric 每条标准写**具体可操作的判断准则** |

**缓解架构:DAG 拆硬规则 + 软评分**:

```
输入 Trace / 生成文本
       │
       ▼
  硬规则层(规则引擎,确定性)
   ├─ 策略违规检测(禁止内容/越权操作)  → Pass/Fail
   ├─ 工具调用格式合规                  → Pass/Fail
   └─ 必填字段完整性                   → Pass/Fail
       │ 通过
       ▼
  软评分层(LLM judge,概率性)
   ├─ 工具选择正确性                   → [0,1]
   ├─ 步骤效率评分                     → [0,1]
   ├─ 内容质量(调用工程6 Q/M 指标)    → [0,5]
   └─ 计划遵从度                       → [0,1]
       │
       ▼
  专家集交叉校验(高风险样本,≥2 judge 模型)
   └─ 分歧大时 → 人工审查队列
```

**安全敏感内容留人工**:涉及越权操作、内容安全边界的 trace 不经 LLM judge,直接进人工审查。

### 4.3 Agent 轨迹评测(Trajectory Eval)

**核心动机**:Agent 可能走错路却得对答案。只看最终输出会遮蔽工具滥用、步骤冗余、计划偏离等深层问题。【已核实,agent trajectory eval 研究】

**Scribe 协作回路中的轨迹评测维度**:

| 维度 | 定义 | 计算方式 |
|---|---|---|
| **工具选择正确性** | Agent 在当前步骤是否调用了正确的工具 | 对比 golden trace / LLM judge |
| **工具参数正确性** | 参数值是否合理(如 search_book 的 scope 正确) | 规则 + LLM judge |
| **步骤效率** | 达成目标所用工具调用次数 vs 期望最少次数 | `expected_steps / actual_steps` |
| **计划质量** | 初始计划(propose_options 产出)是否覆盖了需要的决策点 | LLM judge(对照 AuthorIntent) |
| **计划遵从度** | 执行时是否按批准的计划行事,偏差是否有理由 | 对比计划 Span vs 执行 Span |
| **推理相关性** | Agent 在 chain-of-thought 中引用的证据是否与任务相关 | LLM judge |
| **长任务完成率** | 百万字场景下,多章任务是否完整完成(无丢失/截断) | 确定性指标:预期章节 vs 实际产出 |

**Golden Trace 构建**:
```
人工标注团队对 20-50 个代表性任务写"理想轨迹"
(每个任务:正确工具序列 + 最少步骤 + 期望参数范围)
→ 存入 Langfuse Dataset
→ 每次 Prompt 变更跑 trajectory eval 对比
→ 关键任务(写章节/一致性校验/多方案生成)各建独立 Dataset
```

### 4.4 三层评测体系

```
端到端层(E2E)
  ├─ 输入:用户想象/意见
  ├─ 输出:生成的章节内容 + Agent 行为整体
  ├─ eval:工程6 内容质量(M/Q/H 系列)+ 轨迹效率
  └─ 触发:每章生成完成后(异步)

轨迹层(Trajectory)
  ├─ 输入:单次 Agent 执行的完整 Span 树
  ├─ 输出:工具正确性/步骤效率/计划遵从评分
  ├─ eval:§4.3 六维轨迹指标
  └─ 触发:在线采样(10%)+ CI 全量跑 golden trace

组件层(Component)
  ├─ 单工具/单 Prompt 的输入-输出正确性
  ├─ 例:search_book 的召回准确率,check_consistency 的假阳性率
  ├─ eval:单元式 LLM judge + 规则
  └─ 触发:Prompt/工具实现变更时
```

### 4.5 与工程6 内容质量 eval 的衔接

工程6 的 M/Q/H 系列指标在本文中扮演以下角色:

1. **端到端 eval 的 judge 输入**:生成章节后,调工程6 evaluate() 得 `ChapterQualityReport`,其中 Q4_craft_score / Q3_intent_resonance / M1_booookscore 作为 E2E eval 的内容维度分数写入 Langfuse Dataset。

2. **CI 门禁的质量回退检测**:新版本部署前,在回归集上跑工程6 指标,若 `Q4_avg < baseline × 0.90` 或 `M1_avg < 0.80` → CI 失败(见 §5 门禁矩阵)。

3. **在线漂移检测**:实时监控工程6 指标的滚动均值,连续 3 章低于阈值触发告警,同时将对应 trace 推入离线 eval 队列。

```
工程6 QualityReport
    │ Q4/Q3/M1/Q1 值
    ▼
工程10 Eval Pipeline
    ├─ 写入 Langfuse trace 的 score 字段
    ├─ 更新 CI 基准比对快照
    └─ 驱动在线漂移告警
```

## §5 · Eval 作 CI 质量门禁

### 5.1 门禁矩阵

"能跑但不阻断的 eval 是摆设。"【设计决策】每条 eval 必须绑定门禁行为。

| 门禁类型 | 检查内容 | 阻塞 CI? | 阈值示例 | 失败动作 |
|---|---|---|---|---|
| **质量回退门** | Q4 文字质感均值 vs 基准 | ✅ 阻塞 | `Q4_avg ≥ baseline × 0.90` | 标红 + 阻断合并 |
| **连贯性回退门** | M1 BooookScore 均值 | ✅ 阻塞 | `M1_avg ≥ 0.80` | 标红 + 阻断合并 |
| **策略违规硬门** | 安全/越权/禁止内容检测 | ✅ 阻塞 | 零容忍 | 阻断 + 人工审查 |
| **工具正确性门** | golden trace 上工具选择准确率 | ✅ 阻塞 | `tool_accuracy ≥ 0.85` | 标红 + 阻断合并 |
| **轨迹效率门** | 步骤数 vs 期望最少步骤 | ⚠️ 警告(Warn) | `efficiency ≥ 0.70` | 标黄 + 异步通知 |
| **延迟门** | p95 章节生成延迟 | ⚠️ 警告 | `p95 < 60s` | 标黄 + 趋势追踪 |
| **成本门** | 单章平均 cost vs 基准 | ⚠️ 警告 | `cost_avg < baseline × 1.30` | 标黄 + 预算预警 |
| **长任务完成率门** | 多章任务完整完成率 | ✅ 阻塞 | `completion_rate ≥ 0.95` | 标红 + 阻断合并 |

**门禁分级原则**:
- **阻塞门**:质量/安全/功能正确性回退,任何一项不达标都阻止合并
- **警告门**:效率/延迟/成本劣化,记录趋势但不阻塞(避免误报摆烂)

### 5.2 Prompt 版本化

Prompt 是版本化资产(00 §2.6 "Prompt 模板独立成文件"):

```
prompts/
  chapter_writer_v3.md       ← 写章节主 prompt
  consistency_checker_v2.md  ← 一致性检查 prompt
  option_proposer_v1.md      ← 多方案生成 prompt
  critique_agent_v4.md       ← 评改 Agent prompt
  trajectory_judge_v1.md     ← 轨迹 eval judge prompt
```

**版本化规则**:
1. Prompt 变更必须创建新版本文件(不覆盖旧版本)
2. 每个 Span 记录 `prompt_version` 字段
3. Prompt 变更必须触发对应组件层 eval + CI 门禁
4. 在 Langfuse 中注册为 Prompt 资产,支持 A/B 对比

### 5.3 promptfoo 集成

**promptfoo** 作为 CI 中 eval 运行器【已核实,promptfoo 广泛用于 LLM CI 门禁】:

estimated_cost_usd = (

### 6.3 与工程3/工程9 联动

**工程3 预算熔断联动**:

# 实时成本告警钩子(工程3 消费工程10 的 cost counter)
async def check_budget_circuit_breaker(work_id: UUID):

## §9 · 开放问题

1. **Hermes Hook API 稳定性**:pre/post_tool_call 等 Hook 在 Hermes Agent 不同版本间是否稳定?需在选定版本后验证接口签名。

2. **Golden Trace 冷启动**:系统上线初期无足够标注轨迹,前 20 个任务如何建 golden trace Dataset?建议由工程师手工完成最小集(5-10 条),随使用积累扩充。

3. **LLM judge 成本控制**:对 10% 在线采样做 LLM judge 本身也有成本,需评估是否用小模型(haiku/mini)做初筛,大模型做复核。

4. **跨会话 trace 关联**:同一 work_id 的写作跨越数周,不同 session 的 trace 如何在 Langfuse 中聚合为一个"作品级视图"?当前设计通过 `work_id` label 查询,但 UI 展示需要 Langfuse 的自定义元数据支持,需验证。

5. **eval 基准快照失效**:Q4/M1 基准快照随模型版本升级可能需要重新建立,策略未定(自动重建 vs 人工确认)。
