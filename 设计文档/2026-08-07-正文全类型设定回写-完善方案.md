## 0. 问题陈述（为何现状不对）

### 0.1 用户期望（正确）

```text
正文定稿 / 讨论共识
  → 抽出相对正典的增量（全类型）
  → 统一待确认 / 变更包（人可见、可批）
  → 批准后写入 Surreal 正典 + 知识账本
  → 下章注入与限知帧生效
```

### 0.2 现状（残缺）

| 通道 | 行为 |
|------|------|
| **ingest（旧）** | 抽知识/事件/弧光等；**仅库外人名**进「待确认人物引用」；规则/物件/术语/势力/母题/伏笔 **对不上就跳过，不排队** |
| **canon_loop（新内核）** | 有 ChangePack / PostFinalize / 安全 apply；主张靠 **标记或注入 claims**，非全文 LLM 全类型抽 |
| **UI** | 只有人物 pending；无「待确认设定（全类型）」 |
| **v5 书** | 写前圣经 + 写正文；**未**走定稿全类型回写 |

### 0.3 本方案要达成

**一条统一管线**，覆盖：

- 人物（新实体 + 字段补丁）  
- 势力 / 物件 / 术语 / 世界规则  
- 关系 / 弧光状态 / 伏笔 / 母题  
- 事实命题 + 知识边（L2）  
- 意图层冲突（L0，极高敏）  

并 **退役/吸收** 旧「仅人物待确认」为统一收件箱的一个视图，避免双轨。

## 1. 北极星与铁律

### 1.1 北极星

**任何从正文或讨论得到的「设定增量」，必须先成为可审候选，再经作者批准写入正典；类型覆盖 Codex 全 kind + 关系/伏笔/知识，无一等公民例外。**

### 1.2 铁律

| # | 铁律 |
|---|------|
| F1 | **L0/L1 正典模块禁止静默写**（含 layer 伪装、客户端 approved 伪造） |
| F2 | **禁止** 正文一抽就 `CREATE character/world_rule/...`（历史错误路径） |
| F3 | **全类型** 进同一候选模型 `CanonCandidate`，同一批准总线 |
| F4 | **客观 L2**（知识边等）可自动或一键，但须可审计、可回滚、可关闭 |
| F5 | **矛盾** 高于「新增」：与红线/既有规则冲突必须显式二选一 |
| F6 | **消歧优先于新建**：同名/别名/截断名先合并建议 |
| F7 | **同路径**：失败 STOP → 修抽取/批准/写库 → 同章再跑，禁止 EMERGENCY 灌库 |
| F8 | 旅程可见 **设定债**；高风险债可配置挡开写 N+1 |

## 2. 分层模型（全类型落在哪）

```text
L0  意图层     intent / 红线 / 读者感受
L1  设定正典   character · faction · item · term · world_rule · relation · promise · motif · char_state（基石字段）
L2  动态账本   proposition/fact · knows 知识边 · event 图 · 触碰刷新
L3  章工作物   synopsis · beats · scene_truth · prose · 版本
```

| 类型 | 默认层 | 批准策略 |
|------|--------|----------|
| 新角色 / 补全 appearance·fear·goal… | L1 | 必批 |
| 新势力/物件/术语/规则 | L1 | 必批 |
| 关系新建/演变 | L1 | 必批 |
| 伏笔 plant/advance/abandon | L1 | 必批 |
| 母题新立 / 本章触碰 | L1 新立必批；触碰可 L2 | 新立必批 |
| 弧光 CharState | L1 语义 / L2 记录 | 质变必批，轻触可配置 |
| 事实 + 知识边 | L2 | 默认可自动；`secret`/红线相关升级 L1 审 |
| 意图改写 | L0 | 必批 + 高风险 |

**模块硬门（与现 canon_loop 一致并扩展）**  
`character|faction|item|term|world_rule|relation|promise|motif|char_state|fact|intent` → 无 `approved_item_ids` 不写。  
仅明确标为 **objective_l2** 的 `knowledge`（及可配置的 event 触达）可免 L1 式批准。

## 3. 统一候选模型

### 3.1 `CanonCandidate`（持久化建议表 `canon_candidate`）

```text
id
work
seq                    // 来源章；讨论可为 null
source                 // prose_finalize | discussion | reingest | manual
extractor              // llm_v1 | marker | hybrid
module                 // character|faction|item|term|world_rule|relation|...
op                     // add | patch | deprecate | touch | link_knowledge
target                 // 建议 oid 或 bare name
field                  // 可选字段 key
before / after         // JSON
evidence               // 正文引文 ≤200 字
confidence             // 0~1
risk                   // low|med|high
layer                  // L0|L1|L2（服务端按 module 重算，不信客户端）
status                 // pending|approved|rejected|merged|superseded|expired
disambiguation         // {candidates:[{id,name,score}], action: new|merge|skip}
conflict               // {with_id, with_summary, resolution: keep_canon|keep_claim|edit}
impact                 // {chapters:[], inject_surfaces:[]}
created_at / decided_at / decided_by
change_pack_id         // 可选，归入某次包
```

### 3.2 `ChangePack`（会话/次批）

已有 `canon_loop.ChangePack` **升级为** 对 `CanonCandidate[]` 的视图 + 批量批准：

- 讨论包 / 定稿包 / 全章重抽包  
- `approved_item_ids` 仍是 **唯一** L1 放行凭证  

### 3.3 与旧 `ingest_unverified` 关系

```text
迁移策略：
1. 新抽取一律写 canon_candidate（module=character, op=add）
2. 兼容层：listUnverified API 读 canon_candidate WHERE module=character AND status=pending
   或双写一个版本周期后废弃
3. accept_unverified → 统一走 apply_change_pack / apply_candidates
4. UI「待确认人物引用」→ 升级为「待确认设定」多 Tab（人物|规则|物件|…|全部）
```

## 5. 抽取层（全类型 · 多通道）

### 5.1 通道 A：结构化 LLM 抽取（主）

**单次或分片** 输出统一 JSON（禁止散文）：

```json
{
  "entities": [
    {"module":"character","op":"add|patch","name":"…","fields":{…},"evidence":"…","confidence":0.8}
  ],
  "relations": [
    {"a":"…","b":"…","relation":"…","since_chapter":N,"evidence":"…"}
  ],
  "world_rules": [
    {"op":"add|patch","name":"…","fields":{…},"evidence":"…"}
  ],
  "factions": […],
  "items": […],
  "terms": […],
  "promises": [
    {"op":"plant|advance|touch","text":"…","evidence":"…"}
  ],
  "motifs": […],
  "char_states": […],
  "facts": [
    {"entity":"…","attribute":"…","value":"…","secret":false,"evidence":"…"}
  ],
  "knowledge": [
    {"knower":"…","proposition_hint":"…","via":"saw|told|…","evidence":"…"}
  ],
  "intent_flags": [
    {"field":"red_lines","claim":"…","evidence":"…"}
  ]
}
```

约束：

- 字段 key **必须** 落在 `codex_schema.fields_for(kind)`  
- `evidence` 必须能在正文定位（子串或偏移）  
- confidence &lt; 阈值 → 仍入库 candidate，但 risk 升 med/high，默认不进「建议全批」  

### 5.2 通道 B：既有知识抽取（ingest 改造）

- 保留 learned/did/events 能力  
- **`_resolve_char` 库外 → 写 `canon_candidate`（character/add）**，不再只写 `ingest_unverified`  
- 事件参与者仍 **禁止** 把器物登记为 character candidate（沿用现逻辑）  
- 关系触碰：两端皆库外 → 两条 character candidate + 一条 relation candidate（依赖批准顺序）  

### 5.3 通道 C：确定性标记（开发/测试/作者手写）

现有 `【设定 L1|…】` 保留为 **fixture 与高级作者语法**，与 LLM 结果 **合并去重**。

### 5.4 通道 D：讨论触发

`from-discussion` / 主编话轮结束：

- 对 summary+text 跑同一 Extract（可短上下文）  
- 与草稿 package 对齐，生成 discussion ChangePack  

### 5.5 合并与去重

```text
key = (module, normalize(target), field, op)
同 key：保留 confidence 更高或 evidence 更长
跨通道：marker > llm（可配置）
```

## 6. 消歧与冲突

### 6.1 消歧

| 情况 | 系统建议 |
|------|----------|
| 精确 oid / 名命中 | merge → patch |
| 别名表命中 | merge |
| 编辑距离/向量近邻 | 列出 1~3 候选，**默认不新建** |
| 无候选 | op=add |
| 截断名多命中 | 标 conflict，禁止自动 merge |

### 6.2 冲突

| 情况 | 处理 |
|------|------|
| after 与 before 矛盾且 risk=high | 强制人工选 keep_canon / keep_claim / 手改 |
| 触红线（intent.red_lines） | risk=high，不可「建议全批」 |
| 与 world_rule 硬冲突 | 同上 + 影响章列表 |

## 7. 批准与 Apply（完善）

### 7.1 UI：统一「设定收件箱」

```text
┌ 设定收件箱 / 变更包 ─────────────────────┐
│ Tab: 全部 | 人物 | 规则 | 物件 | 势力 | 术语 │
│      关系 | 伏笔 | 母题 | 知识 | 冲突       │
│ 筛选: 本章 | 全书 pending | 高风险 only     │
│ 每条: 类型 · 摘要 · 引文 · 影响章 · 置信度  │
│ [批准] [拒绝] [合并到…] [编辑 after] [全批建议项] │
└──────────────────────────────────────────┘
```

- 旅程看板：**设定债 = pending 高风险数 + 未处理冲突数**  
- 主编气泡：定稿后系统消息带「本章 N 条待确认设定」+ 深链  

### 7.2 Apply 事务

```text
for id in approved_item_ids (服务端校验):
  load candidate (must pending)
  re-check hard gate (module/layer)
  map → 既有 store API:
    character add/patch → add_entity / update character fields
    world_rule → add_world_rule / patch
    faction/item/term → 对应 API
    relation → add_character_relation / evolve
    promise → plant / advance
    knowledge → add_knowledge (proposition 须先存在则先 add_fact)
    …
  status=approved; audit log
  on failure: 单条 fail-soft 或整包回滚（配置；默认单条 fail + 报告）
```

### 7.3 批准后重放

- 新角色 accepted → **重跑该章 ingest 知识边**（对齐现 accept_unverified replay）  
- 新 fact → 补全被阻塞的 knows  

### 7.4 安全（继承并加强现网）

- 只信 `approved_item_ids`  
- module 硬门，无视客户端 layer=L2  
- apply 前再次 `item_requires_human_approval`  
- 审计：who/when/before/after/evidence

## 13. 实现分期（完善交付，不是最小玩具）

> 用户要求「最完善」：分期仍要 **每期可演示完整价值**，最终形态必须全类型 + UI + Surreal + 迁移 + 补跑。

### Phase P0 — 统一模型与安全写（地基）

- `canon_candidate` schema + store mixin  
- extract 管道接口 + marker 通道写入全 module  
- apply → **Surreal 真写** 至少 character/world_rule/fact/knowledge  
- 废弃 InMemory 作为唯一后端（可保留测试 double）  
- 单测：全 module 硬门、spoof、roundtrip  

**完成定义：** 任意 module 候选未批不写；批后 DB 可回读。

### Phase P1 — 全类型 LLM 抽取

- 分类型或统一 prompt + `codex_schema` 校验  
- 消歧 + 冲突检测  
- finalize / from-discussion **强制** 调 extract 并持久化  
- 兼容 `ingest_unverified` 双写  

**完成定义：** 对含新人物+新物件+新规则的样章，pending 中 **三类皆有**。

### Phase P2 — 统一 UI 与旅程

- 设定收件箱全 Tab  
- 终选后 PostFinalize 抽屉  
- 设定债 + 可选挡 N+1  
- 旧「待确认人物」入口重定向  

**完成定义：** 作者只点 UI 可批完全类型，无需 curl。

### Phase P3 — ingest 并轨与质量

- 知识抽取与设定抽取编排（并行、预算、超时）  
- 重放策略、失败重试、ingest 状态与 candidate 联动  
- 置信度校准、作者「此条永远忽略该类噪声」  

**完成定义：** 一条定稿流水线同时产出知识边候选 + 设定候选，状态可观测。

### Phase P4 — 补跑与验收

- `backfill_canon_from_prose` 对 `book_052a2adb`  
- 证据：`11-canon-full-type-chat.json` / `11-canon-full-type-body.json`  
- 挂 v6.1 九线中「正典闭环」升级为 **全类型** 定义  
- Playwright：终选 → 收件箱 → 批一条规则 + 一条人物  

**完成定义：** 文档与 demo 可演示「正文补全所有设定类型」。

## 15. 风险与对策

| 风险 | 对策 |
|------|------|
| LLM 过抽噪声 | 阈值 + 证据强制 + 批量忽略 + 学习 ignore 模式 |
| 抽不全 | 分通道补抽；作者「再同步本章」；主编补提 |
| 性能/费用 | 定稿才全量；讨论增量；章节分片 |

| 双轨 UI 混乱 | P2 强制合并收件箱 |
| 内存/OOM | 抽取放 demo/worker；Grok 机只跑单测 |
