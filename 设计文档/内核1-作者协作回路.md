## 1. 在回路中的位置与职责

### 1.1 一句话定位

本文定义 **Scribe 协作回路的主交互层**——人只做两件事的那两件事如何真正运转:想象如何进入系统、北极星如何约束一切生成、关键决策如何产出可选方案、意见如何驱动 AI 重做。这是系统对外的脸,也是系统区别于任何通用 AI 写作工具的核心护城河。

### 1.2 协作回路全局图


## 2. 设计目标与百万字挑战

### 2.1 设计目标

| # | 目标 | 可度量指标 |
|---|---|---|
| G-1 | 想象零遗漏——任何时刻抛出的创意都被捕获 | 捕获成功率 ≥ 99%;入口 ≤ 3 步操作到达 |
| G-2 | 北极星始终在线——每次生成都接受意图校验 | AuthorIntent 存在时,所有写作调用携带意图摘要;偏离检测命中率 > 80% |
| G-3 | 方案有真实差异——不给假选项 | 每个 OptionSet 任意两个 option 的差异维度 ≥ 1 个显著差异;人通过率(选了且未重做)≥ 60% |
| G-4 | 意见 → 重做端到端低摩擦 | 从提交自然语言意见到收到新草稿 ≤ 90s;意见解析成功率(parsed_directive 非空) ≥ 90% |
| G-5 | 想象得到使用——调度后被 AI 真正引用 | scheduled Imagination 被实际 used 率 ≥ 85% |
| G-6 | 回路在百万字上可持续 | 500章作品下,Imagination 库检索 ≤ 200ms;FeedbackNote 历史翻页不超过 500ms |

### 2.2 百万字下的具体挑战

**挑战 I:想象库膨胀**
写到第 300 章时,Imagination 库可能已积累数百条碎片:部分已 used,部分 scheduled 等待,部分 captured 未结构化,还有一些早已过时。如果不主动管理,AI 在写第 350 章时会拿到大量无关旧想象,干扰生成质量。
→ 解法:Imagination 状态机(captured→structured→scheduled→used);used 后归档;支持"已过时"手动标记;检索时按 scheduled_for 章节范围和 embedding 相似度双重过滤。

**挑战 II:北极星随长篇演进**
第 1 章写完时作者对这本书的理解和第 300 章时不同。AuthorIntent 不是"写一次永不动"的设定。早期设定的情感弧可能被实际写作过程修正。如果 AuthorIntent 僵化,AI 在后期的偏离检测会产生大量误报。
→ 解法:AuthorIntent 支持版本化(updated_at + 历史快照);偏离检测区分"背叛"(do_not_betray 红线)与"演进"(reader_feeling 自然漂移);红线只增不减,情感弧可随作者主动更新。

**挑战 III:FeedbackNote 历史规模**
500 章 × 平均 3 轮重做 = 1500 条 FeedbackNote。从中学习偏好(内核2)时,早期意见的权重应低于近期意见。前端展示历史时不能一次性全部加载。
→ 解法:FeedbackNote 按章节范围分页;PreferenceSignal 回流时带时间衰减权重;历史检索支持按 target_type/target_id 过滤,不全量扫描。

**挑战 IV:OptionSet 的真实差异难以保证**
LLM 默认会生成"看起来不同但本质相似"的方案。百万字连载里,作者在第 200 次做选择时已能感知方案质量。如果 OptionSet 的差异不够显著,作者会放弃使用这个功能。
→ 解法:OptionSet 生成时强制要求"差异矩阵"(每对 option 在情感/节奏/代价三个维度上至少有一个显著差异);差异矩阵在前端作为"选项说明卡"展示,不依赖作者自行阅读全文对比。

**挑战 V:回路在高并发章节下的调度**
作者可能同时在看第 14 章的意见反馈、第 15 章的方案选择、第 16 章的想象排期。多个任务并发,FeedbackNote 触发的重做不能阻塞新章节的方案生成。
→ 解法:每个 FeedbackNote 触发独立的异步重做任务(工程3/实现3);OptionSet 生成走独立队列;主回路保持异步解耦,前端通过 SSE 订阅各任务状态。

## 3. 详细设计

### 3.1 想象捕获(Imagination)

#### 3.1.1 设计原则

想象是 AI 一切文字的源头——这不是比喻,是技术约束。LLM 在没有主观意图注入的情况下会拉向训练数据均值(平庸)。Imagination 系统的职责是把作者随时迸发的、碎片化的、非结构化的创意,变成 AI 可以在正确时机精准调用的结构化指令。

**三不原则**:
- 不要求作者按格式输入——捕获入口接受任意自然语言
- 不要求作者排期——系统根据当前写作进度自动推荐排期,作者可覆盖
- 不丢弃任何一条——哪怕是"随手一想"也应被存储,可后期手动标记过时

#### 3.1.2 想象的类型与语义

`Imagination.type` 字段的取值域及其语义:

| type | 中文 | 典型输入示例 | AI 实现时机 |
|---|---|---|---|
| `scene_wish` | 场景愿望 | "我想要一场雨夜的背叛,两人在茶馆相遇,没有正面冲突但全是张力" | 在对应情节发展到该场景时注入 |
| `character_impulse` | 人物冲动 | "主角在第一次面对真正的恶意时,应该怯懦而非反击——我觉得这更真实" | 规划到相关章节大纲时注入 |
| `plot_what_if` | 情节假设 | "如果她其实早就知道了呢?这会让第三卷的一切对话都变味" | scheduled_for 指向第三卷起点 |
| `world_idea` | 世界点子 | "这个王国的货币是'记忆',欠债就是字面意义上欠人记忆" | 在世界设定层生成或注入相关章节 |
| `theme_seed` | 主题种子 | "我想让这本书的底色是'每次背叛都有其不得不背叛的理由'" | 注入 AuthorIntent 并持续影响写作 |
| `mood` | 氛围感 | "整个第二卷应该有一种闷热潮湿的压抑感,像梅雨季前的空气" | 写作生成时注入氛围约束 |
| `twist` | 转折 | "第七卷末尾——读者以为是胜利,但其实是另一种形式的失败" | scheduled_for 指向第七卷末章 |

#### 3.1.3 多入口低摩擦采集设计

```
采集入口全景:

┌──────────────────────────────────────────────────────────────────────────────┐
│  入口 A: 快速捕获浮层 (⌘I / 任意时刻)                                          │
│  ┌──────────────────────────────────────────────────────────────────────────┐│
│  │  💡 随手记一个想法…                                             [提交]   ││
│  │                                                                          ││
│  │  [场景] [人物] [情节] [世界] [主题] [氛围] [转折]  ← 可选类型(非必填)    ││
│  │                                                                          ││
│  │  排期: [系统自动推荐] [指定章节/卷] [暂不排期]                            ││
│  └──────────────────────────────────────────────────────────────────────────┘│
│                                                                              │
│  入口 B: 正文编辑器内联捕获 (在正文任意位置输入 // 触发)                        │
│  ┌──────────────────────────────────────────────────────────────────────────┐│
│  │  §14 正文... 韩立走出城门 //                                              ││
│  │                          ↓ 出现内联输入框                                 ││

│                                                                              │
│  入口 C: 批注转想象 (选中正文段落 → 右键 → "变成想象")                          │
│  人读到某段觉得"这里应该还有些什么"→ 直接从正文上下文生成 Imagination 草稿      │
│                                                                              │
│  入口 D: 对话式捕获 (右侧 AI 面板对话框,直接和系统说)                          │
│  "我刚才想到一件事:如果主角发现他父亲就是幕后黑手……"                            │
│  系统识别为 plot_what_if → 询问是否存为想象                                    │
│                                                                              │
│  入口 E: 想象库管理页(专用页面,浏览/编辑/排期/标记过时)                        │
└──────────────────────────────────────────────────────────────────────────────┘
```

**关键 UX 决策**:入口 A 是主入口,≤ 3 秒完成捕获;类型和排期都有智能默认值,作者可以完全不填直接提交——系统用 LLM 在后台结构化,不阻塞捕获动作本身。

#### 3.1.4 Imagination 状态机

```
                          ┌──────────────────────────────────────────────┐
                          │              Imagination 状态机               │
                          └──────────────────────────────────────────────┘

    [作者提交原始文本]
          │
          ▼
    ┌──────────────┐
    │  captured    │  raw_text 已存储;structured=null;status=captured
    │  (初始态)    │  → 后台 LLM 结构化任务入队(非阻塞)
    └──────┬───────┘
           │  LLM 结构化完成
           │  (type/scheduled_for/embedding 填充)
           ▼
    ┌──────────────┐
    │  structured  │  structured(jsonb)已填充;排期推荐已生成
    │              │  → 前端展示推荐排期,作者可修改或保持
    └──────┬───────┘
           │  作者确认排期 OR 系统自动排期(作者未操作超过48h)
           ▼
    ┌──────────────┐
    │  scheduled   │  scheduled_for 已设定(chapter/volume id 或范围)
    │              │  → 进入"待触发"状态,等待实现层到达对应章节
    └──────┬───────┘
           │  实现层(实现2)在写对应章节时检索并引用
           ▼
    ┌──────────────┐
    │    used      │  resulted_in_chapter 已记录;内容已注入生成
    │  (终态之一)  │  → 归档,不再出现在活跃检索中
    └──────────────┘

    并行可达的边缘状态:
    - captured/structured → [过时] (作者手动标记 obsolete=true)
    - scheduled → [重排期] (作者修改 scheduled_for)
    - any → [删除] (软删除,保留 embedding 供品味分析)
```

```

你是一个写作助手。以下是作者随手记下的一个想法片段。

"""
{raw_text}
"""

以 JSON 格式输出:

  "type": "...",
  "core_intent": "...",

  "implementation_hint": "...",
  "confidence": 0.0–1.0
}
```

#### 3.1.5 Imagination 在 AI 实现时的精准调用机制

实现层(实现2-写作生成)在为某章节生成正文前,需要向 Imagination 库发起检索:

```python
def retrieve_relevant_imaginations(
    chapter: Chapter,
    work_id: str,
    limit: int = 5
) -> List[Imagination]:
    """
    为指定章节检索相关的活跃 Imagination。
    双轨检索:调度匹配(精确) + 语义相关(模糊)
    """
    # 轨道1:已排期到本章/本卷的 Imagination(精确,优先)
    scheduled = db.query("""
        SELECT * FROM Imagination
        WHERE work_id = :work_id
          AND status = 'scheduled'
          AND (
            (scheduled_for->>'type' = 'chapter' 
             AND scheduled_for->>'ref_id' = :chapter_id)
            OR
            (scheduled_for->>'type' = 'volume'
             AND scheduled_for->>'ref_id' = :volume_id)
            OR
            (scheduled_for->>'type' = 'range'
             AND :chapter_seq BETWEEN 
                 (scheduled_for->>'from_seq')::int 
                 AND (scheduled_for->>'to_seq')::int)
          )
        ORDER BY created_at ASC
        LIMIT :limit
    """, {
        "work_id": work_id,
        "chapter_id": chapter.id,
        "volume_id": chapter.volume_id,
        "chapter_seq": chapter.seq,
        "limit": limit
    })

    # 轨道2:语义相关但未精确排期的 structured Imagination
    chapter_outline_embedding = get_embedding(
        str(chapter.outline) + " " + chapter.title
    )
    semantic = db.query("""
        SELECT *, 1 - (embedding <=> :query_vec) AS sim
        FROM Imagination
        WHERE work_id = :work_id
          AND status = 'structured'
          AND scheduled_for IS NULL
          AND 1 - (embedding <=> :query_vec) >= 0.75
        ORDER BY sim DESC
        LIMIT :limit
    """, {
        "work_id": work_id,
        "query_vec": chapter_outline_embedding,
        "limit": limit
    })

    # 合并去重,scheduled 优先,semantic 补充
    result = list(scheduled) + [s for s in semantic 
                                 if s.id not in {im.id for im in scheduled}]
    return result[:limit]
```

**注入格式**(插入写作 Prompt):

```
# 写作 Prompt 片段:想象注入区

作者的想象(必须在本章中真实体现,不可忽略):
{% for im in imaginations %}
[想象-{{ loop.index }}] 类型:{{ im.type }} | 指令:{{ im.structured.implementation_hint }}
原文:"{{ im.raw_text[:120] }}"
{% endfor %}

实现要求:
- 上述每个想象必须在生成的章节中有真实对应(不是抽象呼应,是具体场景/行为/细节)

```

实现层生成完成后,回调将对应 Imagination 的 `status` 更新为 `used`,并记录 `resulted_in_chapter`。

### 3.2 北极星(AuthorIntent)

#### 3.2.1 设计原则

AuthorIntent 是一个 1:1 绑定作品的意图对象,不是"主题标签",不是"类型描述"——它是**作者对这本书的第一性问题的回答**:这本书要让读者感受到什么?它的情感弧是什么?我为什么非写不可?我绝不背叛哪些东西?

这个对象的作用是作为 AI 每次执行取舍时的**最高裁判**。当 AI 必须在"更有趣"和"更忠于主题"之间选择,它应该首先查阅 AuthorIntent 而不是靠自己判断。

#### 3.2.2 AuthorIntent 各字段的语义与采集

```
AuthorIntent 字段详解:

id, work_id (1:1), updated_at — 标准字段

reader_feeling (要让读者感受什么)
  类型: text
  语义: 合上书时读者的情感落点。不是情节摘要,不是类型定语。
  示例: "一种温热的孤独感——被爱过,但爱本身是短暂的,而孤独比任何人都长寿"
  采集: 书写向导 §1(开书时引导填写)+ 随时可更新

core_emotional_arc (核心情感弧)
  类型: text
  语义: 主角(或读者情感焦点)从哪种情感状态走到哪种情感状态的弧线
  示例: "从麻木到在意到再次失去到接受失去本身"
  采集: 书写向导 §2

why_write (为什么写)
  类型: text  
  语义: 作者写这本书的内在驱动力——越私密越有效。不需要对外展示。
  示例: "我想写一个从不被人认真对待但始终认真对待他人的人"
  采集: 书写向导 §3(可跳过,但强烈建议填写)

central_promise (核心承诺)
  类型: text
  语义: 这本书向读者暗中许下的承诺——读者相信"这本书会给我X"
  示例: "每一章都会让你觉得某件小事突然有了重量"
  采集: 书写向导 §4

do_not_betray (红线/绝不背叛)
  类型: jsonb — List[RedLine]
  RedLine: { id, description: string, severity: "hard"|"soft" }
  语义: 
    hard → 任何情况下绝不能发生的事(例:"主角不能在未经历代价的情况下成功")
    soft → 强烈倾向避免但可以因特殊原因破例(例:"尽量避免大团圆结局")
  示例:
    { "description": "不能出现任何形式的'爱情能解决一切'", "severity": "hard" }
    { "description": "主角的核心缺陷不能被外部力量治愈,只能被他自己接受", "severity": "hard" }
  采集: 书写向导 §5 + 任意时刻添加 + 系统在生成中自动提取候选供作者确认
```

#### 3.2.4 偏离检测机制

每次 AI 生成结束后(写作生成·评改阶段),自动运行一次轻量偏离检测:

```python
def detect_intent_deviation(
    chapter: Chapter,
    generated_snapshot: Snapshot,
    author_intent: AuthorIntent
) -> DeviationReport:
    """
    检测本次生成是否偏离 AuthorIntent。
    分两级检测:
    Level 1 (快速,同步):硬红线违反 — 比对 do_not_betray 红线
    Level 2 (稍慢,可异步):情感弧偏移 — LLM 判断
    """
    report = DeviationReport(chapter_id=chapter.id, snapshot_id=generated_snapshot.id)

    # ─── Level 1:硬红线比对 ───────────────────────────────────────────
    generated_text = resolve_full_text(generated_snapshot)
    hard_lines = [r for r in author_intent.do_not_betray 
                  if r["severity"] == "hard"]

    for redline in hard_lines:
        # 用 LLM 判断生成内容是否触犯本条红线
        violation = llm_check_redline_violation(
            text=generated_text[:3000],  # 取前3000字降低成本
            redline_description=redline["description"],
            chapter_title=chapter.title
        )
        if violation.is_violated:
            report.violations.append(RedLineViolation(
                redline_id=redline["id"],
                redline_desc=redline["description"],
                violation_evidence=violation.evidence_excerpt,
                severity="hard"
            ))

    # ─── Level 2:情感弧偏移检测 ──────────────────────────────────────
    if not report.has_hard_violations:  # 有硬违反时直接上报,跳过软检测
        arc_check = llm_check_arc_alignment(
            chapter_summary=summarize_chapter(generated_text),
            core_emotional_arc=author_intent.core_emotional_arc,
            reader_feeling=author_intent.reader_feeling,
            chapter_position=chapter.seq  # 靠近结尾的章节要求更严
        )
        report.arc_deviation_score = arc_check.deviation_score  # 0.0-1.0
        report.arc_deviation_note = arc_check.explanation

    return report
```

```

  [无偏离]

    → 高亮违反段落
```

```python
class AuthorIntentHistory:
    """
    AuthorIntent 的历史版本链(非规范数据模型字段,本模块扩展)。
    存储在 AuthorIntent 的扩展字段或独立的 AuthorIntentSnapshot 表中。
    """
    intent_id: str          # 指向 AuthorIntent.id
    version: int            # 递增版本号
    snapshot: dict          # 完整的 AuthorIntent 字段快照
    changed_fields: list    # 本次变更的字段名
    change_reason: str      # 作者注释(可选)
    created_at: datetime

def update_author_intent(
    intent_id: str,
    updates: dict,
    change_reason: str = ""
) -> AuthorIntent:
    """
    更新 AuthorIntent 时:
    1. 创建历史快照
    2. 执行更新
    3. do_not_betray 的 hard 红线只允许新增,不允许删除(防意外操作)
       如需删除 hard 红线,需要二次确认对话框
    """
    current = fetch_author_intent(intent_id)
    
    # 红线保护
    if "do_not_betray" in updates:
        current_hard = {r["id"] for r in current.do_not_betray 
                        if r["severity"] == "hard"}
        new_hard = {r["id"] for r in updates["do_not_betray"] 
                    if r["severity"] == "hard"}
        removed_hard = current_hard - new_hard
        if removed_hard:
            raise RequiresConfirmationError(
                f"正在删除 {len(removed_hard)} 条硬红线,请确认",
                removed_ids=list(removed_hard)
            )
    
    # 创建历史快照
    save_intent_snapshot(current, change_reason)
    
    # 执行更新
    updated = apply_updates(current, updates)
    updated.updated_at = now()
    return save_author_intent(updated)
```

### 3.3 多方案(OptionSet)

#### 3.3.1 设计原则

关键决策点不是由 AI 拍板的——这是铁律。当情节走向、人物抉择、关键场景写法到达一个分叉路口时,系统产出 2–4 个**真实差异化**的方案,作者选择,AI 执行。

"真实差异化"不是"同一件事的四种说法"——是在情感走向、人物代价、情节后果、写法视角等维度上真正不同的选择,每种选择都会让故事走向不同的地方。

#### 3.3.2 OptionSet 触发时机

```
OptionSet 的触发时机分两类:

类型 A: 系统主动触发(实现层自动识别关键决策点)
  触发条件(满足任意一个即触发):
  ① 章节大纲中包含"XX 做出选择/抉择"类叙事节点
  ② 当前情节进入设定的卷结束/高潮 beat_target 附近(前后3章)
  ③ AI 在规划时检测到当前情节有两个以上合理走向且代价差异显著
  ④ 当前章节涉及已排期的 Imagination.type = 'twist' 或 'plot_what_if'

类型 B: 作者手动触发
  触发方式:
  ① 大纲树章节节点 → 右键 → "为此章生成选项方案"
  ② 正文编辑器 → 选中某段落 → "这里我想看几种不同写法"
  ③ AI 面板 → "生成场景写法选项"按钮
```

#### 3.3.6 选择 → rationale 记录 → PreferenceSignal 回流

```python
def record_option_choice(
    optionset_id: str,
    chosen_option_id: str,
    choose_rationale: str,
    user_id: str
) -> None:
    """
    记录作者的选择,并触发 PreferenceSignal 回流。
    """
    optionset = fetch_optionset(optionset_id)
    
    # 1. 更新 OptionSet
    optionset.chosen_option_id = chosen_option_id
    optionset.choose_rationale = choose_rationale
    save_optionset(optionset)
    
    # 2. 触发 PreferenceSignal 回流(→ 内核2)
    chosen = next(o for o in optionset.options if o.option_id == chosen_option_id)
    unchosen = [o for o in optionset.options if o.option_id != chosen_option_id]
    
    # 正向信号:作者选了什么
    create_preference_signal(
        owner_id=user_id,
        work_id=optionset.work_id,
        source="option_choice",
        signal={
            "chosen_emotional_direction": chosen.emotional_direction,
            "chosen_character_cost": chosen.character_cost,
            "optionset_id": optionset_id,
            "chosen_option_id": chosen_option_id,
            "choose_rationale": choose_rationale
        },
        polarity="+",
        weight=1.0
    )
    
    # 负向信号:作者没选什么(间接暗示不偏好)
    for unchosen_opt in unchosen:
        create_preference_signal(
            owner_id=user_id,
            work_id=optionset.work_id,
            source="option_choice",
            signal={
                "unchosen_emotional_direction": unchosen_opt.emotional_direction,
                "optionset_id": optionset_id,
                "unchosen_option_id": unchosen_opt.option_id
            },
            polarity="-",
            weight=0.4  # 未选的权重低于选中的权重
        )
    
    # 3. 触发实现层继续写作
    enqueue_writing_task(
        chapter_id=optionset.decision_point.chapter_id,
        chosen_option=chosen,
        optionset_context=optionset
    )
```

#### 3.4.1 设计原则

这是主交互。不是"评论功能"——是**人驱动 AI 重做的唯一方式**。

人永不亲手改 prose。这不是功能限制,是设计哲学:当人亲自动笔修改 AI 的句子时,两件事情发生了:一、AI 再也不知道它的原稿为什么被改(无法学习偏好);二、人进入了"改稿模式"而不是"创作者模式",认知重心偏移到了"对不对"而不是"好不好"。FeedbackNote 把人保持在"说我要什么"的位置,AI 负责"如何做到"。

#### 3.4.2 FeedbackNote 的覆盖范围

```
FeedbackNote.target_type 的五个维度:

segment  → 针对一个或多个具体段落的意见
           "这段韩立的内心独白太啰嗦,他不是那种会自言自语的人"
           "第三段那个转折跳太快,需要一个中间过渡"

chapter  → 针对整章的意见
           "这章的节奏前松后紧,两章节奏相似,整体张力不够"
           "结尾的钩子太直白,读者能猜到"

option   → 针对某个 OptionSet 中未选中方案的意见(为什么没选)
           "B方案我不喜欢是因为它让韩立太被动了,他不是这样的人"
           (这条会被解析为对"被动人物处理方式"的负向偏好)

setting  → 针对设定圣经某条目的意见
           "韩立的声音档案写错了,他说话应该更简短,不该有长句"

outline  → 针对大纲的意见
           "第二卷这个节奏曲线太平了,中间需要一个小低谷"
```

#### 3.4.3 自然语言批评的解析算法

这是 FeedbackNote 最关键的机制:把随意的自然语言批评转成 AI 可执行的结构化指令。

```python
@dataclass
class ParsedDirective:
    """
    FeedbackNote.parsed_directive 的结构。
    自然语言意见被解析为可直接驱动 AI 改写的指令集。
    """
    # 意见的主要类型
    critique_type: str  # 'tone' | 'pacing' | 'characterization' | 
                        # 'prose_quality' | 'plot_logic' | 'emotion' |
                        # 'detail_level' | 'perspective' | 'structure'
    
    # 核心指令(直接注入改写 Prompt)
    primary_instruction: str   # 例:"压缩至原长度的60%,删除心理独白,保留行动"
    
    # 约束列表(改写时必须遵守)
    constraints: List[str]     # 例:["不改变情节事件","保留韩立的谨慎性格"]
    
    # 参考方向(改写时的品味导向)
    style_direction: str       # 例:"更克制,情感留白更多"
    
    # 范围(改写的最小精确范围)
    scope: str                 # 'segment' | 'paragraph' | 'full_chapter'
    scope_refs: List[str]      # segment_id 列表或 'all'
    
    # 置信度
    parse_confidence: float    # 0.0-1.0;低于0.7时前端显示"请确认理解是否正确"
    
    # 原始意见保留(供追溯)
    raw_critique: str

def parse_feedback_to_directive(
    nl_critique: str,
    target_type: str,
    target_content: str,  # 被批评对象的实际文本或摘要
    work_context: dict,   # 北极星摘要 + 品味模型摘要
    author_intent: AuthorIntent
) -> ParsedDirective:
    """
    将自然语言批评解析为结构化改写指令。
    使用 LLM 解析,但做轻量规则预处理。
    """
    # 规则预处理:识别高频批评模式
    # (减少 LLM 调用成本;常见模式可直接映射)
    pre_parsed = apply_pattern_rules(nl_critique)
    if pre_parsed and pre_parsed.confidence >= 0.85:
        return pre_parsed  # 规则解析置信度足够,直接返回
    
    # LLM 解析(复杂意见)
    return llm_parse_critique(
        nl_critique=nl_critique,
        target_type=target_type,
        target_content=target_content[:500],
        author_intent_summary=format_intent_summary(author_intent),
        taste_model_summary=get_taste_model_summary(work_context["work_id"])
    )

# 规则模式映射表(常见批评 → 直接解析)
PATTERN_RULES = [
    # (正则, critique_type, primary_instruction, confidence)
    (r"太长|太啰嗦|太拖|压缩",
     "detail_level", "压缩至原长度的50-70%,删除冗余修饰和重复叙述", 0.90),
    (r"太短|不够|再多|扩展",
     "detail_level", "扩展至原长度的150-200%,增加细节和感官描写", 0.90),
    (r"节奏.*慢|慢.*节奏|拖",
     "pacing", "加快节奏,削减过渡性描写,强化动作和对话密度", 0.88),
    (r"假|不真实|不像|不对劲",
     "characterization", "重新审视人物行为逻辑,确保符合已建立的性格设定", 0.85),
    (r"更狠|狠一点|力度|冲击",
     "emotion", "加强情感烈度,减少缓冲,让冲突更正面、代价更直接", 0.88),
    (r"太直白|说出来了|别告诉读者",
     "prose_quality", "改为'show don't tell',删除直白情感陈述,用行为和细节承载", 0.90),
    (r"AI腔|套路|陈词滥调|模板",
     "prose_quality", "重写,避免陈词滥调和模板化句式,寻找具体独特的表达", 0.92),
    (r"换.*视角|从.*的角度|用.*的视角",
     "perspective", "切换到指定视角重写", 0.88),
]
```

#### 3.4.5 重做流程:FeedbackNote → 新 Snapshot

```python
def execute_feedback_rewrite(
    feedback_id: str,
    confirmed_directive: ParsedDirective,
    user_id: str
) -> Task:
    """
    执行意见驱动的重做。
    返回一个异步任务(Task),通过 SSE 向前端推送进度。
    """
    feedback = fetch_feedback_note(feedback_id)
    target_content = resolve_target_content(feedback)  # 获取被批评对象的当前内容
    
    # 1. 构建重做 Prompt
    rewrite_prompt = build_rewrite_prompt(
        original_content=target_content,
        directive=confirmed_directive,
        author_intent=fetch_author_intent(feedback.work_id),
        taste_model=fetch_taste_model(feedback.work_id),
        relevant_imaginations=retrieve_relevant_imaginations(
            chapter=fetch_chapter_for_feedback(feedback),
            work_id=feedback.work_id
        )
    )
    
    # 2. 创建重做任务(异步执行)
    task = create_rewrite_task(
        task_type="feedback_rewrite",
        feedback_id=feedback_id,
        prompt=rewrite_prompt,
        model_tier="high",  # 重做用高质量模型
        priority="high"     # 人主动触发,高优先级
    )
    
    # 3. 任务完成后的回调设置
    task.on_complete = lambda result: handle_rewrite_complete(
        feedback_id=feedback_id,
        rewrite_result=result,
        user_id=user_id
    )
    
    return enqueue_task(task)

def handle_rewrite_complete(
    feedback_id: str,
    rewrite_result: RewriteResult,
    user_id: str
) -> None:
    """重做完成后的处理流程"""
    feedback = fetch_feedback_note(feedback_id)
    
    # 1. 创建新 Snapshot(工程4 负责存储)
    new_snapshot = create_snapshot(
        chapter_id=rewrite_result.chapter_id,
        content=rewrite_result.new_text,
        created_by="ai",
        parent_id=rewrite_result.parent_snapshot_id,
        branch_label="ai-draft",
        meta={
            "generated_by": "FeedbackRewriteAgent",
            "feedback_id": feedback_id,
            "directive_type": feedback.parsed_directive["critique_type"]
        }
    )
    
    # 2. 更新 FeedbackNote.resulted_snapshot_id
    feedback.resulted_snapshot_id = new_snapshot.id
    save_feedback_note(feedback)
    
    # 3. 触发 PreferenceSignal 回流(→ 内核2)
    create_preference_signal(
        owner_id=user_id,
        work_id=feedback.work_id,
        source="feedback",
        signal={
            "critique_type": feedback.parsed_directive["critique_type"],
            "primary_instruction": feedback.parsed_directive["primary_instruction"],
            "style_direction": feedback.parsed_directive["style_direction"],
            "feedback_id": feedback_id
        },
        polarity="+",  # 作者提出意见 = 原版是负向信号,重做方向是正向信号
        weight=1.2     # 反馈信号权重略高于选项选择(主动表达意见的信号质量高)
    )
    
    # 4. 重新运行偏离检测
    deviation_report = detect_intent_deviation(
        chapter=fetch_chapter(rewrite_result.chapter_id),
        generated_snapshot=new_snapshot,
        author_intent=fetch_author_intent(feedback.work_id)
    )
    
    # 5. 通知前端(通过 SSE)
    emit_sse_event(
        channel=f"feedback-{feedback_id}",
        event="rewrite_complete",
        data={
            "new_snapshot_id": new_snapshot.id,
            "deviation_report": deviation_report,
            "can_preview_diff": True
        }
    )
```

## 6. 失败模式与缓解

### 6.1 Imagination 结构化失败

| 失败场景 | 表现 | 缓解机制 |
|---|---|---|
| LLM 结构化返回 JSON 格式错误 | `structured` 字段为 null | 自动重试 ≤ 3次;超过则保持 captured 态,前端标记"待整理" |
| 排期推荐不合理(推荐到已写完的章节) | 推荐章节 seq < 当前最新章节 | 过滤检查:structured 后自动剔除已过去的章节范围 |
| 想象量过多导致注入 Prompt 超长 | 生成 Prompt token 超限 | retrieve 限制 limit=5;按相关度截断;高优先级(scheduled)优先 |
| 想象内容与当前情节冲突 | AI 强行注入不相关想象 | implementation_hint 中加"如不适合本章可延后"的弹性措辞;used率度量 |

### 6.2 北极星偏离检测误报

| 失败场景 | 表现 | 缓解机制 |
|---|---|---|
| 硬红线过度宽泛,触发大量误报 | 每章都提示红线违反 | 偏离检测的 `confidence < 0.85` 时不显示警告;误报率超过20%时建议作者细化红线描述 |
| AuthorIntent 演进滞后 | 第300章的写法与100章的意图不匹配 | 系统每50章提示作者"是否需要更新北极星" |
| LLM 判断红线时幻觉 | 明明没违反却报告违反 | 偏离检测使用小模型快速初判 + 有结果时展示证据摘录,作者可一键"标记误报" |

### 6.3 OptionSet 差异化失败

| 失败场景 | 表现 | 缓解机制 |
|---|---|---|
| 方案之间差异不显著 | 三个方案本质相同 | 生成后做差异度自动检验:任意两个方案在三个维度上的余弦相似度 < 0.6,否则重新生成 |
| 生成方案触犯红线 | 某个方案违反 do_not_betray | redline_check 字段标注警告;不直接过滤(作者仍可看到,但有明确标注) |
| 作者反复"都不满意" | 多次重新生成仍不采用 | 每次拒绝后记录 PreferenceSignal(负向),内核2 更新品味模型;第3次拒绝时询问作者"您希望什么样的方向?" |

### 6.4 FeedbackNote 解析失败或误解

| 失败场景 | 表现 | 缓解机制 |
|---|---|---|
| 解析置信度低(<0.7) | 意见被误解导致错误改写 | 展示确认对话框,作者必须确认或修正理解;确认前不触发重做 |
| 重做方向正确但结果仍不满意 | 作者反复提相同类型意见 | 链式反馈机制;内核2 识别到重复负向信号后调整品味模型;第3次同类反馈时提示"是否需要修改品味偏好设置?" |
| 重做破坏了其他非目标内容 | 段落A的意见导致段落B被意外修改 | ParsedDirective.scope_refs 严格限定改写范围;changed_only 校验(改写前后的 non-target 段落 diff 应为空) |
| 大量反馈积压导致重做任务队列阻塞 | 作者连续提交5条意见,都在排队 | 优先级队列:同一 target_id 的新意见可取消旧意见的排队任务(用新版本替换,避免过期改写) |

### 6.5 百万字下的性能退化

| 失败场景 | 表现 | 缓解机制 |
|---|---|---|
| 想象库检索慢(>500ms) | 写作前的 retrieve 步骤变慢 | 增量索引:每次 capture 后实时更新 embedding;scheduled 想象维护内存热缓存(redis) |
| FeedbackNote 历史翻页慢 | 打开历史面板很慢 | 分页(limit=20);按 chapter_id 范围建索引;前端虚拟滚动 |
| AuthorIntent 偏离检测在长章节上超时 | 4000字章节检测超过10s | 分段采样:取章节的前1/4、中间1/4、后1/4 各500字做三次检测,合并结果 |

## 8. 证据与引用

**【稳定知识】人机协同写作中"人保持高层控制、AI执行底层文字"的分工优于"AI全权"**
人作为"策展人(curator)"而非"执行者"在创意协同中的有效性有广泛的 HCI 研究支持。从认知角度,维持用户的"创作自我效能感"(creative self-efficacy)是工具被持续使用的关键——Imagination 捕获和 FeedbackNote 机制都服务于这一目标。

**【稳定知识】LLM 默认趋向训练均值(AI腔/平庸化)**
来自设计哲学文档 §2 已核实引用:BooookScore(arXiv 2310.00785)在多维度质量评估中发现连贯性与细节丰富性存在权衡;主题漂移、角色不稳等问题有多篇专项论文支持(arXiv 2508.03137/2503.23512/2603.05890)。Imagination 注入和 AuthorIntent 偏离检测是直接对抗均值化的设计响应。

**【设计决策】Imagination 状态机的四态设计(captured→structured→scheduled→used)**
旧设计无此机制。四态设计的核心假设是:LLM 结构化不应阻塞捕获(异步执行),排期确认不应强迫作者立即决策(有默认值),used 后归档不应丢失(软删除保留 embedding 供内核2 学习)。此设计经内部推理验证,待产品上线后通过"想象 used 率"度量(目标≥85%)验证。

**【设计决策】FeedbackNote 解析的"规则先行+LLM补充"策略**
纯 LLM 解析的延迟和成本在高频意见场景下不可接受。规则模式表覆盖约 70% 的常见批评类型(基于常见写作批评分析),剩余 30% 走 LLM 精确解析。这是成本-质量权衡。规则表的覆盖率和解析精度需在产品上线后通过"意见解析成功率"度量(目标≥90%)持续校准。

**【设计决策】OptionSet 差异矩阵三维度(情感走向/人物代价/情节后果)**
三维度选取的依据是"好小说"的五种体验中对读者选择产生最直接影响的维度(G1张力/G2情感真实/G3人物活着)。另外两个维度(G4新鲜/G5主题)通过 AuthorIntent 约束间接保证。单纯用文字差异度(如余弦相似度)不足以保证方案真实差异化,故引入结构化差异矩阵。待通过"方案通过率"(目标≥60%)验证。

**【需复核】想象注入的 embedding 相似度阈值(0.75)**
当前阈值为经验值。在稀疏Imagination库(前50章)和稠密库(300章后)中,该阈值的实际精确率/召回率可能显著不同。建议在 Phase 2 建立想象注入召回率自动度量(工程6),据此调整阈值。

## 9. 开放问题

**O-1:想象的"过时"判断是否可以半自动化?**
当前设计完全靠作者手动标记 obsolete。但到第 200 章时,作者可能忘记在第 10 章捕获的某个 mood 想象已经不再适合。系统能否自动检测"此想象描述的情境在最近 N 章的发展中已经与当前故事方向显著背离"?这需要 Imagination.embedding 与最近章节的 embedding 做比对,但如何定义"背离阈值"需要实测数据。

**O-2:AuthorIntent 在多视角/多主角作品中如何适用?**
当前设计假设 AuthorIntent 是全书统一的。但群像小说或多视角叙事中,不同视角线可能有不同的情感弧。是否需要支持"按 POV 角色区分的子意图"?这会显著增加设计复杂度,目前倾向于 MVP 阶段不支持,Phase 2 再评估。

**O-3:OptionSet 的决策点自动识别的误触率**
"关键决策点"的自动识别(类型A触发)依赖实现2 在规划时的判断。误触率过高(每章都产出OptionSet)会让作者产生决策疲劳;误触率过低(真正的转折点没触发)会降低 OptionSet 的使用价值。需要在 Phase 2 建立"作者接受率 vs 触发频率"的自动度量,找到合适的触发阈值。

**O-4:FeedbackNote 链式反馈的最大深度限制**
当前设计允许无限链式反馈。极端情况下作者可能在同一段落上连续反馈 10 次都不满意。这可能表明:①该段落的问题无法通过语言指令解决;②品味模型对该作者的理解不足;③AuthorIntent 对该场景的约束相互冲突。系统是否应该在第 N 次链式反馈时介入,引导作者检查北极星或品味设置?建议在 Phase 2 以"链式反馈深度 > 3 的频率"作为监控指标。

**O-5:想象捕获的"原文保护"与品味学习的冲突**
`Imagination.raw_text` 永不修改(保护作者原始输入)。但 raw_text 可能包含粗糙表达、语法错误、甚至情绪化的词汇。当 PreferenceSignal 从 FeedbackNote 学习时,使用 parsed_directive 而非 raw_text;但想象系统是否应该用 raw_text 的语言风格特征(非内容)反哺品味模型(学习"这个作者习惯用什么样的意象描述他想要的东西")?这是内核2 的开放问题,标记于此。

**O-6:多人协作场景下的回路冲突**
当前设计假设单个作者。如果是作者+编辑协作,FeedbackNote 可能来自不同人,OptionSet 的选择也可能有分歧。AuthorIntent 的所有权归谁?这是产品层决策,当前版本推迟到 Phase 4 之后再定义。

## 与主编(内核0)的对齐增补

本回路由 [内核0-主编智能体](内核0-主编智能体.md) 驱动。三处对齐:

1. **DiscussionThread 是回路的"评议产物"**:主编评议输入后若有实质问题,产出 `DiscussionThread`([00 §4](00-总纲与数据模型.md))。与 OptionSet 的区别——OptionSet 是"给你并列选的方案",DiscussionThread 是"就一个问题的多轮对话+证据+收敛决定",一次讨论可内嵌产出 OptionSet。回路在"AI 评议"后分叉:无实质问题→直接执行;有→开 DiscussionThread→收敛→执行(你可一键 `human_overrode` 覆盖)。
2. **落地映射(对齐 [工程8](工程8-HermesAgent复用方案.md))**:整条回路实现为 Hermes 技能 `SKILL.md`(想象捕获/多方案/意见重做)+ 主编对话循环;四件套实体持久化走自建 MCP Server(PostgreSQL)。
3. **接口**:见 [工程5b-主编与协作API](工程5b-主编与协作API.md) 的 discussion-threads / optionsets / feedback-notes 端点。
